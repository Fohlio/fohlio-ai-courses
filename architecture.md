# Fohlio Tech Course Platform — Architecture

## Overview

Internal course management platform for a 10-lesson tech course. Next.js 16 App Router, Prisma 7 (PostgreSQL via `@prisma/adapter-pg`), Tailwind CSS 4, jose JWT auth, bcryptjs. Solo project (ivanbunin).

### Tech Stack

| Layer | Technology |
|---|---|
| Framework | Next.js 16.1.6 (App Router) |
| Language | TypeScript 5 (strict) |
| UI | React 19, Tailwind CSS 4 |
| Database | PostgreSQL 16 + Prisma 7 (pg adapter) |
| Auth | jose JWT + bcryptjs, cookie-based sessions |
| Deployment | Docker (standalone output) |

## Patterns & Standards

> Generated by `/use-patterns`. Last updated: 2026-04-14.
> Strictness level: **strict** — enforce everywhere.

### Error Handling — Result Pattern

Functions that can fail MUST return a `Result<T, E>` instead of throwing. Exceptions are reserved for truly unexpected errors (bugs, infra failures) which propagate to error boundaries.

```typescript
// lib/result.ts
type Result<T, E = string> =
  | { ok: true; data: T }
  | { ok: false; error: E }

function ok<T>(data: T): Result<T, never> {
  return { ok: true, data }
}

function err<E>(error: E): Result<never, E> {
  return { ok: false, error }
}
```

**Rules:**
- API route handlers: validate input, call service function, map Result to HTTP response
- Service functions (lib/): return `Result<T, E>`, NEVER throw for expected failures
- Never swallow errors silently (empty `catch {}` is a bug)
- Log before transforming or returning an error
- User-facing error messages MUST NOT contain internal details

**Where to throw (boundary exceptions):**
- Prisma connection failures (infra)
- JWT library errors (corrupted tokens)
- `notFound()` / `redirect()` (Next.js control flow)

### Data Transfer & Validation

| Rule | Description |
|---|---|
| **Validate at boundary** | All API route handlers MUST validate input before processing |
| **Trust internally** | Functions in `lib/` receive typed data — no re-validation |
| **Separate input/output types** | API input types (what client sends) vs response types (what API returns) vs internal types |
| **Use Zod at API boundary** | When adding new endpoints, use Zod schemas. Existing manual validation is acceptable but new code MUST use Zod |

```typescript
// Example: new endpoint with Zod validation
import { z } from 'zod'

const SubmitTaskSchema = z.object({
  lessonId: z.string().min(1),
  content: z.object({ type: z.enum(['text', 'pr_link', 'screenshot', 'quiz', 'checklist']) }),
})
```

### Data Access Layer (DAL)

Current state: Prisma called directly in API routes. This is acceptable for the project's scale.

**Rules:**
- Always use explicit `select` — never fetch all columns
- Complex/reused queries MUST be extracted to named functions in `lib/`
- Auth check (`getCurrentUser()`) MUST be the first call in every protected route handler
- Transaction boundaries belong in service-level functions, not route handlers

### Configuration

| Rule | Description |
|---|---|
| **Fail fast** | App MUST crash on missing required env vars at startup, not at runtime |
| **No raw process.env** | Access env vars through typed constants or a config module |
| **Never commit secrets** | `.env*` is gitignored. `.env.example` has all keys without values |
| **NEXT_PUBLIC_ prefix** | Only use for values safe to expose in the browser bundle |

Required env vars:
- `DATABASE_URL` — PostgreSQL connection string
- `JWT_SECRET` — HMAC key for JWT signing

### Server Components vs Client Components

Default is Server Component. Add `"use client"` ONLY when the component needs:
- Event handlers (`onClick`, `onChange`)
- React hooks (`useState`, `useEffect`, `useRef`)
- Browser APIs (`window`, `document`, `localStorage`)

| Server Components | Client Components |
|---|---|
| Data fetching, auth checks | Forms with state, modals |
| Static content, heavy imports | onClick/onChange handlers |
| Database queries via DAL | Animations, real-time UI |

**Current state:** Admin and main pages are `"use client"` with `useEffect` + `fetch`. This works but is suboptimal — new pages SHOULD prefer Server Components with direct data access where possible.

### API Design

All API routes MUST follow this response shape:

```typescript
// Success
{ data: T }
// or for lists:
{ students: T[] }

// Error
{ error: string }
```

| Rule | Description |
|---|---|
| **Auth first** | Every protected endpoint starts with `getCurrentUser()` |
| **HTTP status codes** | 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found |
| **No sensitive data in responses** | Never return `passwordHash` or internal IDs the client doesn't need |
| **Consistent error shape** | Always `{ error: string }` with appropriate status code |

### Auth & Security

| Rule | Description |
|---|---|
| **Middleware for redirects only** | Middleware handles route protection (redirect to `/login`). It is NOT the sole auth layer |
| **DAL verifies auth** | Every API route and data function MUST independently verify the session via `getCurrentUser()` |
| **Role check** | Admin routes MUST check `currentUser.role === "admin"` after auth |
| **JWT in httpOnly cookie** | Never expose JWT to client JavaScript |
| **Password hashing** | bcrypt with 10 salt rounds minimum |
| **Admin by nickname** | Single admin identified by `ADMIN_GITHUB_NICKNAME` constant |

| Element | Convention | Example |
|---|---|---|
| Component files | PascalCase | `LessonCard.tsx` |
| Utility/lib files | camelCase | `content.ts`, `utils.ts` |
| Route dirs | kebab-case | `[lessonSlug]/` |

| Types/Interfaces | PascalCase | `AdminStudentSummary` |
| CSS | Tailwind utility classes | No custom CSS unless scoping lesson content |
| DB tables | snake_case plural | `users`, `task_submissions` |
| DB columns | camelCase (Prisma) | `githubNickname`, `createdAt` |

### Component Patterns

| Rule | Description |
|---|---|
| **Props over global state** | Pass data as props. Use context only for cross-cutting concerns (auth, theme) |
| **Explicit variants** | Use variant props (`color="success"`) not boolean flags (`isSuccess`) |
| **Composition over config** | Prefer `children` and compound components over deeply nested config objects |
| **UI primitives in `ui/`** | Reusable atoms (Button, Card, Badge, Input) live in `components/ui/` |
| **Feature components colocated** | Components specific to a feature live next to their route |

### Tailwind CSS

| Rule | Description |
|---|---|
| **Use `cn()` for conditional classes** | `cn("base", condition && "variant")` — uses clsx + tailwind-merge |
| **No arbitrary values when a token exists** | Use `text-gray-600` not `text-[#6b7280]` |
| **Design tokens** | Primary: `brand` (#3451B2), success: `success`, warning: `warning` |
| **Responsive** | Mobile-first: base → `sm:` → `md:` → `lg:` |
| **Max content width** | Lessons: `max-w-3xl`, admin tables: `max-w-5xl` |

### Testing Strategy

| Layer | Tool | What to Test |
|---|---|---|
| **Unit** | Vitest | `lib/progress.ts`, `lib/content.ts`, utility functions |
| **Integration** | Vitest + test DB | API routes with real PostgreSQL |
| **E2E** | Playwright | Login flow, progress → homework navigation, homework submission, studio lesson lifecycle |

Priority order: integration tests for API routes > unit tests for progress calculation > E2E for critical paths.

**Playwright standards:**
- Config lives in `playwright.config.ts` with a dedicated `setup` project and dependent browser projects
- Authentication state is created by `e2e/auth.setup.ts` and stored in `e2e/.auth/`
- Prefer `getByRole`, `getByLabel`, and explicit `data-testid` hooks over CSS selectors
- Reuse an existing local dev server via Playwright `webServer` when possible; CI should launch its own
- Keep E2E data app-driven: create/login users and ensure draft courses through public APIs where practical

### Prisma Conventions

| Rule | Description |
|---|---|
| **`@@map` on every model** | Map to snake_case table names: `@@map("users")` |
| **cuid for IDs** | `@id @default(cuid())` — no auto-increment |
| **Explicit timestamps** | `createdAt DateTime @default(now())` + `updatedAt DateTime @updatedAt` |
| **Singleton client** | Global cached instance in `lib/prisma.ts` to prevent connection pool exhaustion |
| **pg adapter** | Using `@prisma/adapter-pg` for direct PostgreSQL connection (not Prisma's built-in driver) |

### Docker

| Rule | Description |
|---|---|
| **Standalone output** | `next.config.ts` has `output: "standalone"` for minimal Docker images |
| **Multi-stage build** | deps → builder → runner pattern |
| **Non-root user** | Run as `nextjs:nodejs` (uid 1001) |
| **docker-compose for dev** | PostgreSQL + app, healthchecks on DB |

### Lesson Content Pipeline

Lesson files live in `public/lessons/` as standalone HTML or PDF. The platform:
1. Reads the file via `readLessonContent()` in `lib/content.ts`
2. For HTML: extracts CSS, strips header/goals/homework/footer (rendered by platform components), scopes CSS under `.lesson-content`
3. For PDF: serves the raw file
4. Lesson metadata (title, homework tasks, etc.) is defined in `lib/constants.ts` — NOT in the database

### Series (Tracks)

Courses can be grouped into `Series` (a.k.a. tracks) — Coursera-style learning paths. A series has a slug, title, description, and an ordered list of courses. Two seeded series:

- `backend` — NestJS (order 1) → MikroORM (order 2)
- `ai-gtm` — Fohlio Tech Course (legacy 6 lessons)

Series live in `prisma/schema.prisma` (`Series` model + `Course.seriesId` FK), are seeded by `scripts/seed-series.ts`, and surfaced at `/series` (catalog) and `/series/[slug]` (detail with ordered course cards). The sidebar exposes "Tracks" as the first nav item; root `/` redirects to `/series`.

### Homework Widgets

Homework tasks support a `widget` submission type — interactive in-browser tasks that replace the old text/screenshot-only forms. The widget contract lives at `src/components/homework/widgets/types.ts`:

- Each widget is a `HomeworkWidget<TState>` component with a typed config (baked into the task seed) and per-student state (persisted as `WidgetContent` JSON).
- The registry at `src/components/homework/widgets/registry.ts` maps `widgetId` strings to components.
- `SubmissionWidget` (the host) dispatches to the right widget by id, owns the lifecycle, and forwards `{ state, completed }` updates into the existing `TaskCard` submission flow.
- 12 widgets ship in the initial set: `arch-diagram`, `code-fill`, `code-order`, `concept-match`, `decision-tree`, `error-trace`, `flow-order`, `mcq-justify`, `model-builder`, `query-builder`, `quiz-explain`, `terminal-trace`.

Hard rules for widgets: client component, Tailwind only, mobile down to 320px, ICAP (active input required, no passive click-to-reveal), drag-and-drop = HTML5 only with keyboard fallback, no network calls (submission stays in `TaskCard`).

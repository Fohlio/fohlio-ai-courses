Part 1: The Last 80% Problem

Now that Claude is connected to Notion, Jira, HubSpot, and GitHub, you've probably noticed something annoying. Claude can pull the data — but the output is still generic. The follow-up email doesn't sound like you. The QBR deck has the wrong tone. The sales brief follows some textbook framework instead of your team's actual playbook.

That's not a Claude problem. That's a knowledge transfer problem.

The Restaurant Analogy (continued)

Remember our restaurant. In Lesson 5 we hired a kitchen full of waiters who can fetch ingredients from any pantry: Notion, Jira, HubSpot, GitHub. The brilliant LLM consultant now has access to everything.

But here's the catch: the consultant doesn't know your restaurant's recipes. They can chop vegetables and operate the stove, but every time you order «the house pasta,» you have to re-explain: how al dente, how much salt, what kind of cheese, plate it on the white bowl, never the blue one. Every single time.

That's life with MCP only. Tools connected, but no procedural memory. Each conversation starts from scratch.

A Skill is a recipe card the consultant can read before cooking. «House pasta: 8 minutes, 1 tsp salt, parmesan only, white bowl, parsley garnish.» Claude reads it, follows it, and produces the same dish every time — without you re-explaining.

In one line: MCP is access to the pantry. Skills are the recipes you actually cook. You need both.

What «the last 80%» actually means

For most GTM workflows, the data-gathering part is 20% of the work. The other 80% is how you turn data into output: the framework, the tone, the format, the unwritten team conventions. That's exactly the part you keep re-explaining to Claude in every chat.

📖
Skill
Write the rules once in a file. Claude reads them automatically every time the topic comes up. No re-pasting.

Part 2: What Is a Skill (technically)

A Skill is just a folder. Inside it, one mandatory file called SKILL.md, plus optional supporting files. That's the entire architecture.

🔖
Frontmatter
Always loaded
name + description in YAML at the top of SKILL.md. ~30 tokens. Claude scans these at startup to decide which skill matches a task.
🧠
Body
Loaded on match
Markdown instructions. Workflow steps, output format, gotchas. Loaded into context only when Claude decides the skill applies.
📁
scripts/
Optional
Python or JS code Claude can run without loading into context. Good for deterministic operations: CSV parsing, PDF stamping, score calculations.
📎
references/ & assets/
Optional
Long reference docs and templates / fonts / icons / brand images. Loaded on demand, not at startup.

Progressive disclosure (the secret sauce)

Skills use a clever loading strategy called progressive disclosure. Three levels:

Level What loads When Token cost
1. Metadata Just name + description Always (session start) ~30–50 per skill
2. Body Full SKILL.md instructions When Claude matches the task ~500–5000
3. Resources Referenced files / scripts As needed during execution Effectively unbounded

Why this matters: You can have 50 skills installed and Claude pays only ~1500 tokens at idle (50 × 30). The 5000-token body of any specific skill loads only when its description matches your request. This is why skills scale where stuffing everything into the system prompt does not.

A real SKILL.md frontmatter (Anthropic's pptx skill)

Here's the actual frontmatter from Anthropic's official PowerPoint skill at github.com/anthropics/skills. Notice how aggressive the description is — that's intentional:

---
name: pptx
description: Use this skill any time a .pptx file is involved in any way —
  as input, output, or both. This includes: creating slide decks, pitch
  decks, or presentations; reading, parsing, or extracting text from any
  .pptx file; editing, modifying, or updating existing presentations;
  combining or splitting slide files; working with templates, layouts,
  speaker notes, or comments. Trigger whenever the user mentions "deck,"
  "slides," "presentation," or references a .pptx filename, regardless
  of what they plan to do with the content afterward.
license: Proprietary. LICENSE.txt has complete terms
---

Look at that description carefully. It lists every possible scenario, every keyword the user might say, and even includes «regardless of what they plan to do.» That's not paranoia — that's good skill engineering. We'll come back to why in Part 6.

Part 3: Skills vs MCP vs Subagents — the big confusion

If you've been reading AI Twitter recently, you've seen people argue that Skills replace MCP. Or that Skills are just system prompts. Or that Subagents make Skills obsolete. None of that is right. They are three different primitives that compose.

Back to the restaurant one more time. Imagine you're running a kitchen and trying to scale.

MCP is the delivery system — trucks, suppliers, the door that lets ingredients in. Without MCP, the kitchen can't reach the outside world.

Skills are the recipe book — instructions on how to combine those ingredients into your house dishes. Without skills, every chef cooks a slightly different pasta.

Subagents are specialist chefs — a pastry chef who works in their own corner with their own tools, returning only the finished dessert. Without subagents, your head chef has to do everything in one room and gets overwhelmed.

The Anthropic quote (from claude.com/blog/skills-explained): «MCP connects Claude to external services and data sources. Skills provide procedural knowledge — instructions for how to complete specific tasks or workflows. You can use both together: MCP connections give Claude access to tools, while Skills teach Claude how to use those tools effectively.»

The comparison table

Aspect MCP server Skill Subagent
What it is A connector to a tool or data source A recipe / playbook for a workflow A specialist Claude with its own context
Best metaphor The Hands The Brain The Workers
Use when You need live data: CRM, Slack, Notion, GitHub You repeat the same workflow with the same conventions A task is heavy and would clutter the main chat
Cost model Eager — loads tool list at startup Lazy — loads body only on match Separate context per agent
Who creates it Vendors / engineers Anyone — just Markdown Mostly developers
Released Nov 2024 Oct 2025 2025 (Claude Code)

The layered architecture

Skills sit between the agent and its tools. They tell Claude how to use the data MCP brings in.

Yes, they compose

The most common «aha» moment: a skill can call MCP tools, and a subagent can use skills. From Anthropic's official docs:

  • Skill + MCP: A «weekly pipeline review» skill instructs Claude to query HubSpot via MCP, apply the team's deal-scoring rules, and post a digest.
  • Skill + Subagent: A «research brief» subagent can load the «competitive analysis» skill so its output follows your team's competitor-template.
  • Skill + Skill: «Make a Q1 deck on brand» chains brand-guidelines + xlsx (charts) + pptx (final deck) automatically.
🤔
Common mistakes people make:

«Skills replace MCP» → No. Skills use MCP.
«Use a Skill to fetch live Salesforce data» → Skills can't reach external APIs alone — they need MCP for that.
«A Subagent is a Skill with more steps» → Wrong axis. Skills are what Claude knows; subagents are who is doing the work.
«More MCP servers = smarter Claude» → More servers = more wasted tokens at startup. MCP is for reach, not intelligence.
Mental model: Skills are knowledge. Subagents are workers. MCP is connectivity. They compose.

For a GTM person specifically

Reality check: 80% of skill value for GTM teams comes from Skills themselves. The other 20% comes from MCP connectors your IT team has already wired up (Salesforce, HubSpot, Notion). Subagents are mostly an engineer concern unless you're using Claude Code for technical-adjacent work. Focus on Skills first — they're the highest-leverage thing a non-engineer can build.

Try: a kitchen, a workshop, a sports team, a hospital, a film set. Pick the one that fits your job and write three sentences in your head: what's MCP in your analogy, what's a Skill, what's a Subagent.

Path A: Manus auto-package — the GTM-friendly default

This is the lowest-effort path and the one most of you should use. Manus learns the workflow from your actual successful run, not from your verbal description of it. You don't have to imagine all the edge cases up front — you just do the work once and Manus extracts the skill.

1 Run a real task in Manus to a good result
Open manus.im. Pick a task you do repeatedly: a discovery-call prep, a follow-up email, a competitive battlecard, an account brief. Run it end to end. Refine until you're happy with the output.
2 Ask Manus to package it
In the same conversation, type:

«Package this workflow into a Skill.»

Manus analyzes everything you and it just did, and generates a SKILL.md with the right description, workflow, output format, and any scripts/references it needed.

The new skill shows up in your Manus Skill Library. Open it, give it a clear name (kebab-case, like discovery-call-prep), edit the description if needed using the rules from Part 6 below.
4 Trigger it next time with a slash command
In a new conversation, type /discovery-call-prep. Manus runs the same workflow against your new inputs — in a fresh cloud sandbox, while you do something else.
5 Optional: share to the Team Skill Library
If your team has Manus Team / Enterprise, push the skill to the Team Skill Library so other GTM folks (BDRs, AEs, CSMs) get the same verified workflow. One person builds, ten people benefit.

Why this is the GTM superpower: Building a skill the traditional way means describing edge cases you haven't met yet. Manus's auto-package flips that — you do the work once well, and the skill captures the actual decisions and gotchas you encountered. Skill-by-doing, not skill-by-imagining.

This is the most underrated path for marketing and content people. You already have great work in your sent folder. Let Claude turn it into a skill.

Pick the best emails, posts, briefs, or threads you've written. Variety matters — pick different scenarios (cold email, follow-up, internal update, customer apology). Quality matters more than quantity.

A real skill: the Weekly Status Update

Here's a complete, working SKILL.md you can use as a template. It's the skill that turns «here's what I did this week» into a polished team update in your standard format:

---
name: weekly-status-update
description: Generates a weekly status update in our team's standard
  format. Use when the user asks to "write my weekly update", "draft a
  status report", "summarize this week", "weekly recap", or pastes a list
  of completed tasks and wants them formatted for a team-wide email. Even
  if the user doesn't say "weekly update" explicitly, trigger when they
  paste a bullet list of work items and ask for a summary email.
---

# Weekly Status Update Writer

Generate a status update following the team's standard format.

## Workflow

1. Read the user's input: list of completed work, blockers, plans.
2. If a section is missing, ask one targeted question. Do not invent.
3. Produce the update in the format below. Under 200 words total.

## Output format

Subject: Weekly update — [Team] — Week of [Monday date]

Shipped this week
- [Item, one line, outcome-focused. "Launched X, 50 users onboarded"
  not "worked on X".]

In progress / blockers
- [Item — current state — blocker if any, with the unblocker]

Next week
- [Item — expected outcome]

Metrics (if available)
- [Metric: value, change vs last week]

## Style rules

- Past tense for shipped, present for in-progress.
- Lead each bullet with the user-visible outcome, not internal task.
- No "successfully", "awesome", "great". Plain factual reporting.
- Cut filler ("I am pleased to announce", "As always").

## Gotchas

- If user pastes raw Slack, strip @mentions and emoji first.
- If a metric has no comparison week, omit the parenthetical.
- Never fabricate metrics. If absent, omit the Metrics section.

Anatomy notes: The frontmatter is 6 lines and triggers on multiple phrasings. The body has 5 sections — Workflow, Output format, Style rules, Gotchas, Example. Claude follows them in order. The whole skill is under 100 lines — fast to load, easy to maintain.

Part 6: Description-Writing Rules (the make-or-break field)

Out of all the things you'll write in a skill, the description matters more than every other line combined. Here's why:

The hard truth: If your description doesn't trigger, your skill doesn't exist. Claude will quietly ignore it, you'll think the skill is broken, and you'll blame the body. It's almost always the description. One audit of 214 community skills found that 73% scored below 60/100 on triggering — almost all due to weak descriptions.

The four rules

1 Structure: WHAT + WHEN + trigger phrases
Every description has three parts:
• WHAT the skill does (one sentence)
• WHEN to use it (the situation)
• Trigger phrases users actually say (literal words)

Skip any of those three and you lose triggering reliability.
2 Front-load matchable phrases in the first ~250 chars
Some interfaces (Claude.ai web) truncate the description preview at 200 characters. The first 250 characters do the most matching work. Put the verbs and trigger phrases up front, license/version notes at the end.
3 Be pushy
Claude undertriggers by default — it errs on the side of not using a skill if uncertain. Counteract this with explicit, expansive language: «Use this any time...», «Trigger whenever the user mentions...», «Even if they don't explicitly say X, use this when...». Look at how the official pptx description above uses this pattern.
4 Describe WHEN, not HOW
The most subtle mistake: if your description summarizes the workflow itself, Claude may follow the summary and skip reading the body. Keep the description about triggering conditions; put the workflow in the body.

Bad: «Generates QBRs by pulling HubSpot data, formatting it into 10 slides...»
Good: «Generates QBR decks. Use when the user mentions QBR, quarterly review, customer success summary...»

Anti-patterns table

Bad description Why it fails Fix
«Helps with documents» Vague, no triggers, no specifics Specify document type + actions + trigger phrases
«Processes data» Could mean anything; never matches Name the data type (CSV, HubSpot deals) and verbs
«Step 1: read input. Step 2: ...» Workflow leaked into description — Claude reads, follows, skips body Move steps to body. Description = triggering only.
2-line description Not enough surface area for Claude to match against varied user phrasings Add 3–5 trigger phrases users actually say
Two skills with similar descriptions Claude picks one randomly; behavior diverges Make one description more specific, other more general

Good vs bad — same skill, two descriptions

Bad: «Customer success skill. Helps with QBRs and renewals.»

No trigger phrases. No verbs. Two separate use cases jammed together. Claude will load this maybe 30% of the time it's actually relevant.

Good: «Generates customer-facing QBR decks and internal QBR prep notes for Customer Success. Use this skill when the user mentions QBR, quarterly business review, customer review deck, success plan summary, or pastes data from HubSpot/Gainsight and asks to summarize it for a customer meeting. Trigger even if the user just says ‘prep me for the Acme review’ without using the word QBR.»

Triggers, synonyms, real phrasings, push to over-trigger rather than under-trigger.

How to test if your description works

Single best test: in a new chat, ask Claude:

"When would you use the [your-skill-name] skill?"

Claude will quote your description back. Read its answer:

  • Does it correctly explain when to use the skill?
  • Does it list trigger phrases?
  • Does it sound like it would actually fire on your real prompts?

If «no» to any of those — rewrite the description, not the body.

✋ 60-second exercise
Write a description for a skill that preps you for a discovery call. Apply all four rules: WHAT + WHEN + trigger phrases + pushy language. Aim for ~3 sentences, ~400 characters.
If you wrote «Helps with discovery calls» — that's three of the four rules failed. Try again. List actual phrases your team uses («prep me for...», «research this account...», «intro call brief...»).

Part 8: When NOT to Use a Skill

Skills are not magic. They're a hammer, not the only tool in the box. Knowing when not to reach for one separates novice users from people who actually compound time savings.

Four cases where a skill is the wrong choice

🚫 One-off tasks
If you'll do this exactly once, just write a prompt. Building a skill takes 10–30 minutes; if the task takes 20 and won't repeat, the math doesn't work. Skills earn their keep on repetition.
🚫 Tasks that need live external data
A skill on its own can't call an API. If the workflow is «fetch current Salesforce deals,» you need an MCP server. The skill describes how to use that data; the MCP server retrieves it. Both, not either.
🚫 Heavy multi-step research that pollutes context
If a task needs to read 30 files and run 8 tools, putting it in a skill clutters the main chat. That's a subagent case — spawn an isolated worker that returns only the summary. Most non-engineers won't hit this; mostly relevant for engineers using Claude Code.
🚫 Tasks that need true creativity
Skills enforce consistency. That's the point. But if you're writing the launch tagline or naming a new product, you want divergence, not your usual house style. Turn the skill off (or just don't trigger it) for genuinely creative bursts.

The decision tree

Decision tree: when to reach for which primitive.
🤯
Mistakes I've watched people make:

Built a skill to summarize a single PDF for a one-time meeting. (Should have just prompted.)
Built a skill to fetch current HubSpot deal data. (Skills can't call APIs — needs MCP.)
Installed 12 skills, never tested if they trigger. (Of course nothing happened.)
Wrote a description with the workflow inside it. (Claude followed the summary, never read the body.)

Skills earn their keep on repetition + good descriptions. Both, not either.

Summary

Let's recap the key concepts from this lesson:

Skill A folder with SKILL.md (frontmatter + Markdown body). Procedural knowledge Claude loads when the description matches.
SKILL.md YAML frontmatter (name + description) at the top, instructions in the body. Optional scripts/, references/, assets/.
Description The make-or-break field. WHAT + WHEN + trigger phrases + pushy language. Describe when to fire, not how to work.
Progressive disclosure Three levels: metadata always loaded, body on match, resources on demand. Why 50 skills can coexist cheaply.
Skills vs MCP vs Subagents Skills = brain (knowledge). MCP = hands (tools). Subagents = workers (isolated context). They compose.
Document Skills Anthropic ships pptx, xlsx, docx, pdf, brand-guidelines — on by default on Pro/Max/Team. Compose for on-brand decks.

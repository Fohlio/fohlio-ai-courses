Part 1: Garbage In, Garbage Out

Here's a true story. A team I worked with had a flights API. The price column in Postgres was NUMERIC(10, 2). The handler looked roughly like this:

@Post()
async create(@Body() body: any) {
  return this.flights.create(body);
}

Notice the any. Classic. Then one day the mobile app shipped a regression and started sending:

{
  "code": "FH-204",
  "capacity": "180",           // string, not number
  "price": "ten dollars",      // uhh
  "isInternational": "yes",    // not a boolean either
  "adminOverride": true           // what's THIS field doing here?
}

Postgres rejected the price write — good. But not before three other things happened: capacity was stored as a string in a JSON column elsewhere, isInternational: "yes" evaluated truthy in every business check, and adminOverride: true — a field that wasn't supposed to exist on this endpoint — quietly flipped a privileged flag because someone had once written Object.assign(flight, body) in the service.

The fix wasn't “train the mobile team.” The fix was: never trust the client. Validate the shape, the type, and the allowed fields at the door. That's what this lesson is about.

🛂
Backend dev: “The mobile team sent us garbage data and broke prod.”
Mobile dev: “Your API accepted it.”
Backend dev: “We trusted you.”
Mobile dev: “That was your first mistake.”
Trust is for friends. Validators are for APIs.
🤔 Guess before reading
If a request comes in with an extra field that your endpoint doesn't expect — say, adminOverride: true — what should NestJS do by default? (a) Pass it through silently. (b) Reject the request with 400. (c) Strip the unknown field and continue. Pick one before reading on.
The answer is uncomfortable. Default Nest behavior is (a). You'll meet the option that flips it to (b) or (c) in Part 4.

Part 2: DTOs — Boarding Pass for Your API

A DTO (Data Transfer Object) is a class that describes the shape of data flowing across the boundary of your API. One DTO per direction: CreateFlightDto for what the client sends in, FlightResponseDto for what you send back.

A common mistake: reusing your database entity (the Prisma model, the TypeORM @Entity class) as both the input and the output and the internal representation. It feels DRY. It's actually a coupling disaster.

🗄️
DB Model
Internal — everything
Has id, createdAt, updatedAt, passwordHash, deletedAt, internal flags, foreign keys. The full picture for the database. Lives in Prisma schema or TypeORM entity.
🎟️
DTO
External contract — safe surface
Only what the client should send (CreateFlightDto) or receive (FlightResponseDto). No passwordHash. No internal flags. The narrow, deliberate, validated surface.

At the airport, your passport contains your full identity: your address, parents' names, biometric data, every visa you've ever held. You don't hand the passport to the gate agent at every checkpoint. You hand them a boarding pass — a printed slip that has only what's relevant for this flight: name, seat, gate, time.

Your DB model is the passport. Your DTO is the boarding pass. The boarding pass goes through the X-ray (ValidationPipe). It's standardized: every airline knows the shape. If you handed the gate agent a hand-drawn napkin instead, the X-ray would reject it.

Practical mapping: CreateFlightDto = the form the passenger fills in to book. UpdateFlightDto = the same form, all fields optional, for changing details after the fact. FlightResponseDto = the printed itinerary handed back. Three different forms, one underlying flight record.

Where DTOs live

Convention: a dto/ subfolder inside each feature module. The CLI even has a generator for this:

nest generate class flights/dto/create-flight.dto --no-spec
nest generate class flights/dto/update-flight.dto --no-spec
nest generate class flights/dto/flight-response.dto --no-spec
src/ ├── flights/ │ ├── dto/ │ │ ├── create-flight.dto.ts ← input contract for POST │ │ ├── update-flight.dto.ts ← input contract for PATCH │ │ └── flight-response.dto.ts ← output contract for GET │ ├── flights.controller.ts │ ├── flights.service.ts │ └── flights.module.ts

Part 3: class-validator — Decorate the Boarding Pass

NestJS doesn't ship its own validation library. It integrates with the excellent class-validator + class-transformer pair. Install them:

npm i class-validator class-transformer

Now write a real DTO. Each property gets one or more decorators that describe what valid values look like:

// src/flights/dto/create-flight.dto.ts
import {
  IsString, IsInt, IsBoolean, IsEmail, IsEnum, IsOptional,
  IsArray, ArrayNotEmpty, ValidateNested, Min, Max, Length,
  IsISO8601,
} from 'class-validator';
import { Type } from 'class-transformer';

export enum FlightClass {
  ECONOMY = 'ECONOMY',
  BUSINESS = 'BUSINESS',
  FIRST = 'FIRST',
}

class PassengerDto {
  @IsString()
  @Length(1, 100)
  fullName: string;

  @IsEmail()
  email: string;
}

export class CreateFlightDto {
  @IsString()
  @Length(3, 10)
  code: string;                // e.g. "FH-204"

  @IsInt()
  @Min(1)
  @Max(850)
  capacity: number;

  @IsISO8601()
  departsAt: string;          // "2026-05-01T08:30:00Z"

  @IsBoolean()
  isInternational: boolean;

  @IsEnum(FlightClass)
  flightClass: FlightClass;

  @IsOptional()
  @IsString()
  @Length(0, 500)
  notes?: string;

  @IsArray()
  @ArrayNotEmpty()
  @ValidateNested({ each: true })
  @Type(() => PassengerDto)
  passengers: PassengerDto[];
}

Each decorator answers one specific question. @IsInt — is it an integer? @Min(1) — at least 1? @IsEmail — does it parse as an email? Compose them and you get a precise contract.

The decorators you'll reach for 95% of the time

Decorator Checks Typical use
@IsString() Value is a string Names, codes, free-form text
@IsInt() / @IsNumber() Integer / any number Counts, prices, IDs
@Min(n) / @Max(n) Numeric bounds Capacity 1–850, age 0–120
@Length(min, max) String length bounds Codes, descriptions, slugs
@IsBoolean() Strict true / false Feature flags, toggles
@IsEmail() RFC-ish email shape User registration
@IsEnum(MyEnum) One of an enum's values Status, role, class of service
@IsISO8601() Valid ISO date string Departure times, deadlines
@IsUUID() Valid UUID string Resource IDs
@IsOptional() Skip all other validators if missing Optional fields
@IsArray() + @ArrayNotEmpty() Array, with at least one item Passenger lists, tags
@ValidateNested() + @Type() Recursively validate sub-objects Nested DTOs (passengers, addresses)

Insight: @IsOptional() goes first on the property, before any other validator. It tells class-validator: “if this field is undefined or null, skip the rest of the rules.” Without it, an optional field still has to satisfy @IsString et al when missing — which it can't, so the request fails.

Nested validation gotcha: When a DTO has another DTO inside it (like passengers: PassengerDto[]), class-validator won't recurse on its own. You must add both @ValidateNested({ each: true }) and @Type(() => PassengerDto) from class-transformer. The @Type tells the transformer what class to instantiate; without it, the items stay as plain objects and the validators never fire.

🤔
Junior dev: “Why isn't my nested validation working? I added @ValidateNested!”
Senior dev: “Did you add @Type?”
Junior dev: “Why do I need both?”
Senior dev: “Because JavaScript doesn't carry generic types at runtime, and the validator can't read your mind.”
Junior dev: “...fair.”
The two-decorator tax for nested objects. Pay it once, never debug it again.

Part 4: The Global ValidationPipe

Decorating the DTO does nothing on its own. You need a pipe that intercepts incoming requests, parses the body, instantiates the DTO class, and runs the validators. NestJS ships ValidationPipe for exactly this.

Wire it once, globally, in main.ts:

// src/main.ts
import { NestFactory } from '@nestjs/core';
import { ValidationPipe } from '@nestjs/common';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.useGlobalPipes(
    new ValidationPipe({
      whitelist: true,
      forbidNonWhitelisted: true,
      transform: true,
      transformOptions: { enableImplicitConversion: true },
    }),
  );

  await app.listen(3000);
}
bootstrap();

Four options. Each one matters. Here's what they do and what attack/bug they prevent:

🧹
whitelist: true
Strip any field that's not in the DTO. Unknown fields silently disappear.
🚫
forbidNonWhitelisted: true
If unknown fields are present, reject the request with 400 instead of stripping. Pairs with whitelist.
🔄
transform: true
Turn the plain JSON body into an actual instance of your DTO class. Now body instanceof CreateFlightDto is true.
🔢
enableImplicitConversion: true
Convert "42" to 42 when the type is number. Critical for @Param and @Query, which arrive as strings.
🕵️
Attacker: POST /users { "email": "x@y.com", "password": "...", "isAdmin": true }
Default Nest: “Sure, I'll pass that whole body to the service.”
Service: prisma.user.create({ data: body })
Database: “New admin created!”
Three lines of vulnerable code, ten years of CVEs across every framework. whitelist: true is not optional.

Critical for production: whitelist: true is not the default. Out of the box, NestJS will pass unknown fields through to your handler. Combined with sloppy code like Object.assign(user, body) or Prisma's spread { ...body }, that's a mass assignment vulnerability — the exact class of bug that lets an attacker send { isAdmin: true } and become an admin. Always set whitelist: true and forbidNonWhitelisted: true in production.

Garbage never reaches the handler — the X-ray runs before the gate agent

What a 400 response actually looks like

POST /flights with body { "code": "X", "capacity": "lots" }. With the global pipe wired, you get back:

HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "statusCode": 400,
  "message": [
    "code must be longer than or equal to 3 characters",
    "capacity must not be less than 1",
    "capacity must be an integer number",
    "departsAt must be a valid ISO 8601 date string",
    "isInternational must be a boolean value",
    "flightClass must be one of the following values: ECONOMY, BUSINESS, FIRST",
    "passengers must contain at least 1 elements"
  ],
  "error": "Bad Request"
}

Field-by-field. No code in your handler. Frontend gets a precise list to render under each input. This single config is worth the price of admission to NestJS by itself.

✋ Self-test
Without scrolling up: which two ValidationPipe options work together to reject a request that contains an unknown field? And what attack class do they prevent?
Hint: one strips, one rejects. The pair stops a CVE that's been re-discovered in dozens of frameworks since 2012.

Part 5: Serialization — Don't Leak the Hash

Validation handles incoming data. Serialization handles outgoing data. The classic bug: someone hits GET /users/me, and the response includes passwordHash because the handler did return user; on the raw entity.

NestJS solves this with class-transformer + ClassSerializerInterceptor. Two steps.

Step 1: mark sensitive fields with @Exclude

// src/users/entities/user.entity.ts
import { Exclude, Expose } from 'class-transformer';

export class User {
  id: string;
  email: string;
  fullName: string;

  @Exclude()
  passwordHash: string;

  @Exclude()
  twoFactorSecret?: string;

  createdAt: Date;

  constructor(partial: Partial<User>) {
    Object.assign(this, partial);
  }
}

Step 2: turn on the interceptor

You can apply ClassSerializerInterceptor globally, per-controller, or per-route. Globally is the safest default:

// src/main.ts (additions)
import { ClassSerializerInterceptor } from '@nestjs/common';
import { Reflector } from '@nestjs/core';

app.useGlobalInterceptors(
  new ClassSerializerInterceptor(app.get(Reflector)),
);

Now in your service, return an actual User instance (not a plain object) and the interceptor will strip @Exclude'd fields automatically:

@Get('me')
async me(@Req() req): Promise<User> {
  const raw = await this.users.findById(req.user.id);
  return new User(raw);  // instance, not POJO — interceptor needs this
}

Response: no passwordHash. No twoFactorSecret. Even if someone in two years adds internalNotes to the entity and forgets, you can default-deny by inverting the pattern with @Expose() and excludeAll.

Real example: A 2023 audit at a fintech I consulted with found 14 endpoints leaking passwordHash, refreshToken, or stripeSecretKey. Not because anyone was malicious — because they returned the raw Prisma object. Two-line fix per entity (@Exclude on the sensitive field), one-line global wire-up, problem class extinct.

The default-deny variant: @Expose only

import { Expose, Exclude } from 'class-transformer';

@Exclude()  // hide everything by default
export class UserResponseDto {
  @Expose() id: string;
  @Expose() email: string;
  @Expose() fullName: string;
  // new fields added later are NOT exposed unless you opt in
}

Pair this with plainToInstance(UserResponseDto, user, { excludeExtraneousValues: true }) and you have a response DTO: a separate, deliberate class that says “these are exactly the fields I'm sending out.” Future-proof against accidental leaks.

🔍
Frontend dev: “Hey, why is passwordHash in the /me response?”
Backend dev: “...”
Backend dev: “Don't tell anyone.”
Frontend dev: “The whole React Query devtools panel just told the entire office.”
Serialization is not optional. It's the difference between “works on my machine” and “works without leaking secrets.”

Part 6: Mapped Types — Stop Copy-Pasting DTOs

You've written CreateFlightDto with 8 validated fields. Now you need UpdateFlightDto for PATCH /flights/:id — same fields, but all optional. The wrong move: copy-paste the file, sprinkle @IsOptional() everywhere, drift over time. The right move: mapped types.

Install the helper:

npm i @nestjs/mapped-types

Now compose:

// src/flights/dto/update-flight.dto.ts
import { PartialType } from '@nestjs/mapped-types';
import { CreateFlightDto } from './create-flight.dto';

export class UpdateFlightDto extends PartialType(CreateFlightDto) {}

That's it. UpdateFlightDto has every field from CreateFlightDto, every validator, but every field is now optional. Add a field to CreateFlightDto tomorrow — it shows up here too. No drift.

The four mapped types

📝
PartialType(X)
All fields optional
Use for PATCH endpoints. UpdateFlightDto extends PartialType(CreateFlightDto).
🎯
PickType(X, [...])
Only the listed fields
Use for narrow inputs. LoginDto extends PickType(UserDto, ['email', 'password']).
✂️
OmitType(X, [...])
All fields except the listed
The opposite of Pick. CreateUserDto extends OmitType(UserDto, ['id', 'createdAt']).
➕
IntersectionType(A, B)
Combine two DTOs
Merge fields from both. FullDto extends IntersectionType(BaseDto, ExtraDto).

A real composition

// CreateFlightDto: code, capacity, departsAt, isInternational, flightClass, notes, passengers

// UpdateFlightDto: same fields, all optional
export class UpdateFlightDto extends PartialType(CreateFlightDto) {}

// QuickCreateDto: only the bare minimum required to draft a flight
export class QuickCreateDto extends PickType(CreateFlightDto, [
  'code', 'capacity', 'departsAt',
] as const) {}

// PublicFlightDto: everything except internal fields (if there were any)
export class PublicFlightDto extends OmitType(CreateFlightDto, ['notes'] as const) {}

// AuditedDto: combines a base with an audit trail
class AuditFields {
  @IsString() updatedBy: string;
  @IsISO8601() updatedAt: string;
}
export class AuditedFlightDto extends IntersectionType(CreateFlightDto, AuditFields) {}

The wiring in the controller is unchanged — just point @Body() at the new DTO type:

@Patch(':id')
update(
  @Param('id') id: string,
  @Body() dto: UpdateFlightDto,
) {
  return this.flights.update(id, dto);
}

Story-box callback: in airport terms, CreateFlightDto is the full boarding pass form. UpdateFlightDto (PartialType) is the “change my seat” form — same template, only the field you're updating needs to be filled in. PickType is the “just confirm your name and seat” quick form. The airport doesn't print four totally different forms; they print one and use templates.

Two flavors of mapped-types: @nestjs/mapped-types is the plain version. If you also use Swagger, install @nestjs/swagger instead and import PartialType from there — that one carries OpenAPI metadata along with the validators. We'll meet that in Lesson 7. Don't import from both packages in the same file.

Part 7: API Versioning — Don't Break v1 Clients

Eventually you'll need to ship a breaking change. The response shape needs to change. A field gets renamed. A required field becomes optional. You can't just deploy — you'll break every mobile app that hasn't been force-updated.

NestJS has first-class versioning. Three styles ship out of the box.

1. URI versioning (recommended for public APIs)

// src/main.ts
import { VersioningType } from '@nestjs/common';

app.enableVersioning({
  type: VersioningType.URI,
  defaultVersion: '1',
});
// src/flights/flights.controller.ts
@Controller({ path: 'flights', version: '1' })
export class FlightsControllerV1 {
  @Get()
  list() { return [{ id: 1, code: 'FH-100' }]; }
}

@Controller({ path: 'flights', version: '2' })
export class FlightsControllerV2 {
  @Get()
  list() {
    return [{
      id: 1, code: 'FH-100',
      formattedDate: 'May 1, 2026 at 8:30 AM',
    }];
  }
}

Result: GET /v1/flights hits the v1 controller, GET /v2/flights hits v2. Two clean implementations, no if (version === 2) spaghetti inside one handler.

2. Header versioning

app.enableVersioning({
  type: VersioningType.HEADER,
  header: 'X-API-Version',
});

Client sends X-API-Version: 2. Same controller decorators (@Controller({ path, version })). Cleaner URLs but harder to share/curl.

3. Media-type versioning

app.enableVersioning({
  type: VersioningType.MEDIA_TYPE,
  key: 'v=',
});
// client sends: Accept: application/json;v=2

The most “RESTful by the book” option. Almost nobody uses it in practice.

📱
Mobile dev: “You renamed fullName to name? My app is dead in the App Store.”
Backend dev: “It was just one field!”
Mobile dev: “The App Store review takes a week. The plane just took off.”
Backend dev: “...should I have made /v2?”
Mobile dev: “You should have made /v2.”
Versioning is cheap. Force-updating millions of users mid-flight is not.

When to introduce v2

Change Breaking? Bump version?
Adding a new optional field to response No No — clients ignore unknown fields
Adding a new endpoint No No
Renaming a response field Yes Yes
Removing a field Yes Yes
Changing a field's type Yes Yes
Making a previously optional request field required Yes Yes
Tightening validation (e.g. stricter regex) Often yes Usually yes

Pragmatic rule: ship v2 only when you actually need to break v1 clients. Most APIs in the wild stay on v1 for years. When you do bump, run v1 and v2 side by side for at least one full release cycle of your largest client. Sunset v1 with telemetry: log every v1 request, monitor the count, deprecate when it falls under a threshold.

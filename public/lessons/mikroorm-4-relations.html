The opening hook: any non-trivial domain has cross-references. Order has OrderItems, Customer has Addresses, Book has an Author and a pile of Tags. Mis-modeling those references is the #1 source of confusing N+1 query bugs and FK-violation surprises in production. This lesson gets that right.

Part 1: The Four Relationship Cardinalities

There are exactly four shapes a relationship can take. Memorize them — every relational schema you'll ever model is some combination.

👥
1:1
User ↔ Profile
Each user has at most one profile, each profile belongs to exactly one user. FK lives on one side (usually profile.user_id) with a UNIQUE constraint.
📚
1:M / M:1
Author ↔ Book
An author has many books; a book has one author. The FK book.author_id lives on the M:1 side (Book). Author's books is a virtual collection — no FK column on the author table.
🏷️
M:M
Book ↔ Tag
A book has many tags; a tag belongs to many books. Neither table holds the FK — a third pivot table (book_tags) holds two FKs, one to each side.
🔁
Self-ref
Article ↔ Article
Same entity on both sides — e.g. an article that replies to another article. FK column points back into the same table (article.parent_article_id).

Owning side and inverse side — the single most important rule

Every bidirectional relation has two sides. Exactly one is the owning side: it holds the foreign key in the database. The other is the inverse side: it doesn't store anything new, it just mirrors the relation back so you can navigate from the other direction.

  • M:1 is always the owning side — the “many” row holds the FK to the “one”.
  • 1:M is always the inverse side — declared with mappedBy pointing at the M:1 property.
  • 1:1 — you choose. The side marked with owner: true (or the one without mappedBy) gets the FK column.
  • M:M — you choose, but only one side may own. The owning side controls the pivot table.

Back to the Records Library. A volume might be cross-referenced from many catalog cards — a history monograph cited in three philosophy bibliographies, four religion essays, and one cookbook. But only one side of each cross-reference actually stamps the call number into the catalog. The other side just lists the back-references for convenience.

If both sides tried to stamp the call number independently, you'd have two sources of truth that could disagree. The library decided long ago: every cross-reference has one canonical author, one inscription. That's the owning side. The other end of the line is the inverse — it lists the relationship for browsing, but the truth is somewhere else.

The mapping: Owning side = the table whose row holds the FK column. Inverse side = the property that says mappedBy: 'theOtherProperty' and stores nothing in its own table.
🤔 Predict before reading on
In a Book → Author M:1 relation, which physical table has the foreign key column — the book table or the author table? Answer in three seconds, then keep reading.
Hint: an author can have many books. If the FK lived on the author side, where would you store the second one? Right — you can't. The “many” side always holds the FK.

Part 2: Defining Relations with defineEntity

Now the syntax. We'll build the canonical MikroORM trio — Author, Book, Tag — and use it as the running example for the rest of the lesson. Three entities cover all four cardinalities you'll meet in 95% of real schemas.

Author (the “one” side of 1:M)

// src/entities/Author.ts
import { defineEntity, p, InferEntity } from '@mikro-orm/core';
import { Book } from './Book';

export const Author = defineEntity({
  name: 'Author',
  properties: {
    id: p.bigint().primary(),
    name: p.string(),
    // inverse side: no FK column on `author` table
    books: () => p.oneToMany(Book).mappedBy('author'),
  },
});

export type IAuthor = InferEntity<typeof Author>;

Notice three things. The books property is wrapped in () => — that lazy callback breaks the circular import between Author and Book. mappedBy('author') is required on the inverse side: it tells MikroORM “the FK lives on the author property of Book.” And there is no author_books_id column on the author table — nothing about this property hits the schema.

Book (the M:1 owning side, plus M:M to Tag)

// src/entities/Book.ts
import { defineEntity, p, InferEntity } from '@mikro-orm/core';
import { Author } from './Author';
import { Tag } from './Tag';

export const Book = defineEntity({
  name: 'Book',
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    publishedYear: p.integer().nullable(),
    // owning side of 1:M with Author — FK column `author_id` on `book`
    author: () => p.manyToOne(Author),
    // owning side of M:M with Tag — pivot table `book_tags` is created automatically
    tags: () => p.manyToMany(Tag),
  },
});

export type IBook = InferEntity<typeof Book>;

p.manyToOne(Author) creates an author_id bigint column on book, with a foreign key constraint to author.id. This is the owning side — the database row physically references its parent.

p.manyToMany(Tag) creates a pivot table named book_tags with two columns: book_id and tag_id, both with their own FK constraints, both forming a composite primary key. You don't write that table by hand; MikroORM generates it from the relation declaration. By default the side that doesn't declare mappedBy is the owning one.

Tag (the inverse side of M:M)

// src/entities/Tag.ts
import { defineEntity, p, InferEntity } from '@mikro-orm/core';
import { Book } from './Book';

export const Tag = defineEntity({
  name: 'Tag',
  properties: {
    id: p.bigint().primary(),
    name: p.string().unique(),
    // inverse side — points back to Book.tags via mappedBy
    books: () => p.manyToMany(Book).mappedBy('tags'),
  },
});

export type ITag = InferEntity<typeof Tag>;

Same pattern as Author.books: mappedBy tells MikroORM “the truth lives on Book.tags; this side just mirrors it.” If you defined the relation on both sides without mappedBy, MikroORM would try to create two pivot tables and fail loudly. There is exactly one source of truth per relation.

1:1, briefly

Same vocabulary, smaller scope:

export const User = defineEntity({
  name: 'User',
  properties: {
    id: p.bigint().primary(),
    email: p.string().unique(),
    // owning side: FK `profile_id` on `user` table, with UNIQUE
    profile: () => p.oneToOne(Profile).owner(),
  },
});

The .owner() call (or its options-object equivalent { owner: true }) is what marks this side as the FK holder. The inverse side, on the Profile entity, would use p.oneToOne(User).mappedBy('profile') — same shape as 1:M's inverse.

The four-relation cardinality diagram

Four shapes. The FK direction tells you which side is owning — and which side is just a virtual collection in JavaScript.

Decorator equivalents

If you prefer decorators or you're maintaining an older codebase, the same relations exist:

@Entity()
export class Book {
  @PrimaryKey()
  id!: number;

  @ManyToOne(() => Author)
  author!: Author;

  @ManyToMany(() => Tag)
  tags = new Collection<Tag>(this);
}

The semantics are identical. We use defineEntity through the course because circular imports between related entities “just work” without the Rel<T> wrapper, and TypeScript inference is sharper.

Part 3: Collections — Not a Plain Array

Every 1:M and M:M relation in MikroORM materializes as a Collection<T>. Look at the type signature: it's not Tag[], it's Collection<Tag>. That distinction is load-bearing.

A Collection is a lazy-loaded wrapper. When you fetch a Book without populating its tags, book.tags is a Collection object that exists, but its internal items array is empty and its initialized flag is false. The database has not been queried for tags. Trying to iterate it the wrong way will silently lie to you.

The two states of a Collection

🚫
Uninitialized
Collection exists, but items have never been loaded. isInitialized() returns false. Iterating returns nothing in SQL drivers (silent), or throws in MongoDB.
✅
Initialized
Items array is populated from the DB. isInitialized() returns true. Iterating, .length, .contains(), .getItems() all work correctly.

Operations on a Collection

The full toolbox you'll actually use:

// adding / removing
book.tags.add(tag1, tag2);     // add one or many
book.tags.remove(tag1);         // disconnect (does not delete row by default)
book.tags.set([tag1, tag3]);    // replace entire collection
book.tags.removeAll();          // disconnect everything

// inspecting
book.tags.contains(tag1);       // boolean — only valid if initialized
book.tags.count();              // items.length when initialized
book.tags.isInitialized();      // THE check you should run if uncertain
book.tags.getItems();           // throws if not initialized

// loading
await book.tags.init();          // always reloads from DB
await book.tags.load();          // no-op if already initialized
const tags = await book.tags.loadItems(); // load + return Tag[]
const n = await book.tags.loadCount(); // SELECT COUNT(*) — no entities loaded

The most important method is isInitialized(). The most common bug in MikroORM apps is treating a Collection as if it were already loaded when it isn't. We'll come back to this in Part 5 and especially in Lesson 5.

Important: collection.remove(item) is not em.remove(item). The first only disconnects the relation — e.g. removes a row from the pivot table, or sets the FK to NULL. It does not delete the entity itself unless you also enable orphanRemoval: true (Part 4). The second deletes the row entirely. Mixing them up is how people accidentally delete production data.

🤔 Predict before reading on
You write const book = await em.findOne(Book, 1) and then for (const tag of book.tags) { console.log(tag.name); }. The book has 5 tags in the database. How many console.log calls fire? And how many SQL queries did MikroORM run for the tags?
Trick: zero console.log calls. Zero tag queries. book.tags is uninitialized. The for-loop iterates an empty items array silently. This is why populate exists — and why Lesson 5 spends so much time on it.

Part 4: Cascading persist & remove

When you persist or remove an entity, MikroORM can automatically propagate the operation through its relations. This is application-level cascading — it's the ORM walking the object graph, not the database firing ON DELETE CASCADE. Both exist; both have different rules.

Cascade persist (the default)

By default, Cascade.PERSIST is enabled on every relation. Translation: if you persist an Author with new Books in author.books, the Books are persisted automatically without a separate em.persist(book) call.

const author = em.create(Author, { name: 'Tolstoy' });
em.create(Book, { title: 'War and Peace', author });
em.create(Book, { title: 'Anna Karenina', author });

await em.flush(); // 1 author + 2 books, all inserted in one transaction, FK order respected

Notice we never wrote em.persist(book1). The Books were created with em.create (which registers them in the Identity Map) and they reference the Author, so cascade persist picks them up at flush time.

Cascade remove (opt-in)

The mirror operation is not default. To make em.remove(author) also delete the Books, you must opt in:

books: () => p.oneToMany(Book).mappedBy('author').cascade([Cascade.PERSIST, Cascade.REMOVE]),
// or shorthand:
books: () => p.oneToMany(Book).mappedBy('author').cascade([Cascade.ALL]),

This is conservative on purpose. Auto-deleting children when a parent goes away is the kind of thing that, when wrong, takes out a slice of production. The default is “don't”.

Orphan removal — more aggressive than Cascade.REMOVE

Cascade.REMOVE only fires when you remove the parent entity. Orphan removal additionally fires when a child is disconnected from the collection, even if the parent is still alive:

books: () => p.oneToMany(Book).mappedBy('author').orphanRemoval(),

// later:
author.books.remove(book1); // disconnected from collection
await em.flush();         // with orphanRemoval → DELETE FROM book WHERE id = ...
                          // without it → just UPDATE book SET author_id = NULL (if nullable)

Orphan removal makes sense when a child entity has no meaningful existence outside its parent — a comment without an article, an order item without an order. Use it deliberately.

Database-level FK behavior — updateRule and deleteRule

Separate from ORM cascading, you can configure the actual SQL foreign key constraint:

author: () => p.manyToOne(Author)
            .deleteRule('cascade')   // ON DELETE CASCADE in SQL DDL
            .updateRule('cascade'),  // ON UPDATE CASCADE in SQL DDL

This is the database itself enforcing the rule, regardless of whether the ORM is involved. cascade: [Cascade.REMOVE] works at flush time inside one transaction, with the ORM's knowledge of loaded entities. deleteRule: 'cascade' works at the SQL layer, even when something else (a migration, a manual psql session) deletes a row.

Rule of thumb: use Cascade.REMOVE / orphanRemoval when you want the ORM to walk the loaded object graph and emit DELETEs in dependency order. Use deleteRule when you want the database to enforce referential integrity even when the ORM isn't in the loop. They aren't mutually exclusive — production systems often use both.

Watch out: cascade remove on M:1 is dangerous. If Book.publisher has Cascade.REMOVE and you remove a single book, the publisher gets deleted — but other books that share that publisher (and aren't currently loaded) are now pointing at a deleted row. Cascade remove is safe on 1:M (parent → children) and risky on M:1 (child → shared parent). Avoid it on the M:1 side unless you're certain about ownership.

Part 5: References vs Populated Relations

When you load an Author from the database without populating anything, what's actually in author.books? An uninitialized Collection<Book>. What's in book.author if you load a Book without populating? A reference — a Book-shaped object that contains only the primary key, with all other fields being lazy-loaded if you ever touch them.

const book = await em.findOne(Book, 1);
// book.author exists, but it's a reference — only `id` is populated

console.log(book.author.id);    // 42 (always available, it's just the FK column)
console.log(book.author.name);  // undefined — not loaded yet

This is intentional. If every findOne eagerly loaded every relation, the simplest query would explode into dozens of joins. MikroORM gives you the relation handle for free, and asks you to be explicit about when you want the data behind it.

Two ways to populate. At query time:

const book = await em.findOne(Book, 1, { populate: ['author', 'tags'] });
console.log(book.author.name);     // 'Tolstoy' — fully loaded
for (const tag of book.tags) {  // works — initialized
  console.log(tag.name);
}

Or after the fact, on entities you already have:

const books = await em.find(Book, {});
await em.populate(books, ['author', 'tags']);
// now every book in the array has author and tags loaded

We're racing past this because Lesson 5 is entirely about populating — the three loading strategies, partial loading, the N+1 problem and how to spot it, and dataloaders. For now, internalize the distinction: a relation handle exists by default; the data behind it must be requested.

Part 6: Extending archive-api with Relations

Time to grow our archive-api repo. We'll add Author, refactor Book, add Tag, and update Article (from Lesson 2) so it has tags too. Then we'll persist a complete graph — one author, two books, one article, three tags — in a single flush.

1. The new entity files

archive-api/src/entities/ ├── Article.ts ← updated: add tags M:M, parentArticle self-ref optional ├── Author.ts ← new ├── Book.ts ← updated: add author M:1, tags M:M └── Tag.ts ← new

Use the entity files exactly as shown in Part 2 for Author, Book, Tag. Update Article to add a M:M with Tag:

// src/entities/Article.ts (updated)
import { defineEntity, p, InferEntity } from '@mikro-orm/core';
import { Tag } from './Tag';

export const Article = defineEntity({
  name: 'Article',
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    body: p.string(),
    tags: () => p.manyToMany(Tag),
  },
});

export type IArticle = InferEntity<typeof Article>;

Then add Tag's inverse side for articles too — same pattern as for books:

// src/entities/Tag.ts (final)
export const Tag = defineEntity({
  name: 'Tag',
  properties: {
    id: p.bigint().primary(),
    name: p.string().unique(),
    books: () => p.manyToMany(Book).mappedBy('tags'),
    articles: () => p.manyToMany(Article).mappedBy('tags'),
  },
});

Two M:M inverse relations on the same Tag — that's fine. They become two separate pivot tables (book_tags, article_tags) with no conflict.

2. Update mikro-orm.config.ts

import { Author } from './entities/Author';
import { Book } from './entities/Book';
import { Tag } from './entities/Tag';
import { Article } from './entities/Article';

export default defineConfig({
  entities: [Author, Book, Tag, Article],
  // ...rest unchanged
});

3. Inspect the schema

From the project root:

npx mikro-orm schema:update --dump

Read the output. You should see:

  • A book table with author_id bigint and a foreign key to author.id
  • A book_tags pivot table with book_id and tag_id, both PKs and both FKs
  • An article_tags pivot table with the same shape
  • A tag table with a unique constraint on name

4. Persist a full graph in one flush

// src/main.ts
async function main() {
  const orm = await MikroORM.init(config);
  await orm.schema.refreshDatabase();
  const em = orm.em.fork();

  // 1. one author
  const tolstoy = em.create(Author, { name: 'Lev Tolstoy' });

  // 2. three tags
  const classic = em.create(Tag, { name: 'classic' });
  const russian = em.create(Tag, { name: 'russian' });
  const longRead = em.create(Tag, { name: 'long-read' });

  // 3. two books — both wired to the author and a couple of tags
  em.create(Book, {
    title: 'War and Peace',
    publishedYear: 1869,
    author: tolstoy,
    tags: [classic, russian, longRead],
  });
  em.create(Book, {
    title: 'Anna Karenina',
    publishedYear: 1877,
    author: tolstoy,
    tags: [classic, russian],
  });

  // 4. one article with tags
  em.create(Article, {
    title: 'On Tolstoy and the long form',
    body: '...essay text...',
    tags: [classic, longRead],
  });

  // 5. flush — single transaction
  await em.flush();

  await orm.close();
}

Run it. With debug: true in your config, you'll see the query log. Five things to watch for:

🔐
One BEGIN, one COMMIT
Everything happens inside a single transaction. If any insert fails, all of them roll back.
🔗
Topological order
authors INSERT first, then tags, then books (which need author_id), then article, then pivot rows. The Unit of Work computed dependency order from the FKs.
📦
Batched INSERTs
All three tags in one multi-row INSERT. Both books in another. The pivot rows in two more.
✨
Cascade persist at work
We never wrote em.persist(book) — the books were registered via em.create and pulled into the unit of work via the relation graph.
🔍
Pivot rows
The book_tags and article_tags pivot tables get their rows in dedicated INSERTs, after the books and tags exist.

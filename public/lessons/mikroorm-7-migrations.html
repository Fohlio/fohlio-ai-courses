Part 1: Schema Generation vs Migrations — Two Different Tools

🤔 Predict before you read on
If you change a column type from int to bigint in your entity and let MikroORM auto-generate a migration, will the resulting ALTER TABLE be safe? Or could it cause data loss / a long table-rewrite lock? Take 30 seconds and write your guess.
If your answer is “the framework will handle it,” you'll have a bad week. The honest answer is “sometimes” — and that's exactly why migrations exist as a separate, reviewable step.

Up to now, every demo started with orm.schema.refreshDatabase(). That nukes the schema and rebuilds it from the entity metadata. Great for tutorials. Catastrophic in production.

MikroORM gives you two paths to keeping your database schema in sync with your entities. They're not competitors — they're for two different jobs.

✏️
schema:update
Dev shortcut
Compute the diff between entities and live DB, run the ALTERs. Idempotent. Fast. Zero ceremony. Has a --safe mode that won't drop columns. Never run on prod — no audit trail, no rollback, no peer review.
📜
migration:create
Versioned plan
Generate a TypeScript file with explicit up() and down() SQL. Commit to git. Reviewed in a PR like any other code. Run with migration:up in CI/prod. Reversible. Diffable. Auditable.

Back in the Records Library: schema:update is the architect walking through the building with a sketch pad, deciding to add a shelf here, move a bookcase there, and immediately telling the maintenance crew to make the changes. Useful when you're prototyping the floor plan in an empty wing.

Migrations are the signed reorganization plans. Every wall change is drawn up, dated, signed by the architect, signed by the head librarian, filed in the building's archive. The construction crew reads only the signed plan — not the architect's sketch pad. If the new wing causes problems, the archive contains the exact plan that built it, and the rollback plan that takes it back.

Mapping: Migration = Reorganization Plan, versioned, signed, archived. migration:up = construction crew executing the plan. migration:down = the rollback section of that same plan. mikro_orm_migrations table = the archive ledger of which plans have been applied.
🔥
Junior, 3am Slack message: “hey I ran schema:update --run on prod to fix that column real quick.”
Senior, waking up: “You did what?”
Junior: “The diff looked fine in dev.”
Senior: “Dev had three rows. Prod has 40 million. It dropped legacy_status because your branch removed the property. We have a 4-hour ALTER TABLE running, and the column had data we hadn't backfilled yet.”
Junior: “...is that bad?”
Migrations exist exactly so the dev workflow can't leak into prod. The signed plan would have shown the DROP COLUMN in PR review and someone would have stopped it.

Hard rule, write it on the wall: schema:update --run never touches a database that has real users. It's a dev-loop tool. If you find yourself reaching for it on staging or prod, stop — you want migration:create followed by migration:up.

Part 2: Setting Up the Migrations Module

Migrations are an opt-in extension. Install the package, register it in the ORM config, and the CLI gets a new family of commands.

npm install @mikro-orm/migrations

Then in your config:

// src/mikro-orm.config.ts
import { defineConfig } from '@mikro-orm/postgresql';
import { Migrator } from '@mikro-orm/migrations';
import { Article } from './entities/Article';
import { Author }  from './entities/Author';
import { Tag }     from './entities/Tag';

export default defineConfig({
  entities: [Article, Author, Tag],
  dbName: 'archive',
  user: 'postgres',
  password: 'postgres',
  host: 'localhost',
  port: 5432,
  debug: true,
  extensions: [Migrator],
  migrations: {
    path: './migrations',
    pathTs: './migrations', // dev: run TS source via tsx
    emit: 'ts',                // generated files are TypeScript
    snapshot: true,            // keep the .snapshot file under version control
  },
});

The CLI command alphabet

Command What it does
migration:create Diff entities against the snapshot, emit a new migration file with the SQL needed to bring the schema into line.
migration:create --initial First migration ever. Dumps the full schema:create SQL, marks itself as already applied.
migration:create --blank Empty migration. For data migrations or hand-written SQL.
migration:up Apply all pending migrations in order. Each runs in its own transaction; the whole batch wraps in a master transaction.
migration:down Roll back the most recent migration (or down to a specific version).
migration:list Show what's been applied. Reads from mikro_orm_migrations.
migration:pending Show what's been generated but not yet applied. Useful in CI as a guard.
migration:check Exit code 0 if schema matches entities, non-zero otherwise. Drop into CI to fail PRs that change entities without adding a migration.
migration:fresh Drop everything and re-apply from scratch. Test environments only.

The bookkeeping table

The first time you run migration:up, MikroORM creates a table called mikro_orm_migrations. It tracks which migrations have been applied:

-- approximate shape
CREATE TABLE mikro_orm_migrations (
  id         serial      PRIMARY KEY,
  name       varchar     NOT NULL,
  executed_at timestamptz NOT NULL DEFAULT now()
);

Every time migration:up runs a file, it inserts a row. Every time migration:down runs, it deletes the row. The table is the source of truth for “has this migration run on this database?” — not the file system.

Configurable name. Change migrations.tableName in the config if you want it called something else (some teams prefix with _ to hide it from app queries). The default is fine for most projects.

Part 3: Anatomy of a Migration File

Every migration is a TypeScript class extending Migration, with two methods: up() for applying, down() for rolling back. Here's a real generated file from archive-api after we add a slug property to Book:

// migrations/Migration20260507142301_add_slug_to_book.ts
import { Migration } from '@mikro-orm/migrations';

export class Migration20260507142301_add_slug_to_book extends Migration {

  override async up(): Promise<void> {
    this.addSql(`alter table "book" add column "slug" varchar(255) null;`);
    this.addSql(`update "book" set "slug" = lower(regexp_replace("title", '[^a-zA-Z0-9]+', '-', 'g'));`);
    this.addSql(`alter table "book" alter column "slug" set not null;`);
    this.addSql(`alter table "book" add constraint "book_slug_unique" unique ("slug");`);
  }

  override async down(): Promise<void> {
    this.addSql(`alter table "book" drop constraint "book_slug_unique";`);
    this.addSql(`alter table "book" drop column "slug";`);
  }

}

Three things to notice:

📜
addSql is queued
Each this.addSql(…) appends to a list. The migrator runs the whole list in one transaction. They aren't fired one-by-one as you call them.
🔁
down() is real, not a comment
If you don't write down(), the default implementation throws. That's intentional — an unrollback-able prod migration is a foot-gun. Take 30 seconds at PR time to read it.
🔐
Implicit transaction
Each migration runs in its own transaction by default (transactional: true). The whole batch wraps in a master transaction (allOrNothing: true). One failure = clean rollback.

When to hand-edit a generated migration

Generated migrations are correct for schema changes. They are not always correct for the data implications of those changes. Three cases where you need to edit before merging:

1 Adding a non-null column to a populated table
The auto-generated SQL will be add column "slug" varchar not null — which fails on row 1 because existing rows have no slug. You must edit it to: add nullable, backfill via UPDATE, then alter to SET NOT NULL. The example above shows exactly this pattern.
2 Renaming a column
MikroORM diffing sees a removed column and a new column. The auto migration will drop the old one and create the new one — losing all data. You need to manually replace it with ALTER TABLE … RENAME COLUMN.
3 Type changes that need a cast
Going from varchar to integer? Postgres won't auto-cast. The generated SQL needs a USING column_name::integer clause appended.

Helpers on the Migration class

export class MyMigration extends Migration {
  override async up() {
    // queue SQL — runs in this migration's transaction
    this.addSql(`alter table "article" add column "view_count" int default 0;`);

    // execute SQL inline — runs immediately, useful for control flow
    await this.execute(`select count(*) from "article"`);

    // access the EM if you really need to (discouraged — see warning)
    const em = this.getEntityManager();
  }

  // override to skip the per-migration transaction (rare)
  override isTransactional(): boolean { return false; }
}

Don't use entity classes inside migration files. Migration 20240301 imports the User entity from your codebase. Six months later, the User entity has new fields. The old migration file now references a definition that no longer matches the schema at the time it was written. Your CI tries to re-run it on a fresh DB and explodes. Always use raw SQL via this.addSql — the SQL is locked at write time, the entity is not.

Part 4: Snapshot Diffing — Why MikroORM Looks at a File, Not the Live DB

Here's the part that surprises people. When you change an entity and run migration:create, MikroORM does not diff against the live database. It diffs against a JSON file checked into your repo — the snapshot.

Look in your migrations/ folder after the first migration:create and you'll see a file like .snapshot-archive.json. It's a serialized form of the schema as MikroORM understood it the last time you generated a migration. It's meant to be committed.

The lifecycle of the snapshot

Step 1: you change entity Book — add `slug`
Step 2: you run `npx mikro-orm migration:create --name=add_slug`

  ↓ MikroORM reads `.snapshot-archive.json` (the previous schema)
  ↓ computes the diff against your current entity metadata
  ↓ emits `Migration20260507142301_add_slug.ts` with the up/down SQL
  ↓ rewrites `.snapshot-archive.json` to reflect the NEW schema

Step 3: you commit BOTH files in the same PR.
Step 4: CI runs `migration:up` against staging.

  ↓ Migrator reads mikro_orm_migrations table
  ↓ sees `Migration20260507142301_add_slug` is not there yet
  ↓ runs the SQL inside this.addSql(...) calls
  ↓ inserts a row into mikro_orm_migrations

Why the indirection?

Imagine the architect of the Records Library is asked “what does the building look like right now?” She has two ways to answer:

(a) Walk through every wing, measure every wall. Today's answer depends on what the cleaning crew rearranged overnight, what construction is half-finished in wing C, what shelves a librarian moved without filing paperwork.

(b) Read the master blueprint in the archive. The blueprint is the canonical answer. If the building has drifted from the blueprint, that drift is itself a bug to fix — but the blueprint is what the next reorganization plan diffs against.

MikroORM picks (b). The snapshot file is the master blueprint. Every developer's CI box, staging server, prod replica sees the same blueprint, computes the same diff, gets the same migration. Even if their local databases are in slightly different states.

Concretely: this matters because of CI determinism. If MikroORM diffed the live DB, then:

  • Two developers running migration:create on different local DBs would generate different migrations.
  • A developer with old data still around would see “phantom” columns in the diff.
  • CI would refuse to generate a stable migration because its DB is fresh, while staging's isn't.
  • You'd never get to a state where the same entity change produces the same migration file.

The snapshot decouples migration generation from any specific database state. The migration file is the artifact; the snapshot is its compile-time input. Together they're enough to reproduce the schema on any database, anywhere.

The PR convention that makes this work: when you change an entity, your PR contains three files: (1) the entity change, (2) the new MigrationXXXX.ts file, (3) the updated .snapshot-*.json file. Reviewers check all three. CI verifies migration:check passes. If only (1) is in the PR, CI fails.

Part 5: Seeders — Bootstrapping the Catalog

Migrations change the building. Seeders fill it with books. Different jobs, different lifecycles, different audiences.

🏗️
Migrations
Schema (DDL)
Tables, columns, indexes, foreign keys, constraints. Run once per database, in version order. Auditable, reversible. Run in prod.
🌾
Seeders
Data (DML)
Inserts of rows you want pre-populated: dev fixtures, demo accounts, default tag set, initial admin user. Re-runnable in dev/test. Rarely run in prod.

The package is @mikro-orm/seeder, plus @faker-js/faker for generating realistic fake data. Install both, register the extension:

npm install @mikro-orm/seeder @faker-js/faker
// mikro-orm.config.ts (additions)
import { SeedManager } from '@mikro-orm/seeder';

export default defineConfig({
  // … existing config
  extensions: [Migrator, SeedManager],
  seeder: {
    path: './seeders',
    pathTs: './seeders',
    defaultSeeder: 'DatabaseSeeder',
    emit: 'ts',
  },
});

The Seeder class

A seeder is a class with one method: run(em). Inside it, use the EntityManager you already know — em.create, em.flush. The seed manager runs each seeder in a forked EM and flushes automatically when run resolves.

// seeders/ArticleSeeder.ts
import { EntityManager } from '@mikro-orm/postgresql';
import { Seeder } from '@mikro-orm/seeder';
import { faker } from '@faker-js/faker';
import { Article } from '../src/entities/Article';
import { Tag } from '../src/entities/Tag';

export class ArticleSeeder extends Seeder {
  async run(em: EntityManager): Promise<void> {
    // build a small tag pool
    const tagNames = ['fiction', 'history', 'science', 'philosophy', 'biography'];
    const tags = tagNames.map(name => em.create(Tag, { name }));

    // 50 fake articles, each with 1–3 random tags
    for (let i = 0; i < 50; i++) {
      const picked = faker.helpers.arrayElements(tags, { min: 1, max: 3 });
      em.create(Article, {
        title: faker.lorem.sentence(5),
        slug: faker.lorem.slug(),
        viewCount: faker.number.int({ min: 0, max: 10000 }),
        publishedAt: faker.date.past({ years: 2 }),
        tags: picked,
      });
    }
    // SeedManager flushes automatically when run() resolves
  }
}

The DatabaseSeeder — one entry point

Convention: DatabaseSeeder is the orchestrator. It calls all the others. npx mikro-orm seeder:run runs DatabaseSeeder by default.

// seeders/DatabaseSeeder.ts
import { EntityManager } from '@mikro-orm/postgresql';
import { Seeder } from '@mikro-orm/seeder';
import { ArticleSeeder } from './ArticleSeeder';

export class DatabaseSeeder extends Seeder {
  run(em: EntityManager): Promise<void> {
    return this.call(em, [ArticleSeeder]);
  }
}

Factories — reusable fake-data builders

For repeated entity shapes, a Factory is cleaner than inline faker calls:

// seeders/ArticleFactory.ts
import { Factory } from '@mikro-orm/seeder';
import { faker } from '@faker-js/faker';
import { Article } from '../src/entities/Article';

export class ArticleFactory extends Factory<typeof Article> {
  model = Article;

  definition() {
    return {
      title: faker.lorem.sentence(5),
      slug: faker.lorem.slug(),
      viewCount: faker.number.int({ min: 0, max: 10000 }),
      publishedAt: faker.date.past(),
    };
  }
}

// then in a seeder:
new ArticleFactory(em).make(100); // 100 articles, persisted

Running seeders

# run the default seeder
npx mikro-orm seeder:run

# pick a specific one
npx mikro-orm seeder:run --class=ArticleSeeder

# common dev workflow: drop, re-migrate, re-seed
npx mikro-orm migration:fresh --seed

Use the same machinery in tests. Inside Vitest/Jest, call orm.seeder.seed(DatabaseSeeder) after orm.schema.refresh() in a beforeAll hook. Every test starts with a known dataset, no fixtures by hand.

Part 6: Hands-On — The Production-Shaped Migration Flow

Time to run the whole loop end-to-end on archive-api. By the end of this section you'll have committed an initial migration, generated a diff migration for a real entity change, rolled it back, rolled it forward, and seeded 20 articles.

Step 1 — the initial migration

This is a one-time bootstrap. Your repo currently has entities but no migrations folder. The initial migration captures the current schema as the starting point.

npx mikro-orm migration:create --initial

This creates two files: migrations/Migration2026…_initial.ts with all the create table statements your entities imply, and migrations/.snapshot-archive.json with the schema dump. Both go in your PR.

The migrator marks the initial migration as already applied if it created the schema, so a fresh checkout running migration:up on an existing DB won't try to CREATE TABLE again. Read the file before committing — you should recognize every CREATE TABLE from your entity definitions.

Step 2 — make a real entity change

Add a slug property to Book. We did this conceptually in Part 3; now do it for real.

// src/entities/Book.ts
export const Book = defineEntity({
  name: 'Book',
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    slug: p.string().unique(), // <-- new
    author: p.string(),
    publishedYear: p.integer().nullable(),
    createdAt: p.datetime().onCreate(() => new Date()),
  },
});

Step 3 — generate the diff

npx mikro-orm migration:create --name=add_slug_to_book

Open the generated file. The auto-generated up() will look something like:

override async up(): Promise<void> {
  this.addSql(`alter table "book" add column "slug" varchar(255) not null;`);
  this.addSql(`alter table "book" add constraint "book_slug_unique" unique ("slug");`);
}

Stop. This will fail on a populated table. The generated SQL adds not null immediately, but existing rows have no slug. On a fresh DB it works; on prod with rows it explodes. This is exactly the case Part 3 warned about. Before merging, edit it to backfill safely:

override async up(): Promise<void> {
  // 1. add nullable
  this.addSql(`alter table "book" add column "slug" varchar(255);`);
  // 2. backfill from title
  this.addSql(`update "book" set "slug" = lower(regexp_replace("title", '[^a-zA-Z0-9]+', '-', 'g'));`);
  // 3. now safe to enforce
  this.addSql(`alter table "book" alter column "slug" set not null;`);
  this.addSql(`alter table "book" add constraint "book_slug_unique" unique ("slug");`);
}

override async down(): Promise<void> {
  this.addSql(`alter table "book" drop constraint "book_slug_unique";`);
  this.addSql(`alter table "book" drop column "slug";`);
}

Step 4 — apply, roll back, roll forward

# apply
npx mikro-orm migration:up

# confirm
npx mikro-orm migration:list

# roll back the last migration
npx mikro-orm migration:down

# confirm slug is gone
psql archive -c '\d book'

# roll forward again
npx mikro-orm migration:up

Step 5 — the seeder

Drop in seeders/ArticleSeeder.ts from Part 5, lower the count to 20 for this exercise:

for (let i = 0; i < 20; i++) { /* … */ }

And the DatabaseSeeder. Then:

# start fresh: drop everything, re-run all migrations, then seed
npx mikro-orm migration:fresh --seed

# or seed against the current DB without dropping
npx mikro-orm seeder:run

Connect with psql archive and check: select count(*) from article — you should have 20 rows. Each with a fake-but-plausible title, slug, view count, and 1–3 tags.

You now have the full prod-shaped loop. Entity change → migration:create → review the generated SQL → hand-edit if data implications need it → commit migration + snapshot + entity change in one PR → CI runs migration:check → staging runs migration:up → prod runs migration:up. Same files, same SQL, deterministic.

Summary

✏️
schema:update is dev-only
Sketch pad. Idempotent. Fast. Never hits a database with real users.
🏗️
migrations are signed plans
Versioned, reviewable, reversible. up(), down(), this.addSql, transactions. Run via migration:up; tracked in mikro_orm_migrations.
📸
snapshots make CI deterministic
Diffing happens against a JSON file in your repo, not the live DB. Same entity change → same migration on every developer's machine, every CI run, every staging server.
🌾
seeders fill the catalog
Seeder classes, optional Factory + Faker, dev/test fixtures or default prod data. Different lifecycle from migrations — re-runnable, not versioned.
⚠️
hand-edit when the data implies it
Non-null adds, renames, type casts — the framework can't know you have 40M rows. Three-step backfill is the safe pattern.

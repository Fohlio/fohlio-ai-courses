Part 1: When to Split a Monolith (Honest Take)

Microservices are the most over-prescribed architecture in our industry. Conference talks and Medium posts make it sound like every team needs five services on day one. They don't. Most apps you'll work on at Fohlio absolutely do not.

The honest default: start as a monolith. Use modules to keep boundaries clean. Stay there as long as possible. A well-organized NestJS monolith with clear modules can carry you to tens of millions of requests a day on a few pods. You almost certainly do not have a microservices problem; you have a “our modules are messy” problem.

The hidden costs nobody talks about

🕰️
Latency multiplied
A single HTTP request that used to be one in-process call now becomes 5 network hops. Each adds 1–5ms. Tail latencies get worse fast.
🔍
Distributed tracing required
A bug now spans 4 services. Without OpenTelemetry / a tracing stack, you're grepping logs across pods at 2am.
📈
Schema drift
Service A's UserDto and service B's UserDto diverge in a sprint. Now you've got a contract bug in production.
🔁
Distributed transactions
There are no distributed transactions worth using. Hello, Saga pattern. Hello, eventual consistency.

The honest engineering trade: microservices solve organizational and scaling-shape problems by trading them for operational problems. If your org doesn't have the org problems, you just adopted the operational problems for free.

Real reasons to actually split

📏
Different scale shape
PDF generation needs 16GB RAM, the API needs 1GB. Splitting lets each scale independently.
👥
Different team ownership
Two teams stomping on each other's deploys. Conway's Law: split the service to match the org chart.
🔒
Different security posture
Payments need PCI compliance and auditing. Pulling them out lets the rest of the app stay simple.
🚫
“Microservices are modern”
Not a reason. This is how you end up with 12 services, 12 deploy pipelines, and one product.

Most airports are one big terminal complex. They get bigger, they add wings, but they keep everything under one roof for as long as they can — because shared services (security, baggage, ATC) are easier when they're physically together.

Eventually the runway is on the wrong side of the highway, or the cargo operation is so different (giant trucks, bulk fuel, no passengers) that it makes sense to put it in a satellite terminal across the field. The two buildings still talk — via radio, by van, by tunnel — but they're separate buildings with separate management.

The mapping: Microservices = satellite terminals. The radio between them = the transport layer (TCP, Redis, NATS, etc.). NestJS doesn't care which radio you use; the patterns are the same.
🏗️

Distributed monolith problems with monolithic-app traffic. Speedrunning the worst of both worlds.

Part 2: NestJS Microservice Transports

NestJS abstracts the wire protocol behind a single interface. You write the same controllers, services, and DTOs — just pick which transport carries the messages. Here's the menu:

Transport What it is When to pick it
TCP Built-in, no broker. Direct socket between caller and service. Internal services on the same private network. Simplest setup, no extra infra.
Redis Pub/sub on top of Redis you probably already have. Many subscribers per event, you already run Redis, want loose coupling. Not durable.
NATS Lightweight messaging, fast, simple ops. Cloud-native, microservices-heavy stack. Excellent at-most-once delivery, very low latency.
RabbitMQ Mature broker, durable queues, complex routing. You need durability + complex routing rules. Bank-style work-queue patterns.
Kafka Distributed log. Replayable streams. Event sourcing, analytics pipelines, “we want to replay events from last Tuesday.”
gRPC HTTP/2 + Protobuf. Strongly typed contracts. Polyglot stacks (Go service talking to Node), strict contracts, streaming.

Two communication styles, regardless of transport:

  • Message (request/response) — @MessagePattern on the service, client.send() from the caller. Returns an Observable.
  • Event (fire-and-forget) — @EventPattern on the service, client.emit() from the caller. No response, multiple subscribers OK.

One contract, two formats: the same NestJS code — controllers with @MessagePattern / @EventPattern — works for any of these transports. The transport is a main.ts-level decision, not a code-rewrite. That's the abstraction win.

Two protocols you'll skim past in interviews — quick reference

Protocol One-line summary NestJS transport constant
MQTTPub/sub for IoT and constrained devices. Tiny, low-bandwidth.Transport.MQTT
NATSCloud-native messaging. Sub-millisecond, simple ops.Transport.NATS
RabbitMQ (AMQP)Durable queues, complex routing, mature.Transport.RMQ
KafkaReplayable event log. Big data and streams.Transport.KAFKA
RedisPub/sub on the Redis you already run. Not durable.Transport.REDIS
gRPCHTTP/2 + Protobuf. Strict typed contracts, streaming.Transport.GRPC
TCPBuilt-in. No broker. Direct socket.Transport.TCP

Pragma: 90% of NestJS microservices in the wild use TCP, Redis, or RabbitMQ. Don't pick Kafka or gRPC because they sound impressive — pick them when their shape fits the problem (replayable streams or polyglot typed contracts respectively).

Picking transport: a 30-second decision tree

🔌
TCP
No broker, internal only
Two Nest services in the same VPC. You don't already run Redis/NATS. Default starting point.
🔀
Redis pub/sub
Already running Redis
You use Redis for cache and BullMQ already. Use it for fan-out events too. No new ops cost.
🐑
RabbitMQ
Durable + routing
Messages must survive a broker restart. Complex routing keys. Banking-grade reliability.
📜
Kafka
Event log, replayable
Big data, analytics, event sourcing. Overkill for “send this email” — that's a queue, not a log.
🌟
NATS
Cloud-native, lightweight
If you're greenfielding microservices and want the simplest broker that's still production-grade.
📑
gRPC
Typed, polyglot
Cross-language services, strict contracts, streaming RPC. The cost: managing .proto files.

Part 3: Building a Microservice (TCP)

Let's split “send notifications” out of airport-api into its own NestJS app. We'll keep both apps in the same student repo — airport-api/ for the main app and notifications-service/ as a sibling folder.

Install

npm install @nestjs/microservices

The shape of the split

nestjs-course-yourname/ ├── airport-api/ ← existing main app (HTTP) │ └── src/ │ └── main.ts ← NestFactory.create └── notifications-service/ ← new sibling app (microservice) └── src/ ├── main.ts ← NestFactory.createMicroservice ├── app.module.ts └── notifications.controller.ts

Two folders, two package.json files (or one workspace root if you prefer a monorepo). They share nothing at the code level — only the wire contract (the pattern names and payload shapes).

The microservice's main.ts

// notifications-service/src/main.ts
import { NestFactory } from '@nestjs/core';
import { MicroserviceOptions, Transport } from '@nestjs/microservices';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.createMicroservice<MicroserviceOptions>(
    AppModule,
    {
      transport: Transport.TCP,
      options: { host: '0.0.0.0', port: 4000 },
    },
  );
  await app.listen();
  console.log('Notifications microservice listening on TCP :4000');
}
bootstrap();

Notice: createMicroservice instead of create. Same DI, same modules — different listener.

The notifications controller

// notifications-service/src/notifications.controller.ts
import { Controller, Logger } from '@nestjs/common';
import { MessagePattern, EventPattern, Payload } from '@nestjs/microservices';

@Controller()
export class NotificationsController {
  private readonly logger = new Logger(NotificationsController.name);

  // Request/response: caller awaits a result
  @MessagePattern('send_notification')
  sendNotification(@Payload() data: { userId: string; text: string }) {
    this.logger.log(`-> ${data.userId}: ${data.text}`);
    return { ok: true, deliveredAt: new Date().toISOString() };
  }

  // Fire-and-forget: caller doesn't wait, multiple subscribers OK
  @EventPattern('flight.created')
  handleFlightCreated(@Payload() flight: any) {
    this.logger.log(`Flight created event received: ${flight.id}`);
  }
}

Two patterns, one controller. @MessagePattern expects a return value; @EventPattern doesn't.

Reuse what you already know: the same ValidationPipe, Guards, and Interceptors from Lessons 3–5 work on microservice handlers. Validation, auth, logging — all of it lifts straight over. The transport changes; the patterns don't.

Patterns are values, not strings only: the pattern can be a string ('send_notification') or any plain object ({ cmd: 'send', kind: 'sms' }). Both sides need to use the same pattern. Convention: dotted strings for events (flight.created), commands for requests (send_notification).

Part 4: Calling It from the Main App

The main app needs a ClientProxy — a typed handle that lets it talk to the microservice over the chosen transport.

Two processes, one transport, the same Nest patterns on both ends.

Register the client in the main app

// airport-api/src/flights/flights.module.ts
import { Module } from '@nestjs/common';
import { ClientsModule, Transport } from '@nestjs/microservices';

@Module({
  imports: [
    ClientsModule.register([
      {
        name: 'NOTIFY', // the DI token we'll inject
        transport: Transport.TCP,
        options: { host: 'localhost', port: 4000 },
      },
    ]),
  ],
  controllers: [FlightsController],
  providers: [FlightsService],
})
export class FlightsModule {}

Use the client in the service

import { Inject, Injectable } from '@nestjs/common';
import { ClientProxy } from '@nestjs/microservices';
import { firstValueFrom } from 'rxjs';

@Injectable()
export class FlightsService {
  constructor(
    private readonly prisma: PrismaService,
    @Inject('NOTIFY') private readonly notify: ClientProxy,
  ) {}

  async create(dto: CreateFlightDto) {
    const flight = await this.prisma.flight.create({ data: dto });

    // Fire-and-forget: the microservice may have multiple subscribers
    this.notify.emit('flight.created', flight);

    // Request/response (when you actually need a result):
    const ack = await firstValueFrom(
      this.notify.send('send_notification', {
        userId: dto.userId,
        text: `Your flight to ${flight.destination} is booked.`,
      }),
    );

    return { flight, ack };
  }
}

Async registration (when client config comes from env)

Hard-coding host and port works for the demo. In real life the values live in ConfigService (Lesson 7). Use registerAsync:

ClientsModule.registerAsync([
  {
    name: 'NOTIFY',
    imports: [ConfigModule],
    inject: [ConfigService],
    useFactory: (config: ConfigService) => ({
      transport: Transport.TCP,
      options: {
        host: config.get('NOTIFY_HOST'),
        port: config.get<number>('NOTIFY_PORT'),
      },
    }),
  },
])

Same pattern as every other Nest module's forRootAsync/registerAsync. Once you've seen it twice, you've seen it forever.

send() vs emit()

client.send(pattern, data) client.emit(pattern, data)
Returns Observable<T> Observable<void> (cold)
Pairs with @MessagePattern @EventPattern
Style Request / response Fire and forget
Subscribers Exactly one handler Multiple handlers OK

Error handling across the wire

When the microservice throws, NestJS serializes the error and the caller's Observable errors. Use RpcException for clean error semantics:

// In the microservice
import { RpcException } from '@nestjs/microservices';

@MessagePattern('send_notification')
send(@Payload() data: any) {
  if (!data.userId) {
    throw new RpcException({ code: 'BAD_INPUT', message: 'userId required' });
  }
  // ...
}
// In the caller, catch with rxjs
import { catchError, of } from 'rxjs';

return this.notify
  .send('send_notification', payload)
  .pipe(
    catchError((err) => {
      this.logger.error('Notify failed', err);
      return of({ ok: false }); // degrade gracefully
    }),
  );

Distributed-system reality: the network will fail. Timeouts, broker hiccups, deploy windows. Treat send() as a network call — wrap it with timeouts (rxjs timeout()), retries (only if the operation is idempotent), and a fallback.

✋ Self-test
For each: send or emit?

1. Compute & return a price quote from the pricing service.
2. Tell three downstream services that an order was placed.
3. Get the user's avatar URL from the user service.
4. Notify the audit-log service that admin X did action Y.
1 & 3 = send (you need the answer). 2 & 4 = emit (broadcast, fire-and-forget).
☎️
send(): “Hello, are you there? Can you do this thing? I'll wait. Did you do it? OK thanks bye.”
emit(): “Just FYI, this happened.” *hangs up*
One is a phone call, the other is a postcard. Pick the right channel.

Part 5: Real-time with WebSocket Gateways

Until now, every connection has been short-lived: client opens, sends a request, gets a response, closes. WebSockets flip that — the client keeps a connection open, and the server can push data whenever it wants.

Walk past the arrivals board at any airport. Flights flip from “On time” to “Delayed” to “Boarding” without anyone refreshing the screen. The board is always connected. When a flight changes status, the system pushes the new value — instantly, to every screen at once.

The mapping: WebSocket gateway = the live arrivals board. server.emit('flight_updated', flight) = pushing the new status to every listening screen at once.

Install

npm install @nestjs/websockets @nestjs/platform-socket.io socket.io

The gateway

import {
  WebSocketGateway,
  WebSocketServer,
  SubscribeMessage,
  MessageBody,
  ConnectedSocket,
  OnGatewayConnection,
  OnGatewayDisconnect,
} from '@nestjs/websockets';
import { Server, Socket } from 'socket.io';
import { Logger } from '@nestjs/common';

@WebSocketGateway({ cors: { origin: '*' } })
export class FlightsGateway implements OnGatewayConnection, OnGatewayDisconnect {
  private readonly logger = new Logger(FlightsGateway.name);

  @WebSocketServer()
  server!: Server;

  handleConnection(client: Socket) {
    this.logger.log(`Client connected: ${client.id}`);
  }

  handleDisconnect(client: Socket) {
    this.logger.log(`Client disconnected: ${client.id}`);
  }

  // Client->server: a client subscribes to flight updates
  @SubscribeMessage('subscribe_flights')
  onSubscribe(@ConnectedSocket() client: Socket) {
    client.join('flights-room');
    return { ok: true };
  }

  // Server->clients: called by FlightsService after a PATCH
  broadcastFlightUpdate(flight: any) {
    this.server.to('flights-room').emit('flight_updated', flight);
  }
}

Trigger the broadcast from your service

@Injectable()
export class FlightsService {
  constructor(
    private readonly prisma: PrismaService,
    private readonly gateway: FlightsGateway,
  ) {}

  async update(id: string, dto: UpdateFlightDto) {
    const updated = await this.prisma.flight.update({ where: { id }, data: dto });
    this.gateway.broadcastFlightUpdate(updated);
    return updated;
  }
}

Register FlightsGateway in FlightsModule as a provider. That's it — PATCH /flights/:id now causes every connected dashboard to receive the new flight in real time.

Namespaces — isolating different client populations

One Socket.IO server can host multiple namespaces, each with its own gateway:

@WebSocketGateway({ namespace: '/admin', cors: { origin: '*' } })
export class AdminGateway { /* admin-only events */ }

@WebSocketGateway({ namespace: '/public', cors: { origin: '*' } })
export class PublicGateway { /* public flight board */ }

Clients connect with io('/admin') or io('/public'). Different auth, different events, no risk of cross-talk — and you can scale them independently if one becomes a hot spot.

Rooms — broadcasting to a subset of clients

You rarely want to broadcast to everyone. You want to broadcast to “everyone watching project X” or “everyone subscribed to flight 738.” Socket.IO calls these rooms:

@SubscribeMessage('subscribe_flight')
onSubscribeFlight(
  @ConnectedSocket() client: Socket,
  @MessageBody() flightId: string,
) {
  client.join(`flight:${flightId}`);
  return { ok: true };
}

// Later, on a flight update:
this.server.to(`flight:${flight.id}`).emit('flight_updated', flight);

Rooms are server-side only — clients never know they're “in” a room. They just receive the events you broadcast to it. You can put a single client in dozens of rooms (one per project, one per flight, one per their user-id) and pick the audience precisely.

Tiny HTML test client (drop this in a file and open it)

<!-- test-client.html -->

<script>
  const socket = io('http://localhost:3000');

Multi-instance gotcha: when you scale to multiple pods, a broadcast on pod 1 doesn't reach clients on pod 2. The fix is the Socket.IO Redis adapter — it propagates emits across pods through Redis pub/sub. One config change, no code change. Plan for it before you scale, not after the bug ticket arrives.

Lifecycle hooks worth knowing

🔗
handleConnection
Fires when a client connects. Read the auth token here. Disconnect on failure.
👋
handleDisconnect
Cleanup time. Remove the user from your in-memory presence map, log the disconnect.
🚀
afterInit
Once after the server is up. Wire middleware, attach the Redis adapter, register namespaces.

Auth on a WebSocket connection

HTTP guards don't fire automatically on WS connections — the upgrade happens before any controller. Two common approaches:

// Option A: validate the token in handleConnection
handleConnection(client: Socket) {
  const token = client.handshake.auth?.token;
  try {
    const user = this.jwt.verify(token);
    client.data.user = user;
  } catch {
    client.disconnect(true);
  }
}

// Option B: a NestJS WsGuard you @UseGuards on @SubscribeMessage methods
@UseGuards(WsAuthGuard)
@SubscribeMessage('subscribe_flights')
onSubscribe(@ConnectedSocket() client: Socket) { /* ... */ }

Same JWT logic from Lesson 4 — just different transport.

Part 6: Server-Sent Events — The Loudspeaker

WebSockets are bidirectional. Sometimes you don't need that — you only need server → client pushes. SSE is half a WebSocket: simpler, plain HTTP, auto-reconnect built into the browser.

The airport's announcement loudspeaker only goes one way: from the tower to everyone on the concourse. You can't talk back. You don't need to. You just listen for “Final boarding for flight 738” and react.

The mapping: SSE = the loudspeaker. One-way, server → client, over plain HTTP. Browsers auto-reconnect when the connection drops.

Why SSE often beats WebSockets in 2026

If you only need server-to-client pushes, SSE is almost always the easier choice today:

📡
Just HTTP
Works through every CDN, proxy, and load balancer that already handles HTTP. WS often needs special config.
🔁
Auto-reconnect
The browser's EventSource reconnects automatically. With WS you'd write that loop yourself.
🔐
Auth comes for free
Cookies, headers, JWTs — all the same as a normal HTTP request. With WS, auth on upgrade is its own puzzle.

The SSE endpoint

import { Controller, Sse, MessageEvent } from '@nestjs/common';
import { Observable, interval, map } from 'rxjs';

@Controller('flights')
export class FlightsController {
  @Sse('stream')
  stream(): Observable<MessageEvent> {
    return interval(2000).pipe(
      map((n) => ({
        data: { tick: n, at: new Date().toISOString() },
      })),
    );
  }
}

Open http://localhost:3000/flights/stream in a browser — you'll see a data: event arrive every 2 seconds, forever.

Connecting SSE to your real data — the EventEmitter bridge

The toy example streams a counter. In production, you stream real events — usually piped from EventEmitter2 (Lesson 8) into the SSE stream — so an HTTP route becomes a live data feed:

import { Controller, Sse, MessageEvent } from '@nestjs/common';
import { EventEmitter2 } from '@nestjs/event-emitter';
import { fromEvent, map, Observable } from 'rxjs';

@Controller('flights')
export class FlightsController {
  constructor(private readonly events: EventEmitter2) {}

  @Sse('live')
  live(): Observable<MessageEvent> {
    return fromEvent(this.events, 'flight.updated').pipe(
      map((flight) => ({ data: flight })),
    );
  }
}

Anywhere in the codebase, this.events.emit('flight.updated', flight) — every browser with the SSE stream open instantly receives that flight. No polling, no WebSocket library, no auth dance beyond the original HTTP request.

Client-side (one line of browser API)

const es = new EventSource('http://localhost:3000/flights/stream');
es.onmessage = (e) => console.log(JSON.parse(e.data));

Real example: the “build status” widget on a CI dashboard? SSE. Slack-style chat? WebSockets. Stock ticker page that just needs prices flowing? SSE. Multiplayer cursor on a Figma-style canvas? WebSockets.

Backpressure & cleanup — the SSE catch

SSE connections live forever. If your Observable never completes and never gets unsubscribed, you'll leak listeners every time a tab closes. Two rules:

♻️
Use rxjs
Return a real Observable (not a manual setInterval). Nest unsubscribes when the client disconnects.
🔊
Heartbeat
Some proxies kill idle connections. Emit a comment line every 20s as a keepalive: { data: ':keepalive' }.
🔑
Last-Event-ID
If clients reconnect, browsers send back the last id they saw. Use it to backfill missed events.

Part 7: Hybrid Apps — HTTP + Microservice in One Process

You don't have to pick. NestJS can run an HTTP server and a microservice listener in the same process. This is the typical first step when you're extracting microservices from a monolith — the new service still serves HTTP for tooling/health-checks while listening on the microservice transport for the new contracts.

Most real airports are both: a passenger terminal serving the public face, plus a service entrance round the back where catering trucks and fuel bowsers come and go. Same building, two doors, different protocols. Visitors don't see the back door; vendors don't queue at security.

The mapping: Hybrid app = passenger terminal (HTTP) plus loading dock (microservice transport). One process owns both doors.

The hybrid main.ts

import { NestFactory } from '@nestjs/core';
import { Transport } from '@nestjs/microservices';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule); // HTTP

  app.connectMicroservice({
    transport: Transport.TCP,
    options: { host: '0.0.0.0', port: 4000 },
  });

  await app.startAllMicroservices(); // boot the TCP listener
  await app.listen(3000);                // boot the HTTP server
}
bootstrap();

One AppModule. Same controllers can mix HTTP routes (@Get, @Post) and message handlers (@MessagePattern, @EventPattern). The same DI container backs both.

What you can mix in one controller

@Controller()
export class NotificationsController {
  // HTTP route — for health, debug, manual triggers
  @Get('health')
  health() { return { ok: true }; }

  // Microservice request/response
  @MessagePattern('send_notification')
  send(@Payload() data: any) { /* ... */ }

  // Microservice fire-and-forget event
  @EventPattern('flight.created')
  onFlight(@Payload() flight: any) { /* ... */ }
}

One class, three transports, same DI graph behind all of it.

When to use hybrid

🌱
Early extraction
You're carving a service out. HTTP for the existing clients, microservice transport for new internal callers.
❤️
Health checks
Your platform expects GET /health. The actual work happens over RabbitMQ. Hybrid lets you have both.
🔗
Webhooks + events
External webhooks come in over HTTP; internal events come over Kafka. Same service, two doors.

One more story to put it all together

Picture the same passenger from Lesson 8 booking a flight. The main app (airport-api) handles the HTTP. The notifications service is a satellite terminal connected by TCP. After the flight row is written, the main app:

  1. Calls this.notify.emit('flight.created', flight) — the notifications microservice receives it and starts the email job.
  2. Calls this.gateway.broadcastFlightUpdate(flight) — every browser with the live arrivals board open updates instantly.
  3. The SSE endpoint serving the manager dashboard already has an Observable wired to flight.* events — the dashboard ticks too, no WebSocket needed.

One write, three audiences, three transports, zero blocked threads. That's the payoff of the whole lesson.

Heuristic for picking among today's tools: ask “who needs this?” If another service needs it → microservice transport. If connected users need it → WebSocket gateway (interactive) or SSE (read-only). If both need it → emit it to events and have the gateway and the microservice client both listen.

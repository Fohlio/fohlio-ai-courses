Part 1: Documentation Is a Feature

An API that nobody knows how to use is a broken API. The most beautifully designed endpoints in the world are useless if the frontend team has to ping you on Slack every time they want to know whether capacity is required or what statuses flightClass can take.

The traditional answers all suck:

📝
README.md
Out of date the moment someone merges. Nobody updates it. Nobody reads it.
📮
Postman collection
Lives on one person's laptop. Is “mostly current.” Has six broken requests nobody wants to delete.
🤔
“Just read the controller”
The frontend team is now your second tech support line. Your Slack DMs are an issue tracker.

The right answer: generate the docs from the code itself. Decorate once, and the docs update on every deploy. That's what OpenAPI (formerly Swagger) is for.

📮
Frontend dev: “What's the shape of the response from POST /flights?”
Backend dev: “Check the Postman collection.”
Frontend dev: “It says 200 OK with body tbd.”
Backend dev: “Oh that's old. Read the service file.”
Frontend dev: “Which service?”
Backend dev: “Yeah we should probably set up Swagger.”
The conversation that finally gets the ticket created.

Part 2: Setting Up Swagger

NestJS ships first-class OpenAPI integration. Two installs and seven lines of main.ts get you a fully interactive UI.

npm i @nestjs/swagger swagger-ui-express
// src/main.ts
import { NestFactory } from '@nestjs/core';
import { DocumentBuilder, SwaggerModule } from '@nestjs/swagger';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  const config = new DocumentBuilder()
    .setTitle('Airport API')
    .setDescription('Internal API for flights, gates, passengers')
    .setVersion('1.0')
    .addBearerAuth()
    .build();

  const document = SwaggerModule.createDocument(app, config);
  SwaggerModule.setup('api', app, document);

  await app.listen(3000);
}
bootstrap();

Run the app, open http://localhost:3000/api. You see an interactive UI listing every endpoint Nest has registered, grouped by controller. Each endpoint has an “Try it out” button that fires real requests.

Swagger UI: every endpoint, grouped, runnable, no extra writing

Think of Swagger as the directory map at the entrance of the airport. Every gate is listed. Every airline desk has its hours, location, services, and what languages staff speak. Passengers never have to ask — they walk in, glance at the map, and head to their gate.

Without it, every passenger asks the information desk the same five questions. With it, the desk handles only edge cases. The map is generated daily from the airport's actual operations — never out of date, because it is the schedule.

That's exactly the OpenAPI promise: the docs aren't a separate document maintained by hand. They're projected from your real controllers and DTOs at build time. If you rename a field, the docs rename it too. Stale Postman collections are over.

Part 3: Decorating Endpoints

Out of the box, Swagger picks up your routes (@Get, @Post, etc.) and your DTO class names. To get nice descriptions, response shapes, examples, and auth indicators, you add a few @Api* decorators.

Tag & describe the controller

// src/flights/flights.controller.ts
import {
  Controller, Get, Post, Patch, Delete, Body, Param,
} from '@nestjs/common';
import {
  ApiTags, ApiOperation, ApiResponse, ApiBearerAuth, ApiParam,
} from '@nestjs/swagger';
import { CreateFlightDto } from './dto/create-flight.dto';
import { UpdateFlightDto } from './dto/update-flight.dto';
import { FlightResponseDto } from './dto/flight-response.dto';
import { FlightsService } from './flights.service';

@ApiTags('flights')
@ApiBearerAuth()
@Controller('flights')
export class FlightsController {
  constructor(private readonly flights: FlightsService) {}

  @Get()
  @ApiOperation({ summary: 'List all flights' })
  @ApiResponse({ status: 200, type: [FlightResponseDto] })
  findAll() {
    return this.flights.findAll();
  }

  @Post()
  @ApiOperation({ summary: 'Create a new flight' })
  @ApiResponse({ status: 201, type: FlightResponseDto })
  @ApiResponse({ status: 400, description: 'Validation failed' })
  create(@Body() dto: CreateFlightDto) {
    return this.flights.create(dto);
  }

  @Patch(':id')
  @ApiOperation({ summary: 'Update an existing flight' })
  @ApiParam({ name: 'id', description: 'Flight UUID' })
  @ApiResponse({ status: 200, type: FlightResponseDto })
  @ApiResponse({ status: 404, description: 'Flight not found' })
  update(
    @Param('id') id: string,
    @Body() dto: UpdateFlightDto,
  ) {
    return this.flights.update(id, dto);
  }

  @Delete(':id')
  @ApiOperation({ summary: 'Cancel a flight' })
  @ApiResponse({ status: 204 })
  remove(@Param('id') id: string) {
    return this.flights.remove(id);
  }
}

Decorate the DTOs

The most important decorator on the DTO side is @ApiProperty(). It tells Swagger about each field's type, examples, constraints, and whether it's required.

// src/flights/dto/create-flight.dto.ts (Swagger-aware)
import { ApiProperty } from '@nestjs/swagger';
import { IsString, IsInt, Min, Max, IsBoolean, Length } from 'class-validator';

export class CreateFlightDto {
  @ApiProperty({ example: 'FH-204', description: 'Internal flight code' })
  @IsString()
  @Length(3, 10)
  code: string;

  @ApiProperty({ example: 180, minimum: 1, maximum: 850 })
  @IsInt()
  @Min(1)
  @Max(850)
  capacity: number;

  @ApiProperty({ example: true, description: 'Crosses an international border' })
  @IsBoolean()
  isInternational: boolean;
}

The @Api* decorators worth knowing

Decorator Where What it does
@ApiTags('group') Controller Groups endpoints in the UI sidebar
@ApiOperation({ summary }) Method One-line description shown next to the route
@ApiResponse({ status, type }) Method Documents one possible response. Stack multiple per method.
@ApiBearerAuth() Controller / method Marks the endpoint as requiring a Bearer token
@ApiParam({ name, description }) Method Describes a path parameter
@ApiQuery({ name }) Method Describes a query parameter
@ApiProperty({ example, ... }) DTO field Documents a request/response field
@ApiPropertyOptional() DTO field Same as above, marks the field optional
🤔 Guess before reading Part 4
Look at CreateFlightDto above. Every field has an @ApiProperty() decorator. The TypeScript already says code: string. Why can't Swagger just read the TypeScript and skip the decorators?
Hint: types disappear when TypeScript compiles to JavaScript. Decorators don't. There's a clever fix coming next.

Part 4: The Swagger CLI Plugin

Decorating every DTO field gets tedious fast. A 12-field DTO turns into 24 lines just for @ApiProperty. The Swagger CLI plugin solves this by reading your TypeScript types at compile time and generating @ApiProperty for you behind the scenes.

Turn it on in nest-cli.json:

{
  "$schema": "https://json.schemastore.org/nest-cli",
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "plugins": [
      {
        "name": "@nestjs/swagger",
        "options": {
          "classValidatorShim": true,
          "introspectComments": true
        }
      }
    ]
  }
}

Now your DTO can collapse back to:

import { IsString, IsInt, Min, Max, IsBoolean, Length } from 'class-validator';

export class CreateFlightDto {
  /** Internal flight code, e.g. "FH-204" */
  @IsString()
  @Length(3, 10)
  code: string;

  /** Maximum number of passengers */
  @IsInt()
  @Min(1)
  @Max(850)
  capacity: number;

  /** Crosses an international border */
  @IsBoolean()
  isInternational: boolean;
}

The plugin reads:

  • The TypeScript type → sets type in the OpenAPI spec
  • The ? on optional fields → sets required: false
  • The JSDoc comment (with introspectComments) → sets description
  • The class-validator decorators (with classValidatorShim) → mirrors them as minLength, maximum, etc.

The time savings are real: on a project with ~40 DTOs, switching to the CLI plugin removed roughly 600 lines of boilerplate @ApiProperty calls. The Swagger UI was bit-for-bit identical. The team stopped forgetting to update the docs because there was nothing to forget.

📝
Junior dev: “I added @ApiProperty to all 47 fields in our DTOs.”
Senior dev: “Did you turn on the CLI plugin?”
Junior dev: “The what?”
Senior dev: “...delete the 47 decorators. Add five lines to nest-cli.json. Same result.”
Junior dev: “I just spent two hours on that.”
Senior dev: “Welcome to the cult.”
Five minutes reading docs > two hours of decorator typing. Always.

When to override: the plugin handles 90% of cases. For the other 10% — custom examples, complex enums, polymorphic responses — add an explicit @ApiProperty({ example: ..., enum: ... }) on just that field. The plugin won't fight you; it merges.

Part 5: REST vs GraphQL — When Each Fits

REST is the default for good reasons: every developer knows it, every tool supports it, every CDN caches it. But REST has one structural pain point that grows with your client list: the server decides what's in each response.

If GET /flights/:id returns 25 fields and the mobile app only needs 3, the mobile app pays for all 25. If the dashboard needs flights plus their gates plus their passengers, the dashboard makes 3 round trips — or you build a custom GET /flights/:id/full endpoint, and now you have 14 endpoints instead of 4.

GraphQL flips it: the client declares what it wants, the server fulfills exactly that.

REST: server-defined response. GraphQL: client-defined query.

Comparison table

Dimension REST GraphQL
Response shape Server decides Client decides
Over-fetching Common (extra fields) Rare (only requested fields)
Under-fetching / N+1 RTTs Common Rare (one query, many fields)
Caching HTTP-native (URL = cache key) Harder (POST + body); needs Apollo / Relay
Tooling / debugging curl, Postman, browser tab, every CDN Apollo Studio, GraphiQL, Sandbox
Learning curve Low Medium — SDL, resolvers, N+1 awareness
Best for Public APIs, server-to-server, simple CRUD Rich clients, mobile apps, multi-team frontends

REST is a fixed buffet. The chef decides what's on the line today, you take a plate, you walk through, you take or skip each tray. Cheap, predictable, well-known.

GraphQL is a concierge desk. You walk up and tell them: “I want the salmon, no skin, with the rice from station 4 and the dressing from station 7, on the side.” The concierge runs around for you and brings back exactly that. More work for the kitchen, but you get exactly your meal in one trip.

Pragmatic rule: internal services and public REST-y APIs → REST + Swagger. Multi-screen mobile/web apps with many shapes of the same data → GraphQL pays for itself. Lots of teams ship both.
🍽️
Frontend dev: “The mobile screen needs flight code, gate, and passenger names. Nothing else.”
REST backend dev: “OK we have GET /flights/:id, /gates, /passengers. Three calls. 4KB total.”
Frontend dev: “...we're on a 3G connection on a plane.”
GraphQL backend dev, sliding in: “Want me to write you a query?”
The plane Wi-Fi is the great equalizer.

Part 6: Code-First GraphQL in NestJS

NestJS supports two styles: schema-first (you write a .graphql SDL file, classes generated from it) and code-first (you write TypeScript classes with decorators, the SDL is generated from them). Code-first is the path of least resistance in a NestJS shop — you stay in TypeScript, decorators tell the framework what's a query/mutation/field.

Install

npm i @nestjs/graphql @nestjs/apollo @apollo/server graphql

Wire the GraphQL module

// src/app.module.ts
import { Module } from '@nestjs/common';
import { GraphQLModule } from '@nestjs/graphql';
import { ApolloDriver, ApolloDriverConfig } from '@nestjs/apollo';
import { join } from 'path';
import { FlightsModule } from './flights/flights.module';

@Module({
  imports: [
    GraphQLModule.forRoot<ApolloDriverConfig>({
      driver: ApolloDriver,
      autoSchemaFile: join(process.cwd(), 'src/schema.gql'),
      playground: true,
      sortSchema: true,
    }),
    FlightsModule,
  ],
})
export class AppModule {}

autoSchemaFile tells Nest to write the generated SDL to that path on startup — commit it, diff it on PRs, and you have a free schema review process.

Define an Object Type

// src/flights/flight.model.ts
import { ObjectType, Field, Int, ID } from '@nestjs/graphql';

@ObjectType()
export class Flight {
  @Field(() => ID)
  id: string;

  @Field()
  code: string;

  @Field(() => Int)
  capacity: number;

  @Field()
  isInternational: boolean;

  @Field({ nullable: true })
  notes?: string;
}

Define an Input Type (DTO equivalent)

// src/flights/dto/create-flight.input.ts
import { InputType, Field, Int } from '@nestjs/graphql';
import { IsString, IsInt, Min, Max } from 'class-validator';

@InputType()
export class CreateFlightInput {
  @Field()
  @IsString()
  code: string;

  @Field(() => Int)
  @IsInt()
  @Min(1) @Max(850)
  capacity: number;

  @Field()
  isInternational: boolean;
}

Notice the validators from Lesson 6 still work — the global ValidationPipe applies to GraphQL inputs too. You did not waste any of last week's effort.

The Resolver — GraphQL's controller

// src/flights/flights.resolver.ts
import { Resolver, Query, Mutation, Args, ID } from '@nestjs/graphql';
import { Flight } from './flight.model';
import { CreateFlightInput } from './dto/create-flight.input';
import { FlightsService } from './flights.service';

@Resolver(() => Flight)
export class FlightsResolver {
  constructor(private readonly flights: FlightsService) {}

  @Query(() => [Flight], { name: 'flights' })
  findAll(): Promise<Flight[]> {
    return this.flights.findAll();
  }

  @Query(() => Flight, { name: 'flight', nullable: true })
  findOne(@Args('id', { type: () => ID }) id: string) {
    return this.flights.findOne(id);
  }

  @Mutation(() => Flight)
  createFlight(@Args('input') input: CreateFlightInput) {
    return this.flights.create(input);
  }
}

Register it in the module's providers array — same array as services. Resolvers are providers; the framework discovers them via the @Resolver() decorator.

// src/flights/flights.module.ts
@Module({
  providers: [FlightsService, FlightsResolver],
  controllers: [FlightsController], // REST and GraphQL coexist happily
})
export class FlightsModule {}

Run the app, open http://localhost:3000/graphql. You get the Apollo Sandbox playground — an interactive query editor with autocomplete from your generated schema. Try:

query {
  flights {
    code
    capacity
  }
}

Notice you only asked for code and capacity. The response has only those two fields, even though Flight has five. That's the GraphQL win in one screenshot.

🎯
REST: “Here are all 25 fields. Use what you need.”
Mobile app on 3G: *downloads 25 fields, uses 3, parses for 800ms*
GraphQL: “Tell me which 3 you want.”
Mobile app on 3G: { flight { code, gate, time } }
Mobile app on 3G: *response is 240 bytes*
The API where the client is allowed to be picky.

Mapped types in GraphQL too: @nestjs/graphql ships its own PartialType, PickType, OmitType, IntersectionType — same names as Lesson 6 but they preserve the GraphQL @Field metadata. Use these for UpdateFlightInput: extends PartialType(CreateFlightInput). Don't import them from the REST package.

Part 7: Subscriptions in 90 Seconds

Queries and mutations are request/response. Subscriptions are GraphQL's push channel: the client opens a long-lived connection, the server emits events when something changes.

// src/flights/flights.resolver.ts (additions)
import { Subscription } from '@nestjs/graphql';
import { PubSub } from 'graphql-subscriptions';

const pubSub = new PubSub();  // in real apps: a Redis-backed pubsub

@Mutation(() => Flight)
async createFlight(@Args('input') input: CreateFlightInput) {
  const flight = await this.flights.create(input);
  pubSub.publish('flightCreated', { flightCreated: flight });
  return flight;
}

@Subscription(() => Flight)
flightCreated() {
  return pubSub.asyncIterator('flightCreated');
}

Any client subscribed to flightCreated gets pushed the new flight the moment a mutation runs. Under the hood it's WebSockets, plus an in-memory or Redis-backed pubsub.

Subscriptions vs raw WebSockets: use GraphQL subscriptions when the data flowing through is the same shape as your queries (live-updating lists, dashboards). Use raw WebSockets / Socket.io (Lesson 9) for chat, presence, multiplayer cursors — anything where the message shapes are heterogeneous and not query-shaped. We'll meet WebSockets directly in Lesson 9.

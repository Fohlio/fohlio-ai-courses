Part 1: architecture.md is Law, Not Suggestion

When one engineer writes a service, "convention" lives in their head. When five engineers write one codebase, "convention" without enforcement becomes "everyone's preference" — which is the same thing as "no convention at all." Six months in, you have three different folder layouts, four ways to throw an error, and two ORMs.

Fohlio's solution: a 1,800-line document, asuncion/architecture.md, that codifies how we build. It uses MUST and NEVER language. PRs that violate it get rejected. New rules apply to the PR that adds them — you cannot merge "I'll fix it later."

Every airport you've ever flown through looks self-organizing. Gate agents wave you through; ground crew appears with the bags; flights leave on time. The illusion is that everyone knows what to do intuitively.

They don't. Behind the desks, in every airline office, sits a thick black binder labeled Operations Manual. Every action — how to gate-check a bag, how to reroute a passenger, what the fueling sequence is — is written down. New hires read it. Senior staff still consult it. Audits check against it. The intuition you see is years of compliance with a written rule.

That binder is architecture.md. The rules look bureaucratic until you imagine the airport without them.

Where to find it: asuncion/architecture.md at the repo root. It's referenced from AGENTS.md and CLAUDE.md, both of which exist precisely so AI tools (and humans) can't claim they didn't see the rules.

The actual MUST/NEVER language

Three excerpts, copied from the real file. Notice the tone:

// architecture.md — Repository Pattern (line 235)
- All DB query construction MUST live in repository files
- Services MUST NOT construct ORM queries — delegate to repositories
- Services MUST NOT call em.persist(), em.flush(), or em.transactional() directly
- All persistence MUST go through repository methods

// architecture.md — Pagination (line 1191)
- Unbounded or user-growable collections MUST use cursor-based pagination
- NEVER use offset/page-number pagination for tenant-facing product surfaces
  without explicit human approval

// architecture.md — Soft Delete Lifecycle (line 1275)
- User-facing entities MUST use soft delete by default
- Soft-deleted records MUST be excluded by default via MikroORM @Filter
- Unique constraints on soft-deletable entities MUST use partial indexes
  (WHERE deleted_at IS NULL) so re-creation after deletion is possible

Notice what's not here: words like "should consider" or "we generally prefer." MUST is binary. Either the code complies or it doesn't.

The Module Convention

Every feature module follows the same canonical layout. Open any module in asuncion/src/modules/ and you see the same shape. This is the law transcribed from architecture.md > Module Convention:

src/modules/users/ ├── entities/ ← MikroORM entities │ ├── user.entity.ts │ └── profile.entity.ts ├── dto/ ← request/response DTOs (class-validator) │ ├── create-user.dto.ts │ ├── update-profile.dto.ts │ └── user-response.dto.ts ├── repositories/ ← DB query construction lives here │ └── user.repository.ts ├── assemblers/ ← entity → DTO transformers (static) ├── commands/ queries/ handlers/ ← optional, only for CQRS ├── users.controller.ts ← exactly one primary controller ├── users.service.ts ← exactly one primary service └── users.module.ts

This is a real listing of asuncion/src/modules/users/. The same shape exists in auth/, workspaces/, projects/, contacts/, and every other module in the repo. When a new engineer joins and is asked "where does the password reset logic live?", the answer is no longer "uhh, try grep" — it's "auth module, service file, look for the password method." Predictable. Boring. Correct.

Why "let me just put it here for now" is forbidden: the foundational principle in AGENTS.md is Consistency over novelty. A new pattern is a liability. Three engineers will copy it before anyone notices. Three months later, "for now" is a 200-file commitment. The rule is: if no existing pattern fits, escalate — don't quietly invent one.

Document precedence — what wins when docs disagree

Real teams have feature specs, PRDs, master plans, task prompts, and AI-generated implementation plans flying around in any given week. They contradict each other. AGENTS.md resolves the question explicitly:

Part 2: MikroORM (and Why We Switched From Prisma)

Lesson 4 taught Prisma. Prisma is excellent for learning — the schema file is one of the friendliest APIs in the Node ecosystem, the generated client gives you autocomplete out of the box, and the migration story is straightforward. If you're picking up an ORM for the first time, Prisma is a kind teacher.

Production runs MikroORM v7. From asuncion/package.json:

"@mikro-orm/core": "^7.0.1",
"@mikro-orm/postgresql": "^7.0.1",
"@mikro-orm/nestjs": "^7.0.1",
"@mikro-orm/migrations": "^7.0.1",
"@mikro-orm/seeder": "^7.0.5",

Why MikroORM, specifically

The AGENTS.md "Key Decisions" table calls it out explicitly:

From AGENTS.md: “ORM — MikroORM 7. Why: Better TypeScript support, unit-of-work pattern, built-in soft delete filters.”

Three reasons matter day-to-day:

🔁
Unit of Work
Mutate entities in memory; one flush() writes everything in one transaction. No "did I forget to save?"
🔑
Identity Map
Same row fetched twice = same JS object. Critical for multi-tenant code where the same workspace pops up everywhere in one request.
🔌
Lifecycle hooks & filters
@BeforeCreate, @BeforeUpdate, @Filter('softDelete'). We rely heavily on these for password hashing and soft-delete.

Prisma vs MikroORM — what changes for you

📚
Prisma (what you learned)
Schema file + generated client
Schema in schema.prisma. Active-record-ish: prisma.user.findUnique({where:{...}}). Auto-commits each call. No identity map.
🏭
MikroORM (production)
TypeScript classes + decorators
Entities are TS classes with @Entity, @Property. Repositories extend EntityRepository<T>. Mutate in memory, then em.flush() commits everything atomically.

The same operation in both worlds

Concrete: "create a user, set their profile name, send a welcome email." Same operation, two ORMs. Compare the cognitive shape:

// Prisma — what Lesson 4 taught
const user = await prisma.user.create({
  data: {
    email,
    profile: { create: { firstName, lastName } },
  },
});
await mailer.sendWelcome(user);
// Each prisma call commits independently. If the email fails,
// the user already exists in the DB. You handle that with try/catch + delete.
// MikroORM — what production uses
await this.userRepository.em.transactional(async (em) => {
  const user = em.create(User, { email });
  user.profile = em.create(Profile, { firstName, lastName });
  await em.flush();              // one INSERT per entity, one transaction
  await mailer.sendWelcome(user); // if this throws, the tx rolls back
});

Two differences worth internalizing:

  1. Unit-of-work. In MikroORM you build the in-memory graph, then flush() commits everything atomically. Prisma's create-with-nested-create does similar in one call, but composing multiple operations atomically is more deliberate in MikroORM.
  2. Identity map. If you fetch the same workspace by id twice in one request, MikroORM gives you the same JS object both times. Mutations on one are visible on the other. Prisma returns two separate POJOs — you get correctness only by being careful.

Neither approach is "better" in the abstract. MikroORM's tradeoff fits Fohlio's multi-tenant request shape, where the same workspace and user object thread through 20 service calls per request. The identity map prevents 19 of those from being silent inconsistencies.

A real entity from asuncion

Here's asuncion/src/modules/users/entities/user.entity.ts, lightly trimmed. Look at the lifecycle hook at the bottom — that's where the password actually gets hashed:

import argon2 from 'argon2';
import {
  Entity, Property, Unique, Enum, OneToOne, ManyToMany,
  BeforeCreate, BeforeUpdate,
} from '@mikro-orm/decorators/legacy';
import { BaseEntity } from '../../../common/entities/base.entity.js';
import { UserRepository } from '../repositories/user.repository.js';

@Entity({ tableName: 'users', repository: () => UserRepository })
export class User extends BaseEntity {
  @Unique()
  @Property({ type: 'text', nullable: false })
  email!: string;

  @Property({ type: 'text', nullable: true, hidden: true })
  hashedPassword?: string;

  @Enum({ items: () => UserStatus, nativeEnumName: 'user_status_enum' })
  status: UserStatus = UserStatus.ACTIVE;

  // ... relations omitted ...

  @BeforeCreate()
  @BeforeUpdate()
  async hashPassword(): Promise<void> {
    if (this.hashedPassword && !this.hashedPassword.startsWith('$argon2')) {
      // OWASP params: m=7168, t=5, p=1
      this.hashedPassword = await argon2.hash(this.hashedPassword, {
        memoryCost: 7168, parallelism: 1, timeCost: 5,
      });
    }
  }
}

Three things to notice:

  1. @Entity({ repository: () => UserRepository }) — the entity itself declares which repository class owns it. When you inject UserRepository, NestJS gets back a properly-wired instance.
  2. extends BaseEntity — id: BigInt, createdAt, updatedAt come from src/common/entities/base.entity.ts. Every entity in the repo extends it. No exceptions.
  3. @BeforeCreate() @BeforeUpdate() hashPassword() — password hashing is part of the entity. There is no path through the system that writes a user without hashing its password. The clerk stamps every record before it goes into the archive, automatically.

Migrations

From asuncion/package.json scripts:

"db:migration:auto-generate": "npx mikro-orm migration:create",
"db:migration:up": "npx mikro-orm migration:up",
"db:migration:down": "npx mikro-orm migration:down",
"db:reset": "npm run db:schema:drop && npm run db:migration:up && npm run db:seed",

The CLI is the standard MikroORM workflow: change an entity, run migration:create, MikroORM diffs the schema and writes a migration file, you review it, then migration:up. Identical mental model to Prisma's prisma migrate — different command, same idea.

Pre-launch detail (Key Decisions): the repo is currently entity-first — no migration files are checked in. You edit entities and run db:reset to rebuild from scratch. This switches to migration-first at the first real-data deployment. Don't add migration files until that decision flips.

Part 3: The Repository Pattern — Services Never Touch the ORM

This is the single biggest pattern shift between the textbook and Fohlio production. In the textbook, controllers call services, and services call prisma.user.findUnique(...) directly. In Fohlio, that's a code-review block.

The rule, copied from architecture.md:

Service Pattern, MUST NOTs (line 220):

• MUST NOT construct ORM queries — delegate to repositories via named methods
• MUST NOT call em.persist(), em.flush(), or em.transactional() directly — all persistence MUST go through repository methods
• All raw SQL, Kysely queries, QueryBuilder writes MUST live in repositories

The librarian metaphor

Picture the airport's records archive. It's a long room of filing cabinets, climate-controlled, fluorescent-lit. The cabinets are alphabetized, cross-referenced, indexed.

The records librarian is the only person allowed in. She knows the layout, knows which cabinets to never open without gloves, knows that the “deleted” cabinet is actually the “retired” cabinet and the records there still count for some queries. She has a counter at the front. People file requests at the counter. She walks back, gets what they need, brings it back.

The service is the waiter at the gate. The waiter takes a passenger's request, walks to the counter, says “I need the booking for confirmation code XYZ.” The waiter never enters the archive. The waiter would lose the indexing, file something in the wrong drawer, leave a soft-deleted record visible to the wrong query. So the rule is: waiters file requests; librarians fetch.

In code: service calls this.userRepository.findByEmail(email). Service never calls em.find(), em.findOne(), em.persist(), or em.flush(). The repository owns the transaction boundary too — em.transactional() lives inside repository methods, not in services.

A real repository

Full file: asuncion/src/modules/users/repositories/user.repository.ts. This is the entire public API the rest of the system has, for the User entity:

import { EntityRepository, type FindOneOptions } from '@mikro-orm/postgresql';
import { User, UserStatus } from '../entities/user.entity.js';

export class UserRepository extends EntityRepository<User> {
  findByEmail(email: string, options?: FindOneOptions<User>) {
    return this.findOne({ email }, options);
  }

  findById(id: string, options?: FindOneOptions<User>) {
    return this.findOne({ id }, options);
  }

  findByGoogleId(googleId: string) {
    return this.findOne({ googleId });
  }

  async save(user: User): Promise<void> {
    this.em.persist(user);
    await this.em.flush();
  }

  /**
   * Find by email, or create an INACTIVE user if none exists.
   * Re-checks inside a transaction to prevent race-condition duplicates.
   */
  async findOrCreateByEmail(email: string): Promise<User> {
    const existing = await this.findByEmail(email);
    if (existing) return existing;

    let created!: User;
    await this.em.transactional(async (em) => {
      const recheck = await em.findOne(User, { email });
      if (recheck) { created = recheck; return; }
      const user = em.create(User, { email, status: UserStatus.INACTIVE });
      await em.flush();
      created = user;
    });
    return created;
  }
}

Notice: methods are named after what they return, not what they query. findByEmail, not queryUsersByEmailColumn. findOrCreateByEmail, not upsertUser. The repository is the dictionary of business-meaningful lookups.

The service that uses it

Full file: asuncion/src/modules/users/users.service.ts. Look how thin it is — it's pure orchestration:

@Injectable()
export class UsersService {
  constructor(private readonly userRepository: UserRepository) {}

  async findByEmail(email: string): Promise<User | null> {
    return this.userRepository.findByEmail(email);
  }

  async findOrCreateByEmail(email: string): Promise<User> {
    return this.userRepository.findOrCreateByEmail(email);
  }

  async updateProfile(userId: string, dto: UpdateProfileDto): Promise<User> {
    const user = await this.userRepository.findOneOrFail(
      { id: userId },
      { populate: ['profile', 'currentWorkspaceRole'] },
    );
    if (!user.profile) {
      const profile = new Profile();
      profile.user = user;
      user.profile = profile;
    }
    if (dto.firstName !== undefined) user.profile.firstName = dto.firstName;
    if (dto.lastName !== undefined) user.profile.lastName = dto.lastName;

    await this.userRepository.save(user);
    return user;
  }
}

Zero em.find. Zero em.persist. Zero raw SQL. Every database touch goes through userRepository. The service does what services are supposed to do: orchestrate, validate, decide.

GOOD vs BAD — same operation, two worlds

❌
BAD — service touches ORM
// users.service.ts
async findByEmail(email: string) {
  return this.em.findOne(
    User, { email },
  );
}
✅
GOOD — via repository
// users.service.ts
async findByEmail(email: string) {
  return this.userRepository
    .findByEmail(email);
}

Why this matters in practice:

• Testability. Service specs mock UserRepository — one collaborator, two-line setup. The alternative is mocking EntityManager with all its overloaded signatures.
• Single source of truth for query patterns. Soft-delete filters, populate hints, partial-index lookups — all live in one place per entity. When the index changes, you change one file.
• Test-the-layer-that-owns-the-logic (AGENTS.md #5). Query construction is owned by repositories — they MUST have *.repository.spec.ts tests that hit a real DB. Services get unit tests against mocked repositories. Each layer is tested where its complexity actually lives.

Where transactions live

Architecture.md is unusually opinionated about who owns transactions: repositories, not services.

// architecture.md, Repository Pattern (line 346–348):
- MUST use em.persist() + em.flush() for writes
- Multi-entity writes MUST use em.transactional() inside the repository
  method that owns the operation
- The repository that owns the primary entity owns the transaction
- State-changing methods MUST validate all required related rows inside the
  transaction before mutating state. If an expected related row is missing,
  throw and roll back — MUST NOT silently skip and continue with partial success

Notice the findOrCreateByEmail example we just read — the em.transactional block is in the repository, not the service. The repository re-checks for the row inside the transaction to avoid race conditions. The service just calls this.userRepository.findOrCreateByEmail(email) and gets back a User. This is the unit-of-work pattern at full strength: persistence boundaries are owned by the layer that knows the schema.

Repository spec coverage

Because repositories own the queries, transactions, and persistence invariants, they MUST have spec files — from architecture.md:

“Repositories with raw SQL, transactions, or query construction MUST have *.repository.spec.ts. E2E covers the happy-path wire-up; it does not substitute for repository specs.”

Look at the user module again — asuncion/src/modules/users/repositories/user.repository.spec.ts sits next to the repository file. Open it; it hits a real Postgres (in Docker) and verifies the actual SQL behavior, including soft-delete filter interaction. This is where the test budget goes — not in shallow service mocks.

✋ Predict before reading on
You're writing a unit test for UsersService.updateProfile. Sketch what you mock. Now imagine the service called this.em.findOneOrFail(...) directly — what would you mock instead? Which test is shorter?
The repository version: userRepository = { findOneOrFail: vi.fn(), save: vi.fn() }. The em version: you mock EntityManager with its full signature surface. The latter is brittle and tests almost nothing.

Part 4: Universal Soft-Delete

Nothing in the user-facing data model is ever truly deleted. Workspaces, projects, contacts, roles, memberships — they get a deletedAt timestamp set, and default queries skip them. From architecture.md > Soft Delete Lifecycle (line 1275):

- User-facing entities MUST use soft delete by default
- Hard delete is only for infrastructure records (expired tokens, processed jobs)
- Soft-deleted records MUST be excluded by default via MikroORM
  @Filter({ name: 'softDelete', cond: { deletedAt: null }, default: true })
- Unique constraints MUST use partial indexes (WHERE deleted_at IS NULL)

Why we never hard-delete user data

  • Audit. Who removed what, when. The row is the evidence.
  • Recovery. “I deleted the wrong project” happens weekly in any SaaS. Restore is one column flip.
  • Foreign-key integrity. If we delete a user, every project they touched would lose its created_by. Soft-delete keeps the graph intact.
  • GDPR. Real deletion is a separate hard-delete job that runs on user request, with rules about what to anonymize vs scrub.

The actual entity declaration

From asuncion/src/modules/workspaces/entities/workspace.entity.ts:

@Entity({ tableName: 'workspaces', repository: () => WorkspaceRepository })
@Filter({ name: 'softDelete', cond: { deletedAt: null }, default: true })
export class Workspace extends BaseEntity {
  @Property({ type: 'text', nullable: false })
  name!: string;

  @ManyToOne(() => User, { nullable: false })
  owner!: Rel<User>;

  @Property({ type: 'datetime', nullable: true })
  deletedAt?: Date;

  // ... relations ...
}

Two pieces:

  1. deletedAt?: Date — the column. Nullable. null = active, timestamp = retired.
  2. @Filter({ name: 'softDelete', cond: { deletedAt: null }, default: true }) — MikroORM's filter system. Every em.find(Workspace, ...) or workspaceRepository.findById(...) automatically appends WHERE deleted_at IS NULL. You get this for free, on every query, without remembering.

Deleting and restoring

From the ProjectRepository — soft-delete is just an assignment plus flush:

// inside a transaction in project.repository.ts
for (const link of project.projectUserLinks) {
  link.deletedAt = new Date();   // retire the membership rows
}
project.deletedAt = new Date();   // retire the project itself
await this.em.flush();          // one transaction, atomic

The unique-constraint trap

You have a soft-deleted workspace named "Acme". The user creates a new workspace, also "Acme". Naive UNIQUE(name) rejects it — the soft-deleted row is still in the table.

Fix: partial unique indexes. The constraint only applies to live rows:

CREATE UNIQUE INDEX workspaces_name_active
  ON workspaces (name)
  WHERE deleted_at IS NULL;

architecture.md mandates this for every soft-deletable entity with a unique constraint.

The gotcha that bites everyone once: ORM @Filter('softDelete') only fires for ORM operations. Raw SQL and Kysely bypass it silently, leaking ghost records.

From architecture.md line 349: “All raw SQL — Kysely queries, QueryBuilder writes, and entity formula subqueries — MUST include deleted_at IS NULL on every soft-deletable table.” Look at the project repo's Kysely lookup: .where('deleted_at', 'is', null) — explicit, every time.

Cascading soft-deletes are explicit, not automatic

This is where naive implementations get silently wrong. Consider: you soft-delete a workspace. What happens to its projects? Its memberships? Its roles?

MikroORM does not cascade soft-deletes automatically. From architecture.md:

“Cascading soft deletes MUST be handled explicitly in the service layer — MikroORM does not cascade soft deletes automatically. When a parent is soft-deleted, the service MUST decide which children to soft-delete and execute those writes in the same transaction.”

The service decides the policy (often: soft-delete the workspace, soft-delete all WorkspaceUserLink rows, but leave the actual User rows untouched because the user may still belong to other workspaces). The repository executes the writes inside one em.transactional() block. If anything fails, everything rolls back — no half-deleted aggregate.

This is the exact opposite of how DELETE CASCADE works in raw SQL. You trade convenience for control: the cascade rules live in code you can read and test, not in a foreign-key declaration buried in a migration.

Restore over recreate

When a user re-invites someone they previously removed, we don't create a new membership row alongside the soft-deleted one. We restore the existing row by clearing its deletedAt. From architecture.md:

// pattern: addOrRestore() in repository
const existing = await this.findOne(
  { workspace: workspaceId, user: userId },
  { filters: { softDelete: false } },  // see soft-deleted rows too
);
if (existing?.deletedAt) {
  existing.deletedAt = undefined;        // restore: un-retire the row
  existing.role = newRole;
  await this.em.flush();
  return existing;
}

This avoids ID churn and preserves relationship history. Stripe does it. GitHub does it. Slack does it. We do it.

Part 5: Cursor-based Pagination at Scale

The textbook example for pagination is ?page=5&limit=20. It's intuitive, demos well, and breaks at scale. Fohlio doesn't use it for tenant-facing lists. From architecture.md:

From architecture.md (Pagination, line 1191): “Unbounded or user-growable collections MUST use cursor-based pagination. NEVER use offset/page-number pagination for tenant-facing product surfaces without explicit human approval.”

Why offset breaks

When you ask Postgres for OFFSET 100000 LIMIT 50, the database has to scan and discard the first 100,000 matching rows before returning anything. Page 1 is fast. Page 2,000 is a 200ms query that touches half a million rows for 50 results.

Cursor pagination instead says: “give me the next 50 rows after this anchor.” Postgres uses the index on the sort column, jumps to the anchor, scans 50 rows, returns. Page 2,000 costs the same as page 1.

Same result set; one scales, the other doesn't.

The Fohlio utility

Found at asuncion/src/common/pagination/cursor-pagination.util.ts. Three exports:

export interface PaginatedResult<T> {
  items: T[];
  nextCursor: string | null;
  hasMore: boolean;
}

// Cursor format: base64url(JSON.stringify({ [sortField]: value, id: value }))
export function encodeCursor(sortValues: Record<string, unknown>): string {
  return Buffer.from(JSON.stringify(sortValues)).toString('base64url');
}

export function decodeCursor(cursor: string) {
  try {
    const json = Buffer.from(cursor, 'base64url').toString('utf-8');
    return JSON.parse(json);
  } catch {
    throw new BadRequestException({ code: 'INVALID_CURSOR' });
  }
}

// The repository fetches limit+1 rows; this slices into a result page
// and produces the next cursor from the last included row.
export function paginateResults<T>(
  rows: T[], limit: number, sortField: string,
  getId: (item: T) => string,
  getSortValue: (item: T) => unknown,
): PaginatedResult<T> { /* ... */ }

How a real repository uses it

From asuncion/src/modules/projects/repositories/project.repository.ts — the canonical paginated list query:

async findAllByWorkspaceId(
  workspaceId: string,
  cursor?: string,
  limit: number = 20,
): Promise<ProjectPage> {
  const where: Record<string, unknown> = { workspace: workspaceId };
  if (cursor) {
    const decoded = decodeCursor(cursor);
    // stable sort tuple: position, then id as tie-breaker
    where.$or = [
      { position: { $gt: decoded.position } },
      { position: decoded.position, id: { $gt: decoded.id } },
    ];
  }
  const rows = await this.find(where, {
    orderBy: { position: 'ASC', id: 'ASC' },
    limit: limit + 1,                // fetch n+1, paginateResults trims
    populate: [...PROJECT_POPULATE],
  });
  return paginateResults(
    rows, limit, 'position',
    (r) => r.id,
    (r) => r.position,
  );
}

Three details worth memorizing:

  1. The cursor encodes the full sort tuple, not just id. Sorting by position alone has duplicates — you need id as a tie-breaker. The cursor includes both.
  2. limit + 1 rows. If we get back limit+1, we know there's more. No extra COUNT(*) needed.
  3. The opaque $or condition — this is the SQL pattern for "after this tuple in this sort order." It looks ugly because tuple comparison in SQL is.
🤔 When does cursor pagination NOT work?
Cursor pagination is forward-sequential: page 1, then 2, then 3. When would you actually need offset pagination instead? Think before reading the answer.
Answer: when the user must jump to an arbitrary page (page 47 of an admin export). Cursors don't support that — you can't construct cursor #47 without walking pages 1–46. For backoffice/reporting tools, offset is sometimes acceptable. architecture.md calls these out as documented exceptions.

Part 6: Kysely — the Escape Hatch for Complex Queries

MikroORM is excellent for the 90% of queries that fit its mental model: find by id, find with relations populated, save an entity graph, soft-delete, paginate. The other 10% — window functions, recursive CTEs, custom joins with multiple workspace-scoped subqueries — gets ugly. The QueryBuilder fights you. nativeUpdate is forbidden. Raw SQL strings are forbidden for new sites without explicit justification.

Enter Kysely: a type-safe SQL query builder that types itself off the live DB schema (via kysely-codegen, see asuncion/package.json devDependencies). Same database, same transaction, just a different writing style for queries that are easier to write as SQL.

The records librarian (MikroORM) is excellent at standard requests. “Pull the booking for confirmation XYZ” — she walks back, comes out with one folder. “Pull all bookings for flight 123 with their seats” — same drill, two cabinets.

But occasionally a researcher asks: “I need every booking that contains a passenger whose loyalty points exceed the median for their tier, sorted by booking date, grouped by source airport, with the running total of cancellations in the same fare class within 24 hours of each booking.”

The librarian's standard request form has nowhere to write this. So Fohlio keeps a senior researcher on staff — Kysely — who works alongside the librarian, in the same archive, under the same rules. The waiter still doesn't go in. The waiter still files at the counter. Internally, the librarian routes the weird query to the senior researcher.

The contract: Kysely lives inside repositories. Services don't see Kysely either. architecture.md line 351: “MUST use getKysely(em) from src/common/db/kysely.ts for every Kysely read — NEVER call em.getKysely() directly.” The helper joins the active MikroORM transaction; the raw call doesn't.

The wrapper

From asuncion/src/common/db/kysely.ts:

import type { SqlEntityManager } from '@mikro-orm/sql';
import type { Kysely } from 'kysely';
import type { DB } from './db-types.js';

/**
 * Returns a Kysely instance typed by the project DB schema, participating
 * in the caller's current MikroORM transaction when one is active.
 *
 * em.getKysely() returns a Kysely bound to the connection POOL — its queries
 * do NOT see uncommitted rows, which silently breaks E2E tests that use
 * transaction rollback for isolation. Use this helper instead.
 */
export function getKysely<Schema = DB>(em: SqlEntityManager): Kysely<Schema> {
  const trx = em.getTransactionContext<Kysely<Schema>>();
  return trx ?? (em.getKysely() as Kysely<Schema>);
}

A real Kysely query inside a repository

From asuncion/src/modules/projects/repositories/project.repository.ts — case-insensitive name lookup. MikroORM's $ilike has wildcard-leak risk; the team hand-rolls lower() via Kysely to hit the partial unique index projects_workspace_lower_name_active:

async findByLowerNameAndWorkspace(
  normalizedName: string,
  workspaceId: string,
): Promise<Project | null> {
  const db = getKysely(this.em);              // transaction-aware
  const row = await db
    .selectFrom('projects')
    .select('id')
    .where('workspace_id', '=', workspaceId)
    .where((eb) => eb.fn<string>('lower', ['name']), '=', normalizedName)
    .where('deleted_at', 'is', null)         // MUST: Kysely bypasses @Filter
    .executeTakeFirst();

  if (!row) return null;
  return this.findOne({ id: String(row.id) });   // load via ORM for full graph
}

Pattern: Kysely fetches the id using the index, then the ORM loads the full entity. You get the index hit and the entity graph. Best of both clerks.

When to reach for Kysely

Rule of thumb (from the architecture.md "Choosing a query tool" table): if the MikroORM QueryBuilder fights you for more than 10 minutes, switch to Kysely. If Kysely also fights you (recursive CTEs, PL/pgSQL calls, db-specific extensions), drop to raw SQL via em.getConnection().execute() — but every raw-SQL site MUST carry a one-line comment naming the limitation it works around. The count of raw-SQL sites is a tracked metric; growth = architectural debt.

You can see this hierarchy in the wild — in asuncion/src/modules/catalog/items/queries/catalog-parts-graph.queries.ts, the simpler check uses Kysely with chained joins; the harder five-table self-referential EXISTS check drops to raw SQL with the required justifying comment.

The Choosing-a-Query-Tool table

Architecture.md ships an actual decision matrix. Lightly summarized:

Situation Tool Why
Find by id, find by simple where clause, save an entity graph ORM — em.find, findOne, persist+flush The @Filter('softDelete') fires automatically; identity map deduplicates; lifecycle hooks run.
Joins through an M2M / O2M / M2O relation ORM pivot query + populate The pivot's own @Filter fires; constant 2 batched queries (not N+1).
Custom SQL the QueryBuilder can't express cleanly Kysely via getKysely(em) Type-safe, transaction-aware, generated types from kysely-codegen. Must explicitly add deleted_at IS NULL.
Recursive CTEs, PL/pgSQL, db-specific extensions Raw SQL via em.getConnection().execute() Last resort. Every site MUST carry a one-line comment naming the limitation it works around.

Memorize the order: ORM → Kysely → raw SQL. Going right increases power and decreases safety. Don't skip levels.

Part 7: No Util Files — Explicit Dependencies, Always

This rule comes straight from the team and it has zero exceptions. Every dependency a service needs must arrive through the constructor. No import { doThing } from '../somewhere/thing.util.js' followed by calling doThing(...) inside a method. None.

The reason isn't aesthetic. It's two principles colliding with reality at once: IoC (Inversion of Control) and DI (Dependency Injection). When a service reaches into another file by import and calls a function, the service is in control of where that function comes from. That's the opposite of IoC. And when a test tries to swap that function for a mock, it can't — the import is hardwired. That's the opposite of DI.

The bad shape (what NOT to do)

Picture a gate agent at the airport who needs to verify that a passenger's checked bag belongs to their flight. The agent could pick up a phone and dial the baggage room directly — "Hey Steve, is bag 47 on flight DL112?" — bypassing the dispatch system entirely.

It works. It's fast. But now: who's tracking the call? What if Steve goes on vacation? What happens during a fire drill when you need to simulate the call without actually contacting the baggage room?

That direct phone call is what an imported util function is. Convenient. Untraceable. Unmockable.

The shorthand: if your service has an import { x } from '...util' and calls x(...) inside a method, you have an implicit dependency. That's a bug, even if the code passes review.

Here's the canonical anti-example shared by the team. Look at verifyFamilyWorkspace:

// src/modules/catalog/items/catalog-items.service.ts

import { verifyFamilyWorkspace } from '../families/verify-family-workspace.util.js';

@Injectable()
export class CatalogItemsService {
  constructor(
    private readonly itemRepository: CatalogItemRepository,
    private readonly familyRepository: CatalogFamilyRepository,
    private readonly columnsAttributesValidator: ColumnsAttributesValidator,
  ) {}

  async findAllByFamilyId(
    familyId: string,
    workspaceId: string,
  ): Promise<CatalogItem[]> {
    // The line below is an implicit dependency.
    // It cannot be mocked in unit tests without monkey-patching the import.
    await verifyFamilyWorkspace(familyId, workspaceId, this.familyRepository);

    return this.itemRepository.findAllByFamilyId(familyId);
  }
}

Why this is broken: verifyFamilyWorkspace is now part of the service's behavior, but it doesn't appear in the constructor. Tests can't inject a fake. Static analysis can't see the dependency graph. New engineers can't tell from CatalogItemsService.constructor what this class actually depends on. The util's logic is silently coupled to the service in a way DI was specifically invented to avoid.

The good shape

Promote the util to a class. Inject it. Done.

// src/modules/catalog/families/family-workspace-verifier.ts

@Injectable()
export class FamilyWorkspaceVerifier {
  constructor(private readonly familyRepository: CatalogFamilyRepository) {}

  async verify(familyId: string, workspaceId: string): Promise<void> {
    // ...verification logic that used to live in the .util file
  }
}

// src/modules/catalog/items/catalog-items.service.ts

@Injectable()
export class CatalogItemsService {
  constructor(
    private readonly itemRepository: CatalogItemRepository,
    private readonly familyWorkspaceVerifier: FamilyWorkspaceVerifier, // ← explicit
    private readonly columnsAttributesValidator: ColumnsAttributesValidator,
  ) {}

  async findAllByFamilyId(familyId: string, workspaceId: string) {
    await this.familyWorkspaceVerifier.verify(familyId, workspaceId);
    return this.itemRepository.findAllByFamilyId(familyId);
  }
}

Notice: the constructor now reads like a contract. Anyone glancing at the class knows exactly which collaborators it relies on. A unit test instantiates the service, passes mocks for those three constructor params, and runs in milliseconds with zero filesystem touches.

Key idea: The constructor is the documentation. If a behavior isn't in the constructor, it isn't part of this service's job — or it's a hidden dependency that needs to be made explicit.

The two questions to ask before adding any util file

1 Is it pure (no I/O, no state, no side effects)?
A function like formatDate(d: Date): string or slugify(s: string): string takes inputs and returns outputs. No DB, no clock, no fetch. These are fine as plain exports — they don't need DI. Tests pass real values, get real outputs.
2 Does it touch a repository, the clock, the filesystem, an external API, or anything else mockable?
Then it's a service. Wrap it in @Injectable() and inject it through the constructor. No exceptions. If you find yourself writing a .util.ts file that imports a repository, stop — that's a class waiting to happen.
✋ Quick recall — predict, don't peek
A teammate writes generateInvoiceNumber(workspaceId, invoiceRepository) as a util function. Is that allowed under the rule? What about maskEmail(email: string): string?
First one is broken (touches a repository — should be a service). Second is fine (pure function, no I/O). The test: can you call it with hand-typed values in a test, no setup? If yes, util. If no, service.

Suites (Automock) — making explicit dependencies cheap to test

The team is adopting Suites (formerly Automock) for unit tests. The point of Suites is simple: when every dependency is in the constructor, a test framework can auto-generate mocks for all of them, and you only override the ones that matter for the case you're testing.

// catalog-items.service.spec.ts — Vitest + Suites

import { TestBed } from '@suites/unit';
import type { Mocked } from '@suites/doubles';
import { CatalogItemsService } from './catalog-items.service';
import { CatalogItemRepository } from './catalog-item.repository';

describe('CatalogItemsService', () => {
  let service: CatalogItemsService;
  let itemRepository: Mocked<CatalogItemRepository>;

  beforeEach(async () => {
    // One line. All constructor deps are auto-mocked.
    const { unit, unitRef } = await TestBed.solitary(CatalogItemsService).compile();

    service = unit;
    itemRepository = unitRef.get(CatalogItemRepository);
  });

  it('returns items for a family', async () => {
    itemRepository.findAllByFamilyId.mockResolvedValue([/* fixture */]);

    const result = await service.findAllByFamilyId('fam-1', 'ws-1');

    expect(itemRepository.findAllByFamilyId).toHaveBeenCalledWith('fam-1');
  });
});

No providers: [...] array with manual mocks. No useValue: { findAllByFamilyId: vi.fn() } ceremony. TestBed.solitary(Service) reads the constructor, generates a mock for every parameter, and hands them to you via unitRef. You override only what your test cares about.

Real-world payoff: a service with 6 constructor dependencies used to need ~30 lines of test setup. With Suites it's 2 lines. The reference PR is github.com/Fohlio/fohlio-spechub-backend/pull/60; the quickstart is at suites.dev/docs/get-started/quickstart.

Why the rule and the tool fit together: Suites only works if dependencies are in the constructor. The moment someone slips in verifyFamilyWorkspace(...) from a util import, Suites can't help — that call is invisible to TestBed. The "no util files" rule isn't just about clean code. It's the precondition that makes auto-mocking possible at all.

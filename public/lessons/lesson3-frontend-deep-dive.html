Key Concepts: What Is Code, Anyway?

Before we dive into the frontend, let's make sure we all speak the same language. If you already know these terms — skip ahead to Part 1.

Code = Instructions for the Computer

Code is just text that tells the computer what to do. It looks like English mixed with math symbols. Here's a tiny example:

if (user.isLoggedIn) {
  showDashboard()
} else {
  showLoginPage()
}

This says: "If the user is logged in — show the dashboard. Otherwise — show the login page." That's it. Code is instructions, written step by step.

Analogy: Code is like a recipe. A recipe says "mix flour and water, then bake at 180°C for 30 minutes." Code says "take user data, show it in a table, and when they click 'Save' — send it to the server." Same idea: step-by-step instructions.

Files & Folders = How Code Is Organized

A project is just a folder on your computer with many files inside. Each file contains code for one specific thing — a button, a page, a data request. Folders group related files together.

fohlio-frontend/              # The main project folder
  src/                          # "Source" - all the code lives here
    __fsd__/                    # Organized code (we'll explain this)
      2-pages/                # Each page of the app
        dashboard/            # The Dashboard page
          Dashboard.tsx       # The actual code for the Dashboard

Think of it like a filing cabinet. The project is the cabinet. Folders are the drawers. Files are the individual documents inside. When Cursor opens a project, it shows you this filing cabinet in the left sidebar.

JavaScript & TypeScript = The Language We Write In

Just like people speak English, Russian, or French — code is written in programming languages. Browsers (Chrome, Safari, Firefox) understand one language: JavaScript.

We use TypeScript — it's JavaScript with extra safety. Think of it as JavaScript with spell-check. It catches mistakes before the code runs, not after.

Language What It Is Analogy
JavaScript The language that browsers understand Writing in English
TypeScript JavaScript + safety checks (catches typos and wrong data types) Writing in English with Grammarly turned on

Code files end in .ts (TypeScript) or .tsx (TypeScript with visual elements). When you see these extensions in Cursor — that's our code.

Libraries & Packages = Tools We Don't Build Ourselves

When you need a bookshelf, you don't grow a tree, chop the wood, and build it from scratch. You buy one from IKEA. Software works the same way.

A library (also called a package) is a set of ready-made code created by other developers that we download and use. Instead of building everything from scratch, we "buy" pre-built tools:

What We Need Library We Use IKEA Analogy
Build the interface (buttons, forms, etc.) React The kitchen set — the biggest, most essential purchase
Ready-made UI components Ant Design Matching plates, cups, and cutlery — a coordinated set
Talk to the backend server Apollo Client A delivery service that brings groceries from the store
Our own custom components @fohlio/ui-kit Custom furniture built by our own workshop

All libraries live in a folder called node_modules/. You'll see it in the project — never edit anything there. It's managed automatically.

Fun fact: Our project uses about 1,500 packages. That sounds like a lot, but most are small utilities — like having 1,500 different IKEA parts that together make up your apartment. The command yarn install downloads all of them automatically.

Part 1: The Story of fohlio-frontend

In Lesson 2 we said that Frontend — it's the "dining room" of our restaurant. Guests (users) come here, see the menu (interface), and place orders (requests to backend).

Now let's look inside this dining room and meet the team of libraries that makes it work.

Don't worry! This lesson introduces a lot of names. You don't need to memorize them all. The goal is to recognize them when you see them in the code — like knowing the names of your coworkers without remembering everyone's birthday. Cursor's AI will help you with the details.

The Characters

Our codebase has its heroes — programs and tools that work together to make the dining room function. You don't need to understand them deeply right now, just know who they are and what they do:

⚙️
React
Head Decorator
Builds everything the guest sees: buttons, tables, forms. Without React — the dining room would be empty walls.
🏗️
Rspack
Construction Crew
Every morning before the restaurant opens, Rspack takes all the code files and assembles them into the finished dining room that browsers can show.
🧑‍💼
Apollo Client
Head Waiter
Takes orders from the guests (users), carries them to the kitchen (backend), and brings back the dishes (data). Speaks GraphQL fluently.
📝
Zustand
Notepad on the Wall
Remembers the current state of everything: which tab is open, what's selected, which modal is showing. Simple, fast, reliable.
📁
Redux + Sagas
Old Filing Cabinet
The previous system. Still works, but slow and complicated. Being gradually replaced by the nimble Zustand. Don't create new Redux code!
🏠
@fohlio/ui-kit
Furniture Catalog
A separate library of ready-made components: buttons, inputs, tables. Like ordering furniture from a factory instead of building each chair from scratch.

Imagine: the restaurant is getting ready for the day. Rspack (the Construction Crew) arrives first — takes thousands of code files and in a few seconds assembles them into one working dining room.

Then React (the Head Decorator) steps in. It builds every button, table, and sidebar. When a guest clicks something, React repaints only the changed part — not the entire room.

When the guest wants to see their project data, Apollo Client (the Head Waiter) runs to the kitchen (backend) and brings back exactly the data that was requested. No more, no less.

And Zustand (the Notepad) keeps track of what's happening right now: which project is selected, whether the sidebar is open, what the user is filtering by. If the guest switches a tab, Zustand updates the note, and React immediately repaints the room.

You don't need to memorize these names! Cursor's AI knows all of them. When you work with the code, just describe what you want in plain words, and Cursor will use the right tool. These names are here so you recognize them when you see them in the code.

Example: What Happens When a User Creates a Project

Let's make this concrete. A user opens Fohlio and clicks "Create New Project." Here's what happens behind the scenes — step by step, with all our characters in action:

The full journey of creating a project: from button click to data saved in the database and back

Notice how each character does one job and passes the baton:

React shows the button and the dialog → Zustand remembers what the user typed → Apollo carries the request to the kitchen → Backend saves it in the database → Apollo brings the answer back and caches it → React shows the updated screen.

It all happens in about 1–2 seconds. Six handoffs, invisible to the user. They just see the button, the spinner, and the result.

This same pattern repeats everywhere: adding a product, editing a spec, uploading an image, changing a budget. The characters are always the same, just the "order" changes. Once you understand this flow, you understand 90% of how the frontend works.

The Two Big Upgrades

Every old restaurant has a history. Ours went through two major upgrades. You'll see traces of both the old and new systems in the code, so it's good to know what happened.

Upgrade 1: From REST to GraphQL (How we talk to the kitchen)

In the early days, our dining room had a simple ordering system. The waiter would run to the kitchen with a form: "Give me everything about Project #42." The kitchen would prepare a huge tray with ALL information about the project — even the stuff nobody asked for. This old system was called REST.

The problem? Imagine ordering a salad and getting the entire menu on a tray. Slow and wasteful.

So the restaurant upgraded to GraphQL — a smart ordering system where the waiter says: "I need ONLY the project name, owner, and last 5 items." And the kitchen sends back exactly that. No more, no less.

Why does this matter to you? When you look at the code, you'll see two styles of "talking to the kitchen". The old way (REST) looks like web addresses: /api/projects/42. The new way (GraphQL) looks like a wish list describing exactly what data you want. All new code uses GraphQL.

REST: "give me everything" vs GraphQL: "give me exactly what I need"

Upgrade 2: From Redux to Apollo + Zustand (How we remember things)

With the old system, the restaurant needed a giant filing cabinet (called Redux) to store all the data. Every piece of data had to be manually filed and indexed. It worked, but was slow and complicated.

With the new system, Apollo Client (the Head Waiter) has its own memory. It said: "I'll automatically remember everything the kitchen sends me. No filing cabinet needed." The waiter remembers past orders and can answer repeat questions instantly.

For things like "is the sidebar open?" or "which tab is selected?", the team uses Zustand — a simple notepad. Write it down, read it back. Done.

What Old Way New Way
Asking the kitchen for data REST (old-style web requests) GraphQL (smart requests)
Remembering kitchen data Redux (complicated filing cabinet) Apollo (automatic memory)
Remembering UI state Redux (same complicated system) Zustand (simple notepad)
Where in the code src/data/, src/containers/ src/__fsd__/

Simple rule for you: If you find yourself editing something in src/data/ — that's old code. Fix the bug if needed, but don't add new things there. All new work goes into src/__fsd__/ using the modern tools.

🍕
REST is like texting your ex — you ask one question
and get back 47 things you didn't ask for.
GraphQL is like a therapist — you get exactly
the answer to the question you asked.
Both cost money, but at least GraphQL is faster.

The Room Layout: Feature-Sliced Design (FSD)

The team also reorganized where things live in the code. Before, everything was mixed together — like throwing all your kitchen utensils, plates, and napkins into one drawer. With 400+ files, nobody could find anything.

The new system is called Feature-Sliced Design (FSD). Think of it as a 6-floor building where each floor has a clear purpose:

1 app The building itself: routing, providers, main layout
2 pages Individual rooms: Dashboard, Project Sheet, Billing...
3 widgets Big pieces of furniture: Analytics panel, Budget table...
4 features Interactive things: "Add product" button, approval workflow...
5 entities Core concepts: Project, Contact, Budget, Comment...
6 shared Basic tools everyone uses: UI components, helpers, API utils

The one rule you need to know: New code always goes into src/__fsd__/. If you see folders like src/components/ or src/data/ — that's old code. Don't add new things there.

In the project, this structure lives in the folder src/__fsd__/. When you open it in Cursor, you'll see the 6 numbered folders. If you need to find where something is — just think about which floor it belongs to.

The Great Migration: from the chaotic old wing to the organized FSD structure
🚨
Putting new code in the old src/components/ folder
is like parking in a "No Parking" zone.
You can do it. But someone will find you. And they will not be happy.
src/__fsd__/ is free parking with a view.

Part 2: Environment Variables

Environment variables are like settings on a configuration board. They tell the frontend: "Which kitchen (backend server) should I send orders to?"

They live in a file called .env.local in the project folder. This file is personal to your machine — it's not shared with others via Git, because everyone might connect to a different server.

The Two Most Important Variables

90% of the time, you only care about these two:

Variable What It Does Example
REACT_APP_API_URL Where to send API requests (which backend/kitchen) https://test01.fohlio.io/be
REACT_APP_CABLE_URL Connection for live updates (when someone else edits the same project) wss://test01.fohlio.io/be/cable

When you run make use-test01, the Makefile automatically updates these two variables in your .env.local file. You don't need to edit them manually!

What .env.local Looks Like

# Which backend server to connect to
REACT_APP_API_URL=https://test01.fohlio.io/be
REACT_APP_CABLE_URL=wss://test01.fohlio.io/be/cable

That's it! There are other variables in the file (for analytics, payments, error tracking), but they're only used in production. You don't need to worry about them. If something doesn't work, ask Ivan — it's probably a missing env variable.

Simple rule: After make setup, your .env.local has everything it needs. Just run make use-test01 (or whichever server) to point to the right backend, and you're good to go.

Step 1: Set Up Node.js with nvm

We use a specific Node.js version (v20.12.2). nvm (Node Version Manager) lets you install and switch between versions easily:

# Install nvm (if you don't have it)
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash

# Close and reopen your terminal, then:
nvm install 20.12.2
nvm use 20.12.2

# Verify:
node --version
# Should print: v20.12.2

Why nvm? Different projects might need different Node versions. With nvm, you can switch instantly. The file .nvmrc in the project root tells nvm which version to use. Just run nvm use in the project folder.

Step 2: GitHub Permissions

You need access to two things on GitHub:

  1. Fohlio organization — to clone the repository. Ask your team lead to add you.
  2. GitHub Packages token — to download @fohlio/ui-kit. This requires a special setup.

What is @fohlio/ui-kit? It's our private npm package hosted on GitHub Packages (not the public npm). It contains reusable UI components: buttons, inputs, modals. The project can't install without it.

Step 3: Set Up the GitHub Token for @fohlio/ui-kit

The project uses GitHub Packages to host the private @fohlio/ui-kit package. To download it during yarn install, you need to authenticate. We use the GitHub CLI (gh) for this — it's the easiest way.

3a. Install GitHub CLI

If you don't have gh yet:

# Mac (via Homebrew):
brew install gh

# Verify:
gh --version

3b. Log in to GitHub via CLI

If you haven't logged in to gh yet:

# This will open a browser for OAuth login:
gh auth login

Follow the prompts: choose GitHub.com, HTTPS, and authenticate in the browser.

3c. Add the read:packages Scope and Configure Yarn

These two commands are the magic. Run them in any directory:

# 1. Add the read:packages scope to your gh token
gh auth refresh -s read:packages

# 2. Tell Yarn to use your gh token for @fohlio packages
yarn config set --home 'npmScopes.fohlio.npmAuthToken' "$(gh auth token)"

That's it! Two commands. No manual token copying, no editing ~/.npmrc.

Token setup: just 3 commands using GitHub CLI. No manual token management!

Token expired? If yarn install starts failing with 401 Unauthorized, just re-run the same two commands:

gh auth refresh -s read:packages
yarn config set --home 'npmScopes.fohlio.npmAuthToken' "$(gh auth token)"

How Does This All Connect?

Two config layers work together:

Config Where What It Does
.yarnrc.yml In the project "All @fohlio/* packages come from npm.pkg.github.com"
yarn config --home Your home directory (~/.yarnrc.yml) "Use this token to authenticate with GitHub Packages"

When you run yarn install, Yarn reads the project config ("where to get @fohlio packages") and your home config ("how to authenticate"). Together, they let Yarn download @fohlio/ui-kit.

Step 4: Clone and Set Up

Now let's actually clone and set up the project:

# 1. Clone the repository
git clone git@github.com:Fohlio/fohlio-frontend.git

# 2. Enter the project directory
cd fohlio-frontend

# 3. Use the correct Node.js version
nvm use

# 4. Enable Yarn (if you haven't)
corepack enable

# 5. Setup: install dependencies + create .env.local
make setup

# 6. Point to a staging backend
make use-test01

# 7. Start the dev server!
make s

That's it! Open http://localhost:3000 in your browser. You should see the Fohlio login page. Log in with your staging credentials (ask Ivan for them).

Troubleshooting

Problem Cause Fix

Part 1: Why Three Things Instead of One?

A reasonable question to ask: “Why do I need a Controller and a Service and a Module? Couldn't this be one file?”

Short answer: yes, it could. For about three weeks. Then it can't.

The airport, again

Picture Heathrow Terminal 5. A passenger walks up to the gate with a boarding pass. The gate agent looks at the pass, scans it, says “welcome aboard, your seat is 14C.” That's it. The agent does not personally drive the baggage truck. The agent does not personally fuel the plane. The agent does not personally negotiate ground handling contracts.

If the gate agent did all of that, two bad things would happen. First, every gate would have a 90-minute queue because one person can't do five jobs. Second, the moment the airline switches from baggage vendor X to vendor Y, you'd have to retrain every gate agent at every terminal in the world.

Instead: gate agents talk to ground crew via a dispatch system. The ground crew can change vendors, change processes, even change country — and gate agents notice nothing. That's the separation we want in code.

The same idea in software words: Controllers handle HTTP. Services handle business logic. Modules group them. When the database changes, only the service changes. When the URL scheme changes, only the controller changes. The boundary is the entire point.

What each block actually owns

Block Owns Doesn't own
Controller Routes, HTTP verbs, status codes, request shape Database, business rules, third-party APIs
Service (Provider) Business logic, orchestration, data access How the request arrived (HTTP? CLI? queue?)
Module Wiring — who can see whom, what's exported, what's imported Any actual logic at all — the class body is empty

One request, three stops

Here's what happens when GET /flights/42 hits your app. Notice how each block does one thing and hands off:

The controller never calls new FlightsService() — the DI container hands it the right instance.

Key idea: A well-written controller is boring. A well-written service is also boring. A well-written module is downright dull. Boring is the goal. Excitement in any of these layers usually means a bug.

Part 2: Controllers Deep Dive

A controller is a class decorated with @Controller(prefix). Inside, every method decorated with an HTTP verb decorator (@Get, @Post, etc.) becomes a route. That's the whole concept. The rest is decorators that pull pieces out of the request.

The route prefix

import { Controller, Get } from '@nestjs/common';

@Controller('flights')
export class FlightsController {
  @Get()
  findAll() {
    return 'all flights';     // GET /flights
  }

  @Get('today')
  findToday() {
    return "today's flights"; // GET /flights/today
  }
}

The prefix in @Controller('flights') is glued to every method-level path. @Get() with no argument means “the prefix itself.” @Get('today') means “prefix + /today.” This is gate-numbering: every gate agent at Terminal 2 has gate numbers that start with 2 (2A, 2B, 2C). The prefix is the terminal letter; the method path is the gate.

The HTTP verb decorators

Decorator Purpose Default status
@Get(path?)Read200
@Post(path?)Create201
@Put(path?)Replace whole resource200
@Patch(path?)Partial update200
@Delete(path?)Remove200
@Head(path?)Headers only, no body200
@Options(path?)CORS preflight, capabilities200
@All(path?)Match every verb200

Request data decorators

Inside a route handler you usually need pieces of the incoming request: a path parameter, a query string, a body, sometimes a header. NestJS gives you a decorator for each, so you never have to dig into req manually.

DecoratorPulls fromExample
@Param('id')URL path/flights/42 → id = '42'
@Query('q')Query string?q=NYC → q = 'NYC'
@Body() / @Body('field')JSON bodyPOST body → full object or one field
@Headers('x-token')HTTP headersheader value
@Ip()Client IP'192.168.1.10'
@Req() / @Res()Raw Express objectsescape hatch, use sparingly

A full controller, end-to-end

Here's what a real FlightsController looks like with multiple methods. We'll build the actual service in Part 5 — for now focus on the shape.

import {
  Controller, Get, Post, Patch, Delete,
  Param, Body, Query, HttpCode, ParseIntPipe,
} from '@nestjs/common';
import { FlightsService } from './flights.service';

@Controller('flights')
export class FlightsController {
  constructor(private readonly flights: FlightsService) {}

  @Get()
  findAll(@Query('destination') destination?: string) {
    return this.flights.findAll({ destination });
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.flights.findOne(id);
  }

  @Post()
  create(@Body() body: { destination: string; gate: string }) {
    return this.flights.create(body);
  }

  @Patch(':id')
  update(
    @Param('id', ParseIntPipe) id: number,
    @Body() patch: { gate?: string },
  ) {
    return this.flights.update(id, patch);
  }

  @Delete(':id')
  @HttpCode(204)
  remove(@Param('id', ParseIntPipe) id: number) {
    return this.flights.remove(id);
  }
}

Take a moment to count the lines that talk about HTTP: route paths, status codes, body parsing. Now count lines that talk about flights: zero. The controller is a translator between “HTTP world” and “flights world.” The flights logic lives entirely in the service.

Returning values vs streaming

By default, when you return something from a route handler, Nest takes care of the response: a JS object becomes JSON, a primitive is returned as-is, an async function is awaited. This is what you want 95% of the time.

The 5% case — large file streams, custom headers per byte, Server-Sent Events — uses @Res() to grab the raw Express response object. The moment you do that, Nest steps back: you are now responsible for calling res.send() or the request hangs.

Gotcha: If you ever inject @Res() just to set a cookie or a header, use @Res({ passthrough: true }). Without passthrough, you take over the entire response and your return value is silently ignored.

Status codes, redirects, and headers

import { Controller, Post, Get, HttpCode, Header, Redirect } from '@nestjs/common';

@Controller('gates')
export class GatesController {
  @Post()
  @HttpCode(202)               // override default 201
  @Header('X-Source', 'airport-api') // custom response header
  enqueue() {
    return { status: 'accepted' };
  }

  @Get('old-route')
  @Redirect('/gates/new-route', 301)
  oldRoute() {}
}

@HttpCode changes the default. @Header appends a header to every response from this handler. @Redirect issues an HTTP redirect — the URL and status are baked in at decoration time, but you can also return { url, statusCode } dynamically from the method body to override.

Part 3: Providers Deep Dive

“Provider” is the umbrella term NestJS uses for “a class the DI container manages.” In day-to-day code, providers usually fall into one of three flavors: services, repositories, and helpers. They all look the same from Nest's perspective.

The whole magic is one decorator

import { Injectable } from '@nestjs/common';

@Injectable()
export class FlightsService {
  findAll() {
    return [];
  }
}

@Injectable() tells Nest: “you are allowed to manage instances of this class.” That's it. Nothing else changes about the class. You could remove the decorator and instantiate it manually with new FlightsService() — but then Nest has no idea this class exists, and trying to inject it elsewhere fails.

Three flavors of provider

🛠️
Service
Business logic
FlightsService, BookingsService. Orchestrates work, calls repositories, applies rules. The bulk of your codebase lives here.
🗄️
Repository
Data access
FlightsRepository. Owns the database queries. Service calls it. We'll formalize repositories in Lesson 4 (Prisma).
🔧
Helper / Utility
Pure functions in a class
DateFormatter, GateNumberGenerator. Stateless utilities the DI container hands out. Easy to mock in tests.
📡
Adapter / Client
External I/O
EmailClient, S3Adapter, StripeAdapter. Wraps a third-party SDK so the rest of the app doesn't depend on it directly.

Constructor injection — the contract

You declare what a class needs in its constructor. Nest reads the parameter types and supplies the correct singleton from its container.

@Injectable()
export class FlightsService {
  constructor(
    private readonly repo: FlightsRepository,
    private readonly formatter: DateFormatter,
    private readonly emails: EmailClient,
  ) {}

  async cancel(id: number) {
    const flight = await this.repo.findOne(id);
    await this.emails.notifyPassengers(flight);
    return this.repo.update(id, { status: 'cancelled' });
  }
}

The private readonly shorthand is a TypeScript thing — it both declares a field and assigns the constructor parameter to it in one go. Nest doesn't care about the modifier, but you should always use private (these are internal collaborators) and readonly (you should never reassign them after construction).

Real example: When you write constructor(private readonly flights: FlightsService) {} in a controller, Nest goes to its container, finds the singleton instance of FlightsService, and hands it over. There's no new FlightsService() anywhere in your code. Ops Dispatch is doing the dispatching.

Provider scopes — advanced but worth a quick look

By default, every provider in NestJS is a singleton. One instance, shared across the entire application, for the entire app's lifetime. This is what you want 95% of the time, and it's why DI is fast.

Two other scopes exist for the 5% case:

ScopeLifetimeUse case
Scope.DEFAULT One instance, app lifetime Stateless services. The default. Pick this unless you know you need otherwise.
Scope.REQUEST One instance per HTTP request Per-request state: a request-scoped logger that knows the request ID, a multi-tenant DB connection chosen from a header.
Scope.TRANSIENT New instance every injection site Rare. Loggers that need to capture the class name they're injected into. 
import { Injectable, Scope } from '@nestjs/common';

@Injectable({ scope: Scope.REQUEST })
export class RequestLogger {
  private readonly id = Math.random().toString(36).slice(2, 8);

  log(msg: string) {
    console.log(`[${this.id}] ${msg}`);
  }
}

Aha moment: Request-scoped providers force every consumer up the chain to also become request-scoped. If FlightsController injects a request-scoped logger, the controller itself is also instantiated per request. This costs performance — every request now allocates and tears down an instance graph. Use sparingly.

♻️
Dev: “I made everything REQUEST-scoped, just to be safe.”
Prod: 2x latency, OOM by lunchtime
Dev: “Hmm.”
DEFAULT is default for a reason. Singletons are cheap, instances are not.

Part 4: Modules Deep Dive

Every NestJS app has at least one module — the root AppModule. Real apps have many: FlightsModule, UsersModule, BookingsModule, AuthModule. A module is a terminal: a self-contained area with its own gates, its own crew, and a clear list of which crew it shares with other terminals.

The four properties of @Module

@Module({
  imports:     [],   // other modules whose exports we use
  controllers: [],   // gate agents stationed in this terminal
  providers:   [],   // crew available inside this terminal
  exports:     [],   // crew this terminal lends to other terminals
})
export class FlightsModule {}
PropertyWhat it does
controllers Classes Nest should scan for routes. Listed here once, period.
providers Classes the DI container can hand out inside this module. Private by default.
imports Other modules whose exports you want to consume. Importing a module gives you access to whatever it has exported — nothing more.
exports The subset of your providers that other modules are allowed to inject when they import you.

Encapsulation — the part that trips everyone up

Imagine Terminal 2 has a baggage handler named Steve. Terminal 3 needs Steve for an international transfer. Can Terminal 3 just grab Steve? No. Terminal 3 has to formally request Steve via the airport's inter-terminal agreement. And Terminal 2 has to list Steve on the “people we lend out” roster.

Same in NestJS. FlightsModule declares FlightsService in providers. By default, FlightsService is private — only the controllers and providers inside FlightsModule can inject it. If BookingsModule also needs FlightsService, two things must happen:

1. FlightsModule must export FlightsService.
2. BookingsModule must import FlightsModule.

Why bother? Without encapsulation, every provider would be a global. Any module could inject anything. You'd lose the “wait, who depends on what?” visibility that makes large NestJS apps refactorable. The cost is two extra lines per shared service. The benefit is a year-three codebase you can still navigate.

An end-to-end example

// flights.module.ts
@Module({
  controllers: [FlightsController],
  providers:   [FlightsService],
  exports:     [FlightsService],   // 👈 lend FlightsService out
})
export class FlightsModule {}

// bookings.module.ts
@Module({
  imports:     [FlightsModule],    // 👈 borrow it
  controllers: [BookingsController],
  providers:   [BookingsService],
})
export class BookingsModule {}

// bookings.service.ts
@Injectable()
export class BookingsService {
  constructor(private readonly flights: FlightsService) {} // works
}

Drop either the exports line or the imports line and Nest fails at startup with the famous error:

Nest can't resolve dependencies of the BookingsService (?).
Please make sure that the argument FlightsService at index [0]
is available in the BookingsModule context.

Memorize that error message. You will see it. Often.

Feature modules vs the root module

A feature module wraps one piece of functionality — flights, users, bookings. The root module (AppModule) wires the whole airport together by importing every feature module. Root modules typically have an empty controllers array and a small providers list (cross-cutting things like config). The work happens in feature modules.

// app.module.ts — the root
@Module({
  imports: [FlightsModule, BookingsModule, UsersModule],
})
export class AppModule {}

Shared modules

If three feature modules all need the same utility, you don't import that utility three times — you put it in a SharedModule that exports it, and each feature module imports SharedModule. We'll do exactly this in the homework.

Why it matters at scale: Modules are the unit of cognitive isolation. When a new dev joins and you say “go look at FlightsModule,” they should be able to read it top to bottom without needing to know how BookingsModule works. The encapsulation makes that possible. It's the architectural payoff of writing a few extra lines.

Answer to the recall question from Part 1: Only the service changes. The controller and the module stay identical — they don't know or care whether the data comes from Postgres, Redis, or the moon. That's the whole point.

The service — in-memory store

Open flights.service.ts and replace the body with this:

import { Injectable, NotFoundException } from '@nestjs/common';

export interface Flight {
  id: number;
  destination: string;
  gate: string;
  status: 'scheduled' | 'boarding' | 'cancelled';
}

@Injectable()
export class FlightsService {
  private flights: Flight[] = [
    { id: 1, destination: 'NYC', gate: 'A12', status: 'scheduled' },
    { id: 2, destination: 'LON', gate: 'B04', status: 'boarding' },
  ];
  private nextId = 3;

  findAll(filter?: { destination?: string }) {
    if (filter?.destination) {
      return this.flights.filter(f => f.destination === filter.destination);
    }
    return this.flights;
  }

  findOne(id: number) {
    const flight = this.flights.find(f => f.id === id);
    if (!flight) throw new NotFoundException(`Flight ${id} not found`);
    return flight;
  }

  create(input: { destination: string; gate: string }) {
    const flight: Flight = {
      id: this.nextId++,
      destination: input.destination,
      gate: input.gate,
      status: 'scheduled',
    };
    this.flights.push(flight);
    return flight;
  }

  update(id: number, patch: Partial<Flight>) {
    const flight = this.findOne(id);
    Object.assign(flight, patch);
    return flight;
  }

  remove(id: number) {
    const idx = this.flights.findIndex(f => f.id === id);
    if (idx === -1) throw new NotFoundException(`Flight ${id} not found`);
    this.flights.splice(idx, 1);
  }
}

An in-memory array is fine for now. Lesson 4 swaps it for a real database without changing a line of the controller.

Part 6: Common Pitfalls

Three errors you will hit at some point. Recognize them and you'll fix them in seconds. Don't recognize them and you'll lose an afternoon.

Pitfall 1: Forgetting to add a provider

You created FlightsService, you injected it into FlightsController, but you forgot to list it in FlightsModule.providers. (Usually because you wrote the file by hand instead of using the CLI.)

Error you'll see at startup:

Nest can't resolve dependencies of the FlightsController (?).
Please make sure that the argument FlightsService at index [0]
is available in the FlightsModule context.

Fix: add FlightsService to providers: [...] in flights.module.ts.

Pitfall 2: Forgetting to export a shared provider

Module A's service injects Module B's service. You imported Module B in Module A. But you forgot to exports the service from Module B.

Error: the same “Nest can't resolve dependencies” message, but this time the missing thing is in another module's namespace. The fix is on the providing side, not the consuming side.

Fix: add the service to exports: [...] in the module that owns it.

🔍
Dev: “I imported the module! Why doesn't it work?”
Nest: “Module B never said you could have it.”
Dev: “But I imported it!”
Nest: “Importing is the request. Exporting is the permission.”
Borrowing a library book requires both you walking in and the library being open.

Pitfall 3: Circular dependency (preview)

Module A imports Module B. Module B imports Module A. Now Nest can't decide which to instantiate first. Cue startup explosion.

Error: Nest cannot create the module instance. Often, this is
because of a circular dependency between modules.

NestJS provides forwardRef() as a band-aid:

@Module({
  imports: [forwardRef(() => UsersModule)],
})
export class AuthModule {}

It works. But the better fix is almost always to extract the shared piece into a third module that both depend on. We'll cover this properly in Lesson 5 when authentication forces the issue.

Heuristic: if you reach for forwardRef(), stop. Ask: “is there a third concept hiding here that should be its own module?” The answer is yes about 80% of the time.

Pitfall 4 (bonus): Using new() instead of injection

// ❌ DON'T
@Controller('flights')
export class FlightsController {
  private service = new FlightsService(); // 🚨

  @Get()
  findAll() { return this.service.findAll(); }
}

This compiles. It even appears to work. But you've completely bypassed the DI container: this FlightsService is a separate instance from the one Nest knows about. If anything else holds state in the service (and eventually something will), you've quietly created a split brain.

🤔
Dev: “The cache works on read but doesn't update on write — weird?”
Three hours later: it turns out the “read” instance was the DI singleton, the “write” instance was a new ThingService() someone snuck in.
Singletons are only singletons if you let the framework manage them.

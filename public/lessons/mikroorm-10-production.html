Part 1: The Synthesis — How the Patterns Compose

Pop quiz before we trace one full request. No scrolling.

🤔 Pretest (no notes)
Without re-reading L3: name the four entity states (the lifecycle states an entity moves through inside the EntityManager) and one trigger that moves an entity into each.
If you can name 4/4 with triggers, your retention is solid — head straight into Part 1's story. 2-3/4: jot what you have, finish Part 1, then re-skim L3 tonight. 0-1/4: read L3 first, this lesson is much heavier without it.

Now the synthesis. We're going to walk a single realistic HTTP request all the way through the stack you've built. Every paragraph below is something you've already learned. The new thing is seeing them in order, on one page.

One full lifecycle, one paragraph per layer

The morning shift opens at the Records Library — sorry, at archive-api. A patron walks up to the desk and hands over a request slip: PATCH /articles/42 with a body marking the article as published.

The desk clerk (Nest's HTTP layer) doesn't know anything about the master register. They hand the slip to the floor supervisor. The supervisor's first move is mechanical: pull a fresh ledger off the shelf, label it with this patron's name, and tuck it into a clipboard that follows the patron everywhere they go inside the building. This is the request-scoped em.fork() from L9 — a private working ledger and a private master-catalog page, scoped to one request via Node's AsyncLocalStorage.

The supervisor passes the slip to a subject specialist (the ArticleService) who knows what “publish an article” means. The specialist asks the catalog for article 42, but with a note: “and bring the author and the tags too”. That's populate: ['author', 'tags'] from L4 and L5 — one query plan, not three round trips. The catalog hands back exactly one card per record; if the same patron asked again two minutes later, they'd get the same physical card back, no second trip to the stacks. That's the Identity Map from L1.

The specialist edits the card — sets publishedAt = new Date(), calls article.publish(). That method is just JavaScript; it changes object fields. No SQL has been written yet. Inside the entity sits a @BeforeUpdate hook from L8 that will run later, at flush time, to bump updatedAt and validate the publish state machine. The specialist also calls this.outbox.queue(article, 'article.published') — that creates a new OutboxEvent entity and registers it with the same EntityManager. This is the outbox pattern from L9: the event row will land in the same transaction as the article update, so either both happen or neither does.

The specialist returns. The interceptor wrapping their method is annotated @Transactional(). That decorator from L9 is what triggers em.flush() when the method resolves — and rolls back if it throws. Now the working ledger comes alive. This is the Unit of Work from L1: it walks the managed entities, diffs each against its snapshot, runs the @BeforeUpdate hook, topologically sorts the change-set, opens a transaction, fires one batched UPDATE for article and one INSERT for outbox_event, and commits. The patron gets 200 OK.

The patron walks out. The supervisor tears the working ledger off the clipboard, drops it in the recycling bin. The map page goes with it. Nothing about article 42 leaks to the next patron, even though they may pick up article 42 in their own request a millisecond later.

Every line of that story is something you've already seen. What's new is only the framing: nine lessons, one request, in order. Read it twice. The second pass is the one that locks the synthesis in.

That's the model. The next four parts add a thin operational skin around it: how do we make this run cleanly under real production load, where dev-mode logging would melt our log bill, where boot time matters, where one Postgres primary can't hold all the read traffic, and where multiple Fohlio tenants need data isolation. Nothing you didn't already learn — just the production-grade dial settings.

Part 2: Production Logging

In Lesson 1 you set debug: true. Every SQL statement printed to the console — insert, select, begin, commit, the works. That was deliberate: when you're learning, watching the queries fire is the fastest feedback loop in the world.

In production, debug: true is a footgun. A typical Nest request fires somewhere between 1 and 10 queries. Multiply by your real RPS, multiply by 30 days of log retention, and you've shipped a five-figure Datadog bill in a service that does very little. We need three things instead: structured logs (JSON, machine-readable), only the queries that matter (slow ones), and no leaked secrets.

Structured logger via loggerFactory

The logger option lets you swap the default text logger for any function. The loggerFactory option goes further — it lets you ship a class that controls every namespace. We'll wire MikroORM's logger output through pino (or NestJS's Logger — same idea). Here's the production config:

// src/mikro-orm.config.prod.ts
import { defineConfig } from '@mikro-orm/postgresql';
import { DefaultLogger, LoggerNamespace, LogContext } from '@mikro-orm/core';
import pino from 'pino';

const log = pino({ level: process.env.LOG_LEVEL ?? 'info' });

class PinoOrmLogger extends DefaultLogger {
  log(namespace: LoggerNamespace, message: string, context?: LogContext) {
    log.info({ namespace, took: context?.took, label: context?.label }, message);
  }
  warn(namespace: LoggerNamespace, message: string, context?: LogContext) {
    log.warn({ namespace, took: context?.took, label: context?.label }, message);
  }
  error(namespace: LoggerNamespace, message: string, context?: LogContext) {
    log.error({ namespace, took: context?.took, label: context?.label }, message);
  }
}

export default defineConfig({
  // ... entities, dbName, etc. shared with dev config
  debug: false,                // no per-query log spam
  slowQueryThreshold: 200,     // only log queries >= 200ms
  loggerFactory: (opts) => new PinoOrmLogger(opts),
});

Two switches earn their keep here. debug: false turns off the firehose. slowQueryThreshold: 200 turns on the slow-query namespace. From the docs: “Slow query logs are always emitted when the threshold is met, regardless of the debug setting.” So even with debug off, anything over 200ms still hits your logger as a warning. That's the signal-to-noise ratio you want in production: nothing on the happy path, a clear yellow flag when something is slow enough to matter.

Per-query labels for traceability

When a slow query fires, the line in your dashboard reads select "a0".* from "article" ... — useful, but you'll spend ten minutes finding which endpoint emitted it. Save yourself the grep:

const article = await em.findOne(Article, id, {
  populate: ['author', 'tags'],
  logging: { label: 'PATCH /articles/:id - load aggregate' },
});

The label travels with the query into the slow-query log. In Datadog you can pivot on it. Use it sparingly — on the half-dozen hot paths and the queries you've already tuned once.

Sensitive parameters

The query-params namespace is incredibly useful in dev (it inlines bind parameters into the SQL) and is a compliance disaster in prod. Bound parameters can include API tokens, password hashes if you're updating auth, PII, anything. Two rules:

🚫
Never enable in prod
Don't list 'query-params' in debug: [...] in any production config. Period.
🔍
Filter at the logger
In your PinoOrmLogger, redact patterns like password = ?, api_key = ?, anything that smells like a token. pino has a built-in redact option for exactly this.
📅
Retention policy
Slow-query logs: 14–30 days. Trace logs (if you turn them on temporarily for a Sentry investigation): 24 hours and a calendar reminder to flip them back off.

The dev/prod config split. Don't rely on environment variables to flip debug at runtime — ship a literal mikro-orm.config.prod.ts that's referenced from your build. If a junior accidentally runs the dev config in production, you want it to fail loudly (mismatched DB host, no SSL), not silently fire 50,000 logs/min.

Part 3: Metadata Cache — Pre-Printed Catalog Cards

Every time MikroORM boots, it does a discovery pass: it reads your entity definitions, sniffs TypeScript types via ts-morph, walks every relation, computes column types, generates hydration functions, and assembles a metadata graph. On a laptop, with a small project, this is a few hundred milliseconds you never notice.

On a serverless cold start with thirty entities, this is a sad number. We're talking 1–3 seconds before your app handles its first request. In a Vercel or Lambda environment where instances start and die constantly, this directly hits p99 latency.

The library analogy: every morning, before opening, the librarians re-derive the entire catalog from scratch — reading every spine, transcribing every title, computing every cross-reference. Pointless. The catalog cards never change between deploys. Pre-print them once at build time, ship the printed deck, point the runtime at it.

Generate at build, load at boot

In your CI pipeline, after the TypeScript compile step, run:

npx mikro-orm cache:generate --combined

This produces ./temp/metadata.json — a single file containing every entity's discovered metadata, ready to load. Bundle it with your build artifact (Docker image, Vercel deployment, whatever). Then, in your production config, point at it:

// src/mikro-orm.config.prod.ts
import { GeneratedCacheAdapter, defineConfig } from '@mikro-orm/core';
import metadata from '../temp/metadata.json';

export default defineConfig({
  // ... rest of config
  metadataCache: {
    enabled: true,
    adapter: GeneratedCacheAdapter,
    options: { data: metadata },
  },
});

That's it. At boot, MikroORM sees the pre-baked metadata, skips the entire ts-morph phase, and is ready to take requests in tens of milliseconds. As a bonus, you can move @mikro-orm/reflection to devDependencies — production no longer needs the TypeScript reader at all.

Two checks before you cache: (1) Regenerate metadata.json on every CI build, never commit it — it's a build artifact, not source. (2) If your entity definitions and the cached metadata drift, you'll get loud, mysterious errors at boot. CI should fail the build if cache:generate exits non-zero.

Part 4: Read Replicas — Reading Rooms Off the Master Catalog

Your primary Postgres is doing two jobs at once: serving writes (must be authoritative, must be consistent) and serving reads (can be a few hundred ms behind, can be load-balanced). At any non-trivial scale, that's a problem — the writes are the precious workload, but the reads are 95% of the volume drowning them out.

Postgres solves this with replication. You spin up one or more replicas that stream WAL from the primary and serve read-only queries. The library equivalent: open a few reading rooms — quiet annexes off the main building, each holding a synchronized copy of the master catalog. Patrons who only need to read a record go to a reading room. Patrons who need to change a record still go to the main desk.

Configure replicas in MikroORM

// src/mikro-orm.config.prod.ts
export default defineConfig({
  // primary (writes)
  host: 'archive-primary.internal',
  user: 'archive_master',
  password: process.env.DB_PASSWORD,
  dbName: 'archive',

  // read replicas - only the fields that differ from primary
  preferReadReplicas: true,
  replicas: [
    { name: 'read-1', host: 'archive-replica-1.internal' },
    { name: 'read-2', host: 'archive-replica-2.internal' },
  ],
  // ... entities, logger, metadataCache
});

That's the entire feature. With preferReadReplicas: true (the default), MikroORM routes every SELECT and COUNT outside a transaction to a randomly chosen replica. Writes (INSERT/UPDATE/DELETE) go to primary. Anything inside em.transactional(...) goes to primary too — including reads — because mixing reads and writes across primary and a lagging replica inside one transaction is a correctness nightmare.

The read-after-write trap

Here's the subtle one. Replicas lag. Even on the same Postgres cluster, the replica might be 50–500ms behind. If your handler does:

await em.persistAndFlush(article);    // goes to primary
const reloaded = await em.findOne(Article, id);  // might go to replica

...you risk reading a stale version of the row you literally just wrote. The fix is exactly what the docs spell out: “all queries inside a transaction will use write connection.” Wrap the whole handler in a @Transactional() from L9 (or em.transactional), and the read after the flush will route to primary because it's still in the same transactional scope. This is one of those cases where the framework does the right thing once you put your code in the right shape — you don't need to think about routing per query.

For the rare case where you do need to override per-query, use connectionType:

const reportRow = await em.findOne(
  Article,
  id,
  { connectionType: 'write' },  // force primary even outside a tx
);

When read replicas earn their keep: read-heavy services (dashboards, search, list endpoints), reporting workloads, analytics queries, materialized-view feeders. They are not a free win for write-heavy services or for workloads with strict read-after-write requirements (auth, payments) — in those cases the replica lag will bite you and the operational complexity is not worth it.

Part 5: Multiple Schemas — Floors in the Building

In Lesson 6 you saw filters. A multi-tenant app there used a tenant filter: every query for every entity got an automatic WHERE tenant_id = ? appended. Same database, same tables, separation enforced in software.

Postgres offers a different model: one schema per tenant. Same database, same connection, but each tenant's tables live in their own namespace — tenant_acme.article, tenant_globex.article. The library analogy: same building, but each tenant gets their own floor, with its own copy of every shelf, isolated from the others. Same architecture, no risk of accidentally walking off with someone else's books.

Configure schema-per-tenant

You declare entities with schema: '*' — a wildcard meaning “this entity can live in any schema, decided at runtime”:

export const Article = defineEntity({
  name: 'Article',
  schema: '*',
  properties: { /* ... */ },
});

Then, per request, fork the EM with the tenant's schema:

// usually inside a NestJS guard or middleware
const tenantSchema = `tenant_${tenantId}`;
const tenantEm = em.fork({ schema: tenantSchema });

From here on, every find, persist, flush on tenantEm targets that schema's tables. Including the QueryBuilder. Including transactions. The framework handles it.

Schema-per-tenant vs filter-per-tenant: when to pick which

  Filter (L6) Schema (today)
Tenant count Thousands+, or unbounded Tens to low hundreds
Isolation guarantee Software (one missed filter = data leak) Database namespace (Postgres enforces it)
Per-tenant migrations Free — one migration covers all Loop over schemas in CI, or use the --schema CLI flag
Per-tenant backup/restore Hard (row-level export) Easy (pg_dump --schema=tenant_acme)
Cross-tenant query Trivial — just drop the filter Awkward — needs UNION ALL across schemas
Connection pooling One pool One pool (same DB — this is the win over schema-per-database)

Default to filter for SaaS with many small tenants (the typical Fohlio case). Reach for schema when you have a small number of large tenants who pay for hard isolation, or when ops needs to back up one tenant without affecting the others. Don't pick schema-per-tenant for hundreds of tenants — the migration story stops being fun fast.

Part 6: The Capstone — One PR, Four Concepts

This is the centerpiece. You're going to make one pull request against your mikroorm-course-yourname repo that demonstrates, in working code, at least four of the eight items below. Aim for higher — six is impressive, eight is a flex — but four is the bar to pass.

The eight criteria

Concept From What “done” looks like in the PR
(a) Non-trivial relation with populate L4 + L5 An Article with author: M:1 and tags: M:M, loaded in one endpoint via populate: ['author', 'tags']. Show the SQL is one or two queries, not N+1.
(b) Custom Repository method using QueryBuilder L6 A findPublishedByAuthor(authorId) on ArticleRepository that uses em.createQueryBuilder with a join and a non-trivial WHERE. Hooked up via repository: () => ArticleRepository.
(c) Soft-delete filter L6 A global filter named softDelete with cond: { deletedAt: null }, default-enabled. Plus an admin endpoint that disables it via em.find(..., { filters: { softDelete: false } }).
(d) Migration with a backfill L7 A migration that adds a slug column and backfills it from title for existing rows. Uses this.getKnex() or this.execute, runs in the same transaction.
(e) Embeddable or JSON property L8 An Address embeddable on a Publisher entity (street, city, country) or a JSON metadata property on Article typed via p.json<ArticleMetadata>().
(f) @Transactional service method L9 A publishArticle() service method decorated with @Transactional() that loads the article, mutates it, queues an outbox event, and lets the decorator flush.
(g) @CreateRequestContext background job L9 A @Cron or BullMQ worker decorated with @CreateRequestContext() that processes outbox rows. Demonstrates that EM works outside an HTTP request.
(h) Read replica config + metadata cache L10 A separate mikro-orm.config.prod.ts with replicas: [...] and GeneratedCacheAdapter. CI step that runs cache:generate.

Summary — The Five Things to Take Forward

If you remember nothing else from this course, remember these five.

📚
DataMapper philosophy
Entities are plain objects. Persistence lives in the EntityManager. Your domain stays clean.
🗂️
Identity Map per request
One JS object per row, scoped to one fork, garbage-collected at response. Never leak it across requests.
📝
Unit of Work, one flush
Mutate objects freely. Call flush once per business operation. Get one ordered, batched, atomic transaction.
📦
populate over N+1
If you're loading a list and touching a relation in a loop, you're paying for it. Move the relation into populate.
🛡️
Production hygiene
Structured logs only. Slow-query threshold, not debug: true. Pre-built metadata cache. Migrations as PR-reviewable changes. Never allowGlobalContext.

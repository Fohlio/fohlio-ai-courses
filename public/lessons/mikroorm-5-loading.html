Part 1: The N+1 Problem, Briefly

The most common ORM bug, in the most innocent-looking code:

const authors = await em.find(Author, {});  // 1 query
for (const author of authors) {
  console.log(author.name, author.books.loadCount());
  // each iteration → 1 SQL query (SELECT COUNT(*) FROM book WHERE author_id = ?)
}

100 authors? 101 queries. One for the parents, then one for each child collection. The route runs in 800ms instead of 8ms, and you can't tell from the code that anything's wrong — it looks like a normal for-loop.

The pattern has a name: N+1. One query for N parents, then N additional queries for the N children. It's not specific to MikroORM — every ORM has this trap. The difference is whether you can see it (turn on query logging) and whether the framework gives you a clean fix.

You're at the Records Library. You ask the head librarian for a list of all 100 authors in their collection. They walk to the catalog, pull the list in one trip, hand it over. Good.

Then you ask: “and how many books did each one publish?” The librarian shrugs and walks back into the stacks. Returns with the count for author #1. You ask about author #2. They walk back. You ask about author #3. They walk back. By the time you get to author #100, the librarian has made 100 round trips and is no longer speaking to you.

The fix — and this is the entire point of Lesson 5 — is to ask once: “bring me all 100 authors and the book count for each.” One trip, one cart, all the data on one journey. The ORM has to know in advance what you want; that's what populate tells it.

The mapping: Cart on Wheels = Loading Strategy. Loading 100 books one trip at a time is the SQL equivalent of refusing the cart and carrying volumes one by one.

Part 2: populate — The Explicit Fix

Tell MikroORM, at query time, which relations you intend to use. It will prefetch them in a controlled number of queries instead of one-per-iteration:

const authors = await em.find(Author, {}, {
  populate: ['books'],
});

for (const author of authors) {
  console.log(author.name, author.books.length);
  // books are already initialized — no extra queries
}

With the default BALANCED strategy on an SQL driver, that's two queries total: one for the authors, one SELECT ... FROM book WHERE author_id IN (...) covering all of them at once. Not 101.

Nested paths

Relations are dot-paths. Need books, plus each book's tags, plus each book's author's profile? Easy:

const authors = await em.find(Author, {}, {
  populate: ['books', 'books.tags', 'profile'],
});

TypeScript will autocomplete the available paths. The return type is enhanced to Loaded<Author, 'books' | 'books.tags' | 'profile'>, which means the typed-relation accessor (author.books.$) only compiles when the relation was actually populated — you can't accidentally read uninitialized data.

The '*' wildcard

Populate everything one level deep:

const authors = await em.find(Author, {}, {
  populate: ['*'], // every relation, top-level only
});

Convenient for a small entity. Dangerous for a fat one with seven relations — you might be loading data nobody on the route will ever read. Use it for serializing a single entity at the boundary of an admin tool, not for hot routes.

'*' always uses select-in. The wildcard forces the SELECT_IN strategy because joining every relation in one query risks unbounded cartesian products. If you want a wildcard with joined-strategy semantics, list the paths explicitly.

populateWhere — filter what gets populated

By default, populating loads the full related collection, not just the rows that matched your outer where:

// load books with tag 'classic', and populate ALL their tags (not just classic)
const books = await em.find(Book, { tags: { name: 'classic' } }, {
  populate: ['tags'],
});
// books[0].tags includes ALL tags on the book — 'classic', 'russian', 'long-read'

If you wanted only the matched tags, use populateWhere: 'infer' (or PopulateHint.INFER):

const books = await em.find(Book, { tags: { name: 'classic' } }, {
  populate: ['tags'],
  populateWhere: 'infer', // books[0].tags now contains ONLY 'classic'
});

Both behaviors are useful in different situations. Knowing the default is “all” saves you from a class of confusing bugs when you assume populated collections respect your outer filter.

Part 3: The Three Loading Strategies

Once you've said “populate this,” MikroORM has to actually fetch the data. There are three different SQL shapes it can use, and they have radically different performance characteristics.

🤔 Predict before reading on
You're loading 100 Authors with their Books (avg 5 books each) and a 1:1 Profile. Which combination of loading strategies will be the fastest? (a) all in one big JOIN, (b) one query for authors, one big JOIN for books and tags, (c) three separate SELECT ... WHERE id IN (...) queries, (d) joined for the 1:1, select-in for the 1:M.
Spoiler: (d). And it's the default. Read on for why.
📥
SELECT_IN
Two trips, no cartesian
One query for parents. One SELECT ... WHERE parent_id IN (?, ?, ?) for all children. Avoids row-multiplication. Best for to-many relations with high fan-out.
🔗
JOINED
One trip, one big SQL
Single SQL with LEFT JOINs. Best for to-one relations (M:1, 1:1) where there's no fan-out. Hydrator deduplicates the result.
⚖️
BALANCED
Sane default
Joined for to-one relations, select-in for to-many relations. Combines both wins. The default in MikroORM 7 onward.
📝
When you'd override
Per-query / per-relation
Set strategy in FindOptions, or use populateHints to override per relation path. Property-level wins over query-level wins over global config.

What the SQL actually looks like

Concrete query: 100 Authors, each with their Books. With SELECT_IN:

-- query 1: load all authors
SELECT * FROM author;

-- query 2: load all their books in one shot
SELECT * FROM book WHERE author_id IN (1, 2, 3, ..., 100);

Two queries, ~600 rows total (100 + ~500). Hydrator groups them by author_id and assigns to each Author.books collection.

With JOINED:

-- query 1: one big SQL with a LEFT JOIN
SELECT a.id AS a__id, a.name AS a__name,
       b.id AS b__id, b.title AS b__title, b.author_id AS b__author_id
FROM author a
LEFT JOIN book b ON b.author_id = a.id;

One query. Result set: ~500 rows (one per book), but each row carries a duplicated copy of the author columns. The hydrator de-duplicates by a__id. For 1:M with 5 children each, this is fine. For 1:M with 1000 children each, you've shipped a lot of duplicated parent data over the wire.

With JOINED on M:M (the trap): each book has 5 tags, each book has 3 reviews, each book has 4 chapters. Joining all three together produces 5 × 3 × 4 = 60 rows per book, 6000 rows for 100 books, of which 5900 are redundant. This is the cartesian explosion. The query is fast to write and slow to run.

The strategies side-by-side

Same query, three strategies. BALANCED is the default for a reason — it picks the right tool per relation shape.

How to set the strategy

Three places, in priority order (top wins):

// 1. per-relation, in defineEntity (highest priority)
books: () => p.oneToMany(Book).mappedBy('author').strategy('select-in'),

// 2. per-query, in FindOptions
await em.find(Author, {}, {
  populate: ['books'],
  strategy: 'joined',
});

// 3. globally, in mikro-orm.config.ts (lowest priority)
defineConfig({
  loadStrategy: 'select-in',
  // ...
});

For one specific path, use populateHints:

await em.find(Author, {}, {
  populate: ['books.tags', 'profile'],
  strategy: 'joined',
  populateHints: {
    'books.tags': { strategy: 'select-in' }, // override just this path
  },
});

Strategy is about the shape of data on the wire, not the count of round trips.

Part 4: Partial Loading with fields

Sometimes you don't need every column. A list endpoint that shows author name and book title doesn't need the 4kb biography blob or the book's full-text contents. Drop them with fields:

const authors = await em.find(Author, {}, {
  fields: ['id', 'name', 'books.id', 'books.title'],
  populate: ['books'],
});

Mirror operation: exclude: ['biography'] drops one column without listing the rest.

The FK gotcha

Here is the trap. To populate author.books, MikroORM needs the FK column on the Book side — namely book.author_id. If your fields array doesn't include it, the relation can't link, and the populated collection will be silently empty or wrong:

// WRONG — book.author_id is excluded, populated relation breaks
const books = await em.find(Book, {}, {
  fields: ['id', 'title', 'author.name'], // no 'author' or 'author.id'!
  populate: ['author'],
});
// books[0].author may be undefined — the FK was filtered out

// RIGHT — include the FK column or the relation field path
const books = await em.find(Book, {}, {
  fields: ['id', 'title', 'author', 'author.name'],
  populate: ['author'],
});

Including the relation property name in fields (e.g. 'author') tells MikroORM “keep the FK column.” Then 'author.name' picks which child columns to actually load. Both are needed.

em.populate — ad-hoc population

If you've already loaded entities and need to populate later (e.g. inside a service that didn't know upfront what would be needed):

const books = await em.find(Book, {});

// later, conditionally:
if (req.user.role === 'admin') {
  await em.populate(books, ['author', 'tags']);
}

Same loading strategies apply, same nested-paths syntax. Slightly more flexible at the cost of one extra logical step in your code.

Type-safe relations — a brief mention

When you populate, the return type is enriched. em.find(Author, {}, { populate: ['books'] }) returns Loaded<Author, 'books'>[]. The $ accessor on a populated collection becomes typed:

function listTitles(author: Loaded<Author, 'books'>): string[] {
  return author.books.$.map(b => b.title);  // $ proves it's loaded
}

If you forget to populate, author.books.$ is a TypeScript compile error. We'll lean on this in the project work in later lessons; for now, just know it exists.

Part 5: Dataloaders — Fine-Grained Batching

populate works when you know upfront what you'll need. But sometimes you don't — especially in GraphQL resolvers or per-item pipelines where each iteration may or may not touch a relation.

// resolver-style: each book may load its author independently
for (const book of books) {
  if (shouldShowAuthor(book, ctx)) {
    await book.author.load();   // each call → one SELECT
  }
}

That's another N+1, but you can't simply populate: ['author'] earlier — you'd be loading authors for books that don't need them. The fix is a dataloader: a tiny scheduler that batches all load() calls within a single tick of the event loop into one SELECT ... WHERE id IN (...).

// enable per-call
await book.author.load({ dataloader: true });

// or globally in config
defineConfig({
  dataloader: DataloaderType.ALL, // REFERENCE | COLLECTION | ALL | true | false
});

// or on em.populate
await em.populate(items, ['author'], { dataloader: true });

How the magic works: each load({ dataloader: true }) call doesn't fire a query immediately. It registers a request and returns a Promise. At the end of the current microtask tick, the dataloader collects every registered ID, fires one batched query, and resolves all the Promises.

Trade-off: dataloaders add one extra microtask of latency per batch (negligible) in exchange for collapsing N queries into 1 (huge). They shine in GraphQL where the query shape isn't known statically. Outside GraphQL, prefer populate — it's clearer and uses the same machinery without the indirection.

Part 6: Tuning archive-api

Time to feel this in code. We'll reproduce N+1 on the archive-api repo from Lesson 4, then fix it four different ways and capture the query log each time.

Setup: seed some data

Make sure your main.ts from Lesson 4 has run, so you have at least 10 articles each with a few tags. If you only have 1 article, loop the create calls 10 times with different titles before continuing. Then add a script:

// src/scripts/loading-experiments.ts
import { MikroORM, LoadStrategy } from '@mikro-orm/postgresql';
import config from '../mikro-orm.config';
import { Article } from '../entities/Article';

async function run() {
  const orm = await MikroORM.init(config);
  const em = orm.em.fork();

  // ---------------------- experiment 1: N+1 ----------------------
  console.log('\n=== N+1 ===');
  const articles1 = await em.find(Article, {});
  for (const a of articles1) {
    const n = await a.tags.loadCount(); // fires one COUNT per article
    console.log(a.title, n);
  }

  em.clear(); // reset the identity map between experiments

  // ---------------------- experiment 2: populate ----------------------
  console.log('\n=== populate (BALANCED default) ===');
  const articles2 = await em.find(Article, {}, { populate: ['tags'] });
  for (const a of articles2) {
    console.log(a.title, a.tags.length);
  }

  em.clear();

  // ---------------------- experiment 3: JOINED ----------------------
  console.log('\n=== JOINED ===');
  const articles3 = await em.find(Article, {}, {
    populate: ['tags'],
    strategy: 'joined',
  });
  console.log('count:', articles3.length);

  em.clear();

  // ---------------------- experiment 4: SELECT_IN ----------------------
  console.log('\n=== SELECT_IN ===');
  const articles4 = await em.find(Article, {}, {
    populate: ['tags'],
    strategy: 'select-in',
  });
  console.log('count:', articles4.length);

  await orm.close();
}

run().catch(console.error);

Read the four logs

Run with npx tsx src/scripts/loading-experiments.ts. You should see:

❌
Experiment 1: N+1
1 SELECT for the articles, then N additional SELECT COUNTs — one per iteration. For 10 articles, 11 queries total.
⚖️
Experiment 2: populate (BALANCED)
2 queries: one for articles, one SELECT FROM article_tags ... WHERE article_id IN (...) joined to tag. Default behavior.
🔗
Experiment 3: JOINED
1 query with a LEFT JOIN through the pivot table. Watch the row count balloon if you have many tags per article — M:M is exactly where JOINED hurts most.
📥
Experiment 4: SELECT_IN
2 or 3 queries (article, pivot rows, tag rows) with no row duplication. Often the best choice for M:M with high fan-out.

Pull a sample of each log into your homework write-up. The point of the exercise is calibration: you want the visceral feel of “this many queries for this many entities, with this strategy, equals this latency.”

Summary

🔁
N+1 = 1 + N round trips
Iterating a list and touching an unpopulated relation per item. The default mode of any ORM if you don't tell it otherwise.
🔍
populate
Tell MikroORM upfront what you'll need. Nested paths, the '*' wildcard, and populateWhere for filtering populated rows.
⚖️
Three strategies
SELECT_IN (separate queries, no cartesian), JOINED (one query, cartesian risk on to-many), BALANCED (joined to-one + select-in to-many; default).
✂️
Partial loading
fields drops columns. Always include the FK or the relation property name when you populate — otherwise the join silently breaks.

Dataloaders
Microtask-batched load() calls. Use when populate doesn't fit (GraphQL resolvers, conditional per-item loads).

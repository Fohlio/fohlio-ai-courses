Part 1: Move Slow Work Off the Request Path

Picture the controller you wrote in Lesson 6. POST /flights creates a flight. Easy. Now product comes back with three more requirements:

📧
Send email
Confirm to the passenger that the flight is booked. SMTP call: ~800ms.
📊
Recompute analytics
Refresh the dashboard rollup for the day. ~300ms of DB aggregation.
🔗
Sync to partner system
POST to a partner airline's API. Sometimes 200ms, sometimes 6 seconds, sometimes 502.

If you cram all of that into the controller, your POST /flights just went from 80ms to ~7 seconds in the worst case — and one timeout in any of those calls breaks the entire flight creation. That's not a backend, that's a hostage situation.

The gate agent at JFK doesn't load your suitcase onto the plane themselves. They print a tag, slap it on the bag, drop it on the conveyor belt, and tell you: “You're good to go.”

The bag ride to the cargo hold takes minutes. The agent doesn't wait. They've already moved on to the next passenger. The conveyor belt — that's a queue. Bags get processed when a baggage handler is free. If a handler is sick, the belt buffers. If a bag falls off, the system retries. The passenger never knows.

Meanwhile, the airport's PA system announces: “Ground crew, gate B14, flight 738 closing.” Anyone listening on that channel reacts — the fueler, the catering crew, the pushback driver. The agent doesn't call each one. That broadcast — that's an event.

The mapping: Queue (BullMQ) = the conveyor belt. Events (EventEmitter2) = the airport PA system. Cron jobs = the nightly cleaning crew that runs whether anyone asked or not. Caching = the express check-in lane for frequent flyers. All four exist so the gate agent can hand off and keep moving.

The two big tools, in one sentence each

📦
BullMQ Queue
Durable, retryable, observable
Use when the work must happen, even if it takes a while or fails the first time. Email sending. Partner sync. Webhook delivery. Backed by Redis.
📢
EventEmitter2
Fast, in-process, fire-and-forget
Use when one module needs to tell others “something happened” without knowing who's listening. Cache invalidation. Audit log. Dashboard refresh.

Rule of thumb: if losing the work would cause user-visible damage (missed email, missed payment), use a queue. If it's a soft signal that other parts of the app react to, use an event. We'll come back to this exact decision in the homework.

🤔 Guess before reading
If you crash the Node process right after emitting an event with EventEmitter2, what happens to the event? Now: same scenario, but you added a job to a BullMQ queue. What happens to the job?
The answer is exactly why one tool fits one job and not the other. We'll confirm in Parts 3 and 4.
🔥
Junior: “The POST /flights endpoint takes 7 seconds.”
Senior: “What's it doing?”
Junior: “Creating the flight, sending an email, syncing to three partner APIs, recomputing the daily report, and warming the cache.”
Senior: “...how many of those does the user actually need to wait for?”
Junior: “...one.”
The other six are conveyor-belt work. Drop them off, walk away.

Part 2: Caching with cache-manager

Caching is the cheapest performance win you'll ever get. If a GET endpoint returns the same answer for the same input for the next 60 seconds, why hit the database every single time?

Frequent flyers at the airport get to use the express check-in counter. They scan a card, the system already knows them, they breeze through in 8 seconds instead of 4 minutes. That's caching. The slow path (full check-in: ID verification, baggage weighing, seat assignment) still exists for everyone else — but the system answers the easy questions instantly for the regulars.

The mapping: Cache hit = express lane. Cache miss = full check-in. TTL = how long the airline trusts that your details haven't changed before they re-verify.

Install

npm install @nestjs/cache-manager cache-manager

Wire the module

import { Module } from '@nestjs/common';
import { CacheModule } from '@nestjs/cache-manager';

@Module({
  imports: [
    CacheModule.register({
      ttl: 60_000,    // 60 seconds, in ms
      max: 100,       // max items in memory before LRU eviction
      isGlobal: true, // available everywhere without re-importing
    }),
  ],
})
export class AppModule {}

Out of the box, this is in-process memory. Restart the server, the cache is gone. That's fine for development. Production wants Redis — we'll get there in two pages.

Cache a GET endpoint declaratively

import { Controller, Get, UseInterceptors } from '@nestjs/common';
import { CacheInterceptor, CacheTTL } from '@nestjs/cache-manager';

@Controller('flights')
@UseInterceptors(CacheInterceptor)
export class FlightsController {
  constructor(private readonly flightsService: FlightsService) {}

  @Get()
  @CacheTTL(30_000) // override module default for this route
  findAll() {
    return this.flightsService.findAll();
  }
}

That's it. The first request hits the service. Every request to the same URL within 30 seconds returns the cached body without ever calling findAll. The cache key is derived from the request URL.

First request: miss, DB hit, populate cache. Next requests within TTL: hit, ~40× faster.

Manual cache control (when the interceptor isn't enough)

Sometimes you want to read or write the cache yourself — for example, invalidate it after a write.

import { Inject, Injectable } from '@nestjs/common';
import { CACHE_MANAGER } from '@nestjs/cache-manager';
import { Cache } from 'cache-manager';

@Injectable()
export class FlightsService {
  constructor(
    @Inject(CACHE_MANAGER) private readonly cache: Cache,
  ) {}

  async findAll() {
    const cached = await this.cache.get<Flight[]>('flights:all');
    if (cached) return cached;

    const fresh = await this.prisma.flight.findMany();
    await this.cache.set('flights:all', fresh, 60_000);
    return fresh;
  }

  async create(dto: CreateFlightDto) {
    const flight = await this.prisma.flight.create({ data: dto });
    await this.cache.del('flights:all'); // invalidate list cache
    return flight;
  }
}

HTTP module — calling external APIs the Nest way

Quick detour, because it shows up alongside caching all the time. @nestjs/axios wraps Axios so it plays nicely with DI, interceptors, and observability:

npm install @nestjs/axios axios
import { HttpModule, HttpService } from '@nestjs/axios';
import { firstValueFrom } from 'rxjs';

@Module({ imports: [HttpModule.register({ timeout: 5000 })] })
export class WeatherModule {}

@Injectable()
export class WeatherService {
  constructor(private readonly http: HttpService) {}

  async forecast(city: string) {
    const { data } = await firstValueFrom(
      this.http.get(`https://api.weather/${city}`),
    );
    return data;
  }
}

The combo you'll want: HttpService for the call, cache.set for the result with a sensible TTL, BullMQ if the call is part of a longer workflow that needs retries.

Switch to Redis for production

In-memory caching dies on every deploy and doesn't share across instances. Production wants Redis. The current ecosystem standard is Keyv:

npm install @keyv/redis cacheable
import { CacheModule } from '@nestjs/cache-manager';
import { createKeyv } from '@keyv/redis';

CacheModule.registerAsync({
  isGlobal: true,
  useFactory: async () => ({
    stores: [createKeyv('redis://localhost:6379')],
    ttl: 60_000,
  }),
});

Same API on your service side. The store changed; your code didn't. That's the whole point of cache-manager: pluggable backend.

Real example from Fohlio land: the materials catalog endpoint returns ~3,000 items per project. Without caching, every dashboard load hits Postgres for the full list. With a 5-minute Redis cache and @CacheTTL(300_000), that endpoint went from 240ms to 12ms p95 — and Postgres CPU dropped from 30% to 4% during peak hours.

Caching footgun: caching authenticated endpoints by URL alone is a data-leak factory. User A's request gets cached — user B with a different role gets A's data back. If you cache anything user-specific, include the user ID in the cache key (or use trackBy on the interceptor). When in doubt: don't cache it.

🧀
Manager: “The dashboard is slow.”
Dev: “Let me add caching.”
*adds 60s cache*
Manager: “The dashboard is fast! ...wait, why does it still show old data after I edited the project?”
Dev: “...let me add cache invalidation.”
The two hard problems in computer science: cache invalidation, naming things, and off-by-one errors.

Three cache key strategies you'll actually use

🔑
URL-based
Default for CacheInterceptor. Fine for fully public lists. Dangerous for auth.
👤
URL + user ID
Override CacheInterceptor.trackBy() to include the JWT subject. Per-user cache.
🏷️
Tagged keys
Manual: cache.set('flights:project:'+id, ...). On any flight write, del the matching tag pattern.

Part 3: Background Jobs with BullMQ

BullMQ is the de facto Node.js job queue. It runs on Redis. NestJS wraps it with @nestjs/bullmq so you get the same DI patterns you already know.

The flow in one diagram

The producer adds; the worker consumes. They never block each other.

Install & wire

npm install @nestjs/bullmq bullmq
// app.module.ts
import { BullModule } from '@nestjs/bullmq';

@Module({
  imports: [
    BullModule.forRoot({
      connection: { host: 'localhost', port: 6379 },
    }),
    BullModule.registerQueue({ name: 'emails' }),
  ],
})
export class AppModule {}

The producer (your existing service)

import { Injectable } from '@nestjs/common';
import { InjectQueue } from '@nestjs/bullmq';
import { Queue } from 'bullmq';

@Injectable()
export class FlightsService {
  constructor(
    private readonly prisma: PrismaService,
    @InjectQueue('emails') private readonly emailsQueue: Queue,
  ) {}

  async create(dto: CreateFlightDto) {
    const flight = await this.prisma.flight.create({ data: dto });

    await this.emailsQueue.add(
      'send-confirmation',        // job name (within the queue)
      { flightId: flight.id },     // job payload
      {
        attempts: 5,
        backoff: { type: 'exponential', delay: 1000 },
        removeOnComplete: true,
        removeOnFail: 100, // keep last 100 failures for debugging
      },
    );

    return flight; // HTTP response goes out NOW. Email happens later.
  }
}

The processor (a separate class, runs in the worker)

import { Processor, WorkerHost } from '@nestjs/bullmq';
import { Job } from 'bullmq';
import { Logger } from '@nestjs/common';

@Processor('emails')
export class EmailProcessor extends WorkerHost {
  private readonly logger = new Logger(EmailProcessor.name);

  async process(job: Job): Promise<void> {
    switch (job.name) {
      case 'send-confirmation':
        await this.sendConfirmation(job.data.flightId);
        return;
      default:
        throw new Error(`Unknown job: ${job.name}`);
    }
  }

  private async sendConfirmation(flightId: string) {
    this.logger.log(`Sending confirmation for flight ${flightId}`);
    // pretend SMTP call here
    await new Promise(r => setTimeout(r, 800));
  }
}

Register the processor in the same module as the queue:

@Module({
  imports: [BullModule.registerQueue({ name: 'emails' })],
  providers: [EmailProcessor, FlightsService],
})
export class FlightsModule {}

Delays, repeats, and priorities — one options object

Most BullMQ power lives in the third argument to queue.add:

// Run in 60 seconds
await queue.add('reminder', payload, { delay: 60_000 });

// Recurring — cron-style, lives in Redis (survives restarts)
await queue.add('daily-summary', {}, {
  repeat: { pattern: '0 9 * * *', tz: 'UTC' },
});

// Priority: lower number = higher priority
await queue.add('send-vip-email', payload, { priority: 1 });
await queue.add('send-bulk-email', payload, { priority: 10 });

// Idempotency — same job ID won't be added twice
await queue.add('sync-partner', payload, { jobId: `flight-${flight.id}` });

That last pattern — jobId for idempotency — saves you when a webhook fires twice or a user double-clicks a button. The second add is a no-op while the first is still alive in the queue.

What you get for free

🔁
Retries
5 attempts with exponential backoff (1s, 2s, 4s, 8s, 16s) — just from the options object.
💾
Durability
Jobs live in Redis. Crash the Node process; restart it; the job is still there waiting.
⏰
Delays & cron
delay: 60_000 for “run in 1 min”; repeat: { pattern: '0 9 * * *' } for daily at 9am.
👁️
Observability
Plug in Bull Board (a UI) to see queues, jobs, failures, and retry timers in real time.
💥
Email service: *503 Bad Gateway*
Express app: “Whelp, the user's signup just failed. Tell them to try again in an hour.”
BullMQ: “Cool, I'll try in 1 second. Then 2. Then 4. Then 8. Then 16. After 5 tries I'll log it and move on.”
One of these is a feature; the other is a customer support ticket.

Advanced — concurrency: by default, the processor handles one job at a time. Bump it: @Processor('emails', { concurrency: 10 }). Now ten jobs run in parallel within the same worker. Beware: rate limits on external APIs become your problem at this layer, not the queue's.

Observability — Bull Board in 6 lines

You will eventually have a question like “why is the email queue at 4,000 jobs?” The answer is a UI you mount inside your Nest app:

npm install @bull-board/api @bull-board/express @bull-board/nestjs
import { BullBoardModule } from '@bull-board/nestjs';
import { ExpressAdapter } from '@bull-board/express';
import { BullMQAdapter } from '@bull-board/api/bullMQAdapter';

@Module({
  imports: [
    BullBoardModule.forRoot({ route: '/queues', adapter: ExpressAdapter }),
    BullBoardModule.forFeature({ name: 'emails', adapter: BullMQAdapter }),
  ],
})
export class AppModule {}

Now http://localhost:3000/queues shows every queue, every job, every retry, every failure reason. Lock it behind an admin guard before shipping — it exposes job payloads.

Part 4: EventEmitter2 — The In-Process PA System

Sometimes you don't need durability. You just need module A to tell module B (and C and D) that something happened — without A having to know B, C, and D exist.

The radiology desk at the airport hospital doesn't call every paramedic personally when a patient comes in. They radio: “Code blue, gate 14.” Anyone on that frequency reacts. The desk doesn't know who's listening, doesn't wait for confirmation, doesn't care.

That's EventEmitter2. The producer emits. Listeners run. Producer keeps moving.

The mapping: EventEmitter2 = the airport-wide radio. emit('flight.created', ...) = key the mic and broadcast. @OnEvent('flight.created') = anyone tuned to that channel reacts. Same Node process — not durable, not cross-instance.

Install & wire

npm install @nestjs/event-emitter
// app.module.ts
import { EventEmitterModule } from '@nestjs/event-emitter';

@Module({
  imports: [EventEmitterModule.forRoot()],
})
export class AppModule {}

Emit

import { Injectable } from '@nestjs/common';
import { EventEmitter2 } from '@nestjs/event-emitter';

@Injectable()
export class FlightsService {
  constructor(private readonly events: EventEmitter2) {}

  async create(dto: CreateFlightDto) {
    const flight = await this.prisma.flight.create({ data: dto });
    this.events.emit('flight.created', flight);
    return flight;
  }
}

Listen

import { Injectable, Logger } from '@nestjs/common';
import { OnEvent } from '@nestjs/event-emitter';

@Injectable()
export class AnalyticsListener {
  private readonly logger = new Logger(AnalyticsListener.name);

  @OnEvent('flight.created')
  handleFlightCreated(flight: Flight) {
    this.logger.log(`Recompute analytics for ${flight.id}`);
    // expensive, but happens off the request path
  }
}

Three modules — analytics, audit, cache — can each have their own listener for flight.created. FlightsService doesn't import any of them. That's the decoupling.

A real Fohlio-shaped example

Imagine the user updates a project's name. Several modules care:

🗂️
CacheModule
Wants to cache.del('projects:list') so the next list request is fresh.
📝
AuditModule
Wants to record “User X renamed project Y at time Z.”
📊
SearchIndexModule
Wants to update the project's entry in the search index.

Without events, ProjectsService.update would import all three modules and call them in sequence. Tight coupling, hard tests. With events, it just does:

this.events.emit('project.updated', project);

Each of the three modules has its own @OnEvent('project.updated') listener. ProjectsService doesn't know they exist. Adding a fourth listener tomorrow is a one-file change.

Sync vs async listeners

By default, emit() calls listeners synchronously. If your listener is async and slow, the emit is slow too. Two ways out:

// Option A: emit and don't await
this.events.emit('flight.created', flight);
// listeners run on next tick; emit returns immediately

// Option B: explicitly async
@OnEvent('flight.created', { async: true })
async handle(flight: Flight) { /* ... */ }

Limit you must respect: EventEmitter2 lives in one Node process. Two app instances behind a load balancer? Each has its own EventEmitter. An emit on instance A is invisible to listeners on instance B. The moment you scale horizontally, you need a queue or a real pub/sub broker (Redis, NATS — that's Lesson 9).

Wildcards & namespaces — a small superpower

Turn on wildcards in the module config and your event names become a tiny query language:

EventEmitterModule.forRoot({
  wildcard: true,
  delimiter: '.',
  maxListeners: 20,
})
// One listener catches every flight.* event
@OnEvent('flight.*')
audit(payload: any) {
  this.audit.record(payload);
}

// emit: 'flight.created', 'flight.updated', 'flight.cancelled'
// all three flow into the audit listener

Useful for cross-cutting concerns — audit logs, analytics fan-out — without writing one listener per event name.

Queue vs Event — the decision table

Question BullMQ Queue EventEmitter2
Survives crash? Yes (Redis-backed) No (in-memory)
Crosses process boundaries? Yes No
Retries on failure? Yes, configurable No (you handle it)
Latency ~1–10ms (Redis hop) <1ms (function call)
Best for Email, sync, webhooks, anything that must happen Cache invalidation, audit logs, fan-out signals
✋ Self-test
For each of these, pick BullMQ or EventEmitter2 (no peeking):

1. Send password reset email after POST /forgot-password.
2. Invalidate the in-memory users:list cache after a user is updated.
3. Charge a credit card via Stripe after order placed.
4. Update an in-memory online-users counter when someone logs in.
1 & 3 = BullMQ (must succeed, may retry). 2 & 4 = EventEmitter2 (cheap signal, OK if a crash loses one). The pattern: would a lost event cause a refund or a complaint? → queue. Would it cause a stale dashboard for 30 seconds? → event.

Part 5: Scheduled Tasks — @nestjs/schedule

Some work isn't triggered by a request — it's triggered by the clock. Nightly cleanup. Hourly stats. Every 30 seconds, prune expired tokens. That's what @nestjs/schedule is for.

The airport's cleaning crew doesn't need anyone to call them. Every night at 2am, they sweep the terminals. Every Sunday they deep-clean. Every 15 minutes during the day, someone empties the trash near gate B14.

Nobody dispatches them. They're on a schedule. That's @Cron.

The mapping: @Cron('0 2 * * *') = nightly sweep. @Interval(900000) = every 15 min (in ms). @Timeout(5000) = run once, 5 seconds after boot.

Install & wire

npm install @nestjs/schedule
import { ScheduleModule } from '@nestjs/schedule';

@Module({
  imports: [ScheduleModule.forRoot()],
})
export class AppModule {}

The three decorators

import { Injectable, Logger } from '@nestjs/common';
import { Cron, Interval, Timeout } from '@nestjs/schedule';

@Injectable()
export class CleanupService {
  private readonly logger = new Logger(CleanupService.name);

  // Every night at midnight (server time)
  @Cron('0 0 * * *', { name: 'nightly-cleanup', timeZone: 'UTC' })
  async nightlyCleanup() {
    const cutoff = new Date(Date.now() - 30 * 86_400_000);
    const { count } = await this.prisma.flight.deleteMany({
      where: { status: 'cancelled', updatedAt: { lt: cutoff } },
    });
    this.logger.log(`Pruned ${count} stale cancelled flights`);
  }

  // Every 10 seconds
  @Interval(10_000)
  heartbeat() {
    this.logger.debug('tick');
  }

  // Once, 5 seconds after the app boots
  @Timeout(5_000)
  warmCache() {
    this.logger.log('Warming caches on startup');
  }
}

The Dynamic Schedule API — jobs you add at runtime

Decorators are great for fixed schedules. But sometimes you want to schedule a job per user — e.g., a one-time reminder 24 hours after signup. That's where SchedulerRegistry comes in:

import { Injectable } from '@nestjs/common';
import { SchedulerRegistry } from '@nestjs/schedule';
import { CronJob } from 'cron';

@Injectable()
export class ReminderService {
  constructor(private readonly scheduler: SchedulerRegistry) {}

  scheduleReminder(userId: string, when: Date) {
    const name = `reminder-${userId}`;
    const job = new CronJob(when, () => {
      console.log(`Reminder for ${userId}`);
      this.scheduler.deleteCronJob(name);
    });
    this.scheduler.addCronJob(name, job);
    job.start();
  }
}

But honestly: for one-shot delayed work that must survive a restart, BullMQ's delay option is nine times out of ten the right tool. The dynamic schedule API is fine for in-process timers; it's not durable. Server restart = jobs lost.

Cron syntax in 30 seconds

Pattern Meaning
* * * * *Every minute
0 * * * *Every hour, on the hour
0 0 * * *Every day at midnight
*/5 * * * *Every 5 minutes
0 9 * * MON-FRI9am on weekdays
CronExpression.EVERY_DAY_AT_MIDNIGHTSame as 0 0 * * * (typed enum, harder to typo)

Multi-instance gotcha: if you run the same Nest app on three pods, each pod runs the cron three times. For most cleanups that's fine (idempotent deleteMany). For things like “send the daily summary email” you do not want three copies. Two fixes: (a) put a row-lock advisory check at the top of the job, or (b) use a BullMQ repeatable job — only one worker grabs each occurrence.

🕑
Cron at midnight: *fires job*
Cron at 12:00:00.001: *fires job again, on the second pod*
Cron at 12:00:00.002: *fires job again, on the third pod*
Customer: “Why did I get three copies of the same daily report?”
Three pods, three crons, one inbox. Math doesn't lie.

Part 6: Logging — Pick One and Stick With It

NestJS ships with a built-in Logger. It's fine for development. For production you almost always want structured JSON logs — that's where Pino or Winston come in.

Built-in Logger

import { Injectable, Logger } from '@nestjs/common';

@Injectable()
export class FlightsService {
  private readonly logger = new Logger(FlightsService.name);

  create(dto: CreateFlightDto) {
    this.logger.log(`Creating flight to ${dto.destination}`);
    this.logger.warn('Capacity above 90%');
    this.logger.error('Booking failed', error.stack);
  }
}

Pretty colored output in dev, the class name as the context tag, five log levels (verbose, debug, log, warn, error). For 80% of apps this is enough.

When you outgrow it — Pino

Pino is the fastest Node logger. Structured JSON by default. Plays nicely with log aggregators (Datadog, Loki, CloudWatch).

npm install nestjs-pino pino-http
import { LoggerModule } from 'nestjs-pino';

@Module({
  imports: [
    LoggerModule.forRoot({
      pinoHttp: {
        level: process.env.LOG_LEVEL ?? 'info',
        transport: process.env.NODE_ENV === 'development'
          ? { target: 'pino-pretty' }
          : undefined,
      },
    }),
  ],
})
export class AppModule {}

Now every HTTP request gets a request-id, timing, status code, and any logs you make inside the handler are tagged with that request-id. Searching logs in production becomes “give me everything for req abc123” instead of “grep for the timestamp.”

🤔 Pick before reading
You're deploying a new NestJS service to production tomorrow. Which logger do you pick: built-in Logger, Pino, or Winston? Why?
My answer: Pino, almost always. Winston is fine but slower and config-heavier. The built-in Logger is great until you need to query logs in Datadog/Loki by request-id — which is approximately day 3 of production.

Advanced — correlate logs with queues: when you add a job to BullMQ, attach the current request-id to the job data. The processor pulls it back out and uses it as the log context. Now you can trace one user action across the HTTP layer and the worker layer in your log aggregator.

Replacing the default Nest logger globally

// main.ts
import { Logger } from 'nestjs-pino';

async function bootstrap() {
  const app = await NestFactory.create(AppModule, { bufferLogs: true });
  app.useLogger(app.get(Logger));
  await app.listen(3000);
}

Now everything — the framework's own bootstrap logs, your this.logger.log(...) calls, the request logs — all flow through Pino with structured JSON.

The five log levels — when to use which

Level Use for Example
errorSomething broke. A human should look.Payment failed, DB connection lost.

Discipline: production logs at info by default. Crank to debug via env var only when investigating. verbose in prod = your log bill in 30 days will be a discussion topic.

The full async airport — how the pieces fit

Look at the airport map you've built across this lesson. A passenger taps “Book” (HTTP request). The gate agent (controller) calls the service. The service writes the booking, then drops three handoffs:

  1. A bag tag on the conveyor belt — queue.add('send-confirmation', ...). The email will happen, even if the SMTP server is down right now.
  2. A PA announcement — events.emit('flight.created', ...). Cache invalidates, audit logs, search index all react.
  3. The passenger sees their boarding pass — the response goes back — in 80ms.

Meanwhile, the cleaning crew (cron) sweeps cancelled flights at midnight. The express check-in lane (cache) keeps the next 50 list-requests at 2ms. And every step is logged with a request-id so you can trace one user's journey through all of it.

That's the toolkit. Use it as a system, not as four isolated tools.

Summary

Five tools, one principle: only do in the request what the request actually needs.

🚀
Caching
@nestjs/cache-manager. CacheInterceptor + @CacheTTL. In-memory in dev, Redis in prod.
📦
Queues
@nestjs/bullmq. Producer adds, processor consumes. Retries, delays, durability for free.
📢
Events
@nestjs/event-emitter. emit + @OnEvent. Same-process pub/sub. Decouples modules.
⏰
Cron
@nestjs/schedule. @Cron, @Interval, @Timeout. Watch out for multi-instance double-fire.
📜
Logging
Built-in Logger for dev, Pino for prod, request-id everywhere.

Coming up in Lesson 9: we go cross-process. WebSocket gateways for live updates, Server-Sent Events for one-way streams, and full microservices over TCP / Redis / NATS / RabbitMQ / Kafka / gRPC. Same NestJS patterns — just a different transport under the hood.

Part 1: The Four Entity States

Every entity instance in your code is in exactly one of four states at any moment. The state determines what the EntityManager will do with it on the next flush(). If you internalise this picture, half the surprises in MikroORM go away.

All entity transitions. The two big ones to remember: em.create() takes you to New; em.flush() takes you to Managed.

The four states, concretely

🆕
New
Created with em.create(Article, {...}). Tracked. Will be inserted on flush.
✅
Managed
In the Identity Map, has a PK, has a snapshot. Mutations are diffed on flush.
✌️
Detached
No EM owns it. em.flush() ignores its mutations. Happens after em.clear() or when a forked EM is GC'd.
❌
Removed
Marked via em.remove(entity). Will be DELETEd on the next flush, then disappears from the map.

One subtle point that catches people: a new Article() with the new keyword and no em.create() or em.persist() isn't in any of these states. It's just a JS object that the ORM doesn't know about. To get it tracked, you call em.persist(entity), which moves it to the New state.

Part 2: Persist & Flush Mechanics

Three ways to put a new entity into the New state. They look interchangeable; they're not.

em.create() — the 95% case

const article = em.create(Article, {
  title: 'On Long Novels',
  slug: 'on-long-novels',
  body: '...',
});
// `article` is now in the New state. No SQL fired yet.
await em.flush();
// INSERT goes out, `article` becomes Managed, gets its PK.

Since v6, em.create() auto-persists. You don't need a separate em.persist() call. It also runs the onCreate hooks, fires the beforeCreate events, and registers the entity in the Identity Map. This is the path you should reach for by default.

new Entity() + em.persist() — when you need the constructor

const article = new Article();
article.title = 'On Long Novels';
article.slug = 'on-long-novels';
article.body = '...';

em.persist(article);
await em.flush();

Two extra lines for the same outcome. The reason this path exists: if you used the defineEntity + class style and your class has a real constructor with required arguments, em.create() calls don't run the constructor — they assign properties directly. So if you need constructor logic to fire (validation, derived fields), you're doing new Article(...) and then em.persist().

cascade-persist on relations — the freebie

Say you create an Article and assign a freshly-created Tag to it:

const tag = em.create(Tag, { name: 'classics' });
const article = em.create(Article, {
  title: 'On Long Novels',
  tags: [tag],
});
await em.flush();
// Both INSERTs go out, in the right order, in one transaction.

You don't have to em.persist(tag) separately. The relation tells the Unit of Work to cascade. Lesson 4 covers cascading rules in full; for now just know it works for the obvious case.

Why flush only writes the diff

You saw this in Lesson 1 in the abstract. Here's what it looks like in code:

const article = await em.findOne(Article, 1);

article.title = 'New title';
// `viewCount`, `body`, `slug`, etc — unchanged

await em.flush();
// SQL: update "article" set "title" = 'New title', "updated_at" = ... where "id" = 1
// Note: only `title` and `updated_at` (via onUpdate) appear in SET.

The Unit of Work compares your current article object against the snapshot it took when you loaded the row. Only changed columns end up in the UPDATE. This isn't an optimization — it's a correctness property. If two requests both touch the same row and only the columns they each modified, neither overwrites the other's columns. (Real concurrent safety still needs locking; we'll get there in Lesson 5.)

Part 3: Finding Entities — The FilterQuery DSL

🤔 Predict before reading on
You want articles where viewCount > 100 AND (author = 'Tolstoy' OR publishedYear > 2000). Without scrolling, take 30 seconds and write your guess for what the FilterQuery object looks like.
If you've used Mongoose or Prisma, your guess is probably 80% right. The operators MikroORM uses ($gt, $or, $and) borrow the MongoDB convention. The answer is at the end of this section — check yours against it.

The five fetch methods

Method Returns When to use
em.find(Entity, where, options?) Entity[] You expect 0+ matches. The workhorse list query.
em.findOne(Entity, where, options?) Entity | null You expect 0 or 1. null on miss.
em.findOneOrFail(Entity, where) Entity Miss is an error condition (e.g. lookup by URL slug in a controller).
em.findAll(Entity, options?) Entity[] No where. Convenience for “everything in this table”.
em.findAndCount(Entity, where, options?) [Entity[], number] Paginated UI: page of rows + total count, in one call.

The conditions object

A FilterQuery is just a plain object. Equality is the simple case:

const drafts = await em.find(Article, { publishedAt: null });
const tolstoy = await em.find(Book, { author: 'Tolstoy' });

For anything beyond equality, you reach for the operator set. Every operator is a key starting with $:

OperatorSQLExample
$gt / $gte> / >={ viewCount: { $gt: 100 } }
$lt / $lte< / <={ publishedAt: { $lt: new Date() } }
$ne!={ status: { $ne: 'archived' } }
$in / $ninIN / NOT IN{ id: { $in: [1, 2, 3] } }
$likeLIKE{ title: { $like: '%Tolstoy%' } }
$re~ (regex){ slug: { $re: '^draft-' } }
$andAND{ $and: [{...}, {...}] }
$orOR{ $or: [{...}, {...}] }

And here's the answer to the recall-box prediction:

const hits = await em.find(Article, {
  $and: [
    { viewCount: { $gt: 100 } },
    {
      $or: [
        { author: 'Tolstoy' },
        { publishedYear: { $gt: 2000 } },
      ],
    },
  ],
});

The top-level keys are AND'd implicitly, so a flat object works for the common AND case. You only need $and when you want to combine multiple conditions on the same property — e.g. { $and: [{ viewCount: { $gt: 10 } }, { viewCount: { $lt: 100 } }] }.

Searching by relation fields — the JOIN trick

This is the feature that makes the DSL feel ergonomic. You can nest a relation in the WHERE and MikroORM auto-joins:

// find articles whose author's name is 'Tolstoy'
const articles = await em.find(Article, {
  author: { name: 'Tolstoy' },
});
// SQL: select "a0".* from "article" as "a0"
//      left join "author" as "a1" on "a0"."author_id" = "a1"."id"
//      where "a1"."name" = 'Tolstoy'

One important caveat: the JOIN here is for filtering, not for loading. The returned Article objects will have an unhydrated reference for author — not the full author entity. To actually load the author too, pass populate: ['author']. We cover populate strategies in Lesson 4.

Cursor pagination — brief mention

For large lists, offset-pagination breaks once the list shifts under you. em.findByCursor gives you keyset pagination via opaque cursor strings. We touch on this in the advanced homework; for now just know the seam exists:

const page = await em.findByCursor(Article, {
  first: 10,
  after: previousCursor,
  orderBy: { id: 'desc' },
});
// page.items, page.endCursor, page.hasNextPage

Part 4: References, Partial Loading, and wrap()

Sometimes you want to refer to an entity without loading its row. Two scenarios:

  • Setting a foreign key: article.author = ???. You don't need the author's name; you just need its ID.
  • Deleting by ID: em.remove(???). You don't need to load the row first; you have the ID.

The escape hatch is em.getReference:

const authorRef = em.getReference(Author, 42);
// authorRef looks like (Author) { id: 42 } — unhydrated

article.author = authorRef;
await em.flush();
// SQL: insert into article ... values (..., 42)
// No SELECT was ever fired against the author table.

The reference is a real entity instance — it just doesn't have its non-PK properties loaded. If you read authorRef.name, you get undefined. If you actually need the data, you call wrap(authorRef).init() to fire a lazy SELECT.

The wrap() helper — meta-API for any entity

import { wrap } from '@mikro-orm/core';

const ref = em.getReference(Author, 42);
wrap(ref).isInitialized();    // false
await wrap(ref).init();          // fires SELECT
wrap(ref).isInitialized();    // true now

wrap(article).toObject();      // plain JS object copy
wrap(article).toJSON();        // for HTTP responses

Every managed entity has a hidden __helper property that wrap() exposes type-safely. You'll reach for it most often when you need to know “is this entity hydrated yet?” or “serialise this for an HTTP response”.

Partial loading with fields and exclude

By default em.find selects every column. For wide tables you can narrow:

// only id + title — body, metadata, etc are skipped
const articles = await em.find(Article, {}, {
  fields: ['title', 'slug'],
});
console.log(articles[0].title);    // ok
console.log(articles[0].body);     // undefined

fields is an allowlist; primary keys are always selected. There's also exclude for the inverse: select everything except the listed columns.

Footgun: if you use fields and forget to include the FK column for a relation, that relation can't be linked properly when you populate. Example: loading { fields: ['title'] } on Article and then trying to populate author — the author_id wasn't selected, so the join can't happen. Either include the FK explicitly ('author' in fields) or skip fields for that query.

Part 5: Identity Map Proof-of-Life

Lesson 1 promised the Identity Map saves round trips. Now we'll see it in action with the query log open.

Same primary key, twice

const a1 = await em.findOne(Article, 1);
const a2 = await em.findOne(Article, 1);
console.log(a1 === a2); // true

Query log:

[query] select "a0".* from "article" as "a0" where "a0"."id" = 1 limit 1
<-- second findOne fires no SQL -->

One SELECT. The second findOne looked up id = 1 in the Identity Map, found a hit, and returned the cached instance. a1 === a2 is true because they're literally the same object reference.

Same row, different lookup — the surprising case

const b1 = await em.findOne(Article, { slug: 'on-long-novels' });
const b2 = await em.findOne(Article, { slug: 'on-long-novels' });
console.log(b1 === b2); // true!

Query log:

[query] select "a0".* from "article" as "a0" where "a0"."slug" = 'on-long-novels' limit 1
[query] select "a0".* from "article" as "a0" where "a0"."slug" = 'on-long-novels' limit 1

Two SELECTs — but b1 === b2. Why? Because the Identity Map is keyed by primary key, not by query. MikroORM still has to issue the SELECT (it can't know without asking the DB whether the row exists), but once Postgres returns row id 1, MikroORM looks up id = 1 in the Identity Map, finds the cached instance from the first query, and returns that — not a freshly hydrated copy. The second SELECT does fire, but the JS object you get back is the same reference.

Two takeaways from this: (1) The Identity Map prevents duplicate object instances, not duplicate queries. To deduplicate by-slug queries, you cache the slug yourself. (2) Because the same instance is returned, any in-memory mutations a previous handler made are still visible — which is the correctness property the map exists to protect.

Junior: “I called em.findOne(Book, 1) in a loop, 100 times. The query log only shows one SELECT. Is the database broken?”
Senior: “That's the Identity Map.”

Senior: “You got zero database calls. That's better than free.”
Junior: “What about findOne(Book, { title: 'War and Peace' }) twice?”

Part 6: Hands-on — CRUD against archive-api

Time to stitch all of this into one runnable script. Open archive-api from Lesson 2 and replace src/main.ts with the following. We'll create five articles, find the popular ones, increment view counts, remove a draft, and watch the query log.

// src/main.ts
import { MikroORM, wrap } from '@mikro-orm/core';
import config from './mikro-orm.config';
import { Article } from './entities/Article';

async function main() {
  const orm = await MikroORM.init(config);
  await orm.schema.refreshDatabase();
  const em = orm.em.fork();

  // 1. CREATE — five articles, mix of published and drafts
  for (let i = 1; i <= 5; i++) {
    em.create(Article, {
      title: `Article #${i}`,
      slug: `article-${i}`,
      body: `Body of article ${i}.`,
      viewCount: i * 50, // 50, 100, 150, 200, 250
      publishedAt: i % 2 === 0 ? null : new Date(),
    });
  }
  await em.flush();
  // One INSERT, five rows. One transaction.

  // 2. FIND — all articles with viewCount > 100
  const popular = await em.find(Article, {
    viewCount: { $gt: 100 },
  });
  console.log(`popular: ${popular.map(a => a.title).join(', ')}`);

  // 3. UPDATE — bump every popular article's viewCount by 1
  for (const a of popular) {
    a.viewCount += 1;
  }
  // no flush yet — changes pile up in the Unit of Work

  // 4. DELETE BY REFERENCE — remove article #2 (a draft) without loading it
  const draftRef = em.getReference(Article, 2n);
  em.remove(draftRef);

  // 5. SINGLE FLUSH — UPDATEs and DELETE go out together
  await em.flush();
  // One BEGIN, one batched UPDATE (CASE expression), one DELETE, one COMMIT.

  // 6. PROVE THE IDENTITY MAP — read the same article twice
  const first = await em.findOne(Article, 1n);
  const again = await em.findOne(Article, 1n);
  console.log(`same instance? ${first === again}`); // true — no second SELECT
  console.log(`hydrated? ${wrap(first!).isInitialized()}`); // true

  await orm.close();
}

main().catch(console.error);

Run npm start and watch the log. You should see roughly:

✨
5 inserts in 1 SQL
A single multi-row INSERT, wrapped in begin/commit.
🔍
1 SELECT for the popular query
A where "view_count" > 100 with no JOIN.
🔁
1 batched UPDATE + 1 DELETE
In the same begin/commit. The update uses a CASE expression to set per-row values.
🗂️
Identity Map cache hit
Two findOne(Article, 1n) calls, one SELECT in the log.

That's a real CRUD slice in 30 lines, with one transaction, exactly the queries you'd want, and a free Identity Map cache. The mental shift Lesson 1 promised — describe changes as object mutations, then flush — is no longer abstract. Run with debug logging. Submit a screenshot showing: the batched UPDATE + DELETE in one transaction, then exactly one SELECT for both findOne calls. The second call must not produce a second query.

    Model answer / self-check

    The screenshot must show: (1) a single BEGIN…COMMIT wrapping the UPDATE and DELETE in one flush; (2) one SELECT WHERE id = 1 after the flush; (3) no second SELECT for the second findOne — the Identity Map returns the same in-memory instance. If you see two SELECTs: you likely forked the EM or cleared it between the two calls.

  2. Why does a by-title query still fire SQL? ≈ 15 min

    In 4–6 sentences: why does MikroORM still issue a SELECT when you call em.findOne(Book, { title: 'War and Peace' }) twice in a row, even though it returns the same JS instance both times? What does the Identity Map use as its key, and why is that the right design? Submit as text.

    Model answer / self-check

    The Identity Map is keyed by primary key, not by arbitrary filter conditions. MikroORM cannot know that { title: 'War and Peace' } resolves to id=42 without asking the database. After the first SELECT it registers the returned instance under id=42. The second call re-runs the query, gets id=42 in the result row, and returns the already-managed JS instance — same object reference, but SQL still fires. Caching by arbitrary filter would require MikroORM to track every possible condition and invalidate on every write — effectively a query cache.

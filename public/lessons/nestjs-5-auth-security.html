Part 1: Why Auth Is a First-Class Concern

Right now, your airport-api has a public DELETE /flights/:id endpoint. Anyone with curl and your URL can wipe your database. That's not a bug — that's the default state of any HTTP server. The internet is open. You make it closed.

🚪

*Launch happens*
Founder: “We'll add auth in v2.”
*v2 ships*

Auth is not a feature you add later. It's the door on the building.

Two words: authentication and authorization

🆔
Authentication
Who are you?
Verify identity. Email + password, OAuth, API key, biometric. Output: a verified user identity.
🔑
Authorization
Are you allowed?
Given a verified identity, decide what they can do. Roles, permissions, ownership checks.

Authentication happens once per session. Authorization happens on every request. They use the same wiring — guards — but they answer different questions.

Back to the airport. There are two checkpoints, in this order. First: at the security gate, a guard looks at your boarding pass and your ID. The pass is real, the photo matches, you signed it — you're who you claim to be. That's authentication.

Second: at the gate to the lounge, another agent checks whether your boarding pass says "Business" or "Economy." Same passenger, same valid ID — but only one of them gets through. That's authorization.

The mapping: Boarding pass + ID = JWT (carries identity, signed, tamper-evident). Security guard = AuthGuard('jwt') (verifies the token). Lounge gate agent = RolesGuard (checks the claim inside the token). Bcrypt = the tamper-proof seal on a sealed envelope — if someone changes the contents, the seal breaks visibly.

Part 2: Password Hashing with bcrypt

The first rule of storing passwords: you don't store passwords. You store hashes. The difference is what saves your career when the database leaks.

Hash vs encryption — the critical distinction

If your DB leaks, an encrypted password is one stolen key away from disaster. A hashed password is just noise.

Encryption is two-way: a key turns plaintext into ciphertext, and the same key reverses it. Useful for data you need to read again later (credit card numbers stored for refunds). Catastrophic for passwords — if anyone gets the key, every password is plaintext.

Hashing is one-way: input goes in, a fixed-length scrambled output comes out, and there is no function that turns the output back into the input. To check a login, you hash the submitted password and compare hashes. You never decrypt anything because there's nothing to decrypt.

Real-world reminder: in 2012, LinkedIn leaked 6.5M user passwords stored as unsalted SHA-1 hashes. Within days, 90%+ were cracked. SHA-1 is fast — great for checksums, terrible for passwords. Bcrypt is intentionally slow and salted. Use bcrypt (or argon2). Never roll your own.

Bcrypt in NestJS — install and use

npm i bcrypt
npm i -D @types/bcrypt
import * as bcrypt from 'bcrypt';

// On registration:
const SALT_ROUNDS = 10;
const hash = await bcrypt.hash(plainPassword, SALT_ROUNDS);
// store `hash` in the user row. plainPassword goes out of memory immediately.

// On login:
const matches = await bcrypt.compare(submittedPassword, user.passwordHash);
if (!matches) throw new UnauthorizedException();

SALT_ROUNDS = 10 means bcrypt does 2^10 = 1024 hashing iterations. Roughly 100ms per password on modern hardware. Slow enough that brute-forcing a leaked DB at 1000 guesses/second would take centuries. Fast enough that one user logging in doesn't notice.

Salt is automatic: bcrypt embeds a unique random salt inside every hash output (the $2b$10$ prefix). Two users with the same password get different hashes. You don't have to manage salts by hand — common mistake in homegrown auth.

NestJS doesn't ship its own auth library. It uses Passport — the standard Node.js auth library, with 500+ strategies (local, JWT, OAuth, SAML, the lot). NestJS wraps Passport in @nestjs/passport so each strategy plugs cleanly into the DI system as a guard.

Step 2: AuthService — register and validate

// src/auth/auth.service.ts
import { Injectable, UnauthorizedException, ConflictException } from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import * as bcrypt from 'bcrypt';
import { UsersService } from '../users/users.service';

@Injectable()
export class AuthService {
  constructor(
    private readonly users: UsersService,
    private readonly jwt: JwtService,
  ) {}

  async register(email: string, password: string) {
    const existing = await this.users.findByEmail(email);
    if (existing) throw new ConflictException('Email already registered');
    const passwordHash = await bcrypt.hash(password, 10);
    const user = await this.users.create({ email, passwordHash });
    return this.sign(user.id, user.email, user.role);
  }

  async validateUser(email: string, password: string) {
    const user = await this.users.findByEmail(email);
    if (!user) throw new UnauthorizedException();
    const ok = await bcrypt.compare(password, user.passwordHash);
    if (!ok) throw new UnauthorizedException();
    return user;
  }

  async login(email: string, password: string) {
    const user = await this.validateUser(email, password);
    return this.sign(user.id, user.email, user.role);
  }

  private sign(sub: number, email: string, role: string) {
    const payload = { sub, email, role };
    return { access_token: this.jwt.sign(payload) };
  }
}

Part 4: JWT Strategy & AuthGuard('jwt')

The login endpoint hands back an access_token. From that point on, every protected request must carry it in the Authorization: Bearer <token> header. We need a guard that:

  1. Extracts the token from the header
  2. Verifies the signature against our secret
  3. Decodes the payload
  4. Attaches the user to request.user
  5. Rejects with 401 if anything is wrong

That's the JwtStrategy.

Set up the JwtModule

Add to .env:

JWT_SECRET="change-me-to-a-long-random-string"
JWT_EXPIRES_IN="1d"
// src/auth/auth.module.ts
import { Module } from '@nestjs/common';
import { JwtModule } from '@nestjs/jwt';
import { PassportModule } from '@nestjs/passport';
import { AuthService } from './auth.service';
import { AuthController } from './auth.controller';
import { JwtStrategy } from './jwt.strategy';
import { UsersModule } from '../users/users.module';

@Module({
  imports: [
    UsersModule,
    PassportModule,
    JwtModule.register({
      secret: process.env.JWT_SECRET,
      signOptions: { expiresIn: process.env.JWT_EXPIRES_IN ?? '1d' },
    }),
  ],
  controllers: [AuthController],
  providers: [AuthService, JwtStrategy],
})
export class AuthModule {}

JwtStrategy — the verification step

// src/auth/jwt.strategy.ts
import { Injectable } from '@nestjs/common';
import { PassportStrategy } from '@nestjs/passport';
import { ExtractJwt, Strategy } from 'passport-jwt';

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor() {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: process.env.JWT_SECRET,
    });
  }

  validate(payload: { sub: number; email: string; role: string }) {
    // Whatever this returns becomes `request.user` in your controllers
    return { id: payload.sub, email: payload.email, role: payload.role };
  }
}

validate() runs only after the signature has been verified and the token isn't expired. If anything fails earlier, the strategy short-circuits with 401 and your method never runs. You don't have to write any of that — passport-jwt does it for you.

Protecting a controller

// src/flights/flights.controller.ts
import { AuthGuard } from '@nestjs/passport';
import { UseGuards, Req } from '@nestjs/common';

@Controller('flights')
@UseGuards(AuthGuard('jwt'))     // ← every route below requires a valid JWT
export class FlightsController {
  // ...all your existing handlers

  @Get('me')
  whoAmI(@Req() req: any) {
    return req.user;  // { id, email, role } from JwtStrategy.validate()
  }
}

Apply @UseGuards at the class level to protect every method, or at the method level to protect just one. Public endpoints (login, register) have no guard.

The full flow, end to end

Five steps. Steps 2–4 are entirely free — you just declared @UseGuards(AuthGuard('jwt')).

Part 5: Role-Based Access Control

JWT verification answers "who are you?" Now we answer "are you allowed to do this?" The pattern: a custom decorator that tags a route with a required role, plus a guard that reads the tag and compares it to the user's role.

The @Roles() decorator

// src/auth/roles.decorator.ts
import { SetMetadata } from '@nestjs/common';

export const ROLES_KEY = 'roles';
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles);

SetMetadata attaches a key/value to the route's metadata. It does nothing on its own — it just leaves a label that another guard will read.

The RolesGuard

// src/auth/roles.guard.ts
import { CanActivate, ExecutionContext, Injectable, ForbiddenException } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { ROLES_KEY } from './roles.decorator';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
      ctx.getHandler(),
      ctx.getClass(),
    ]);
    if (!required || required.length === 0) return true;       // no roles → allow

    const { user } = ctx.switchToHttp().getRequest();
    if (!user || !required.includes(user.role)) {
      throw new ForbiddenException('Insufficient role');
    }
    return true;
  }
}

Reflector is NestJS's helper for reading metadata at runtime. getAllAndOverride checks both the method and the class — method-level @Roles() wins over class-level if both are present.

Apply it to a route

// src/flights/flights.controller.ts
import { AuthGuard } from '@nestjs/passport';
import { Roles } from '../auth/roles.decorator';
import { RolesGuard } from '../auth/roles.guard';

@Controller('flights')
@UseGuards(AuthGuard('jwt'), RolesGuard)
export class FlightsController {

  @Get()
  findAll() { /* any logged-in user */ }

  @Delete(':id')
  @Roles('admin')               // ← only admins
  @HttpCode(204)
  remove(@Param('id', ParseIntPipe) id: number) {
    return this.flightsService.remove(id);
  }
}

Order matters in @UseGuards(). AuthGuard runs first, attaches request.user; RolesGuard runs second, reads request.user.role. Reverse them and RolesGuard sees an undefined user.

Advanced: for fine-grained permissions (not just roles), the same pattern scales — create a @Permissions('flight.delete') decorator and a PermissionsGuard that checks user permissions in the database. We'll touch this in Lesson 9.

Part 6: Production Security Layer

Auth handles "who" and "what." Production security handles everything else: someone scanning your endpoints, someone hammering /login with 50,000 password guesses, someone embedding your API in a malicious page. Four standard tools cover 95% of the surface.

Helmet — sane HTTP security headers

npm i helmet
// src/main.ts
import helmet from 'helmet';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.use(helmet());                 // ← one line, dozens of headers
  await app.listen(3000);
}

Helmet sets ~15 security-related response headers: Content-Security-Policy, X-Frame-Options, Strict-Transport-Security, X-Content-Type-Options, etc. Each blocks a specific class of attack (clickjacking, MIME sniffing, mixed content). The defaults are sensible — you mostly only customize CSP.

CORS — controlling who calls your API

app.enableCors({
  origin: ['http://localhost:3000', 'https://app.fohlio.com'],
  credentials: true,
  methods: ['GET', 'POST', 'PATCH', 'DELETE'],
});

By default, browsers refuse cross-origin XHR. CORS opens specific origins. Never use origin: '*' in production — that disables the protection. List the exact frontends that should be allowed to call you.

Rate limiting with @nestjs/throttler

npm i @nestjs/throttler
// src/app.module.ts
import { ThrottlerModule, ThrottlerGuard } from '@nestjs/throttler';
import { APP_GUARD } from '@nestjs/core';

@Module({
  imports: [
    ThrottlerModule.forRoot([{ ttl: 60_000, limit: 10 }]), // 10 req / 60s
    // ...other modules
  ],
  providers: [
    { provide: APP_GUARD, useClass: ThrottlerGuard },         // applied globally
  ],
})
export class AppModule {}

11th request from the same IP within a minute → 429 Too Many Requests. Lower the limit specifically on /auth/login to slow down credential stuffing — @Throttle({ default: { ttl: 60_000, limit: 5 } }) on the login handler.

Cookies, sessions, and CSRF

JWTs in the Authorization header (what we built) are immune to CSRF — the browser doesn't send them automatically across origins. The moment you switch to cookie-stored auth (e.g. for SSR apps), CSRF becomes a real threat and you need csurf tokens, SameSite=Lax on the cookie, and secure: true in production.

Storage CSRF risk XSS risk When to use
JWT in Authorization header None — not auto-sent High if stored in localStorage SPAs, mobile apps
JWT in HttpOnly cookie Yes — needs CSRF tokens Lower — JS can't read it SSR apps, classic web
Express session Yes — needs CSRF tokens Same as cookie Stateful traditional apps

The trade-off, plainly stated: there is no auth storage that is safe against both XSS and CSRF without help. If your frontend has an XSS vulnerability, your auth is compromised regardless of where you stored the token. The defenses are both layers, not just one.

Part 7: Putting It All Together — the Protected Airport

Walk through the airport one more time, with everything we built today.

A passenger arrives. Helmet is the building's structural code — reinforced glass, blast-proof doors. Quiet, always there. CORS is the receptionist who only lets passengers from approved travel partners through the front entrance. Rate limiting is the queue-management system that politely tells the same person they've already approached the desk too many times in a minute.

The passenger reaches the security checkpoint. AuthGuard('jwt') is the TSA agent: examines the boarding pass (token), checks the holographic seal (signature) against the master pattern (JWT secret), confirms it hasn't expired. Pass — the passenger is verified.

At the lounge entrance, RolesGuard looks at the boarding pass class. Business? Welcome in. Economy? Sorry, members only — 403. Same valid passenger, different door, different rule.

And finally the passenger reaches their gate — your controller. Everything has been verified upstream. The handler does its job knowing the request is safe.

The big idea: Each layer adds one specific protection. None of them are sufficient alone. Together they're "defense in depth." NestJS lets you express each layer with one decorator, then forget about it.

A spec is data, not a document

Chapter 4. Areas, Schedules, columns — and why a spec row can answer questions

Dana opens the Marriott project and scrolls through the lobby, through the restaurant, into the guest-room block. Six hundred rooms. She pauses on a single armchair line item. Its finish field reads UP-HB-113. Not “warm taupe.” Not “the brownish one Linda approved at the March review.” A code — precise, machine-readable, queryable. If a supplier marks that finish discontinued, the system will know. If someone swaps it for the wrong one, the diff will surface. That is the thing that did not happen eighteen months ago when sixty wrong chairs arrived at a loading dock, and it is the whole reason Fohlio models a spec row the way it does.

Part 1. The room is the unit of truth

Before a single product enters a spec, someone has to answer: “where does it go?” Fohlio’s answer is the Area. An Area is a room or zone inside a project — lobby, guest room, restaurant, corridor, spa reception. Every line item in the spec is attached to an Area (or sits at the project level if it’s a shared item that spans zones) [1].

This looks obvious until you work out what it means at scale. The Marriott project has six hundred guest rooms. Each room gets an armchair, a desk lamp, a bed frame, a mirror, artwork. That is not six hundred independent spec-building exercises. Dana defines one canonical “Guest Room” Area, specs all its items once, and the quantity rollup takes care of the rest. In the data model, there is one armchair slot, not six hundred. The number 600 surfaces in the totalQty calculation, not as duplicated rows [4].

Grace’s Cedar & Oak is almost the opposite. Twelve rooms at the boutique inn, almost none with the same furniture. “Room 3 needs to feel different from Room 7 — that’s what people pay for,” Grace told Dana during onboarding. So each Area is nearly its own world. Thirty bespoke line items, thirty distinct finish codes, twelve suppliers. No repetition lever to pull.

The data model is identical to the Marriott spec. The Areas exist, the slots exist, the items exist. The only difference is that for Grace, qty × area_instances = qty × 1 almost always. The chaos is contained — which is exactly what “spec as database” means at SMB scale.

Entity note: Area belongs to a Project. A ProjectItemSlot references one Area (or null for project-level items). Deleting an Area does not cascade-delete its slots — they become unassigned, not lost. Soft-deletion pattern; deleted_at on the Area record [4].

In Lesson 1, the entity tree was: Workspace → Project → Areas → Items. This lesson fills in the middle layers with precision. The word “Items” in that tree is actually four concepts stacked: Schedule, ItemColumns, ProjectItemSlot, and ProjectItem.

Part 2. Schedules: categories with schemas

Every FF&E spec has categories — “Furniture,” “Lighting,” “Soft Goods,” “Finishes.” Fohlio calls these Schedules. But a Schedule in Fohlio is not just a label to sort rows under. It owns a column definition [1].

A Schedule carries a list of ItemColumns. Each column has: a machine key, a human label, a data type (text / number / select / boolean), and optionally a list of allowed values. A Furniture schedule might have columns for finish code, material, COM status, and install type. A Lighting schedule has columns for voltage, lamp base, fixture type, and dimmability. When Dana assigns a product to the Furniture schedule, that line item’s ProjectItem gains those columns — and the values she enters for each one are stored in a key-value map called columnsAttributes [4].

🤔 Predict before you read on
If a Schedule defines the column keys and a ProjectItem stores the values in columnsAttributes, what happens to existing items’ column values when a column is removed from the Schedule schema after the spec is built? Make your best prediction — are those values lost, preserved, or surfaced as warnings?
Think about what “key-value map” means when the key definitions change underneath it.

The answer: the old values remain in columnsAttributes as orphaned attributes. The column key still exists in the map; the schema just no longer declares it. Fohlio surfaces these as “unknown column” indicators in the UI rather than silently discarding them. This is the deliberate tradeoff of the entity-attribute-value pattern: flexible schema without database migrations, at the cost of schema-level enforcement. Adding a column to a Schedule does not require touching existing items. Removing one does not corrupt them [4].

Part 3. Slot and Item — why the split exists

In Lesson 3, we watched a product move from the catalog into the spec. But “a line item in the spec” is actually two entities stacked on each other: ProjectItemSlot and ProjectItem. The split encodes a real workflow decision, not an engineering accident [4].

The Slot is the position in the spec. It carries a reference number, an Area assignment, and a quantity. It represents “we need something here.” The Item is the product choice that fills the slot. It holds the link to a CatalogFamily and a specific CatalogItem variant (as established in Lesson 3), the columnsAttributes map with all the Schedule column values, and a sync state. One Slot has exactly one primary Item and zero-to-many alternatives.

The split exists because “what position do we need to fill?” and “which exact product fills it?” are answered by different people at different times. Dana creates the slot: position 12, lobby, lounge chair, qty 4. Helen reviews the approved catalog and assigns the primary product to it. Later, if that product becomes unavailable before procurement (exactly the kind of situation that caused the $40k loss), Dana or Marco can replace the primary Item without touching the Slot at all — the reference number, the Area assignment, and the quantity survive untouched [4].

The full spec data model. A Slot holds position, Area, and quantity. A primary Item holds the product choice and all column values. Alternatives sit beside the primary — same slot, different candidates ready if the primary is unavailable.

Part 4. qty and totalQty — scale in two numbers

One of the most common questions engineers ask when reading the data model for the first time: “why are there two quantity fields?” The answer is written in the Marriott spec [2].

qty on a ProjectItemSlot is the count per Area instance. Four armchairs in one guest room: qty = 4. But there are 600 instances of the “Guest Room” Area. totalQty = qty × area_instance_count = 4 × 600 = 2,400. Marco’s purchase order is for 2,400 armchairs. Getting this wrong by a factor of 600 is not a rounding error — it is the entire order [4].

Grace’s Cedar & Oak is nearly the opposite: most Areas are unique instances. “Room 3” is not “Room 4.” For Grace, totalQty = qty × 1 = qty almost always. The field still exists, still computes, still drives her purchase orders. The math is just less dramatic.

Three clients, one concept: Marriott deploys Area repetition to define scale without duplicating data — 600 identical rooms, one spec definition. The Church of Jesus Christ does the same across hundreds of meetinghouses: Brother Andersen’s team defines one standard floor plan, sets an instance count, and the totalQty rollup gives them the full procurement volume. Then they negotiate MOQ against that volume. Grace uses the same model for a single property: twelve rooms, totals equal per-room quantities. One entity, three scales.

Part 5. Finish is a code, not a word

The $40k mistake from Lesson 1 happened because a finish was recorded as a human-readable string. “Warm taupe upholstery” and “closest match warm taupe” look similar in a printed document. In a database, they are different rows pointing to different supplier SKUs at different prices — and a database can tell them apart [3].

Fohlio stores finish as a structured column value, not free text. When Dana enters UP-HB-113 in the finish column of a Furniture line item, that code resolves through the catalog: it maps to a specific supplier finish, which in turn maps to a price and a lead time. The spec does not print “warm taupe” — it prints the code, and the code is the truth. A code can be queried. It can be diffed when the catalog updates. It can trigger a sync-state flag when the supplier marks that finish discontinued [4].

Compare that to what happens when a designer types “warm taupe” in a notes field. There is nothing to query, nothing to diff, nothing to flag. The spec will print “warm taupe” for eighteen months while the finish quietly disappears from the supplier’s range. Nobody catches it until the chairs are on a truck with the wrong upholstery. That is the document failure Dana lived through. The structured code is what prevents it.

A spec isn’t a document. It’s a database that happens to know how to print itself on paper.

The finish code lives in columnsAttributes on the ProjectItem, alongside all other Schedule-defined column values. Every key in the map is a column ID from the Schedule schema. Every value is typed and validated at entry time. That makes the row queryable: “show me every project in this workspace using finish UP-HB-113” returns a precise answer in milliseconds. Try that across six hundred separate Excel files.

Part 6. What “queryable” enables downstream

In Lesson 3 we watched a product enter the catalog as a CatalogFamily / CatalogItem pair. Now we can be precise about what that structured reference enables once the product is inside a spec [3].

Because a ProjectItem carries typed foreign keys to catalog entities — not text descriptions — Fohlio can answer questions that no printed document can:

🔍
Cross-project search
“Which projects use supplier X or finish Y?” — milliseconds, not hours of manual searching.
📊
Takeoff / quantity rollup
Total units by supplier, finish, schedule — computed from qty × area count. Marco’s PO quantities come from here.
🔔
Sync-state alerting
Catalog item updated → every spec slot referencing it can be flagged automatically. Full story in Lesson 8.
💰
Budget rollup
Spec total = ∑(unit price × totalQty). A price change in the catalog propagates to the budget immediately. Lesson 6.

None of this requires clever engineering. All of it follows from a single decision made back in Lesson 1: the spec is normalized relational data, not a printable table. Areas, Schedules, Slots, and Items are the machinery that makes that decision concrete.

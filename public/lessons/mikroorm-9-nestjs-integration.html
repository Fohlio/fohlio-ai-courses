Part 1: The Integration Package

Back in the NestJS course we said modules are terminals at an airport. Each terminal owns a piece of the operation; you walk between them through controlled gates. Today we equip a terminal with a Records Library — a records desk inside the terminal where every counter agent can request, modify, and file documents.

Imagine a terminal at the airport that handles passport renewals. It needs a records library: every passport application has a paper trail, every renewal updates the master catalog, every batch of renewals at end of shift gets signed off. We don't want each agent to walk to a city-wide archive every time. We want a desk inside the terminal, with the same library protocols, scoped to that terminal's traffic.

The mapping: NestJS module = terminal. MikroOrmModule.forRoot() = installing the records desk. forFeature([Book]) = the specialist clerk who only handles books. RequestContext middleware = a fresh ledger handed to every passenger as they walk in.

Install

npm install @mikro-orm/core @mikro-orm/nestjs @mikro-orm/postgresql
npm install @nestjs/common @nestjs/core @nestjs/platform-express
npm install reflect-metadata rxjs

Three groups. @mikro-orm/nestjs is the bridge package — it provides MikroOrmModule, the DI-aware @InjectRepository decorator, and the request-scope middleware. The Nest packages are standard. reflect-metadata is required for Nest's own decorators (it's not used by MikroORM defineEntity, but Nest wants it).

The forRoot / forFeature pattern

You'll recognize this shape if you've used TypeOrmModule. Two methods, two responsibilities.

🏛️
forRoot(config)
Once, in AppModule
Boots the ORM, opens the Postgres pool, registers the request-context middleware, exposes the global EntityManager and MikroORM providers.
🔍
forFeature([Book])
Per feature module
Registers EntityRepository<Book> in the DI container so a service in this module can @InjectRepository(Book). No new connection, just typed handles.

Wiring the AppModule

// src/app.module.ts
import { Module } from '@nestjs/common';
import { MikroOrmModule } from '@mikro-orm/nestjs';
import config from './mikro-orm.config';
import { BookModule } from './book/book.module';

@Module({
  imports: [
    MikroOrmModule.forRoot(config),
    BookModule,
  ],
})
export class AppModule {}
// src/book/book.module.ts
import { Module } from '@nestjs/common';
import { MikroOrmModule } from '@mikro-orm/nestjs';
import { Book } from '../entities/Book';
import { BookController } from './book.controller';
import { BookService } from './book.service';

@Module({
  imports: [MikroOrmModule.forFeature([Book])],
  controllers: [BookController],
  providers: [BookService],
})
export class BookModule {}

Note: forRoot takes the same config object you've been using since Lesson 1 — the defineConfig result from mikro-orm.config.ts. Nothing about your entity definitions changes.

Part 2: The Request-Scoped EntityManager

Now the part that quietly does the most work. Remember Lesson 1: the global orm.em is a factory; you must fork() per request or you poison the Identity Map across users. In Express we wired this with RequestContext.create in middleware. In Nest, the @mikro-orm/nestjs package wires it for you, automatically, on every HTTP request.

How it works under the hood

  1. An HTTP request arrives. Nest's HTTP layer dispatches to your controller.
  2. Before the route handler, the MikroOrmMiddleware calls RequestContext.create(orm.em, next).
  3. RequestContext.create wraps the rest of the request inside an AsyncLocalStorage frame containing a fresh em.fork().
  4. Anywhere downstream — controller, service, repository, even helper modules — injecting EntityManager resolves to that fork.
  5. The response is sent. The fork is dropped. Garbage collection reclaims the Identity Map.

Injecting EntityManager and EntityRepository

// src/book/book.service.ts
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@mikro-orm/nestjs';
import { EntityManager, EntityRepository } from '@mikro-orm/postgresql';
import { Book } from '../entities/Book';

@Injectable()
export class BookService {
  constructor(
    private readonly em: EntityManager,
    @InjectRepository(Book)
    private readonly bookRepo: EntityRepository<Book>,
  ) {}

  async findAll() {
    return this.bookRepo.findAll();
  }
}

Notice both options work side-by-side. Inject the bare EntityManager for general use; inject a typed EntityRepository<Book> when you want a typed handle scoped to one entity. They share the same fork — the repository is a thin wrapper around the EM.

Import the EntityManager from your driver package — @mikro-orm/postgresql, not @mikro-orm/core. The driver package re-exports a more specific type that includes createQueryBuilder and other Postgres-specific methods. Import from core and you'll lose those at compile time.

The injected EM is a fork, not the global

This is the cognitive trap most TypeORM refugees hit. When you write private readonly em: EntityManager, what you actually receive is a proxy. Internally, every method call (find, persist, flush) routes through orm.em.getContext(), which checks the AsyncLocalStorage and returns the request-scoped fork. So the BookService class is a singleton, but each method call resolves to a different fork depending on which request is in flight.

Two consequences:

  • Don't hold entities in class fields. this.cachedBook = await em.findOne(Book, 1) in a singleton service is a leak. The next request gets a stale entity from a closed fork.
  • Don't pass EM instances to other services through method arguments when they could just inject their own. Each service should resolve to the contextual fork on its own. Passing the EM around bypasses the contextual lookup and can pin you to the wrong fork.
📝
TypeORM dev: “I cached the User entity on the service for performance.”
Senior: “On a singleton service?”
TypeORM dev: “Yes! It's the same user every time.”
Senior: “...for which request?”
TypeORM dev: “Why would that… oh.”
Request scope is the answer; @CreateRequestContext is the patch when you're outside a request.

Part 3: Background Workers — @CreateRequestContext

🤔 Predict before reading on
A Bull queue handler in your Nest app calls em.find(Book, 1). There is no HTTP request in flight, no middleware ever ran, no AsyncLocalStorage frame was opened. Predict: does it work, throw, or silently use the wrong scope?
There's a config flag (allowGlobalContext) that changes the answer. Without it, MikroORM 7 detects the missing fork. With it, you get worse than an error — you get cross-request bleed. The decorator we're about to introduce is the right answer.

Outside the request, there's no fork

The Nest middleware runs only on HTTP traffic. Three places where you do not have a request:

  • Queue handlers (Bull, BullMQ, RabbitMQ consumers, SQS) — the message arrives in a worker loop, not via HTTP
  • Scheduled tasks (@Cron, setInterval, any timer) — the runtime fires the callback on its own thread of control
  • App lifecycle hooks (OnModuleInit, bootstrap scripts, seed runners)

In all three, calling em.find() on the injected EM with no fork would either throw (with allowGlobalContext: false, the safe default in v7+) or silently return an entity from the global EM, which is exactly the cross-request bleed scenario.

The fix: @CreateRequestContext

Decorate the top-level method that owns the work. The decorator wraps the method body in RequestContext.create(orm.em, ...) — identical to what the HTTP middleware does, just triggered by the decorator instead.

// src/jobs/cleanup.consumer.ts
import { Process, Processor } from '@nestjs/bull';
import { CreateRequestContext, MikroORM } from '@mikro-orm/core';
import { EntityManager } from '@mikro-orm/postgresql';
import { Book } from '../entities/Book';

@Processor('cleanup')
export class CleanupConsumer {
  constructor(
    // MikroORM is required by the decorator
    private readonly orm: MikroORM,
    private readonly em: EntityManager,
  ) {}

  @Process('archive-stale-books')
  async handleJob(job: { data: { cutoff: string } }) {
    await this.archiveStale(new Date(job.data.cutoff));
  }

  @CreateRequestContext()
  async archiveStale(cutoff: Date) {
    const stale = await this.em.find(Book, { lastSeen: { $lt: cutoff } });
    for (const b of stale) b.archived = true;
    await this.em.flush();
  }
}

Two subtle things:

  1. The decorator goes on a separate method (archiveStale), not on handleJob. @Process from Bull and @CreateRequestContext can fight over the function reference; the safe pattern is one wrapper method that the queue calls, which then calls the decorated worker method.
  2. You must inject MikroORM on the constructor — the decorator looks it up by reflection. Without it, you get a runtime error the first time the job fires.

@EnsureRequestContext — the lighter-touch sibling

@CreateRequestContext() always creates a new fork, even if one already exists. @EnsureRequestContext() reuses the existing context if one is in scope, only creating a new fork when there isn't one. Use it on helper methods that might be called from both HTTP handlers (already have a fork) and queue handlers (don't).

Part 4: Transactions in NestJS

You already use a transaction every time you call flush(). By default MikroORM wraps the change-set in BEGIN ... COMMIT implicitly. But there are three escalation levels for when implicit isn't enough.

✨
1. Implicit (default)
em.flush() opens its own transaction. One business operation = one flush = one transaction. Good for simple writes.
🔐
2. @Transactional()
Decorator on a service method. Wraps the whole method in em.transactional(). Use when one method spans multiple flushes that must be atomic.
📑
3. em.transactional(...)
Explicit callback. Use when the transaction boundary doesn't align with a method boundary, or you want isolation level / propagation control.

The @Transactional decorator

// src/book/book.service.ts
import { Injectable } from '@nestjs/common';
import { Transactional } from '@mikro-orm/core';
import { EntityManager } from '@mikro-orm/postgresql';
import { Book } from '../entities/Book';
import { AuditLog } from '../entities/AuditLog';

@Injectable()
export class BookService {
  constructor(private readonly em: EntityManager) {}

  @Transactional()
  async createWithLog(dto: { title: string; author: string }) {
    const book = this.em.create(Book, dto);
    await this.em.flush();   // gets the new id

    this.em.create(AuditLog, {
      action: 'book.created',
      bookId: book.id,
      ts: new Date(),
    });
    await this.em.flush();   // part of the same transaction

    return book;
  }
}

Both flushes happen inside the same BEGIN ... COMMIT. If the second one throws (constraint violation, network blip), the book insert rolls back too — even though it had already been flushed to the database. That's the difference between flushed and committed.

Why not put @Transactional on a controller?

Anti-pattern: @Transactional on a controller method. Controllers are responsible for HTTP shape — parsing requests, authn/authz, response codes, content negotiation. They are not responsible for business invariants. The transaction boundary belongs to the unit of business work, which lives in the service. Putting it on the controller couples HTTP concerns to database concerns and means a unit-test of the service can't see the transactional behavior. Always push it down one layer.

Part 5: The Transactional Outbox Pattern

One particular kind of multi-step work is so common and so easy to get wrong that it deserves its own pattern. You have an HTTP handler that does two things: write a row to the database, and publish an event to Kafka / RabbitMQ / SNS / a webhook. Both must happen, or neither should.

The naive approach is wrong

// DON'T DO THIS
async createBook(dto) {
  const book = this.em.create(Book, dto);
  await this.em.flush();
  await this.kafka.publish('book.created', book);  // crash window!
}

Flush succeeds. Then the process crashes (OOM kill, deploy rollover, network partition). The Kafka publish never happens. The book exists in your database, but no downstream service ever hears about it. The system is forever inconsistent and there's no audit trail of what was lost.

Flipping the order doesn't help — publish first, write second is just as bad in the opposite direction (Kafka has the event but the book never got persisted).

The pattern: write the event into a row, in the same transaction

The library has a "pending publication" tray. Whenever a record gets sealed at the end of shift, anything that needs to leave the building (an outgoing letter, a notice to another archive, a press release) is dropped into the tray as part of the same sign-off. The head librarian's signature commits both the master register entry and the pending-publication slip together — or neither, if the shift is rolled back.

A separate clerk — the dispatcher — runs a loop on a different schedule. They walk the tray, send everything in it, mark each item as sent, repeat. If they miss a beat, the items wait. If they crash mid-walk, the next dispatcher picks up the unprocessed items.

The mapping: Pending-publication tray = outbox table. Sign-off = the same transaction that wrote the business row. Dispatcher = a cron worker draining the outbox. Idempotency = the dispatcher always marks rows as processed, never republishes the same row.

The Outbox entity

// src/entities/OutboxEvent.ts
import { defineEntity, p } from '@mikro-orm/core';

export const OutboxEvent = defineEntity({
  name: 'OutboxEvent',
  properties: {
    id: p.bigint().primary(),
    eventType: p.string(),
    payload: p.json<Record<string, unknown>>(),
    createdAt: p.datetime().onCreate(() => new Date()),
    processed: p.boolean().default(false),
  },
});

Writing inside the same flush

@Transactional()
async createBook(dto: { title: string; author: string }) {
  const book = this.em.create(Book, dto);
  this.em.create(OutboxEvent, {
    eventType: 'book.created',
    payload: { title: dto.title, author: dto.author },
  });
  await this.em.flush();
  return book;
}

One flush, one transaction, two rows. They commit or roll back together — the database itself enforces atomicity.

The dispatcher

// src/jobs/outbox.dispatcher.ts
@Injectable()
export class OutboxDispatcher {
  constructor(
    private readonly orm: MikroORM,
    private readonly em: EntityManager,
  ) {}

  @Cron('*/5 * * * * *')  // every 5 seconds
  @CreateRequestContext()
  async drain() {
    const events = await this.em.find(
      OutboxEvent,
      { processed: false },
      { orderBy: { createdAt: 'ASC' }, limit: 100 },
    );

    for (const e of events) {
      console.log('publishing', e.eventType, e.payload);
      // real implementation: await broker.publish(e.eventType, e.payload);
      e.processed = true;
    }

    await this.em.flush();
  }
}

At-least-once, not exactly-once. If the dispatcher crashes after publishing but before the flush that marks rows processed, those events get re-published next run. Consumers must be idempotent. With multiple dispatchers, use FOR UPDATE SKIP LOCKED (lockMode: LockMode.PESSIMISTIC_PARTIAL_WRITE) so two workers don't race for the same row.

BookController and BookService

// src/book/book.controller.ts
import { Body, Controller, Get, Post } from '@nestjs/common';
import { BookService } from './book.service';

@Controller('books')
export class BookController {
  constructor(private readonly books: BookService) {}

  @Get()
  list() {
    return this.books.findAll();
  }

  @Post()
  create(@Body() dto: { title: string; author: string }) {
    return this.books.createWithLog(dto);
  }
}
// src/book/book.service.ts
import { Injectable } from '@nestjs/common';
import { Transactional } from '@mikro-orm/core';
import { EntityManager } from '@mikro-orm/postgresql';
import { Book } from '../entities/Book';
import { AuditLog } from '../entities/AuditLog';

@Injectable()
export class BookService {
  constructor(private readonly em: EntityManager) {
    // log the EM identity per request to prove fork-per-request
    console.log('BookService got EM:', (em as any).id ?? 'no-id');
  }

  findAll() {
    return this.em.findAll(Book);
  }

  @Transactional()
  async createWithLog(dto: { title: string; author: string }) {
    const book = this.em.create(Book, dto);
    await this.em.flush();
    this.em.create(AuditLog, { action: 'book.created', bookId: book.id });
    await this.em.flush();
    return book;
  }
}

Summary

🏛️
The bridge package
@mikro-orm/nestjs ships MikroOrmModule.forRoot(config) for the AppModule and forFeature([Book]) for feature modules. EntityManager and typed EntityRepository<T> are auto-injected.
🗂️
Request scope — automatic
Middleware opens an AsyncLocalStorage frame with a fresh fork on every HTTP request. The injected EM is a proxy that resolves to the current frame. Singleton services, per-request forks.
🔁
@CreateRequestContext
Decorator for queue handlers, cron jobs, lifecycle hooks — anywhere there's no HTTP middleware to do the fork for you. Inject MikroORM on the constructor.
🔐
@Transactional & outbox
@Transactional() on services for multi-flush atomicity; never on controllers. The outbox pattern co-commits a row to outbox with the business write so cross-system events can never be lost.

    Model answer / self-check

    The screenshot must show two distinct numeric IDs (e.g., "EM id: 2" and "EM id: 3") logged for two POST requests.   2. @Transactional on controller vs service + L7/L8 callback ≈ 25 min

    Part A (L9): In 4–6 sentences explain why @Transactional() on a controller method is an anti-pattern while on a service method it is idiomatic. Reference separation of concerns. Part B (L7–L8 callback): Your BookService.createWithLog() is decorated with @Transactional(). A migration later adds a NOT NULL column to AuditLog without a default. Describe step by step what happens to in-flight createWithLog transactions when the migration runs. What does this tell you about the order of migration deployment vs service deployment in production? Submit both parts as text.

    Model answer / self-check

    Part A: Controllers are HTTP adapters — they should not own transactional state. @Transactional() on a controller couples the HTTP layer to the database boundary and prevents calling the same logic from a queue handler or cron job. A service decorated with @Transactional() is callable by any client uniformly. Part B: Postgres DDL acquires ACCESS EXCLUSIVE lock, so the migration blocks until active transactions on that table finish. After the migration commits, any new createWithLog call that does not supply the new column will fail with a NOT NULL constraint violation — until the service code is also deployed. Lesson: always add NOT NULL columns with a DEFAULT first, deploy the service, then remove the default in a follow-up migration.

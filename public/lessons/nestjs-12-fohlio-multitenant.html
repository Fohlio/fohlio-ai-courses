Part 1: Multi-tenancy — One Airport, Many Airlines

Fohlio is a multi-tenant SaaS. A single deployed instance serves dozens of customer companies (we call them workspaces). Their data shares the same Postgres, the same Redis, the same Node processes — but it must never cross. A Delta gate agent can never accidentally hand a United passenger's boarding pass to someone else.

Picture LAX. One airport. Same TSA, same baggage carousels, same air traffic control. But each airline has its own counters, its own manifest, its own cargo hold. A Delta agent at gate 12 can see every Delta passenger today — because that's their job — but they can't see anyone flying United, even though United departs from gate 14 right next door.

That's Fohlio. A workspace is an airline. Every passenger (user), every flight (project), every piece of cargo (project item) carries an airline-code stamp — the workspaceId. Every query at every layer filters by that stamp. Always.

The mapping: Workspace = Airline. workspaceId = the airline-code stamp on every record. @CurrentUser() = the gate agent who reads your boarding pass and instantly knows which airline you're with.

The cardinal rule

Every entity that can belong to a customer has a workspaceId (or a workspace relation). Every SELECT, every UPDATE, every DELETE includes workspace_id = $1 in the WHERE clause. Forgetting this on a single query is not a bug — it is a data leak. There is no second chance.

The architectural rule is documented in asuncion/architecture.md as a non-negotiable: “Every workspace-scoped query MUST include the workspace filter. This is a security requirement — a missing filter leaks data across tenants. The workspaceId comes from the URL param (nested routes) or @CurrentUser().workspaceId from the JWT. Controllers pass it to services; services pass it to repositories.”

Note the chain: controller → service → repository, with workspaceId threading through every step. No hidden context, no implicit lookups. The argument is in every signature.

Two important details. First, workspaceId comes from the URL (POST /workspaces/:workspaceId/projects) — it's a nested route. Second, the WorkspaceScopeGuard (see src/modules/auth/guards/workspace-scope.guard.ts) compares the URL's workspaceId against the JWT's wsId. If they differ, you get a 403. The user can't reach into a workspace they're not in, even if they edit the URL.

The route nesting is set up at the module level — from architecture.md:

RouterModule.register([
  {
    path: 'workspaces',
    module: WorkspacesModule,
    children: [{ path: '/:workspaceId/users', module: UsersModule }],
  },
]);

Every users-related URL becomes /workspaces/:workspaceId/users/.... The :workspaceId param is structurally part of the route — you cannot accidentally hit /users without specifying which workspace. The shape of the URL itself enforces the multi-tenant contract.

Cardinal sin: forgetting workspaceId on one SELECT leaks data across companies. Forgetting it on one DELETE destroys someone else's data. There is no recovery for either of these in production. This is why Fohlio has a layered defense: a guard at the controller, the workspaceId threaded through every service argument, and explicit filters in every repository method.

Two architectural patterns to make this safe

🛡️
Cut at the controller
URL param + Guard
Workspace is a URL param (:workspaceId). A guard validates it matches the JWT. Services receive it as a typed argument. This is what Fohlio uses today.
🔍
Auto-inject via base repo
CLS-context filter
A base repository reads workspaceId from request-scoped context (nestjs-cls) and injects it into every query. Less boilerplate, harder to debug.

Fohlio uses the explicit pattern. Yes, you write workspaceId in every service argument. Yes, it's verbose. The trade-off is intentional: data isolation should be visible in code, not implicit in middleware. When a senior engineer reads a service method, they should see the workspace filter at a glance.

The WorkspaceScopeGuard — the second line of defense

Even with explicit filters, mistakes happen. That's why Fohlio adds a guard layer that runs before the controller body. From src/modules/auth/guards/workspace-scope.guard.ts:

@Injectable()
export class WorkspaceScopeGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest<{
      user: JwtAccessPayload;
      params: Record<string, string>;
    }>();

    const workspaceId = request.params['workspaceId'];
    if (!workspaceId) {
      return true;        // not a workspace-scoped route
    }

    const { wsId } = request.user;
    if (!wsId || wsId !== workspaceId) {
      throw new ForbiddenException();
    }
    return true;
  }
}

This guard runs on every request to a route under /workspaces/:workspaceId/.... It compares the URL's workspaceId param to the JWT's wsId. Mismatch → 403 instantly. The user can craft any URL they want; if the JWT says they belong to ws_001 and they ask for ws_002's projects, the guard kills the request before the controller method even runs. Defense in depth: URL guards + repository filters + assemblers stripping internal fields. Three layers, because one layer always eventually has a bug.

Part 2: The @CurrentUser Decorator — Typed Identity, One Argument

The gate agent reads the boarding pass. They know your seat, your flight, your airline — instantly, every time, without you spelling it out. @CurrentUser() is that gate agent for every Fohlio controller method.

Here is the actual file — src/common/decorators/current-user.decorator.ts, every line of it:

import { createParamDecorator, type ExecutionContext } from '@nestjs/common';
import type {
  JwtAccessPayload,
  CurrentUserPayload,
} from '../../modules/auth/types/jwt-payload.types.js';

export const CurrentUser = createParamDecorator(
  (_data: unknown, ctx: ExecutionContext): CurrentUserPayload => {
    const request = ctx.switchToHttp().getRequest<{ user: JwtAccessPayload }>();
    return {
      userId: request.user.sub,
      workspaceId: request.user.wsId,
    };
  },
);

Sixteen lines. That's the whole thing. Note what it does and what it doesn't do:

  • It does not verify the JWT. The JwtAuthGuard already did that — see src/modules/auth/guards/jwt-auth.guard.ts — and stuck the decoded payload onto request.user.
  • It does not hit the database. Identity comes from the signed token, not from a query.
  • It does reshape the raw JWT payload ({ sub, wsId, type, ... }) into a domain-friendly object ({ userId, workspaceId }).

And here's the typed payload it returns — from src/modules/auth/types/jwt-payload.types.ts:

export interface JwtAccessPayload {
  sub: string;            // userId (BigInt as string)
  wsId?: string;          // workspaceId, optional until switch-workspace
  type: 'access';
  impersonatedBy?: string;
  iat?: number;
  exp?: number;
}

export interface CurrentUserPayload {
  userId: string;
  workspaceId?: string;
}

Using it

Once it exists, every controller method that needs identity gets it as a typed parameter:

@Get('me')
getMe(@CurrentUser() user: CurrentUserPayload) {
  return {
    userId: user.userId,
    workspaceId: user.workspaceId,
  };
}

@Post('projects')
create(
  @Body() dto: CreateProjectDto,
  @CurrentUser() user: CurrentUserPayload,
) {
  return this.projectsService.create({
    actorId: user.userId,
    workspaceId: user.workspaceId!,
    ...dto,
  });
}

Why this matters: Fohlio has hundreds of endpoints. Each one needs userId and workspaceId. Without the decorator: every controller imports types, drills into req.user, casts to the right shape, handles missing fields. With it: one parameter, one type, zero ceremony. This is the highest-leverage 16 lines in the codebase.

How request.user got there in the first place

The decorator reads request.user. Who set it? The JwtAuthGuard, applied globally. From src/modules/auth/guards/jwt-auth.guard.ts (excerpted):

canActivate(context: ExecutionContext): boolean {
  if (this.isPublic(context)) return true;

  const token = this.extractRawToken(context);
  if (!token) {
    this.throwException('Unauthorized', context);
    return false;
  }

  try {
    const payload = this.jwtService.verify(token, {
      secret: this.configService.get('JWT_ACCESS_SECRET'),
    });
    if (payload.type === 'refresh') {
      this.throwException('Unauthorized', context);
      return false;
    }
    this.updateContext(payload, context);  // → request.user = payload
  } catch {
    this.throwException('Unauthorized', context);
    return false;
  }

  return true;
}

Three details worth flagging. First, the guard handles both HTTP and WebSocket contexts — a Fohlio peculiarity, since one auth flow has to cover both REST and Socket.IO. Second, it explicitly rejects refresh tokens (type === 'refresh') on access endpoints — a refresh token must only be used at the refresh endpoint. Third, @Public()-decorated routes opt out, which is how the login endpoint can be reached without a token in the first place.

This is the contract: the guard verifies the token and stuffs the payload onto the request. The decorator reads it back, typed. Together they replace what would otherwise be a tangle of req.headers.authorization parsing in every controller.

Part 3: Stateful JWT + Redis — The "Do Not Fly" List

Lesson 5 introduced JWT. JWT is great. JWT is also, by default, stateless — and that's the problem.

The pure-JWT problem

A signed JWT is a printed boarding pass. Once issued, it is valid until expiry. The server never asked Redis “is this token still good?” — it just verified the signature and the timestamp. Whoever holds the pass walks through.

Now imagine: 9:00 AM, an employee is fired. 9:01 AM, IT disables their account. 9:02 AM, that employee — with the JWT they got at 8:45 — downloads the entire customer list. The signature is still valid. The expiry hasn't hit. Pure JWT cannot stop them.

The fix is the airport's do-not-fly list. The boarding pass is still printed and still valid-looking. But security has a live list at the desk that they check against, every single time. Boarding pass + matching name on the live list = you fly. Boarding pass alone = not enough.

That's stateful JWT. The signature proves the token is authentic. Redis answers “is this user's session still active?” on every request. If the answer is no, you're out — even though your token would happily verify in a vacuum.

The mapping: JWT alone = printed boarding pass. Redis lookup (AuthStateService) = the live do-not-fly list checked at the security desk. Every request checks both.

The real Fohlio AuthStateService

From src/modules/auth/auth-state.service.ts — key methods, paraphrased to fit:

@Injectable()
export class AuthStateService {
  constructor(private readonly redisService: RedisService) {}

  // Active refresh session, keyed by userId. Logout = del. 
  async storeRefreshSession(
    userId: string,
    sessionId: string,
    ttlSeconds: number,
  ): Promise<void> {
    await this.redisService.cacheClient.set(
      `refresh_session:${userId}`,
      sessionId,
      'EX',
      ttlSeconds,
    );
  }

  async hasRefreshSession(userId: string, sessionId: string): Promise<boolean> {
    const active = await this.redisService.cacheClient.get(`refresh_session:${userId}`);
    return active === sessionId;
  }

  // Brute-force defense: lock account after N failed logins.
  async recordFailedLoginAttempt(email: string, lockoutSec: number, max: number) { /* INCR + EX */ }
  async getLockoutTtlSeconds(email: string): Promise<number> { /* TTL */ }

  // One-shot password reset tokens.
  async storePasswordResetToken(email: string, hash: string, ttl: number) { /* SET EX */ }
  async consumePasswordResetToken(hash: string): Promise<string | null> { /* GET + DEL */ }
}

Three live state machines live in Redis: active refresh sessions, account lockouts, and one-shot reset tokens. Each of them is something a stateless JWT cannot do.

Pure JWT vs stateful JWT, side by side

One extra Redis hit per request. In exchange: an off switch you can pull at any time.

Real-world scenarios this enables: employee fired (delete the refresh session, all their tokens stop working on next request); password changed (rotate the session id, every device must re-login); suspicious activity detected (set a lockout key, block logins for N minutes); plan downgraded (clear cached permissions); brute-force protection (count failed logins in Redis with a TTL). None of these are possible with pure JWT.

The cost: one extra Redis round-trip per authenticated request. Redis is sub-millisecond on the same machine, ~1ms across a VPC. That is a price we cheerfully pay.

🤔 Predict before reading on
Pure JWT, no Redis. An employee is fired at 9:00 AM. Their access token expires after 15 minutes; their refresh token after 7 days. How long can the fired employee keep accessing the system?
15 minutes minimum (the access token still works). Up to 7 days if they keep refreshing. With stateful JWT and a single Redis DEL: zero seconds.

Part 4: Socket.IO at Scale — the RedisIoAdapter

Lesson 9 introduced WebSocket gateways. They work great — on one Node process. The moment you scale to N instances behind a load balancer, the in-memory connection map fragments. Instance A knows about its sockets. Instance B knows about its sockets. Neither knows about the other's.

Result: a notification emitted from instance A reaches half your users. The other half are connected to instance B and see nothing. “It works on my laptop” — because on your laptop there's only one instance.

💻
Dev: “The realtime feature works perfectly!”
QA: “On staging, half the messages don't arrive.”
Dev: “Strange, works on my machine.”
DevOps: “Staging has 3 replicas. Your machine has 1.”
Dev: “...”
Single-process Socket.IO is a lie that scales right up to your first replica.

The fix: airport-wide PA system

The airport doesn't have separate announcements for each terminal — that would be chaos. There's one PA system, one signal, broadcast everywhere. RedisIoAdapter is that PA system for Socket.IO. Every emit goes to Redis pub/sub. Every instance subscribes. Every instance receives. Every connected client hears the announcement, no matter which instance they're on.

Here's Fohlio's adapter — src/common/adapters/redis-io.adapter.ts:

import { type INestApplication } from '@nestjs/common';
import { IoAdapter } from '@nestjs/platform-socket.io';
import { type Server, type ServerOptions } from 'socket.io';
import { createAdapter } from '@socket.io/redis-adapter';
import { RedisService } from '../../modules/redis/redis.service.js';

export class RedisIoAdapter extends IoAdapter {
  private adapterConstructor: ReturnType<typeof createAdapter>;
  private readonly redisService: RedisService;

  constructor(app: INestApplication) {
    super(app);
    this.redisService = app.get(RedisService);
  }

  connectToRedis() {
    this.adapterConstructor = createAdapter(
      this.redisService.publisherClient,
      this.redisService.subscriberClient,
    );
  }

  createIOServer(port: number, options?: ServerOptions): Server {
    const server = super.createIOServer(port, options) as Server;
    server.adapter(this.adapterConstructor);
    return server;
  }
}

Two Redis clients: a publisherClient (publishes events) and a subscriberClient (listens for events from other instances). The Socket.IO Redis adapter wires them into the Socket.IO server. Done. The wiring in main.ts:

function bootstrapRedisAdapter(app: INestApplication) {
  const adapter = new RedisIoAdapter(app);
  adapter.connectToRedis();
  app.useWebSocketAdapter(adapter);
}

Topology

The Redis adapter turns N independent Socket.IO servers into one logical server

Real-world example: Fohlio's collaborative project items. Two users editing the same project from different browsers may land on different Node instances behind the load balancer. When user A saves a change, the WebSocket gateway emits item.updated. Without the Redis adapter, only users on instance A see the update. With it, every connected user sees it within milliseconds — collaborative editing, live notifications, presence indicators all become possible.

Authentication on the WebSocket side

One subtle thing about Fohlio's setup: the same JwtAuthGuard handles both HTTP and WebSocket auth. The guard sniffs the context type:

private extractRawToken(context: ExecutionContext): string | null {
  switch (context.getType()) {
    case 'http':
      return this.handleHttpRequest(context.switchToHttp().getRequest());
    case 'ws':
      return this.handleWsRequest(context.switchToWs().getClient());
    case 'rpc':
      return null;
  }
}

private handleWsRequest(socket: Socket): string | null {
  return socket.handshake?.auth?.token as string | null;
}

HTTP grabs the token from Authorization: Bearer .... WebSocket grabs it from the handshake's auth.token. Same identity flow, two transports. The decoded payload then lands either on request.user (HTTP) or client.data.user (WS), and the same @CurrentUser() decorator gives gateway methods their typed user payload.

Production gotcha: Socket.IO with RedisIoAdapter changes one critical assumption. With a single instance, the socket connection state is local memory — you can store user-to-socket mappings in a Map in the gateway. With Redis adapter, those maps fragment across instances. To target a specific user, use Socket.IO rooms (socket.join(\`user:\${userId}\`)) and emit to the room (server.to(\`user:\${userId}\`).emit(...)) — the adapter routes to whichever instance holds that user.

Part 5: The Worker — A Separate Building Across the Runway

In Lesson 8 we taught BullMQ. The natural question: where do those queue consumers actually run? Same Node process as the API? Same module? Some teams do exactly that. Fohlio doesn't — and the reason is architectural, not aesthetic.

The maintenance hangar at a major airport is a different building. It's across the runway. It has its own electricity, its own fire suppression, its own staff schedule. Why? Because you don't want a tire repair to take down the passenger terminal. And a maintenance crew needs different equipment, different shifts, different scaling than gate agents.

Same airport, same flights served, but a separate building. That's the worker process at Fohlio. The API process is the terminal — it serves passenger requests fast, scales by traffic. The worker process is the hangar — it processes background jobs, scales by queue depth, can be restarted independently without dropping a single HTTP request.

The mapping: Worker process (src/worker/) = the maintenance hangar across the runway. Same airport, same data, but its own building, its own crash domain, its own scaling profile.

Two entrypoints, one codebase

Fohlio's repo has two Node entrypoints. Look at package.json — the scripts give it away:

Two binaries, same repo, same dependencies. Each spins up its own NestJS application. The worker entrypoint, in full — src/worker/worker.ts:

import { NestFactory } from '@nestjs/core';
import { WorkerModule } from './worker.module.js';

async function bootstrap() {
  const worker = await NestFactory.create(WorkerModule);
  await worker.listen(process.env.WORKER_PORT ?? 3001);
}

await bootstrap();

Nine lines. Different root module (WorkerModule instead of AppModule), different port, no Swagger, no global guards for HTTP routes — because there are no HTTP routes. From src/worker/worker.module.ts:

@Module({

The worker imports only what its consumers need. MailConsumer and SyncCacheFanoutConsumer live in src/worker/consumers/ — they're regular BullMQ @Processor classes (Lesson 8 material), just registered in this separate module instead of in AppModule.

Same process vs separate process

🍽️
Same process
Easy in dev. Painful in prod.
One npm start. Easier to debug. But: a slow PDF job blocks event loop → HTTP latency spikes. A worker memory leak crashes the API. You scale workers by buying more API instances.
🏭
Separate process
Two binaries. Two scaling axes.
Independent crash domain. Scale by queue depth, not API traffic. Different memory limits. Restart workers anytime — not a single HTTP request dropped. Two entrypoints to maintain; worth it.

Insight: this is the practical 80% of “microservices” without any of the cost. Same repo, same deploy pipeline, same team owns both binaries. You get independent scaling and crash isolation — the actual benefits of microservices — without service discovery, gRPC contracts, distributed tracing complexity, or duplicate boilerplate. Most teams who think they need microservices actually need this.

✋ Self-test
A long-running PDF generation job is stuck for 30 seconds. What happens to a user trying to GET /projects at the same time, in each setup?

(a) Single-process API + workers. (b) Separate API process and worker process.
(a) The HTTP request waits behind the blocked event loop — or fails the load balancer's health check. (b) The HTTP request returns in 50ms, oblivious to the worker's struggles.

Two consumers, both BullMQ @Processor classes:

src/worker/ ├── worker.ts ← entrypoint, NestFactory.create(WorkerModule) ├── worker.module.ts ← only the modules consumers need └── consumers/ ├── mail.consumer.ts ← sends transactional emails via Postmark └── sync-cache-fanout.consumer.ts ← recomputes catalog cache when items change

The API process enqueues a job (queue.add('mail.invitation', {...})). The job sits in Redis. Whichever worker instance is free picks it up, runs the consumer, marks the job done. The API never knew. The worker can be restarted, deployed, scaled, debugged, OOM-killed and replaced — the API keeps serving 200s the entire time.

Operational reality: in production, Fohlio runs the API and the worker as separate Kubernetes deployments. The API has tighter memory limits but more replicas (HTTP traffic is bursty). The worker has higher memory limits but fewer replicas (jobs are CPU/RAM-heavy but throughput is steadier). They share the same Redis, the same Postgres, the same secrets — but they are scheduled, monitored, and scaled independently. That's the architectural payoff for the extra main.ts.

Part 6: Sentry Before Bootstrap, Helmet, Swagger, ValidationPipe

The last piece is the order of operations in main.ts. It's deceptively important. Get the order wrong and the airport opens before the radios turn on.

Sentry first — before everything

Look at the very first line of src/main.ts:

import './instruments.js';

import { NestFactory } from '@nestjs/core';
// ...everything else

That side-effect import comes from src/instruments.ts:

import * as Sentry from '@sentry/nestjs';
import { config } from 'dotenv';

config();

if (process.env.SENTRY_DSN) {
  Sentry.init({
    dsn: process.env.SENTRY_DSN,
    sendDefaultPii: true,
  });
}

Sentry has to initialize before the modules it instruments are loaded. If you initialize Sentry on line 50, and NestFactory imports a module on line 30, the modules on line 30 won't have any of Sentry's hooks — their errors will silently disappear.

The incident response team turns on its radios before the airport opens for business, not after the first crash. If a plane lands and there's a problem at 6:00 AM but radios don't come on until 6:05, those five minutes of incidents are invisible. Same with Sentry — the import order is the on-switch for the radios.

The mapping: import './instruments.js' as the first line of main.ts = the incident response team turning on radios before opening the airport.

The full bootstrap order

From src/main.ts — what runs and in what order:

import './instruments.js';                    // 0. Sentry FIRST

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  const configService = app.get(ConfigService);

  bootstrapSecurity(app, configService);          // 1. Helmet
  bootstrapCors(app, configService);              // 2. CORS allowlist

  app.use(json({ limit: bodyLimit }));            // 3. Body limit
  app.use(urlencoded({ extended: true, limit: bodyLimit }));

  app.enableVersioning({ type: VersioningType.URI }); // 4. /v1/...

  app.useGlobalPipes(new ValidationPipe({         // 5. Validation
    transform: true,
    whitelist: true,
    forbidNonWhitelisted: true,
  }));

  if (configService.get('SWAGGER_ENABLED') === 'true') {
    await bootstrapSwagger(app);                  // 6. /docs (optional)
  }

  bootstrapRedisAdapter(app);                       // 7. Socket.IO + Redis

  await app.listen(configService.get('PRIMARY_PORT') ?? 3000);
}

await bootstrap();

What each piece does

Helmet — with one important caveat

// from main.ts bootstrapSecurity()
app.use(helmet({
  contentSecurityPolicy:
    configService.get('SWAGGER_ENABLED') === 'true'
      ? false                // CSP off when Swagger is mounted
      : { directives: cspDirectives },
  crossOriginEmbedderPolicy: false,
}));

Helmet sets a battery of security headers (X-Content-Type-Options, Strict-Transport-Security, etc.). The Swagger UI uses inline scripts — CSP would block them and the docs page would render broken. Solution: turn CSP off only when Swagger is enabled (typically dev/staging). In production, Swagger is off and CSP is on.

ValidationPipe — the three flags that matter

new ValidationPipe({
  transform: true,             // raw plain objects → typed DTO instances
  whitelist: true,             // strip fields not in DTO
  forbidNonWhitelisted: true,  // 400 if extra fields are sent
})

Three flags. transform means @Body() arrives as an actual CreateProjectDto instance, not a plain object. whitelist drops anything not declared in the DTO. forbidNonWhitelisted goes further: if the client sends an extra field, reject the request with a 400. This is Lesson 6 in production form.

Swagger — with the @ApiBearerAuth dance

// from main.ts bootstrapSwagger()
const options = new DocumentBuilder()
  .setTitle('SpecHub API')
  .setVersion('0.1.0')
  .addBearerAuth()
  .build();
await SwaggerModule.loadPluginMetadata(metadata);
const document = SwaggerModule.createDocument(app, options, {
  deepScanRoutes: true,
});
SwaggerModule.setup('docs', app, document);

addBearerAuth() tells Swagger UI to show the “Authorize” button. Endpoints decorated with @ApiBearerAuth() automatically have the lock icon and use the entered token. loadPluginMetadata + deepScanRoutes picks up DTO types from the SWC plugin's metadata file — without this you get tons of any in the generated schema.

The order is non-trivial. Sentry must come before NestFactory.create — otherwise instrumentation hooks miss the modules being loaded. Helmet must come before route handlers — otherwise some headers don't make it onto the responses. ValidationPipe must be installed before app.listen — otherwise the first second of traffic skips validation. Most of these are silent failures: nothing crashes, things just don't work as intended. Verify by reading the boot logs and checking response headers.

CORS, body limits, and URL versioning

Three smaller pieces from the same main.ts that show how production hardening composes:

// CORS allowlist from a comma-separated env var.
// Bearer auth = no cookies = credentials:false (no preflight surprises).
const frontendUrls = (configService.get('FRONTEND_URL') ?? '')
  .split(',')
  .map((s) => s.trim())
  .filter(Boolean);
app.enableCors({
  origin: frontendUrls.length > 0 ? frontendUrls : false,
  credentials: false,
  methods: ['GET', 'POST', 'PATCH', 'PUT', 'DELETE', 'OPTIONS'],
});

// Uploads go direct to S3 via presigned URLs — API bodies stay small.
const bodyLimit = configService.get('BODY_SIZE_LIMIT') ?? '1mb';
app.use(json({ limit: bodyLimit }));
app.use(urlencoded({ extended: true, limit: bodyLimit }));

// All routes are versioned: /v1/workspaces/...
app.enableVersioning({ type: VersioningType.URI });

Three production lessons embedded in twelve lines. (1) CORS is an explicit allowlist read from config; never origin: '*' in production. (2) Body limit is small (1mb default) because file uploads bypass the API entirely — the frontend gets a presigned S3 URL and uploads directly. The API never carries multi-megabyte bodies. (3) URL versioning (/v1/...) is on from day one, so when the inevitable v2 redesign comes, you can run both versions side-by-side without breaking existing clients.

The Express 5 quirk Fohlio hit

// Express 5 defaults query parser to 'simple' (flat keys only).
// We rely on bracket-nested query params (e.g. filter[slug][value]=X) — use 'extended' (qs).
(app.getHttpAdapter().getInstance() as Express).set(
  'query parser',
  'extended',
);

This is the kind of one-liner that doesn't appear in any tutorial but matters in production. Express 5 changed its default query parser to a stricter, simpler one. Fohlio's filter DSL uses bracket-nested keys (think ?filter[status][eq]=active). Without this single set('query parser', 'extended'), every filtered list endpoint silently breaks. The kind of bug that only surfaces in the third bug-bash session before launch.

Pattern to internalize: production-grade main.ts files are boring — ten or fifteen utility calls in a precise order, each fixing a specific operational concern. There's no clever code here. There's just experience compressed into bootstrap order. When you read a Fohlio-style main.ts, every line is a postmortem.

Twelve lessons ago we walked into an empty hangar and asked: why do we need a framework at all?

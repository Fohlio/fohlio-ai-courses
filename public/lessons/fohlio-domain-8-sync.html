Why a Spec Rots

Chapter 8. How Fohlio catches the discontinued finish before it costs $40k

7:14 a.m. Dana Reyes is back at the same desk, the same mug of coffee going cold, the same cursor blinking. From the outside it looks like every other Tuesday morning at the studio. Inside Dana’s head it is the particular silence she gets before a big project moves into procurement — the pause just before a lot of money gets committed on paper.

The Marriott spec has been alive for eight months. Four days before Marco sends the purchase order, an icon appears next to one of the lobby chair line items. Orange. Dana hovers over it.

“Finish Camel Latte has been discontinued by the supplier. Closest available replacement: Desert Sand (similar, not identical). Item sync state: broken.”

She stares at the orange icon for a moment. Eighteen months ago there was no icon like this. The line item sat in the spec and said nothing, while the finish quietly disappeared from the supplier’s catalog. The PO went out. Sixty chairs arrived at the warehouse in the wrong color. The rework invoice was roughly forty thousand dollars and a month’s slip in schedule.

Today Dana clicks “Replace,” picks an approved alternative, and updates the spec in under three minutes. Marco’s PO goes out clean. The mistake that defined the first chapter of this course — the one that opened Lesson 1 — does not happen. This chapter is the explanation of how.

Part 1. Why a spec goes stale without anyone touching it

Every line item in a project is not a copy of catalog data. It is a reference. The slot stores a catalogFamilyId (and optionally a catalogItemId), and through that reference it resolves the finish, photo, dimensions, and price from the catalog at query time. Smart design: a single edit in the catalog propagates everywhere immediately [4].

The problem is exactly that the catalog is alive. A manufacturer quietly retires a finish. A supplier drops a SKU from their price list. Helen updates a family description. Dana adds a new variant for another client. All of these events happen asynchronously relative to every open project — no notification, no “are you sure?” While the Marriott spec was going through client approvals, while the budget was being negotiated in phase 3, and while Marco was gathering quotes for the RFQ (covered in Lessons 6 and 7), the catalog changed several times over [2].

That is exactly what happened eighteen months ago. The Camel Latte finish vanished from the supplier’s catalog during a period when the project was parked on a client approval queue. The spec did not know. The PO went out with stale data.

A spec isn’t a document. It’s a database that happens to know how to print itself on paper.

Because the spec is a database — not a snapshot — it must also know when its source changed. Otherwise it collapses back into a document: beautiful, formatted, and quietly wrong.

Part 2. Four sync states

Every project line item carries a syncState — a cached result of the last comparison against the catalog. Fohlio tracks four possible values [4].

✨
new
Item added manually or from a project; no catalog family linked yet. Neutral — not stale, not synced.
✅
ready
Item matches the catalog. Data is consistent. Safe to include in a PO.
⚠️
updates
Catalog has new data not yet applied to this item. The reference is still live; user decides whether to pull.
❌
broken
Reference resolves to nothing — family or variant deleted or discontinued. Requires a human decision to fix.

The key implementation detail: syncState is a computed cache, evaluated on demand, not a persisted field updated by catalog triggers. Fohlio recalculates it when a project is opened or when the sync service is explicitly called. This is a deliberate tradeoff: instead of firing on every catalog write — which would hammer the database proportionally to the number of open projects — the system does lazy evaluation at read time [4].

Under the hood — SyncStateCache: the item object carries three derived booleans — hasDiff, orphanedRefs, and componentsDiverged. Their combination determines the final syncState. hasDiff = true → updates. orphanedRefs = true → broken. Both false → ready.

States new → ready → updates → broken with pull / push / replace transitions. Dashed arrows are rare edge cases.

Part 3. Pull, push, and replace — three different answers to drift

When a user sees a warning on a line item — updates or broken — there are three distinct operations available. The names rhyme with Git, and the similarity is not accidental: the logic is the same, but the direction is specific to this domain.

⇓ Pull — bring catalog updates into the project item
The catalog changed (updated description, new finish option, corrected price) and the user wants to absorb those changes into the project. The item is overwritten with catalog data. Used when state is updates. The reference stays the same; only the resolved values change.
⇑ Push — save item edits back to the catalog
Dana refined a line item in the project — added a custom dimension, corrected a finish code — and wants that refinement to become part of the firm’s shared library. Push transfers the project item’s data back into the catalog. Requires catalog_edit permission; Helen controls who has it.
⇄ Replace — swap the product in the slot for a different one
The reference is broken — the finish was discontinued, the family deleted. Pull does nothing because there is nothing left to pull. Replace lets the user pick a different family or variant from the catalog. This is exactly what Dana did with the Desert Sand option: the reference changed from a dead end to a live one, and the state flipped back to ready.

Priya (staring at the three buttons): “Wait — pull takes from catalog into the project, push sends from project to catalog. That’s backwards from Git.”

Part 4. Orphaned references — the quiet $40k

An orphaned reference is a link that goes nowhere. The item stores catalogItemId = "abc-123", but that variant no longer exists in the catalog. Not updated — gone. That is the distinction that separates updates from broken.

Orphaned refs are dangerous precisely because of their silence. Until the sync recalculation runs, the item looks completely normal on screen. The last-known values — finish name, photo, dimensions, price — are still displayed. Everything looks fine. But those values are an archive, not the truth [4].

That is what killed Dana eighteen months ago. The Camel Latte finish became orphaned somewhere during the third week of the approval queue. The sync recalculation never ran before the PO was sent. The supplier filled the order with the closest available alternative. Sixty chairs arrived at the warehouse in the wrong color.

Three common paths to an orphaned ref:

1 Variant deleted from the catalog
Supplier retired a SKU. Helen removed it from the library. Project items that linked to it now reference a void — the catalogItemId resolves to nothing.
2 Family restructured or re-keyed
The catalogFamilyId changed during a catalog reorganization. Old references from projects point at a key that no longer exists.
3 Parts / BOM drift
An item references sub-components (Parts) that have themselves changed in the catalog. The componentsDiverged flag catches this separately from the parent item’s own hasDiff. (Recall from Lesson 3: a CatalogFamily can carry sub-component families that are themselves versioned.) [3]

Sync proposals are the system’s attempt to shorten the recovery path. When a product similar to a broken item appears in the catalog — same supplier, similar finish code, related SKU — Fohlio can automatically surface it as a suggested replacement. One click to confirm or dismiss, instead of manually hunting through the full catalog library.

Part 5. Optimistic concurrency — when two people edit the same item

On the Marriott project, Dana and Priya are both in the spec at the same time. Dana opens item 3141 — a lobby chair — and changes the finish. Priya, in a different browser tab, changes the quantity on the same item. Without any protection, whichever save arrives second silently overwrites the first.

Fohlio uses optimistic concurrency: every object carries a version field. When a user opens an item, they receive its current version — say, version = 14. On save, the client sends version = 14 along with the change. The server checks: if the database currently holds version = 14, it writes the update and increments to 15. If the database already holds version = 15 (someone else saved first), it returns HTTP 409 Conflict [4].

// Client sends the version it opened with
PATCH /v1/workspaces/:wsId/projects/:pId/items/:itemId
{
  "version": 14,
  "finish": "Desert Sand"
}

// If the DB is already at version=15 → server responds:
HTTP 409 Conflict
{
  "error": "version_conflict",
  "current_version": 15
}

On a 409, the client is responsible for re-fetching the current state, showing the user the conflict, and letting them decide how to merge. No silent overwrites. The same mechanism protects catalog records when two projects push different edits to the same family concurrently.

Why optimistic? Because the system assumes conflicts will be rare — and does not pessimistically lock objects when they are opened. On a 600-room Marriott project, five people may be editing simultaneously; most of their changes don’t touch the same rows. Optimistic locking keeps throughput high and only penalizes real collisions.

Part 6. Three clients, one sync engine

The sync engine is a single subsystem. What it means to each of the three clients is completely different. This is the “Three clients, one concept” beat — the same beat that runs through every chapter of this course.

Marriott — 600 rooms, one standard. Linda approves a brand-standard update: new upholstery on the lobby chairs across the entire chain. Helen edits the catalog family. The sync engine computes updates on every one of the affected items across all 600 rooms. Dana triggers a bulk pull — all rooms update in a single operation. Without Fohlio that would be 600 manual edits in a spreadsheet. With Fohlio it is one button [2].

Engineering note: bulk pull is a batch operation that applies the same catalog diff to N items in a single request. Optimistic concurrency applies per object — on any individual 409, the batch reports the conflicting items rather than rolling back entirely.

The Church of Jesus Christ — one kit, thousands of buildings. Brother Andersen approves a new furniture supplier for the meetinghouse standard — 12% cheaper. The catalog source is updated on the chair family. Every project referencing that family picks up updates. When those projects pull, the new price flows in and the budget recalculates automatically across each building’s spec. That is what stewardship of donated funds looks like at a technical level [1].

Grace — the garage instead of a procurement department. Grace doesn’t watch catalog update notifications. There is no Helen to manage her library, no Marco to catch lead times. That is exactly why the sync engine matters more for her than for either enterprise client: she has no bandwidth to manually monitor discontinuations. The orange broken icon is her only safety net. It exists — this is the design decision behind it — because smaller operators are the ones who cannot afford to discover the problem at the warehouse [3].

Chapter summary

Today the loop that opened in Chapter 1 closes. The sync engine isn’t a feature layered on top of the domain. It is the answer to the domain’s fundamental property: the spec is a live database, and the catalog is its source of truth. When the source moves faster than the project reaches procurement, you need a mechanism that catches the divergence before it becomes a dollar amount.

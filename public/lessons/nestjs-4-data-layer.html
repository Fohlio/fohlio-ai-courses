Part 1: From Memory to Database

Open the FlightsService you built in Lesson 2. Somewhere in there is a line that looks like this:

private flights: Flight[] = [];

That's a Node.js array. It lives in the process's memory. The moment you stop the server — or the server crashes, or you deploy a new version, or your laptop reboots — every flight you ever created is gone. Forever. Unrecoverable.

This is fine for a demo. It is catastrophic for anything real. The first thing every production API needs is a place to put data that survives the process.

💥
Junior: “The flights endpoint works perfectly in dev!”
Senior: “Cool. Restart the server.”
Junior: “...okay, restarted.”
Senior: “Now hit GET /flights.”
Junior: “It returns an empty array. Why is it empty?”
Because RAM is not a database. Welcome to backend.

What “persistence” actually means

A database is a separate process — usually on a separate machine — that holds your data on disk and gives you a network protocol to query it. Your Node.js app talks to it over TCP. When your app restarts, the database doesn't care. It just sits there, holding everything.

The most common database for application backends is PostgreSQL. It's open source, battle-tested, free, and supports basically every feature you'll ever need. Throughout this course, we'll use Postgres. The lessons translate directly to MySQL, SQLite, or any other SQL database — the ORM hides the differences.

Back to the airport. Every flight, every passenger, every gate assignment, every baggage tag — all of that has to be written down somewhere that survives shift changes, power outages, and the occasional renovation. That somewhere is the airport's central records archive.

The archive is its own building. Has its own staff. Has its own filing system. Gate agents don't walk into the archive and rummage through cabinets — that would be slow, error-prone, and probably illegal. Instead, there's a records clerk who knows exactly how to file something, how to retrieve it, how to update it without losing the rest of the file. Gate agents just say "give me passenger X" and the clerk hands them the right folder.

The mapping: Database = the archive (PostgreSQL, the building that holds everything). ORM = the records clerk (Prisma, who knows how to file and retrieve). Schema = the filing system itself (which cabinet holds what). Migration = renovating the cabinets without losing the files.
🤔 Guess before reading on
Without an ORM, your service would have to write SQL strings by hand — something like SELECT * FROM flights WHERE id = $1. Name two things that can go wrong with this approach. (Hint: think about what happens when a junior dev names a column wrong, or when the request body has an apostrophe in it.)
Part 2 will list more reasons. But the two you came up with are probably the top two.

Part 2: Why You Need an ORM

An ORM — Object-Relational Mapper — is a library that turns SQL queries into method calls and rows into typed objects. Instead of writing strings of SQL, you write TypeScript:

// Without an ORM (using node-postgres directly)
const result = await client.query(
  'SELECT * FROM flights WHERE destination = $1 AND gate = $2',
  [destination, gate]
);
const flights = result.rows; // any[]. No types. Welcome to runtime errors.

// With Prisma
const flights = await prisma.flight.findMany({
  where: { destination, gate },
}); // Flight[] — fully typed, autocomplete, compile-time check

The pain of raw SQL, in detail

💀
Raw SQL
Strings everywhere
Typos surface at runtime. Column renames break code silently. SQL injection is one missed parameter away. Result rows are any. No autocomplete. No refactor support.
📑
Prisma
Schema is the source of truth
One schema.prisma file generates a typed client. Column rename = compile error in every place that referenced it. Parameters are bound automatically — no injection. Autocomplete on every query.

Real-world horror story: A junior dev renamed users.email to users.email_address in a Postgres migration. The team was using raw SQL. Nothing crashed at startup. The login endpoint just silently returned 401 for every user for two hours, because the auth query referenced email which no longer existed. With Prisma, that rename would have been caught at tsc time.

What an ORM actually does for you

📐
Type safety
Schema → generated types. Every query result is shaped. flight.destinaton won't compile.
🔐
Parameter binding
No string concatenation. SQL injection is impossible by construction.
🔀
Migrations
Schema changes are diffed and turned into reversible SQL files. No more "did anyone run this on staging?"
🔗
Relations
Joins become include: { airline: true }. The result is correctly typed as Flight & { airline: Airline }.
🔍
Query introspection
Log every query Prisma generates. Spot N+1 problems early. Tune indexes with confidence.

Which ORM — the NestJS landscape

NestJS is ORM-agnostic. The framework just gives you DI; what you put inside an @Injectable() service is your choice. Three serious options:

ORM Style When you'd pick it
Prisma Schema-first, generated client You want maximum type safety, minimum boilerplate, and great DX. Default choice for new projects in 2026.
TypeORM Decorator-based entities, ActiveRecord or DataMapper You like Java/Spring style. Heavy use of inheritance. Need niche DB features Prisma doesn't expose yet.
MikroORM Identity Map / Unit of Work (Hibernate-style) You're coming from Doctrine/Hibernate and want that exact mental model. Less common.

This lesson uses Prisma. It's what most new NestJS projects pick today, and it's what you'll see in 9 out of 10 NestJS job postings. We'll touch TypeORM at the end so you recognise it.

Part 3: Setting Up Prisma

Three commands and one config file. That's the whole setup.

Step 1: Get a Postgres running

The fastest way to get Postgres on your machine is Docker. Drop this docker-compose.yml at the root of airport-api:

# docker-compose.yml
version: '3.9'
services:
  db:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: airport
      POSTGRES_PASSWORD: airport
      POSTGRES_DB: airport
    ports:
      - '5432:5432'
    volumes:
      - db-data:/var/lib/postgresql/data
volumes:
  db-data:
docker compose up -d
# → postgres listening on localhost:5432

Don't have Docker? Postgres.app on macOS, the official installer on Windows, or your distro's package manager on Linux all work. The connection URL changes; everything else in this lesson is identical.

Step 2: Install Prisma

npm i -D prisma
npm i @prisma/client

# scaffold prisma/ directory and a .env file
npx prisma init

npx prisma init creates two things:

airport-api/ ├── prisma/ │ └── schema.prisma ← your schema lives here ├── .env ← DATABASE_URL goes here └── ...

Open .env and set:

DATABASE_URL="postgresql://airport:airport@localhost:5432/airport?schema=public"

Step 3: Define the schema

Open prisma/schema.prisma and replace its contents with this:

// prisma/schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model Airport {
  id      Int      @id @default(autoincrement())
  code    String   @unique // JFK, LAX, SFO
  name    String
  city    String
  country String
  flights Flight[]          // reverse relation
}

model Flight {
  id          Int      @id @default(autoincrement())
  number      String   @unique           // "BA178"
  destination String
  gate        String?
  departsAt   DateTime
  airportId   Int
  airport     Airport  @relation(fields: [airportId], references: [id])
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@index([airportId])
}

The schema.prisma language is its own thing — not TypeScript, not SQL. It's declarative: you describe what your data looks like and Prisma generates everything else. Read it top to bottom: a Flight has an id, a number, a destination, an optional gate, departure time, and a foreign key to Airport. The airport field on Flight isn't a column — it's the typed relation Prisma will let you include in queries.

Notice: gate String? — the question mark means optional/nullable. departsAt DateTime with no question mark means required. This is the entire null-safety story in your data layer, in one character.

Step 4: Run the first migration

npx prisma migrate dev --name init

This single command does four things:

1 Diffs your schema against the database
DB is empty, schema has 2 models. Diff = "create both tables."
2 Generates a SQL migration file
Drops it in prisma/migrations/<timestamp>_init/migration.sql. Commit this to git.
3 Applies the migration
Runs the SQL against your local database. Tables now exist.
4 Regenerates the typed client
Updates node_modules/.prisma/client with the latest types. Your TypeScript now knows about Flight and Airport.
One command, four side effects, all reversible. Schema → SQL → DB → typed client.

Open prisma/migrations/<timestamp>_init/migration.sql. You'll see the actual SQL Prisma generated — CREATE TABLE, foreign key constraints, indexes. This is the file your DBA reviews in a PR. Prisma is just a generator; the real artifact is SQL, in git, plain to read.

Why a migration file matters: In a team, "how does staging's schema differ from prod's?" is a question you must be able to answer instantly. With migration files in git, the answer is "diff the migrations folder between the two branches." Without them, the answer is "I don't know, let's pray."

Part 4: PrismaService — The NestJS Way

Prisma's docs show you this:

import { PrismaClient } from '@prisma/client';
const prisma = new PrismaClient();
// use prisma.flight.findMany() etc

This works. Don't do it in a NestJS app. If you scatter new PrismaClient() across files, you create multiple connection pools, you have no lifecycle hooks, you can't mock it in tests, and you've broken the entire DI promise. Instead, wrap it in an injectable service exactly once.

Generate the module and service

nest g module prisma
nest g service prisma

Open src/prisma/prisma.service.ts:

import { Injectable, OnModuleInit, OnModuleDestroy } from '@nestjs/common';
import { PrismaClient } from '@prisma/client';

@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy {

  async onModuleInit(): Promise<void> {
    await this.$connect();
  }

  async onModuleDestroy(): Promise<void> {
    await this.$disconnect();
  }
}

Three things to notice:

1 extends PrismaClient
Your service is a PrismaClient. Every method (flight, airport, $transaction) is inherited. You're not wrapping — you're labelling.
2 OnModuleInit → connect on startup
Nest calls onModuleInit() after the DI graph is built but before requests start flowing. Connection failures crash the app at startup — not at the first request.
3 OnModuleDestroy → clean shutdown
When Nest tears down (SIGTERM during a deploy, for example), connections close cleanly. No orphan connections piling up on Postgres.

Now src/prisma/prisma.module.ts:

import { Module } from '@nestjs/common';
import { PrismaService } from './prisma.service';

@Module({
  providers: [PrismaService],
  exports: [PrismaService], // ← critical: lets other modules inject it
})
export class PrismaModule {}

exports is what tells Nest "any module that imports PrismaModule can inject PrismaService." Forget it, and you'll get a "PrismaService is not in the current module's scope" error at startup.

Wire it into AppModule

// src/app.module.ts
import { Module } from '@nestjs/common';
import { PrismaModule } from './prisma/prisma.module';
import { FlightsModule } from './flights/flights.module';

@Module({
  imports: [PrismaModule, FlightsModule],
})
export class AppModule {}

Back to the airport. Why don't gate agents each have their own private records clerk hidden under the desk? Because then ten gate agents would each be opening, holding, and closing their own connection to the archive at the same time — the archive's loading dock would jam, sessions would leak, and nobody would know who's actually talking to it.

Instead, the airport employs one records clerk per shift, available to every gate agent who needs a file. The clerk arrives before the first flight (onModuleInit), works for every agent that asks (injection), and clocks out when the airport closes (onModuleDestroy).

That's the singleton pattern, expressed by NestJS DI. One PrismaClient instance, one connection pool, lifecycle managed by the framework, available to every service that asks for it.

Part 5: Replacing the In-Memory Store

Time to delete that array. Open src/flights/flights.service.ts. Here's the before:

// BEFORE — Lesson 2's in-memory version
@Injectable()
export class FlightsService {
  private flights: Flight[] = [];

  findAll() { return this.flights; }
  create(dto: CreateFlightDto) {
    const flight = { id: Date.now(), ...dto };
    this.flights.push(flight);
    return flight;
  }
  // ...
}

And here's the after:

// AFTER — Prisma-backed
import { Injectable, NotFoundException } from '@nestjs/common';
import { PrismaService } from '../prisma/prisma.service';
import { CreateFlightDto, UpdateFlightDto } from './dto';

@Injectable()
export class FlightsService {
  constructor(private readonly prisma: PrismaService) {}

  findAll() {
    return this.prisma.flight.findMany({
      orderBy: { departsAt: 'asc' },
    });
  }

  async findOne(id: number) {
    const flight = await this.prisma.flight.findUnique({
      where: { id },
      include: { airport: true },
    });
    if (!flight) throw new NotFoundException(`Flight ${id} not found`);
    return flight;
  }

  create(dto: CreateFlightDto) {
    return this.prisma.flight.create({ data: dto });
  }

  update(id: number, dto: UpdateFlightDto) {
    return this.prisma.flight.update({
      where: { id },
      data: dto,
    });
  }

  remove(id: number) {
    return this.prisma.flight.delete({ where: { id } });
  }
}

The constructor now takes PrismaService. Every method is one Prisma call. The whole class is shorter than the in-memory version was, and now your flights survive a restart.

Don't forget to import PrismaModule

Open src/flights/flights.module.ts:

import { Module } from '@nestjs/common';
import { PrismaModule } from '../prisma/prisma.module';
import { FlightsController } from './flights.controller';
import { FlightsService } from './flights.service';

@Module({
  imports: [PrismaModule],     // ← so we can inject PrismaService
  controllers: [FlightsController],
  providers: [FlightsService],
})
export class FlightsModule {}

The autocomplete payoff

Hit this.prisma.flight. in your IDE. You'll see findMany, findFirst, findUnique, create, createMany, update, upsert, delete, count, aggregate, groupBy. Every argument is typed. where only accepts the columns Flight actually has. data requires the fields your schema marks as required.

This is what it means for the schema to be the source of truth: change schema.prisma, run prisma migrate dev, and every consumer of the wrong shape lights up red until you fix it.

Part 6: Migrations & Seeding

The three migration commands

Command When What it does
prisma migrate dev Local development Creates a new migration file, applies it, regenerates the client. Will reset the DB if it detects drift.
prisma migrate deploy Staging / production Applies pending migrations only. Never generates new ones, never resets. Safe in CI/CD pipelines.
prisma db push Prototyping only Pushes the current schema directly without creating a migration file. Don't use in real codebases — you lose the audit trail.

Rule of thumb: if a teammate or a CI server will ever run this database, you need migrate dev + migrate deploy. The migration file is the contract. db push is for the first 30 minutes of a hackathon and nothing else.

Seeding — sane defaults for local dev

You don't want every developer to manually POST /flights ten times to have something to look at. Seed the DB instead. Create prisma/seed.ts:

import { PrismaClient } from '@prisma/client';
const prisma = new PrismaClient();

async function main() {
  const jfk = await prisma.airport.upsert({
    where: { code: 'JFK' },
    update: {},
    create: { code: 'JFK', name: 'John F. Kennedy', city: 'New York', country: 'USA' },
  });

  await prisma.flight.createMany({
    data: [
      { number: 'BA178', destination: 'LHR', gate: 'A12',
        departsAt: new Date('2026-05-01T18:00:00Z'), airportId: jfk.id },
      { number: 'AF007', destination: 'CDG', gate: 'B4',
        departsAt: new Date('2026-05-01T20:30:00Z'), airportId: jfk.id },
    ],
    skipDuplicates: true,
  });
}

main().then(() => prisma.$disconnect());

Wire it up in package.json:

"prisma": {
  "seed": "ts-node prisma/seed.ts"
}

Now npx prisma db seed populates a fresh DB with realistic data. prisma migrate dev auto-runs the seed when it resets the database. Onboarding a new dev becomes: git clone && docker compose up -d && npm i && npx prisma migrate dev && npm start.

Seeding is also your test fixture. Same script, different DB URL, before each integration test. We'll come back to that in Lesson 9 (Testing).

Part 7: TypeORM in 60 Seconds

You'll meet TypeORM in older NestJS codebases. The mental model is different — entities are TypeScript classes decorated with @Entity(), columns are decorated with @Column(), and the ORM scans them at runtime.

// flight.entity.ts (TypeORM style)
import { Entity, Column, PrimaryGeneratedColumn } from 'typeorm';

@Entity()
export class Flight {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ unique: true })
  number: string;

  @Column()
  destination: string;
}
// flights.service.ts (TypeORM style)
@Injectable()
export class FlightsService {
  constructor(
    @InjectRepository(Flight) private flightsRepo: Repository<Flight>,
  ) {}

  findAll() { return this.flightsRepo.find(); }
}

Prisma vs TypeORM — the honest comparison

Dimension Prisma TypeORM
Source of truth schema.prisma file TS classes with decorators
Type safety Generated, exhaustive Decent, leaks any in advanced queries
Migrations Built-in, schema-diff based Built-in, but you often write them by hand
Inheritance / polymorphism Limited — not the goal Strong — STI, table-per-class, etc.
Raw SQL escape hatch $queryRaw, well-typed queryBuilder, very expressive
Maturity in 2026 Default for new projects Common in projects that started 2018–2022

When to choose TypeORM: heavy class-inheritance domain models, you need its specific Postgres features (custom types, advanced query builder), or you're maintaining an existing TypeORM codebase. Otherwise, in 2026, default to Prisma.

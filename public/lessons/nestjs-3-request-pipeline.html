Part 1: A Request's Journey Through the Airport

So far we've treated the controller as if requests just — appear in it. They don't. Between the network and your findAll() method, NestJS runs a fixed sequence of stages. Each stage has a job, a clear contract, and the ability to short-circuit the whole thing.

The airport analogy — one more time, with feeling

You walk into the airport. Before you board a plane, you pass through a fixed sequence:

1. Curbside / Entrance. A friendly-but-bored agent maybe checks your boarding pass exists. Logs that you entered. (Middleware.)

2. Security checkpoint. The hard yes/no: do you have a valid ticket and ID for this flight, or are you turned away? (Guard.)

3. Flight recorder starts. An invisible system starts a stopwatch the moment you enter the gate area. It will stop when you board, recording how long the journey took. (Interceptor — before phase.)

4. Baggage X-ray. Your bags get scanned and tagged. Anything malformed gets rejected before it reaches the plane. (Pipe.)

5. The gate agent does the actual work — scans your pass, points to the seat. (Controller / handler.)

6. Flight recorder stops. Stopwatch closes. Maybe the system tags every checked bag with the flight number. (Interceptor — after phase.)

7. Lost & Found Desk. If anything went wrong — missing bag, denied boarding — passengers go here, where the chaos is converted into a polite official answer. (Exception Filter.)

The same flow in code terms: Middleware → Guards → Interceptors (before) → Pipes → Handler → Interceptors (after) → Response. If any stage throws, the request is yanked out of the pipeline and handed to an Exception Filter.

Why so many stages?

Because each one answers a different question:

Stage The question it answers Returns
Middleware“Want to do something raw at the request level?”void + calls next()
Guard“Should this request be allowed in?”boolean
Interceptor (before)“Want to wrap or observe the call?”passes control onward
Pipe“Is the input the right shape?”transformed value (or throws)
Handler“What's the answer?”the response value
Interceptor (after)“Want to massage the response?”final response
Exception Filter“Something exploded — how do we tell the client?”error response

Key idea: Each pipeline stage is the right answer to a different design question. Most bugs in NestJS apps come from picking the wrong stage. Validate input in a Guard? Will work, but you've conflated “allowed?” with “well-formed?”. Format errors in an Interceptor? Will work for happy paths, miss most error cases. The art is matching the question to the stage.

Part 2: Middleware

Middleware is the oldest concept in the pipeline — it predates NestJS by a decade. Express middleware. Connect middleware. Same idea, same signature: (req, res, next) => .... NestJS happily accepts both function-style and class-style middleware.

The signature

// function form
function simpleLogger(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next();
}

Three things are true about middleware:

  1. It runs first, before anything Nest-specific.
  2. It must call next() or the request hangs forever.
  3. It works at the raw HTTP level — you don't yet know which controller will handle this request.

Class-form middleware (the NestJS-y way)

The class form supports DI — you can inject a logger or a config service into your middleware. Here's a logging middleware that times the response:

// src/common/middleware/logger.middleware.ts
import { Injectable, NestMiddleware, Logger } from '@nestjs/common';
import { Request, Response, NextFunction } from 'express';

@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  private readonly log = new Logger('HTTP');

  use(req: Request, res: Response, next: NextFunction) {
    const start = Date.now();
    res.on('finish', () => {
      const ms = Date.now() - start;
      this.log.log(`${req.method} ${req.originalUrl} ${res.statusCode} — ${ms}ms`);
    });
    next();
  }
}

Wiring middleware into the app

Middleware doesn't go in the @Module decorator — it gets registered via the configure() method. The module class implements NestModule:

// app.module.ts
import { Module, NestModule, MiddlewareConsumer } from '@nestjs/common';
import { LoggerMiddleware } from './common/middleware/logger.middleware';

@Module({
  imports: [FlightsModule, UsersModule],
})
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(LoggerMiddleware)
      .forRoutes('*'); // every route, every method
  }
}

You can be more selective with .forRoutes('flights'), .forRoutes({ path: 'flights', method: RequestMethod.GET }), or .exclude(...). For request logging, '*' is the right call.

Aha: Middleware is the only pipeline stage where you write to res directly via the Express object. Every other stage works through Nest's abstractions. That's because middleware is Express — Nest just hands you the raw request and trusts you.

📜
Express dev: “Middleware is everything! Auth? Middleware. Validation? Middleware. Response shaping? Middleware. CORS? Middleware.”
NestJS dev: “...you have five different tools. Use them.”
Express dev: “But middleware works.”
NestJS dev: “A hammer also works on screws.”
Just because you can stuff everything into middleware doesn't mean you should.

Part 3: Guards

A guard answers exactly one question: “Is this request allowed to proceed?” It returns true (let it through), false (deny with 403), or throws an exception (deny with whatever the exception says, e.g. 401).

The interface

interface CanActivate {
  canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean>;
}

That's it. One method. Returns a boolean (sync or async). Nest hands you an ExecutionContext — a bundle of metadata about the request, the handler being invoked, the controller class, and any custom metadata you've attached.

A real-world guard: API key check

// src/common/guards/api-key.guard.ts
import {
  Injectable, CanActivate, ExecutionContext, UnauthorizedException,
} from '@nestjs/common';

@Injectable()
export class ApiKeyGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest();
    const key = req.headers['x-api-key'];

    if (!key) {
      throw new UnauthorizedException('Missing X-Api-Key header');
    }
    if (key !== process.env.API_KEY) {
      throw new UnauthorizedException('Invalid API key');
    }
    return true;
  }
}

Applying a guard

Three scopes, smallest to largest:

// 1. on a single method
@Get('admin')
@UseGuards(ApiKeyGuard)
adminOnly() { ... }

// 2. on a whole controller
@UseGuards(ApiKeyGuard)
@Controller('flights')
export class FlightsController { ... }

// 3. globally, in main.ts
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalGuards(new ApiKeyGuard());
  await app.listen(3000);
}

Gotcha: If you instantiate a guard with new ApiKeyGuard() in useGlobalGuards, it lives outside the DI container — it can't inject anything. To register a global guard with DI, use the APP_GUARD token in your providers (we'll show this pattern in Lesson 5 with auth).

🛂
Passenger: “I lost my boarding pass.”
TSA agent: “You can't go through security.”
Passenger: “But the gate is right there!”
TSA agent: “Yes. And you'll never see it.”
Guards don't argue. They return false and the request goes home.

Part 4: Interceptors

Interceptors are the most powerful and the most over-engineered stage in the pipeline. They wrap the handler — you get a hook before the handler runs and a hook after it returns. Both halves use RxJS observables, which trips up almost everyone the first time.

The interface

interface NestInterceptor {
  intercept(
    context: ExecutionContext,
    next: CallHandler,
  ): Observable<any> | Promise<Observable<any>>;
}

Don't be scared by “Observable.” You can think of next.handle() as “the rest of the pipeline as a thing I can pipe through.” You return an observable that — eventually — emits the response value.

Example 1: a timing interceptor

// src/common/interceptors/timing.interceptor.ts
import {
  Injectable, NestInterceptor, ExecutionContext, CallHandler, Logger,
} from '@nestjs/common';
import { Observable } from 'rxjs';
import { tap } from 'rxjs/operators';

@Injectable()
export class TimingInterceptor implements NestInterceptor {
  private readonly log = new Logger('Timing');

  intercept(ctx: ExecutionContext, next: CallHandler): Observable<any> {
    const handler = ctx.getHandler().name;
    const start = Date.now();
    return next
      .handle()
      .pipe(
        tap(() => this.log.log(`${handler} took ${Date.now() - start}ms`)),
      );
  }
}

Read the code top to bottom: capture start → call next.handle() (this runs the handler) → .pipe(tap(...)) says “when the handler emits its result, run this side-effect.” The tap operator doesn't change the value — it just observes.

Example 2: response wrapper

A common pattern: every API response should be wrapped in { data: ... }. Instead of doing this in every controller, an interceptor does it once.

import {
  Injectable, NestInterceptor, ExecutionContext, CallHandler,
} from '@nestjs/common';
import { Observable } from 'rxjs';
import { map } from 'rxjs/operators';

@Injectable()
export class WrapResponseInterceptor implements NestInterceptor {
  intercept(ctx: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(map((data) => ({ data })));
  }
}

Now GET /flights — which used to return [{...}, {...}] — returns { data: [{...}, {...}] }. Apply globally with app.useGlobalInterceptors(new WrapResponseInterceptor()) and your entire API gets a consistent shape for free.

Real example: Every Stripe API response has { object: 'list', data: [...], has_more: bool }. They didn't write that wrapper in every endpoint — they wrote it once in something like an interceptor and applied it everywhere. That's the kind of consistency interceptors give you for two dozen lines of code.

Part 5: Pipes

A pipe transforms or validates an input value. Two outcomes: it returns the (possibly transformed) value, or it throws. If it returns, the value Nest passes to your handler is whatever the pipe returned. If it throws, the request never reaches the handler.

Built-in pipes

PipeWhat it doesThrows if
ParseIntPipeConverts to numbernot a valid integer
ParseFloatPipeConverts to numbernot a valid float
ParseBoolPipeConverts to booleannot 'true' / 'false'
ParseUUIDPipeValidates UUID stringnot a valid UUID
ParseEnumPipeValidates against enumnot a valid enum member
ParseArrayPipeSplits a CSV stringnot parseable
DefaultValuePipeSupplies fallback if undefinednever
ValidationPipeValidates DTOs via class-validatorany field fails its rules — we'll dive in Lesson 6

Using a built-in pipe

You already saw this in Lesson 2:

@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {
  return this.flights.findOne(id);
}

:id in the URL is always a string — that's just how URLs work. ParseIntPipe intercepts it, converts to a number, and either passes the number to your handler or throws a 400 Bad Request if it can't. Without the pipe, you'd be doing parseInt(id) in every controller method, manually checking NaN, manually throwing.

Writing a custom pipe

The interface is one method:

interface PipeTransform {
  transform(value: any, metadata: ArgumentMetadata): any;
}

Here's a pipe that trims and lower-cases query string values — useful for things like ?destination=NYC being treated the same as ?destination=nyc:

// src/common/pipes/lowercase.pipe.ts
import { Injectable, PipeTransform } from '@nestjs/common';

@Injectable()
export class LowercasePipe implements PipeTransform<string, string> {
  transform(value: string): string {
    if (typeof value !== 'string') return value;
    return value.trim().toLowerCase();
  }
}
@Get()
findAll(@Query('destination', LowercasePipe) destination?: string) {
  return this.flights.findAll({ destination });
}

The handler now receives a clean, normalized string. The transformation is invisible to the controller's logic, which is exactly the point.

🧳
Controller: “Give me an integer.”
URL: “Here's '42'.”
Controller: “That's a string.”
URL: “That's all URLs have. Strings.”
Pipe: “Step aside, I got this. parseInt... 42. You're welcome.”
The reason every controller in the codebase doesn't have its own parseInt dance.

Why pipes deserve their own stage: validation logic is the leakiest abstraction in any backend. If you put it in the controller, every controller has it. If you put it in middleware, you don't have access to handler metadata. Pipes are the right place — they run after Guards (so you don't validate requests you'd reject anyway) but before the handler (so the handler can trust its inputs). The whole pipeline order makes more sense once you stare at this for a minute.

Part 6: Exception Filters

Things break. Pipes throw, services blow up, the database is down. NestJS catches every uncaught error and runs it through an exception filter, which decides what HTTP response to send back. There's a default filter that's perfectly fine, but most production apps want a custom one for consistent error formatting.

Throwing exceptions

Anywhere in your code path — controller, service, guard, pipe — you can throw a built-in HTTP exception:

import {
  NotFoundException, BadRequestException, ForbiddenException,
  UnauthorizedException, ConflictException, InternalServerErrorException,
} from '@nestjs/common';

throw new NotFoundException('Flight 42 not found');     // 404
throw new BadRequestException('destination is required');  // 400
throw new UnauthorizedException();                          // 401
throw new ForbiddenException();                             // 403
throw new ConflictException('Flight number already taken');  // 409

Each maps to the right status code automatically. The default filter serializes them as { statusCode, message }.

The base class: HttpException

For one-off cases:

throw new HttpException(
  { code: 'GATE_LOCKED', message: 'Gate is locked' },
  HttpStatus.LOCKED,
);

A custom global exception filter

Most APIs want errors to look like { error: { message, code, timestamp } } instead of Nest's default { statusCode, message }. Here's how:

// src/common/filters/all-exceptions.filter.ts
import {
  ExceptionFilter, Catch, ArgumentsHost, HttpException, HttpStatus, Logger,
} from '@nestjs/common';
import { Request, Response } from 'express';

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly log = new Logger('Exceptions');

  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const res = ctx.getResponse<Response>();
    const req = ctx.getRequest<Request>();

    const status = exception instanceof HttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    const message = exception instanceof HttpException
      ? exception.getResponse()
      : 'Internal server error';

    if (status >= 500) this.log.error(exception);

    res.status(status).json({
      error: {
        code: status,
        message: typeof message === 'string' ? message : (message as any).message,
        path: req.url,
        timestamp: new Date().toISOString(),
      },
    });
  }
}

@Catch() with no argument means “catch every exception type.” You can narrow it: @Catch(HttpException) or @Catch(NotFoundException, BadRequestException).

Wiring the filter globally

// main.ts
async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalFilters(new AllExceptionsFilter());
  await app.listen(3000);
}

Now every error — whether it's a NotFoundException you threw on purpose or an unexpected TypeError: Cannot read properties of undefined — comes back as a uniform JSON shape. Frontend developers will buy you coffee.

📞
Frontend dev: “The error response is sometimes { message }, sometimes { error }, sometimes { statusCode, message }. What format do you actually return?”
Backend dev: “Yes.”
The hour spent writing a global exception filter pays itself back the first sprint.
✋ Self-test — don't peek
A handler throws NotFoundException('Flight 42'). The request also passed through a TimingInterceptor earlier in the pipeline. Does the interceptor's tap() still log the duration? If yes, what value does it see?
Hint: tap() only fires on success. RxJS observables have a separate “error” channel. To run code on errors too, you'd use catchError or finalize.

Part 7: The Order — One Diagram to Rule Them All

If you only memorize one thing from this lesson, memorize this diagram. Every NestJS request follows this exact path:

Solid arrows = happy path. Dashed red = any thrown exception is yanked sideways into the filter.

How to read it

  1. Linear top-to-bottom on the happy path. Every stage runs in order. If a stage doesn't apply (no guards on this route, no custom interceptor), it's still “there” — just empty.
  2. Any throw = sideways into the filter. A guard returning false, a pipe throwing on bad input, the handler throwing, the service throwing — all roads lead to the exception filter.
  3. Interceptors are the only stage that runs twice. Once before the handler, once after. That's why “before” appears at step 3 and “after” at step 6.

Part 1: Embeddables — Composition Without a Separate Table

Until now, every entity in your library has lived in its own table. Author in author, Article in article, Tag in tag. That works right up until you hit the address.

An author has a postal address. So does the publisher, the contributor, and the customer who orders the bound volume. Five entities, five copies of the same four columns: street, postalCode, city, country. And the day the postal service renames zip to postalCode, you write five identical migrations.

📮
Junior: “I added the address to the User table. Five new columns: address_street, address_zip...”
Senior: “Now do Customer.”
Junior: “Five more columns.”
Senior: “Now Vendor.”
Junior: “...five more.”
Senior: “Now product owner says rename zip to postalCode.”
Junior: “Three migrations, three pull requests, three failed deploys.”
Senior: “Or one embeddable.”
Embeddables exist for exactly this. The address is a value object, not an entity.

Cards inside cards

Back in the Records Library: every author has a master catalog card. Pinned to the front of that card is a smaller index card with the author's contact details — address, phone, email. The contact card is not its own filing cabinet. It has no independent identity. It belongs to the author and travels with the author. If the author leaves the library, the contact card leaves too.

That's an embeddable. It's a value object glued to the entity that owns it. No primary key of its own, no separate table by default, no independent existence.

The mapping: Embeddable = sub-card on the front of the master catalog card. Same handwriting, same drawer, lives and dies with the host record.

Defining an embeddable

Add the embeddable: true flag in defineEntity, then reference it from the host with p.embedded(...):

// src/entities/Address.ts
export const Address = defineEntity({
  name: 'Address',
  embeddable: true,
  properties: {
    street: p.string(),
    postalCode: p.string(),
    city: p.string(),
    country: p.string(),
  },
});

// src/entities/Author.ts
export const Author = defineEntity({
  name: 'Author',
  properties: {
    id: p.bigint().primary(),
    name: p.string(),
    address: () => p.embedded(Address),
  },
});

Don't forget to register Address alongside Author in your config's entities: [...] array. Embeddables go through discovery just like real entities.

Two storage modes — inline columns vs JSON column

Here is the part that surprises people. The same embeddable definition can be persisted two different ways depending on a single flag.

🗂️
Inline (default)
Flattened columns
Each embeddable property becomes its own column on the host table, prefixed with the property name: address_street, address_postal_code, address_city, address_country. Indexable, queryable like any column, fully relational.
📦
JSON object
Single jsonb column
Whole embeddable serialized into one jsonb column. Use p.embedded(Address).object(). Compact, schema-flexible, easy to add fields without migration. Heavier to query, harder to index, JSONB updates rewrite the whole field.

The default — inline — is what you want most of the time. You get real columns, real indexes, real query plans. The DDL schema:update generates for our Author looks like this:

create table "author" (
  "id" bigserial primary key,
  "name" varchar(255) not null,
  "address_street" varchar(255) not null,
  "address_postal_code" varchar(255) not null,
  "address_city" varchar(255) not null,
  "address_country" varchar(255) not null
);

Switch to JSON storage by chaining .object(). The same definition then produces a single address jsonb column instead of four flattened ones — same JS shape, very different physical layout.

Querying still works in both modes. em.find(Author, { address: { city: 'Stuttgart' } }) generates an indexable WHERE in inline mode, and a JSONB path expression ("address"->>'city' = 'Stuttgart') in JSON mode. The query is the same JS; the SQL is not.

When to pick which

Pick inline columns when you query individual fields often, need indexes on them, the shape is stable, or disk size matters. Pick JSON storage when you almost always read the embeddable as a whole, the shape is genuinely flexible per row, or you expect to add optional fields without migrations.

Array embeddables are always JSON. If you write p.embedded(Address).array() — an author with multiple addresses — MikroORM has to use JSON regardless of .object(). There is no relational way to flatten an arbitrary-length array of structs into columns.

Part 2: Inheritance — STI vs JOINED vs Mapped Superclass

The next compositional question. The library catalogs documents: books, journals, manuscripts. They share a title, an author, a publication year. They diverge: a book has an ISBN, a journal has a volume and issue, a manuscript has a folio shelf number. How do you model that?

🤔 Predict before reading on
Suppose you put every Book, Journal, and Manuscript row into one shared document table with a type column. Then you ask: find all Books with publishedYear > 2000. Does Postgres scan the entire document table, or does the WHERE narrow it efficiently? Take ten seconds and write your guess.
Hint: think about what an index on (type, published_year) would do. The answer determines whether STI is fast or catastrophic at your scale.

Three strategies

MikroORM gives you three ways to model an inheritance hierarchy. Each has a clear winner for a clear scenario; pick wrong and you pay forever.

📚
Mapped Superclass
Base class is just shared property definitions. Each subclass has its own table, fully independent. No polymorphic queries.
🗂️
Single Table (STI)
One table holds every subtype. A discriminator column says which row is which. Subtype-specific columns are nullable.
🔗
Class Table (TPT / JOINED)
One table per concrete subtype, plus a parent table. Child rows reference the parent by primary key. Every read JOINs.

Single Table Inheritance — STI

One table for the whole hierarchy. A discriminator column tells the ORM how to hydrate each row.

// src/entities/Document.ts
export const Document = defineEntity({
  name: 'Document',
  abstract: true,
  discriminatorColumn: 'type',
  properties: {
    id: p.bigint().primary(),
    type: p.enum(['book', 'journal', 'manuscript'] as const),
    title: p.string(),
    publishedYear: p.integer().nullable(),
  },
});

export const Book = defineEntity({
  name: 'Book', extends: Document, discriminatorValue: 'book',
  properties: { isbn: p.string().nullable() },
});

export const Journal = defineEntity({
  name: 'Journal', extends: Document, discriminatorValue: 'journal',
  properties: {
    volume: p.integer().nullable(),
    issue: p.integer().nullable(),
  },
});

// Manuscript follows the same pattern with folioShelf.

The generated DDL is one table with all the columns:

create table "document" (
  "id" bigserial primary key,
  "type" varchar(255) not null,
  "title" varchar(255) not null,
  "published_year" int null,
  "isbn" varchar(255) null,
  "volume" int null,
  "issue" int null,
  "folio_shelf" varchar(255) null
);
/* type is the discriminator; isbn is only set on books;
   volume/issue only on journals; folio_shelf only on manuscripts */

Notice that every subtype-specific column is nullable. It has to be — a journal row has no ISBN. This is the architectural cost of STI.

Querying is fast. em.find(Book, { publishedYear: { $gt: 2000 } }) becomes:

select * from "document" where "type" = 'book' and "published_year" > 2000;

Single table, single index scan. Polymorphic queries (em.find(Document, ...)) work too — same table, no JOIN, hydrate to the right subclass based on the discriminator.

Table-Per-Type — TPT (also called JOINED)

One table per concrete type, plus a base table. The base table holds the shared columns. Each child table has the same primary key and a foreign key to the base.

// same definitions, but on the base:
export const Document = defineEntity({
  name: 'Document',
  abstract: true,
  inheritance: 'tpt',  // the only change
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    publishedYear: p.integer().nullable(),
  },
});

The DDL becomes three normalized tables: a base document(id, title, published_year), plus book(id, isbn) and journal(id, volume, issue) — each child's id is both its primary key and a foreign key to document(id) with ON DELETE CASCADE.

Each column is properly typed and properly NOT NULL where it should be. But every read of Book JOINs to document; every insert of a Book writes to two tables; em.find(Document, {}) LEFT JOINs all child tables to figure out the concrete type.

The full STI vs TPT trade-off is summarized in the four-quadrant diagram further below. The headline: STI is one table with nullable subtype columns and zero JOINs; TPT is N+1 normalized tables with mandatory JOINs on every read.

Default heuristic: reach for STI first. The hidden cost (nullable subtype columns) is real but predictable. The cost of TPT (JOIN on every read) tends to surprise people in production. Switch to TPT only when subtype divergence makes STI's nullable column count embarrassing — rule of thumb, more than ~6 unique columns per subtype, or when a subtype has its own large indexes.

Mapped superclass — the “just share fields” option

If you don't actually need polymorphic queries — if Book, Journal, and Manuscript are independent entities that just happen to share title and publishedYear — mark the base as abstract: true without a discriminator. Each subclass gets its own table with the inherited fields inlined. There is no document table at all. Useful for shared timestamp/audit fields (createdAt, updatedAt, tenantId) across unrelated entities.

Part 3: JSON Properties — Typed Bags of Stuff

Sometimes the data is genuinely unstructured. An article has a metadata blob: feature flags set by the editor, a free-form list of related links, a per-article SEO override, an experimental analytics ping. None of this fits a relational column. JSON is the right answer.

Defining a typed JSON column

// src/entities/Article.ts
import { defineEntity, p } from '@mikro-orm/core';

export type ArticleMetadata = {
  featured: boolean;
  seoTitle?: string;
  relatedLinks: { href: string; label: string }[];
  experimentBucket?: 'a' | 'b' | 'c';
};

export const Article = defineEntity({
  name: 'Article',
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    slug: p.string().unique(),
    metadata: p.json<ArticleMetadata>().nullable(),
  },
});

The p.json<Shape>() helper gives you compile-time type safety on reads and writes, while persisting to a real Postgres jsonb column.

Querying inside JSONB

MikroORM lets you traverse JSON paths in FilterQuery just like nested objects:

const featured = await em.find(Article, {
  metadata: { featured: true },
});

// Postgres: where ("metadata"->>'featured')::bool = true

For more complex shape-based predicates, JSONB has its own operator family that maps directly: $contains (@>), $contained (<@), $exists / ? (top-level key exists), ?& (all listed keys exist), ?| (any of the listed keys exist). MikroORM passes them straight through to Postgres.

Indexing JSONB

A JSONB column without an index is just a slow blob of bytes. Two patterns matter:

  1. Path index — index a single field you query often. create index on article ((metadata->>'featured')). Cheap, surgical.
  2. GIN index — covers any @> / ? / ?& query. create index on article using gin (metadata). Bigger, slower to maintain, but a single index covers many query shapes.

You declare these in MikroORM via the entity-level @Index hint or in a hand-written migration. For the path-index variant the helper is concise:

properties: {
  metadata: p.json<ArticleMetadata>().nullable(),
},
indexes: [{ properties: 'metadata.featured' }],

The JSON trap — concurrent counters

Never put a counter inside JSONB. Postgres updates JSONB by rewriting the whole field. There is no native “increment this number” SQL for a JSON path. So if two requests both do metadata.viewCount++ at the same time, one of them wins and the other is silently overwritten. With a plain int column you can use UPDATE ... SET view_count = view_count + 1 and Postgres serializes it for you at the row level. Read-modify-write inside JSONB has no such guarantee.

The same warning applies to any field where the new value depends on the old value — toggles, accumulators, last-seen timestamps that must monotonically increase. JSONB is for shape-flexible reference data, not for hot counters.

Part 4: Virtual & View Entities

Two read-only escape hatches for when your entity should be backed by a query, not a table.

📑
Virtual entity
In-memory expression
A SQL string or QueryBuilder callback. Evaluated at query time. No database object created. No primary key. Use for ad-hoc denormalized read models.
🏛️
View entity
Real DB view
Generates CREATE VIEW in your migrations. Has a primary key. Tracked by schema diff. Use for stable reporting views you want versioned with the schema.

Virtual entity — example

export const AuthorStats = defineEntity({
  name: 'AuthorStats',
  expression: `
    select a.id as author_id, a.name, count(b.id) as book_count
    from author a
    left join book b on b.author_id = a.id
    group by a.id, a.name
  `,
  properties: {
    authorId: p.bigint(),
    name: p.string(),
    bookCount: p.integer(),
  },
});

const stats = await em.find(AuthorStats, { bookCount: { $gt: 5 } });

Notice: no primary key. No table is created. The where clause from your find() is appended to the expression at query time.

View entity — example

Same shape, but add view: true and a primary key. Now schema:update emits a CREATE VIEW:

export const AuthorStats = defineEntity({
  name: 'AuthorStats',
  tableName: 'author_stats_view',
  view: true,
  expression: 'select ...',
  properties: {
    authorId: p.bigint().primary(),
    name: p.string(),
    bookCount: p.integer(),
  },
});

Both are read-only. Modifying a property and calling flush() is a silent no-op. If you want write-through behavior, you need a real entity backed by a real table.

Part 5: Lifecycle Hooks & Subscribers

Standing procedures, written on the entity

The library has standing procedures. Before any new volume gets registered, the clerk stamps today's date on the back. Before any volume goes out for binding, the catalog is updated. Before any volume is destroyed, a final entry is added to the destruction ledger.

These are not optional. They run every time, automatically, no matter who initiates the action. They live next to the operation they wrap.

The mapping: Lifecycle hook = standing procedure attached to the entity. Subscriber = department-wide procedure that watches every entity. Same idea, different scope.

The hook menu

MikroORM fires hooks at well-defined points in an entity's lifecycle. Every hook receives an EventArgs with the entity and the EntityManager.

  • @OnInit — entity constructed via em.create() or hydrated from a row (synchronous only)
  • @OnLoad — fully loaded from the database, not for unhydrated references (async)
  • @BeforeCreate / @AfterCreate — around the INSERT for a new entity
  • @BeforeUpdate / @AfterUpdate — around the UPDATE for a changed entity
  • @BeforeUpsert / @AfterUpsert — around em.upsert(), the dedicated pair because upsert doesn't know its fate
  • @BeforeDelete / @AfterDelete — around the DELETE
  • beforeFlush / onFlush / afterFlush — subscriber-only, full access to the change-set list
  • beforeTransactionStart / commit / rollback — subscriber-only, around the transaction boundaries

The canonical example — auto-slugify

Every Article needs a URL slug. We could ask every caller to set it. We won't — we'll attach a standing procedure.

// src/entities/Article.ts — same Article from Part 3, plus a hook
import { type EventArgs } from '@mikro-orm/core';

Article.addHook('beforeCreate', (args: EventArgs<IArticle>) => {
  const a = args.entity;
  if (!a.slug) {
    a.slug = a.title.toLowerCase().replace(/[^a-z0-9]+/g, '-').replace(/^-|-$/g, '');
  }
});

Now any code path that creates an Article — controller, queue handler, seed script — gets the slug for free, before the INSERT is fired. The hook runs inside the Unit of Work commit phase, after change-set computation, just before the SQL goes to the wire.

@BeforeCreate hook vs the onCreate property modifier

Way back in Lesson 2, you saw p.datetime().onCreate(() => new Date()). That's the property-level onCreate, not a hook. Both fire at insert time. Use which?

  • onCreate property modifier — one field, computed from a closure that doesn't see the entity. Perfect for createdAt: new Date(). Local, declarative.
  • @BeforeCreate hook — needs access to other fields on the entity. Slug-from-title, derived totals, normalization. The hook receives the whole entity instance.

Subscribers — the department-wide procedure

A subscriber is a separate class that listens to events from many entities. Use it when:

  • You want the same logic applied to many entity types (audit log, soft-delete, change broadcast)
  • You need the change-set list across the whole flush (not one entity at a time)
  • You want event logic out of the entity definition for testability
// src/subscribers/AuditSubscriber.ts
import { EventArgs, EventSubscriber } from '@mikro-orm/core';

export class AuditSubscriber implements EventSubscriber {
  async afterCreate(args: EventArgs<unknown>) {
    console.log('created', args.changeSet?.name, args.changeSet?.entity);
  }
  async afterUpdate(args: EventArgs<unknown>) {
    console.log('updated', args.changeSet?.name, Object.keys(args.changeSet?.payload ?? {}));
  }
}
// register in mikro-orm.config.ts: subscribers: [new AuditSubscriber()]

Hooks fire inside the flush. Don't call em.flush() from inside a hook. It throws. Don't call em.persist() either — you can cause undefined behavior because the change-set has already been computed. If you need to create new entities reactively, use the subscriber-level beforeFlush event, which fires before change-set computation.

Part 6: Custom Types — Money, Email, Encrypted Columns

Sometimes the column type and the JS type are not the same shape. Money is the canonical case: stored as bigint cents in the database (no float weirdness), exposed as a Money { amount, currency } value object in JS. Email stored as varchar, exposed as an Email class with validation. An encrypted column stored as bytea, exposed as a plain string.

The escape hatch is a custom Type. You extend the abstract Type<RuntimeType, RawType> class and implement two methods:

  • convertToDatabaseValue(value, platform) — JS to DB on the way in
  • convertToJSValue(value, platform) — DB to JS on the way out

The MoneyType

// src/types/MoneyType.ts
import { Type } from '@mikro-orm/core';

export class Money {
  constructor(public readonly cents: bigint, public readonly currency: string) {}
  format() { return `${(Number(this.cents) / 100).toFixed(2)} ${this.currency}`; }
}

export class MoneyType extends Type<Money | null, string | null> {
  convertToDatabaseValue(value: Money | null | undefined) {
    return value == null ? null : `${value.cents}:${value.currency}`;
  }
  convertToJSValue(value: string): Money {
    const [cents, currency] = value.split(':');
    return new Money(BigInt(cents), currency);
  }
  getColumnType() { return 'varchar(64)'; }
}

Use it on a property:

price: p.type(MoneyType).$type<Money, string>().nullable(),

Now article.price is a Money instance with a format() method, but the database holds a humble varchar. The conversion is automatic and the type is symmetric — the same Type handles both directions of the round trip.

Property validation is a related lighter-weight pattern. If you only need to reject bad input (not transform shape), use p.string().check(...) or a property-level setter. Custom types are for when the in-memory shape genuinely differs from the on-disk shape.

Summary

📇
Embeddables
Value objects glued to a host entity. Inline columns by default; .object() switches to JSONB. Same JS shape, two physical layouts.
🗂️
Inheritance
STI: one table, discriminator column, fast scans, nullable subtype columns. TPT: one table per type, JOINs on every read, normalized. Mapped superclass: just shared properties, no polymorphism.
📦
JSON properties
p.json<Shape>() for typed JSONB. Index with path or GIN. Never put a counter inside — whole-field rewrites lose updates.
📑
Virtual & view entities
Virtual: in-memory expression evaluated at query time. View: real CREATE VIEW tracked by schema. Both read-only.
📝
Hooks & subscribers
Hooks live on the entity for entity-specific procedures. Subscribers live separately for cross-entity logic and flush-level events. Don't call flush() from inside a hook.
💰
Custom types
Extend Type<Runtime, Raw> when the JS shape and DB shape differ. Money, Email, encrypted columns. Two methods: convertToDatabaseValue, convertToJSValue.

    Model answer / self-check

    Part A: Postgres stores JSONB as a binary blob. Updating a single key requires rewriting the entire column value. Part B: up() should: addColumn('article', { name: 'view_count', type: 'int', default: 0 }), then addSql("UPDATE article SET view_count = (metadata->>'viewCount')::int WHERE ..."), then addSql("UPDATE article SET metadata = metadata - 'viewCount'").

Part 1: When em.find Isn't Enough

For the first five lessons we leaned on em.find, populate hints, and the occasional FilterQuery operator like $gt. That handles roughly 85% of a CRUD service. This lesson is about the other 15%.

Five concrete cases where the EntityManager can't help you and you have to reach for the QueryBuilder:

📊
Window functions
ROW_NUMBER() OVER (PARTITION BY author_id ORDER BY published_at DESC) — “latest article per author”.
🧮
Custom aggregates
percentile_cont, weighted averages, anything past count/sum/avg.
🔁
Subqueries
“Articles whose tag count is above the global average.” You need a subquery in WHERE.
🎛️
Dynamic conditions
A search endpoint that conditionally adds 8 different filters based on what the user typed.
📑
Complex GROUP BY + HAVING
“Authors with at least 3 articles in 2025 whose average view count is above 1000.”

For everything else — find by id, find by relation, findAndCount, populate trees — QueryBuilder is overkill. The mental rule from Lesson 1 still holds: describe the change as objects, flush. Escalate only when you must.

Back in the Records Library: most readers walk to the desk and say “I want every Tolstoy book published before 1880.” The Head Librarian writes that on a standard slip, hands it to the runner, and books appear.

But occasionally a researcher walks in with something stranger: “For each genre, give me the volume with the highest checkout count in the last 90 days, and a running total of pages across the top three.” Standard slips can't express that. The Head Librarian pulls out a blank request slip with custom filter sections — the QueryBuilder. The researcher fills in joins, groupings, window aggregates, and the runner executes exactly that plan.

Mapping: standard FilterQuery = pre-printed request slip. QueryBuilder = blank slip with custom filter sections. em.execute('SELECT …') = walking into the stacks yourself with a flashlight.
🤯
Junior: “I wrote 200 lines of QueryBuilder to fetch articles by status and tag. I wanted full control over the SQL.”
Senior, opens the file: “em.find(Article, { status: 'published', tags: { name: { $in: ['hot', 'new'] } } }). One line. Same SQL. Same results.”
Junior: “But what if I need it more dynamic?”
Senior: “Then build the FilterQuery object dynamically. QB is an escape hatch, not the front door.”
The QueryBuilder is the most over-used part of MikroORM. Reach for it last, not first.

Part 2: QueryBuilder Anatomy

You get a QueryBuilder one of two ways. Both return the same thing — the second just lets you pre-name the root alias, which matters once you start joining.

// short form, no explicit alias
const qb = em.qb(Article);

// explicit alias — needed for joins and raw SQL fragments
const qb = em.createQueryBuilder(Article, 'a');

From there you chain. Every method returns the same QB instance, fluent-API style.

The method alphabet

Method What it does
.select(fields) Choose which columns to return. '*' for all, an array for specific fields.
.where(cond) Sets the root WHERE clause. Replaces previous where calls.
.andWhere / .orWhere Compose conditions across multiple lines without rebuilding the object.
.leftJoin / .innerJoin Join a relation by property path. Add AndSelect variants if you also want the joined data hydrated.
.groupBy / .having Group rows + filter the groups. HAVING runs after aggregation; WHERE runs before.
.orderBy { publishedAt: 'desc' }. Multiple keys = multi-column sort.
.limit(n) / .offset(n) Pagination. Combine with getResultAndCount() for the “rows + total” pattern.

Two terminal methods, two universes

This is the most important slide in the lesson. The same QB chain finishes one of two ways, and the choice has consequences.

📄
.execute()
Raw rows, no Identity Map
Returns plain objects. Not registered in the Identity Map. Not tracked by the Unit of Work. Use for reports, exports, dashboards. Modifying the result and calling flush will do nothing.
🔌
.getResult()
Managed entities
Returns hydrated entity instances. Registered in the Identity Map, tracked by the Unit of Work. Modify a property, call flush, get an UPDATE. .getSingleResult() for one, .getResultAndCount() for paginated.
// raw — fast, but you can't change anything via flush
const rows = await em.qb(Article)
  .select(['id', 'title', 'view_count'])
  .where({ viewCount: { $gt: 1000 } })
  .execute();
// rows[0] is a plain object, not an Article instance

// hydrated — entities go into the Identity Map
const articles = await em.qb(Article)
  .select('*')
  .where({ viewCount: { $gt: 1000 } })
  .getResult();
articles[0].title = 'New Title';
await em.flush(); // fires UPDATE — change-tracking works

Back to the Library: .execute() is the runner photocopying the requested page and handing you the copy. The original stays on the shelf, untouched. You can scribble on the copy all you want; the master register doesn't care.

.getResult() is the runner bringing the actual volume to your carrel. It's now logged in the Master Catalog under your name. Annotate the margin, and the Working Ledger records the change. End-of-shift sign-off (flush) writes those margin notes back into the master register.

Practical rule: reports/CSV exports/dashboards → .execute(). Anything you might mutate → .getResult().

Joins: filter-only vs hydrated

This catches everyone once. leftJoin joins the table for filtering and ordering only. leftJoinAndSelect joins and populates the relation on the result. Choose by intent.

// I just want to filter by tag.name — books arrays will NOT be populated
const articles1 = await em.qb(Article, 'a')
  .select('*')
  .leftJoin('a.tags', 't')
  .where({ 't.name': 'fiction' })
  .getResultList();
// articles1[0].tags is NOT initialized

// I want the tags hydrated on the result
const articles2 = await em.qb(Article, 'a')
  .select('*')
  .leftJoinAndSelect('a.tags', 't')
  .where({ 't.name': 'fiction' })
  .getResultList();
// articles2[0].tags is fully populated

Pagination footgun. When you join a to-many relation and use limit, SQL limits rows, not root entities. MikroORM auto-detects this and wraps the root selection in a subquery so limit 10 means “10 articles, not 10 rows of article×tag”. Use setFlag(QueryFlag.DISABLE_PAGINATE) only when you really want raw row limits.

Part 3: Query Conditions — the FilterQuery Operator Alphabet

🤔 Pretest before you read on
Without looking up: how would you express (price > 100 AND tag IN ('hot', 'new')) OR featured = true using FilterQuery? Take 30 seconds and write your guess in a comment.
If you reach for raw SQL, you're under-using FilterQuery. The answer is below — using $or, $and, $gt, and array shorthand.

FilterQuery is the same condition object you've used inside em.find. It works identically in qb.where(…). Operators are MongoDB-style: dollar-prefixed keys.

Comparison operators

Operator SQL equivalent Example
$eq = { status: { $eq: 'published' } } — or just { status: 'published' }
$ne <> { deletedAt: { $ne: null } }
$gt / $gte > / >= { viewCount: { $gt: 1000 } }
$lt / $lte < / <= { publishedAt: { $lte: new Date() } }
$in / $nin IN / NOT IN { id: { $in: [1, 2, 7] } } or { id: [1, 2, 7] }
$like / $ilike LIKE / ILIKE (Postgres) { title: { $ilike: '%mikroorm%' } }
$re ~ regex (Postgres) { slug: { $re: '^post-\\d+$' } }
$fulltext to_tsquery { searchableTitle: { $fulltext: 'data mapper' } } — needs a FullTextType column or a fulltext index.

Logical operators

$and joins clauses with AND, $or with OR, $not inverts. Nest them as deeply as you need.

// answer to the pretest above
const hits = await em.find(Article, {
  $or: [
    {
      $and: [
        { price: { $gt: 100 } },
        { tags: { name: { $in: ['hot', 'new'] } } },
      ],
    },
    { featured: true },
  ],
});

Same object works inside qb.where(…). The QB rewrites it into the same WHERE clause MikroORM would have built for em.find. There is no “raw mode” vs “managed mode” for conditions — same compiler, same SQL.

Postgres-specific JSONB operators

If you have a jsonb column (e.g. metadata: { tags: ['x', 'y'] }), Postgres has dedicated operators that beat any client-side filtering. MikroORM exposes them directly:

Operator Postgres SQL Use case
$contains @> JSONB on left contains JSONB on right. { metadata: { $contains: { tags: ['hot'] } } }
$contained <@ JSONB on left is contained in JSONB on right.
$overlap && Arrays share at least one element.
$hasKey / $hasKeys / $hasSomeKeys ? / ?& / ?| JSONB has key(s).

Collection operators — $some, $none, $every, $size

For relation collections. These compile to subqueries.

// authors with at least one article tagged 'fiction'
em.find(Author, { articles: { $some: { tags: { name: 'fiction' } } } });

// authors who have NO articles at all
em.find(Author, { articles: { $none: {} } });

// authors whose every article is published
em.find(Author, { articles: { $every: { status: 'published' } } });

// authors with between 3 and 10 articles
em.find(Author, { articles: { $size: { $gte: 3, $lte: 10 } } });

The 90% rule. If you find yourself dropping to the QueryBuilder “just for a complex condition,” pause and ask: can FilterQuery express this? Nine times out of ten the answer is yes, and you keep the type safety, the populate hint inference, and the implicit joins.

Part 4: Raw SQL Fragments — the Last Escape Hatch

Sometimes the operator alphabet doesn't have what you need. extract(year from published_at), custom Postgres functions, window expressions, computed comparisons. For these, MikroORM gives you two helpers, both Postgres-aware and parameterized.

import { raw, sql } from '@mikro-orm/postgresql';

raw() — the function form

Use raw(sqlString, params?) when you need a SQL fragment as either a key or a value in your filter.

// "articles published in 2025"
await em.find(Article, {
  [raw('extract(year from published_at)')]: 2025,
});

// inside QB.where
const rows = await em.qb(Article)
  .select('*')
  .where({ [raw('lower(title)')]: { $like: '%mikroorm%' } })
  .getResultList();

// with parameters — never concatenate strings
await em.qb(Article)
  .select(['*', raw('count(*) over () as total')])
  .where('view_count > ?', [1000])
  .execute();

sql tagged template — the prettier form

// equivalent to raw('lower(title)')
await em.qb(Article)
  .select(['*', sql`u.first_name || ' ' || u.last_name`.as('fullName')])
  .orderBy({ fullName: 'asc' });

Dropping all the way to em.execute()

When even the QueryBuilder is in the way (a one-off bulk update on millions of rows, a Postgres-specific VACUUM ANALYZE, a stored procedure call), you have em.execute(sqlString, params). It honours the current transaction context and respects the EM fork.

const result = await em.execute(
  'update article set view_count = view_count + 1 where slug = ?',
  ['top-of-the-hour'],
);
// returns { affectedRows, … } — no Identity Map involvement at all

Safety rule. Always parameterize. em.execute(`select * from user where email = '${email}'`) is a SQL injection waiting for the wrong customer. Use ? placeholders and pass values in the second argument. Same in raw() — the second argument is a real array of parameters, bound by the driver.

The escalation ladder. 1) em.find with FilterQuery. 2) FilterQuery + raw() for the one weird key. 3) em.qb() with chained methods. 4) QB with raw fragments. 5) em.execute(). Stop one rung lower than feels “safe” — you almost never need rung 5.

Part 5: Filters — Soft-Delete Once, Forever

Filters are the most under-appreciated MikroORM feature. They let you attach a condition to an entity that gets injected into every find, findOne, findAndCount, count, nativeUpdate, and nativeDelete — unless you explicitly opt out for one query.

The two killer use-cases: soft delete (rows exist but should be hidden by default) and multi-tenancy (every query gets scoped by tenantId from request context).

The Records Library has Restricted Stacks. Every volume in there exists in the catalog, has a card, has a barcode — but a regular reader's request for “all books by Tolstoy” returns only the open-stacks copies. The librarian quietly drops the restricted titles before handing you the list. Not because they don't exist; because your reader ID doesn't have clearance.

If you walk in with the right credentials, you say “include restricted stacks,” and they come back too. The data was never gone — the filter just hid it from default view.

Mapping: Filter = the rule the librarian silently applies before answering any question. Soft-delete filter = restricted stacks for deleted volumes. Multi-tenant filter = restricted stacks scoped per organization.

Defining a filter on the entity

With defineEntity, filters live in the filters map on the schema. The condition is either a static object or a callback that takes args.

// src/entities/Article.ts
import { defineEntity, p, InferEntity } from '@mikro-orm/core';

export const Article = defineEntity({
  name: 'Article',
  filters: {
    softDelete: {
      cond: { deletedAt: null },
      default: true, // applied automatically on every query
    },
  },
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    slug: p.string().unique(),
    viewCount: p.integer().default(0),
    publishedAt: p.datetime().nullable(),
    deletedAt: p.datetime().nullable(),
    createdAt: p.datetime().onCreate(() => new Date()),
  },
});

export type IArticle = InferEntity<typeof Article>;

From now on, em.find(Article, {}) silently appends and "deleted_at" is null to the SQL. You don't have to remember it. New developers don't have to remember it. The filter is the convention.

Toggling filters per query

// default — soft-delete filter is on, deleted rows hidden
const live = await em.find(Article, {});

// admin endpoint — show every row, including soft-deleted
const all = await em.find(Article, {}, { filters: { softDelete: false } });

// drop *every* filter for one query
const raw = await em.find(Article, {}, { filters: false });

Soft delete in practice

// instead of em.remove(article), do this:
article.deletedAt = new Date();
await em.flush(); // fires UPDATE with deleted_at = now()

// next find call won't see the row, even by ID
const nope = await em.findOne(Article, article.id); // null

Multi-tenant filters — the real-world pattern

For multi-tenant SaaS, you want every query scoped by tenantId. You don't trust developers to remember; you let the framework enforce it. Define a global filter at ORM init, set its parameter from request context, and every fork inherits it.

import { MikroORM, RequestContext } from '@mikro-orm/core';

const orm = await MikroORM.init({
  filters: {
    tenant: {
      cond: args => ({ tenantId: args.tenantId }),
      default: true,
    },
  },
  // … rest of config
});

// in your request middleware:
app.use((req, res, next) => {
  RequestContext.create(orm.em, () => {
    const em = orm.em.getContext();
    em.setFilterParams('tenant', { tenantId: req.user.tenantId });
    next();
  });
});

From now on, anywhere in your codebase, em.find(Article, {}) auto-appends and "tenant_id" = $1. A bug that forgets to filter? Doesn't compile to a security incident; the filter catches it.

Filters and joins. Since v6, filters apply to relations too — they become part of the JOIN ON condition. So your soft-delete filter on Article also automatically hides deleted articles when they appear via Author.populate(['articles']). You don't have to remember; the JOIN does.

Filters in QueryBuilder

QB skips filters by default — this is intentional, since you might be writing reports that need all rows. To opt back in, call qb.applyFilters(…):

const qb = em.qb(Article);
await qb.applyFilters({ softDelete: true });
const articles = await qb.getResultList();

Part 6: Repositories — Typed Shortcuts You Probably Don't Need

This is the lesson where I tell you a feature exists and then tell you to skip it most of the time. em.getRepository(Article) returns an EntityRepository<Article>. It's a thin wrapper around the EntityManager, scoped to one entity type, with no special powers.

const articles = em.getRepository(Article);

const recent = await articles.find({ status: 'published' }, { limit: 10 });
// identical to em.find(Article, { status: 'published' }, { limit: 10 })

The default repository is just sugar — it saves you from passing Article to every call. Useful if you like the syntax, optional otherwise. Note: since v6, repositories no longer have persist, persistAndFlush, remove, or flush. Those live on the EntityManager, where they belong.

When custom repositories actually pay off

The real value of repositories is as a single home for the QueryBuilder chains specific to one entity. If your codebase has findHotArticles being reinvented in three controllers with slightly different SQL each, that's the moment.

The Subject Specialist analogy from Lesson 1: the science librarian doesn't have any power the head librarian doesn't have. But if you only need science books, walking to the science desk is friendlier — they know the local quirks. They have a few well-worn search slips taped to the desk: “all titles published in the last 5 years,” “cross-references to peer-reviewed journals,” etc.

That's a custom repository. Same authority as the EM, but a typed home for the queries that are specific to this entity.

Defining a custom repository

// src/repositories/ArticleRepository.ts
import { EntityRepository } from '@mikro-orm/postgresql';
import { raw } from '@mikro-orm/postgresql';
import { type IArticle } from '../entities/Article';

export class ArticleRepository extends EntityRepository<IArticle> {
  findHotArticles(minViews: number) {
    return this.em
      .qb(this.entityName, 'a')
      .select('*')
      .where({ viewCount: { $gt: minViews } })
      .orderBy({ viewCount: 'desc' })
      .getResultList();
  }

  searchByTitle(q: string) {
    return this.em
      .qb(this.entityName, 'a')
      .select('*')
      .where({
        $or: [
          { title: { $ilike: `%${q}%` } },
          { [raw('lower(slug)')]: { $like: `%${q.toLowerCase()}%` } },
        ],
      })
      .getResultList();
  }
}

Wiring it into the entity

Tell defineEntity which repository class to use. Pass it as a callback — this avoids circular import problems.

// src/entities/Article.ts (continued)
import { ArticleRepository } from '../repositories/ArticleRepository';

export const Article = defineEntity({
  name: 'Article',
  repository: () => ArticleRepository,
  filters: { softDelete: { cond: { deletedAt: null }, default: true } },
  properties: { /* … */ },
});

Now em.getRepository(Article) is typed as ArticleRepository. Calling .findHotArticles(1000) works, autocompletes, and lives in one file instead of three controllers.

Heuristic. Skip custom repositories until you have either (a) the same QB chain repeated in 3+ places, or (b) a domain operation that genuinely belongs on the entity boundary (e.g. “publish article” with an event emit). Otherwise the indirection costs more than it saves.

Part 7: Hands-On — Soft-Delete + Article Repository

Time to wire all of this into archive-api. By the end of this section you'll have:

  1. An Article entity with a softDelete filter that hides deleted rows by default.
  2. An ArticleRepository with two methods: findHotArticles(minViews) and searchByTitle(q).
  3. A demo script that shows the SQL with the filter active and without, side-by-side in the query log.

Step 1 — the entity

Already shown above. Drop it in src/entities/Article.ts. Make sure your mikro-orm.config.ts includes Article in the entities array.

Step 2 — the repository

Already shown. Drop it in src/repositories/ArticleRepository.ts. Wire it into the entity definition.

Step 3 — the demo

// src/main.ts
import { MikroORM } from '@mikro-orm/postgresql';
import config from './mikro-orm.config';
import { Article } from './entities/Article';

async function main() {
  const orm = await MikroORM.init(config);
  await orm.schema.refreshDatabase();

  const em = orm.em.fork();
  const articles = em.getRepository(Article);

  // seed: 3 live, 1 hot, 1 soft-deleted
  em.create(Article, { title: 'Intro to Mikro',    slug: 'intro',   viewCount: 120  });
  em.create(Article, { title: 'Hot take on QB',    slug: 'qb',      viewCount: 5000 });
  em.create(Article, { title: 'Filters explained', slug: 'filters', viewCount: 200  });
  em.create(Article, { title: 'Old draft', slug: 'old', viewCount: 10,
                       deletedAt: new Date('2024-01-01') });
  await em.flush();

  // 1) default find — soft-delete filter ON, draft hidden
  console.log('\n--- with filter (default) ---');
  const live = await em.find(Article, {});
  console.log('rows:', live.length); // 3

  // 2) bypass filter — see all rows
  console.log('\n--- filter disabled ---');
  const all = await em.find(Article, {}, { filters: { softDelete: false } });
  console.log('rows:', all.length); // 4

  // 3) repository — typed methods, QB under the hood
  console.log('\n--- findHotArticles(1000) ---');
  const hot = await articles.findHotArticles(1000);
  console.log('hot:', hot.map(a => a.title));

  console.log('\n--- searchByTitle("filt") ---');
  const matches = await articles.searchByTitle('filt');
  console.log('matches:', matches.map(a => a.title));

  await orm.close();
}

main().catch(console.error);

What the query log proves

With debug: true in your config, you'll see two key differences in the SQL:

--- with filter (default) ---
[query] select "a0".* from "article" as "a0" where "a0"."deleted_at" is null

--- filter disabled ---
[query] select "a0".* from "article" as "a0"

One WHERE clause appears or disappears. That's all it took to make soft-delete invisible-by-default across your entire codebase.

Part 1: Three Ways to Define an Entity

In Lesson 1 we wrote our first entity with defineEntity. That wasn't the only option. MikroORM 7 ships three different ways to declare an entity, and they all produce the same metadata at runtime. The shape you pick is a code-style choice, not a runtime choice.

Here's the same Article entity written all three ways. Skim them first; we'll dissect the trade-offs after.

Option A — defineEntity + class extension

// src/entities/Article.ts
import { defineEntity, p } from '@mikro-orm/core';

const ArticleSchema = defineEntity({
  name: 'Article',
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    slug: p.string().unique(),
  },
});

export class Article extends ArticleSchema.class {
  // you can add domain methods here, e.g.
  isPublished(): boolean {
    return this.publishedAt != null;
  }
}
ArticleSchema.setClass(Article);

Option B — defineEntity standalone

// src/entities/Article.ts
import { defineEntity, p, InferEntity } from '@mikro-orm/core';

export const Article = defineEntity({
  name: 'Article',
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    slug: p.string().unique(),
  },
});

export type IArticle = InferEntity<typeof Article>;

Option C — decorators (legacy)

// src/entities/Article.ts
import { Entity, PrimaryKey, Property } from '@mikro-orm/decorators/legacy';

@Entity()
export class Article {
  @PrimaryKey()
  id!: bigint;

  @Property()
  title!: string;

  @Property({ unique: true })
  slug!: string;
}

So which do I pick?

All three produce identical SQL. The differences are ergonomic and cultural. Here's how we frame it on the team:

Style Pick when Watch out for
defineEntity standalone Most cases. Pure data classes, no domain methods, you want the shortest possible file. Hover types are noisy (an intersection of generics). You can't add instance methods.
defineEntity + class You want clean hover types, you need domain methods (fullName(), isPublished()), or you want to extend a base class. Two extra lines of boilerplate. Must remember setClass() before MikroORM.init().
Decorators You're porting a TypeORM codebase, or your team strongly prefers the decorator look. Requires experimentalDecorators + emitDecoratorMetadata. Doesn't play with esbuild/swc without plugins.

Course default: we use defineEntity standalone — the same shape you saw for Book in Lesson 1. It's the most compact, requires zero TypeScript config, and is the recommended modern path in the MikroORM v7 docs. If you find yourself adding domain methods often, switch to the class variant. Both are first-class.

🤔
Junior: “I added experimentalDecorators: true, why does the build still scream about decorator metadata?”
Senior: “You also need emitDecoratorMetadata. And import 'reflect-metadata'. And it has to be the first import in your entry file.”
Junior: “Three knobs to write a class field?”
Senior: “That's why we use defineEntity.”
Decorators work; they just bring three TypeScript flags to a one-property fight.

Part 2: Property Types & Modifiers

Every property in defineEntity is a chain: a type followed by zero or more modifiers. Both halves come from the p helper (which is just an alias for defineEntity.properties).

A property = type chain. Each modifier adds metadata; the schema generator reads the metadata and builds DDL.

The types you'll use 95% of the time

p.<type>() Postgres column JS type When to reach for it
p.string() varchar(255) string Names, titles, short text. Override length with .length(n).
p.text() text string Long-form bodies, descriptions. No length cap.
p.integer() int4 number Counts, view counts, small IDs. Range ±2.1B.
p.bigint() int8 bigint Primary keys for production tables. We default to this.
p.boolean() boolean boolean Flags, soft-delete markers, feature toggles.
p.datetime() timestamptz Date createdAt, publishedAt, anything with timezone.
p.uuid() uuid string Public-facing IDs you don't want to leak row counts.
p.float() real number Inexact numerics — ratings, sensor data.
p.decimal() numeric string Money. Always money. Never float for money.
p.json<T>() jsonb T Schemaless metadata, settings blobs. Pass a TS shape.
p.enum(...) text + check constraint your enum Status fields, roles. Use .nativeEnumName() for a real Postgres enum.

The modifiers

Modifiers chain. Order doesn't matter for the schema; pick whatever reads best. The most-used set:

// the workhorse modifiers
p.string().primary()              // add to PK
p.string().unique()               // unique index
p.string().nullable()             // drops NOT NULL
p.string().length(512)            // varchar(512) instead of (255)
p.integer().default(0)            // DB-side DEFAULT 0
p.datetime().defaultRaw('now()') // DB-side DEFAULT now()
p.datetime().onCreate(() => new Date())   // ORM-side, on insert
p.datetime().onUpdate(() => new Date())   // ORM-side, on update
p.string().index()                // btree index
p.text().lazy()                   // excluded from default SELECT
p.integer().version()              // optimistic locking column

Nullable vs optional — the gotcha that bites everyone once

TypeScript-optional (title?: string) and database-nullable (NULL column) are different concerns. Conflating them is the most common bug new MikroORM users ship.

📝
.nullable()
Database-level
The DDL drops the NOT NULL constraint. The column can hold NULL. Type becomes T | null. This is what you want when the value is genuinely unknown for some rows.
✏️
TS-optional ?:
Input-shape only
Just means “you may omit this when constructing”. Has nothing to do with the database. With defineEntity, this is implicit when you set onCreate or default.

The cleanest mental model: if a row could exist without this value, use .nullable(). If a value is always set but the API caller doesn't have to provide it, use .default() or .onCreate().

Default vs onCreate vs onUpdate — whose hands does the value pass through?

Three knobs that all set values automatically. They differ in who runs them and when.

💾
.default(0)
Postgres-side. DEFAULT 0 in the DDL. Even raw SQL inserts get the value. Use for static literals.
🔧
.defaultRaw('now()')
Postgres-side, but the value is a SQL expression. Use for now(), gen_random_uuid(), server-side defaults.
📝
.onCreate(() => new Date())
ORM-side, on insert. Runs in JS just before the row is sent to Postgres. Use when the value depends on JS context (a config flag, a user ID).
✏️
.onUpdate(() => new Date())
ORM-side, on update. Runs every time the change-set fires an UPDATE. Classic updatedAt column.

Subtle but important: default('hello') is the database's hello. onCreate(() => 'hello') is JS's hello. They look the same on a clean insert, but they diverge if a different process inserts a row directly — only the default survives that path. Audit columns that must be set should always live as DB defaults, not JS hooks.

🤔 Predict before reading on
You declare publishedAt: p.datetime().nullable(). A reader runs em.create(Article, { title: 'Hi' }). Then they call article.publishedAt. What value comes back — null, undefined, or a TypeScript error?
Think about it before scrolling. The answer hinges on the difference between “not yet flushed” and “round-tripped from Postgres”. Hint: em.create just builds the JS shape; the value you see is whatever JS gives you for an unset property.

Part 3: Primary Keys — bigint, uuid, or composite?

Every entity needs a primary key. MikroORM enforces this at boot. The shape you pick determines insert performance, URL look, and how you handle horizontal scale.

In our Records Library, every volume has a unique call number. Two questions are different: “how does the catalog produce a new call number?” and “what does it look like when you read it off the spine?”

Some libraries hand the catalog a sequential number machine: 000001, 000002, 000003. Easy to read, fast to print, but anyone who sees a call number can guess how many volumes you have. Other libraries print a long random-looking code on every spine: 9c3e-7f81-…. Nobody can guess your collection size, but the code is awkward to read out loud, and inserting a new volume requires generating that code somewhere first.

And occasionally the call number is two pieces: subject code + acquisition number. This is rare, but it shows up for inherently composite records — say, “the third edition of book X”.

The MikroORM mapping: p.bigint().primary() = sequential call number (Postgres SEQUENCE, fast). p.uuid().primary() = random call number (UUID, opaque, distributable). Composite PK = two-part call number.

bigint — the default for production tables

export const Article = defineEntity({
  name: 'Article',
  properties: {
    id: p.bigint().primary(),
    // ...
  },
});

Behind this, Postgres creates an int8 column with a sequence. Inserts are fast (one round trip to nextval()), the column is 8 bytes, and indexes on it are tight.

Why big int and not plain int? An int4 tops out at ~2.1 billion. That sounds like a lot until you ship a feature that writes one row per page-view, hit ~250 rows/second, and run out of IDs in two months. bigint tops out at 9.2 quintillion. You will not exhaust it.

One quirk: in JavaScript, MikroORM v6+ maps Postgres bigint to the native BigInt type, not number. That means article.id has type bigint, and article.id + 1 requires article.id + 1n. If that's annoying, you can opt into BigIntType('string') or BigIntType('number') in advanced cases — but stick with the default unless you have a reason.

uuid — for public-facing IDs

export const Tag = defineEntity({
  name: 'Tag',
  properties: {
    id: p.uuid().primary().defaultRaw('gen_random_uuid()'),
    name: p.string(),
  },
});

A 16-byte random ID. Postgres generates it server-side via gen_random_uuid() (built into pgcrypto, available since PG13). It's opaque — nobody can tell from 9c3e7f81-… whether you have ten rows or ten million. It also lets a client generate the ID before the row hits the database, which is sometimes useful for offline-first apps.

Trade-offs: UUIDs are 2× the storage of a bigint, and random insertions fragment the index more than a sequential one. For an internal table you'll only ever hit by FK, that doesn't matter. For a hot append-only table doing 50k inserts/second, it can.

Composite primary keys

Sometimes the natural key is two columns. The classic example is a join-table for a many-to-many: (book_id, tag_id). You declare it by marking both columns as .primary():

export const BookTag = defineEntity({
  name: 'BookTag',
  properties: {
    book: () => p.manyToOne(Book).primary(),
    tag: () => p.manyToOne(Tag).primary(),
    addedAt: p.datetime().onCreate(() => new Date()),
  },
});

MikroORM stores composite PKs internally as ordered tuples. em.findOne(BookTag, [bookId, tagId]) looks them up. We won't lean on these in the course — we'll see explicit M:N tables in Lesson 4 — but you should know they exist for the day a designer hands you a legacy schema with a real composite key.

Course rule of thumb: use bigint for every primary key by default. Reach for uuid when the ID escapes into the URL bar or the public API and you don't want a competitor to scrape your row counts. Composite PKs are a last resort, and even then mostly for legacy schemas.

Part 4: Naming Strategy & Column Mapping

You may have noticed something in the Lesson 1 logs:

insert into "book" ("title", "author", "published_year", "created_at") ...

You wrote publishedYear in TypeScript. Postgres got published_year. You wrote createdAt. Postgres got created_at. Nobody told MikroORM to do that — that's the default UnderscoreNamingStrategy at work.

The strategy is simple: every camelCase property name is converted to snake_case at the database layer. Same for the table name (BookTag entity becomes book_tag table). The conversion is bidirectional: when MikroORM hydrates a row, it reads published_year back into publishedYear.

When (and how) to override

Two levels of escape hatch. The narrow one: override the column name for a single property.

export const Article = defineEntity({
  name: 'Article',
  properties: {
    id: p.bigint().primary(),
    // snake_case default would be `published_at` —
    // but say a legacy column is called `published_date`
    publishedAt: p.datetime()
      .nullable()
      .fieldName('published_date'),
  },
});

The wide one: override the table name for the whole entity.

export const Article = defineEntity({
  name: 'Article',
  tableName: 'articles', // default would be "article" — pluralise here
  properties: { /* ... */ },
});

The widest: change the naming strategy globally in mikro-orm.config.ts. We won't do that on this course; the underscore strategy is the de-facto Postgres convention and matches what most teams ship.

Why this matters in practice: if you adopt MikroORM into a system that already has tables, you'll either rename your TypeScript identifiers to fit the DB convention (bad — loud, churn-y) or use fieldName/tableName overrides on every property to map onto the legacy DB (also bad — verbose). The middle ground is to write a small custom NamingStrategy class that encodes whatever convention the legacy schema uses. It's an afternoon's work and pays back forever.

Part 5: Validation, Defaults & Lifecycle Preview

You've seen length, nullable, default, onCreate. Three more pieces complete the per-property toolkit you need before we wire up the Article.

Length and string size

p.string() defaults to varchar(255). That's an arbitrary historical default. For a column that's clearly a slug (max ~80 chars) or clearly a long blob (a body), be explicit:

title: p.string().length(200),     // varchar(200)
slug:  p.string().length(80).unique(),
body:  p.text(),                   // no length, use text type

Why bother? Two reasons. First, the DDL is documentation: someone reading varchar(80) understands “this is a slug” faster than varchar(255). Second, Postgres won't enforce more than what you ask — so a runaway client can shove a 250kB string into a default varchar(255) only if you didn't bound it. Bound your strings.

Required vs implied-required

By default every property is NOT NULL in the DB. You only opt out with .nullable(). That's the inverse of TypeORM. It catches a class of bugs at boot rather than at the first INSERT.

If a property has an onCreate or a default, the TypeScript signature treats it as optional in em.create calls (you don't have to pass it), but the column is still NOT NULL. The ORM and the DB agree: the value will be set, just not by your hand.

A glimpse of lifecycle hooks

Lesson 8 covers hooks in full. For now, the one-line preview: onCreate and onUpdate are per-property hooks that fire during the Unit of Work. There's also a richer system — beforeCreate, afterCreate, beforeUpdate, afterDelete, etc. — that fires on the whole entity. You attach them via defineEntity({ hooks: ... }) or Article.addHook(...).

// teaser — full coverage in Lesson 8
Article.addHook('beforeCreate', (args) => {
  if (!args.entity.slug) {
    args.entity.slug = args.entity.title.toLowerCase().replace(/\s+/g, '-');
  }
});

Don't sweat this now — just know the seam exists. For Article we'll set timestamps with onCreate/onUpdate and that's enough.

Part 6: Hands-on — Add Article to archive-api

Open the archive-api project from Lesson 1. We're going to add a second entity and watch the schema generator handle two tables in one shot.

Step 1 — create the Article entity

New file: src/entities/Article.ts.

// src/entities/Article.ts
import { defineEntity, p, InferEntity } from '@mikro-orm/core';

export const Article = defineEntity({
  name: 'Article',
  properties: {
    id: p.bigint().primary(),
    title: p.string().length(200),
    slug: p.string().length(120).unique(),
    body: p.text(),
    publishedAt: p.datetime().nullable(),
    viewCount: p.integer().default(0),
    metadata: p.json<{ source?: string; lang?: string }>().nullable(),
    createdAt: p.datetime().onCreate(() => new Date()),
    updatedAt: p.datetime()
      .onCreate(() => new Date())
      .onUpdate(() => new Date()),
  },
});

export type IArticle = InferEntity<typeof Article>;

Eight properties. Notice the deliberate choices: title is varchar(200) not the default 255, slug is varchar(120) + unique, body is text (no length cap), viewCount has a DB-side default of 0, publishedAt is genuinely nullable (a draft has no publish date), and updatedAt uses both onCreate and onUpdate so it's set on the first INSERT and refreshed on every UPDATE.

Step 2 — register it in the config

Edit src/mikro-orm.config.ts:

// src/mikro-orm.config.ts
import { defineConfig } from '@mikro-orm/postgresql';
import { Book } from './entities/Book';
import { Article } from './entities/Article'; // ← new

export default defineConfig({
  entities: [Book, Article], // ← new
  dbName: 'archive',
  user: 'postgres',
  password: 'postgres',
  host: 'localhost',
  port: 5432,
  debug: true,
});

Step 3 — preview the SQL the schema generator would emit

Before you change anything in the DB, let's look at what the schema generator wants to do. From the project root:

npx mikro-orm schema:create --dump

You should see two create table statements: the existing book (with the columns from Lesson 1) and the new article. Glance at the article one carefully:

create table "article" (
  "id" bigserial primary key,
  "title" varchar(200) not null,
  "slug" varchar(120) not null,
  "body" text not null,
  "published_at" timestamptz null,
  "view_count" int not null default 0,
  "metadata" jsonb null,
  "created_at" timestamptz not null,
  "updated_at" timestamptz not null
);
alter table "article" add constraint "article_slug_unique" unique ("slug");

Read this. Every choice we made in TypeScript shows up here: the length(200) became varchar(200), nullable() became NULL, default(0) became NOT NULL DEFAULT 0, unique() became a separate unique constraint. The onCreate on created_at/updated_at is not visible here — that's the ORM-side hook, invisible to the database.

Step 4 — persist a mixed batch

Replace src/main.ts with this:

// src/main.ts
import { MikroORM } from '@mikro-orm/postgresql';
import config from './mikro-orm.config';
import { Book } from './entities/Book';
import { Article } from './entities/Article';

async function main() {
  const orm = await MikroORM.init(config);
  await orm.schema.refreshDatabase();
  const em = orm.em.fork();

  em.create(Book, { title: 'War and Peace', author: 'Tolstoy', publishedYear: 1869 });

  em.create(Article, {
    title: 'On Long Novels',
    slug: 'on-long-novels',
    body: 'War and Peace clocks in at 1,225 pages...',
    publishedAt: new Date(),
    metadata: { source: 'in-house', lang: 'en' },
  });
  em.create(Article, {
    title: 'Draft: A Note on Editing',
    slug: 'draft-a-note-on-editing',
    body: 'Editing is the art of removal...',
    metadata: { lang: 'en' },
    // publishedAt omitted — it's nullable, this is a draft
  });

  await em.flush();

  const drafts = await em.find(Article, { publishedAt: null });
  console.log('drafts:', drafts.map(d => d.title));

  await orm.close();
}

main().catch(console.error);

Run npm start. Read the logs carefully. You should see:

✨
One INSERT per table
Books and articles are batched per table. Two SQL statements, both inside the same begin/commit.
🔐
Single transaction
Both tables, one transaction, atomic. Drop the DB connection mid-flush and you'd get nothing, not partial state.
📝
Drafts come back
The find with publishedAt: null returns the unpublished article. NULL is a real, query-able value.

You just modeled a real schema in TypeScript and watched MikroORM emit production-shaped DDL from it. Lengths, defaults, uniqueness, nullability, JSON columns, ORM-side timestamps — all driven from one declaration per entity. From here, every later lesson is wiring (relations, queries, migrations, transactions, hooks, NestJS).

Summary

Four takeaways for Lesson 2:

🏷️
Three styles, one runtime
defineEntity standalone (course default), defineEntity + class (when you need methods), decorators (legacy migrations). All produce the same metadata.
🔗
Type chain → SQL column
p.<type>().<modifier>()... turns into a single column with constraints. nullable = NULL, default = DB-side, onCreate = ORM-side.
🔑
PK choice is a real decision
bigint for production by default. uuid when the ID escapes into URLs or you need offline ID generation. Composite PKs only for legacy schemas.
🗂️
camelCase ↔ snake_case for free
UnderscoreNamingStrategy is the default. Override per-column with fieldName, per-table with tableName, globally only if you must.

Part 1: The Final Mile

You can build an entire NestJS app, run it locally, demo it to your team, get applause, and still ship something that explodes the first weekend at 3am. The reason isn't usually the code — it's everything around the code. The wiring is fine. The fire alarm isn't.

What "production-ready" actually means

Production-ready isn't a checkbox on a Jira ticket. It's a list of properties your service has even when nobody is watching. Five of them, in roughly the order you should add them:

🧪
Tested
A change that breaks behavior is caught locally, not by a customer.
🩺
Healthy
The platform can ask "are you alive?" and get an honest answer in <100ms.
📡
Observable
Every error in prod ends up somewhere a human will see it before the customer does.
🚀
Deployed
Shipping a change is one command. Rolling back is one command. No SSH heroics.
🔁
Automated
Tests run on every push. Deploys happen from main. Humans approve, machines execute.

Imagine the airport again. Construction is done. The terminals are gleaming, the gates are numbered, the baggage carousels spin smoothly. Then the airport authority shows up for inspection. They don't care that the architecture is beautiful. They want to see five things, in order: can you simulate every scenario without real passengers? (tests). Can the FAA radar see you're operational? (health checks). If a plane skids off a runway, who sees it first — you or CNN? (Sentry / observability). Can you open another terminal next year without breaking this one? (deployment). And when a new piece of equipment arrives, does it get plugged in by hand or by the runway control system? (CI/CD).

Pass all five and they hand you the keys. Fail any one and the airport stays empty. Today is opening day. Let's pass the inspection.

The honest version: most teams ship without one or two of these, and they survive. But each missing piece is a small bet that nothing weird will happen. NestJS gives you all five with very little code — the ratio of "code written" to "production guarantees gained" is the best of any Node framework.

Part 2: Unit Tests with Jest

NestJS ships Jest as the default test runner, and it ships @nestjs/testing as the framework's official test harness. You don't have to choose a stack — you just have to use it.

The test pyramid, briefly

Many cheap unit tests, a few expensive E2E tests. Don't invert it.

The pyramid says: write lots of fast unit tests for individual classes, fewer integration tests, and a small handful of end-to-end tests that exercise the real wire. We'll write both unit and E2E in this lesson — that's enough for a service to be confidently shippable.

The TestingModule pattern

The trick of testing a NestJS class isn't “import the class and call new”. It's “ask Nest to build a tiny module that contains just this class and its mocked dependencies.” That's what Test.createTestingModule() does — it's a mini DI container scoped to one test file.

// flights.service.spec.ts
import { Test, TestingModule } from '@nestjs/testing';
import { FlightsService } from './flights.service';
import { PrismaService } from '../prisma/prisma.service';

describe('FlightsService', () => {
  let service: FlightsService;
  let prisma: { flight: { findMany: jest.Mock; create: jest.Mock } };

  beforeEach(async () => {
    prisma = {
      flight: {
        findMany: jest.fn(),
        create: jest.fn(),
      },
    };

    const module: TestingModule = await Test.createTestingModule({
      providers: [
        FlightsService,
        { provide: PrismaService, useValue: prisma },
      ],
    }).compile();

    service = module.get(FlightsService);
  });

  it('returns all flights', async () => {
    const flights = [{ id: '1', destination: 'NYC', gate: 'A12' }];
    prisma.flight.findMany.mockResolvedValue(flights);

    const result = await service.findAll();

    expect(result).toEqual(flights);
    expect(prisma.flight.findMany).toHaveBeenCalledTimes(1);
  });

  it('creates a flight with the given payload', async () => {
    const dto = { destination: 'LHR', gate: 'B7' };
    prisma.flight.create.mockResolvedValue({ id: '2', ...dto });

    const result = await service.create(dto);

    expect(result.id).toBe('2');
    expect(prisma.flight.create).toHaveBeenCalledWith({ data: dto });
  });
});

Notice what's happening: FlightsService is the real thing. PrismaService is a fake we control. We hand that fake to Nest's DI via useValue, and Nest wires the real service against the fake dependency. We're testing one class in isolation — no database, no network, no surprise.

Real benefit: these tests run in <200ms total. You can run them on save. When a teammate breaks findAll by adding a sneaky .where clause, your terminal lights up red before the change ever reaches a PR review.

The override pattern for full modules

If you'd rather import the whole FlightsModule (including its real PrismaModule imports) and only swap one thing, use .overrideProvider().useValue():

const module = await Test.createTestingModule({
  imports: [FlightsModule],
})
  .overrideProvider(PrismaService)
  .useValue(mockPrisma)
  .compile();

Same outcome, less manual wiring. Use this when the module under test has many providers and you only care about replacing one or two of them.

✋ Quick check
In the spec above, why do we call compile() at the end of the chain? What would happen if we forgot it and tried to get(FlightsService) immediately?
Hint: compile() is what actually instantiates the providers and resolves the DI graph. Without it, the module is just metadata.

Part 3: E2E Tests with Supertest

Unit tests prove your classes work. E2E tests prove your app works. They boot the entire Nest application in memory and hit it with real HTTP requests via Supertest. No actual port is opened — Supertest talks to the in-memory HTTP server directly.

The shape of an E2E test:

// test/flights.e2e-spec.ts
import { Test } from '@nestjs/testing';
import { INestApplication, ValidationPipe } from '@nestjs/common';
import * as request from 'supertest';
import { AppModule } from '../src/app.module';
import { PrismaService } from '../src/prisma/prisma.service';

describe('Flights (e2e)', () => {
  let app: INestApplication;
  let created: { id: string };

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({
      imports: [AppModule],
    })
      .overrideProvider(PrismaService)
      .useValue(createInMemoryPrismaMock())
      .compile();

    app = moduleRef.createNestApplication();
    app.useGlobalPipes(new ValidationPipe({ whitelist: true }));
    await app.init();
  });

  afterAll(async () => {
    await app.close();
  });

  it('POST /flights creates a flight', async () => {
    const res = await request(app.getHttpServer())
      .post('/flights')
      .send({ destination: 'NYC', gate: 'A12' })
      .expect(201);

    expect(res.body).toMatchObject({ destination: 'NYC', gate: 'A12' });
    created = res.body;
  });

  it('GET /flights/:id returns the created flight', () =>
    request(app.getHttpServer())
      .get(`/flights/${created.id}`)
      .expect(200)
      .expect((res) => {
        expect(res.body.id).toBe(created.id);
      }));
});

The first test creates a flight and saves the result. The second uses that ID to fetch the same flight. Two tests, real HTTP semantics, real validation, real serialization — no mocks of the Nest layer itself. The only thing we replaced is the database, because hitting a real Postgres in CI is expensive and flaky.

Where E2E tests live: by Nest convention, in the test/ directory at the project root, with the suffix .e2e-spec.ts. There's a separate npm run test:e2e script that picks them up. Unit specs (.spec.ts) sit next to the file they test, inside src/.

Unit vs E2E — when to write which

If you're testing… Write a… Why
A pure piece of business logic Unit test Fast, deterministic, fails for one obvious reason
A service that calls another service Unit test (mock the dependency) You're testing this layer, not its collaborators
That a route returns the right status code E2E test Status codes happen at the HTTP layer, not in your service
That validation rejects bad input E2E test The pipe runs in the actual request flow, not in a unit
That guards block unauthorized callers E2E test Guards are part of the request pipeline; integration is the point
A complex algorithm with 12 branches Unit test (one per branch) E2E for 12 branches would be slow and obscure which one broke

Insight: a 70/30 split (unit / E2E) is healthy for most NestJS services. If you're writing 80%+ E2E tests, your tests are probably slow and brittle. If you're writing 100% unit tests, you're not catching wiring bugs — the kind where the controller forgot to inject the service or the validation pipe wasn't registered.

🔍
Test that mocks everything: “Everything passed!”
Production: 500 Internal Server Error
Developer: “But the test passed!”
Senior dev: “You mocked the bug.”
If your test never fails, ask whether it ever could.

Part 4: Health Checks with Terminus

Now your tests pass. The service runs. Time to ship it — but the platform you're shipping to (Vercel, Kubernetes, Railway, AWS, your reverse proxy) needs a way to ask: “hey, are you alive? are you ready for traffic?” That question has a standard answer: a /health endpoint.

Why platforms care

A load balancer in front of your service pings /health every few seconds. If you respond with 200, you stay in the rotation. If you respond with 500 (or don't respond at all), the load balancer pulls you out and either reroutes traffic to a healthier instance or restarts you. This loop is invisible to you when it works — and the difference between “our service had a 4-hour outage” and “our service had a 30-second blip” when it doesn't.

A load balancer + a /health endpoint = self-healing service. No engineer needed at 3am.

Liveness vs readiness

Two flavors of health check, and they answer different questions:

🩺
/health/live
Liveness
"Is the process running and not deadlocked?" If this fails, the platform restarts the container. Should be cheap and almost-always-yes.
🚦
/health/ready
Readiness
"Are you ready to serve a real request?" Checks the DB, Redis, downstream APIs. If this fails, traffic is paused (no restart).

Wiring it up with @nestjs/terminus

npm install --save @nestjs/terminus @nestjs/axios axios

Generate a health module and controller:

nest g module health
nest g controller health

Then wire Terminus into the module and add the indicators you care about:

// src/health/health.module.ts
import { Module } from '@nestjs/common';
import { TerminusModule } from '@nestjs/terminus';
import { HttpModule } from '@nestjs/axios';
import { HealthController } from './health.controller';
import { PrismaModule } from '../prisma/prisma.module';

@Module({
  imports: [TerminusModule, HttpModule, PrismaModule],
  controllers: [HealthController],
})
export class HealthModule {}
// src/health/health.controller.ts
import { Controller, Get } from '@nestjs/common';
import {
  HealthCheckService,
  HealthCheck,
  HttpHealthIndicator,
  HealthIndicatorResult,
} from '@nestjs/terminus';
import { PrismaService } from '../prisma/prisma.service';

@Controller('health')
export class HealthController {
  constructor(
    private readonly health: HealthCheckService,
    private readonly http: HttpHealthIndicator,
    private readonly prisma: PrismaService,
  ) {}

  @Get()
  @HealthCheck()
  check() {
    return this.health.check([
      () => this.http.pingCheck('self', 'http://localhost:3000'),
      () => this.prismaCheck(),
    ]);
  }

  private async prismaCheck(): Promise<HealthIndicatorResult> {
    try {
      await this.prisma.$queryRaw`SELECT 1`;
      return { database: { status: 'up' } };
    } catch (err) {
      return { database: { status: 'down', message: err.message } };
    }
  }
}

Hit GET /health:

{
  "status": "ok",
  "info": {
    "self": { "status": "up" },
    "database": { "status": "up" }
  },
  "error": {},
  "details": {
    "self": { "status": "up" },
    "database": { "status": "up" }
  }
}

Real-world: Terminus has built-in indicators for TypeORM, Mongoose, Sequelize, MikroORM, Prisma, microservices, gRPC, disk, and memory. The custom prismaCheck above is one approach; @nestjs/terminus also exposes a PrismaHealthIndicator directly. Either way, the contract is the same: return { name: { status: 'up' | 'down' } }.

Insight: don't put expensive checks in /health/live. If your liveness check pings the database and the DB is slow, the platform will restart you — making things worse. Liveness should answer in milliseconds. Readiness can do the deeper checks.

Part 5: Error Tracking with Sentry

Question: when an exception happens in your prod app right now, where does it go? If your honest answer is “console.error, and we maybe see it if we tail the logs,” you have an observability problem. console.error is what you use during development. In prod, you need an error tracker that captures the stack, the request context, the user, and groups duplicates so you don't see the same bug 10,000 times. Sentry is the boring, correct default.

Why not just logs?

Logs are a stream. Errors are events. You don't want to scroll through a million lines of access logs hunting for the one stack trace at 03:14:22. You want a dashboard that says: “this exception happened 47 times in the last hour, here's the stack, here's the user, here's the request body.” That's the difference between console.error and Sentry.

Setup

npm install --save @sentry/nestjs @sentry/profiling-node

Create an instrument.ts file. It must be imported before any other module so Sentry can patch the runtime:

// src/instrument.ts
import * as Sentry from '@sentry/nestjs';
import { nodeProfilingIntegration } from '@sentry/profiling-node';

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.NODE_ENV ?? 'development',
  integrations: [nodeProfilingIntegration()],
  tracesSampleRate: 1.0,
  profilesSampleRate: 1.0,
});

Then in main.ts, the import order matters:

// src/main.ts
// IMPORTANT: this must be the very first import.
import './instrument';

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
bootstrap();

Register the SentryModule and the global filter in AppModule:

// src/app.module.ts
import { Module } from '@nestjs/common';
import { APP_FILTER } from '@nestjs/core';
import { SentryModule } from '@sentry/nestjs/setup';
import { SentryGlobalFilter } from '@sentry/nestjs/setup';

@Module({
  imports: [
    SentryModule.forRoot(),
    // ...the rest of your app's modules
  ],
  providers: [
    { provide: APP_FILTER, useClass: SentryGlobalFilter },
  ],
})
export class AppModule {}

That's it. Unhandled exceptions now appear in your Sentry dashboard with full stack traces, request context, and grouping by fingerprint.

Manual capture for "expected" errors you still care about

Sometimes you catch an error in a service, log it, and move on — but you still want Sentry to know. Use Sentry.captureException:

import * as Sentry from '@sentry/nestjs';

try {
  await this.paymentGateway.charge(amount);
} catch (err) {
  Sentry.captureException(err, {
    tags: { source: 'payments' },
    extra: { amount, userId },
  });
  throw new PaymentFailedException();
}

Source maps — or don't bother

If you skip source maps, your stack traces in Sentry will look like minified TypeScript output: v.prototype.h calling g.j. Useless. Upload source maps with the wizard:

npx @sentry/wizard@latest -i sourcemaps

HttpException is intentionally not captured by default. Sentry's NestJS integration treats HttpException (and its subclasses like NotFoundException, BadRequestException) as control flow, not bugs. That's almost always what you want — a 404 isn't an error to alert on. If you want to capture them too, configure that in your filter.

Part 6: Production Logging

Sentry catches errors. Logs catch everything else — the breadcrumbs you'll need when something weird happens that wasn't an exception. The default Nest logger is fine for development. For production, swap to structured JSON via Pino so your logs are queryable in Datadog, Loki, CloudWatch, or whatever your platform offers.

npm install --save nestjs-pino pino-http
npm install --save-dev pino-pretty
// src/app.module.ts (relevant pieces)
import { LoggerModule } from 'nestjs-pino';

@Module({
  imports: [
    LoggerModule.forRoot({
      pinoHttp: {
        level: process.env.LOG_LEVEL ?? 'info',
        transport:
          process.env.NODE_ENV === 'development'
            ? { target: 'pino-pretty' }
            : undefined, // raw JSON in prod
        redact: ['req.headers.authorization', 'req.headers.cookie', '*.password'],
      },
    }),
  ],
})
export class AppModule {}

And in main.ts:

import { Logger } from 'nestjs-pino';

const app = await NestFactory.create(AppModule, { bufferLogs: true });
app.useLogger(app.get(Logger));

Log levels

Level Use for Default in prod
errorSomething broke and a human should investigateon
warnRecoverable issue, retry, deprecated path usedon
infoNotable lifecycle events (startup, shutdown, big actions)on
debugDetailed flow useful when chasing a bugoff
traceEvery function call, basically. Local only.off

Never log secrets. Not passwords, not API tokens, not Authorization headers, not full PII. The redact array above is your friend — add to it whenever a new sensitive field shows up. A leaked log file is the same as a leaked database. Treat it that way.

Part 7: Deployment Options

Three reasonable paths to ship a NestJS app in 2026. Pick whichever matches your team's existing infrastructure — none of them are wrong.

▲
Vercel / Serverless
Easiest, cheapest start
Zero infra. Each request spins up a function. Great for low-to-medium traffic. Cold starts on the free tier. Watch out for stateful things (BullMQ workers, websockets).
🖥️
Node + PM2
Classic, predictable
Long-running Node process behind nginx or Caddy. Cheapest at scale. You manage the box. Perfect when you already have ops capacity.
🐳
Docker / K8s
Most flexible, most overhead
Build a container image, ship it anywhere — ECS, GKE, Fly.io, Railway, your own cluster. Same image in dev and prod.

Path A: Vercel (serverless)

NestJS works on Vercel via the @vercel/node runtime and a single adapter file. Vercel's recent updates support Nest with near-zero config — you mostly just need an entry point at api/index.ts:

// api/index.ts
import { NestFactory } from '@nestjs/core';
import { ExpressAdapter } from '@nestjs/platform-express';
import { AppModule } from '../src/app.module';
import express from 'express';

const server = express();
let ready: Promise<void>;

async function bootstrap() {
  const app = await NestFactory.create(AppModule, new ExpressAdapter(server));
  app.enableCors();
  await app.init();
}

ready ??= bootstrap();

export default async function handler(req, res) {
  await ready;
  server(req, res);
}

Add a minimal vercel.json:

{
  "version": 2,
  "builds": [{ "src": "api/index.ts", "use": "@vercel/node" }],
  "routes": [{ "src": "/(.*)", "dest": "api/index.ts" }]
}

Then vercel deploy. Done. The free tier is enough for a capstone demo.

Insight: on Vercel, your Nest app starts once per cold-start and is reused for warm requests. That means startup-time work (DB pool creation, Sentry init) happens lazily and gets amortized. But long-running things — cron jobs, BullMQ workers, websocket gateways — don't fit the model. Run those on a real server and use Vercel only for the HTTP API.

Path B: Node + PM2 + reverse proxy

# on the server
npm ci --omit=dev
npm run build
npm install -g pm2

# start the compiled app under PM2 with cluster mode
pm2 start dist/main.js --name airport-api -i max
pm2 save
pm2 startup

Put nginx or Caddy in front, terminate TLS, proxy to localhost:3000. PM2 restarts the process on crashes and gives you pm2 logs, pm2 monit, and zero-downtime reloads. This is what most "boring" production setups still look like — and there's nothing wrong with that.

Path C: Docker

A multi-stage Dockerfile that builds the TS, then ships only the compiled output and prod dependencies:

# Dockerfile
FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=5s --start-period=20s \
  CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "dist/main.js"]
docker build -t airport-api .
docker run -p 3000:3000 --env-file .env airport-api

That image runs anywhere — ECS, Fly.io, Railway, GKE, your laptop. The HEALTHCHECK directive uses the same /health endpoint we built in Part 4. Layered defense.

Picking a path: for the capstone, Vercel is the easiest. Pick it unless you already have a server or a Docker host you'd rather use. The grading rubric doesn't care which one — it cares that /health returns 200 from a public URL.

Part 8: CI/CD with GitHub Actions

The final automation. Right now, your tests run when you remember to run them. CI flips that — tests run on every push, no exceptions, no “I forgot to run them locally.” A green check on the PR means the test suite passed for that exact commit on a clean machine. That's a much stronger guarantee than “works on my machine.”

The minimal workflow

Drop this in .github/workflows/ci.yml:

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Use Node.js 22
        uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Build
        run: npm run build

      - name: Unit tests
        run: npm run test -- --ci --coverage

      - name: E2E tests
        run: npm run test:e2e

Push it. Open the Actions tab on GitHub. Watch the green check appear (or the red X, which is the test suite doing its job).

Optional: deploy on push to main

Add a second job that runs only on main and only if tests passed:

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Vercel
        run: npx vercel --prod --token=${{ secrets.VERCEL_TOKEN }}

That's the whole CI/CD loop in roughly 40 lines of YAML. From this point on, every push is automatically tested. Every merge to main is automatically deployed. Humans approve, machines execute.

Real benefit: CI/CD is the single biggest force multiplier for a small team. It removes the entire class of bug that goes “works on my machine” and it removes the entire class of outage that goes “I forgot to deploy after merging.” The capstone bonus task asks you to set this up — do it.

Part 1: The Active Record Hangover

You already met Prisma in the NestJS course. It's fine. It's fast to learn. For a small service, it's plenty. So why are we spending ten lessons on a different ORM?

Here's the moment most teams hit the wall. You have a request that needs to:

  1. Load an Order
  2. Update three of its OrderItems
  3. Insert two new StockMovements
  4. Mark the customer's loyalty record as tier = 'gold'
  5. Commit it all atomically, or none of it

In a Prisma-style world, you write five queries, wrap them in $transaction([...]), and pray you didn't forget one. In an Active Record world (TypeORM 0.x, Sequelize, Eloquent in PHP), each entity is responsible for saving itself: order.save(), item.save(), item.save(), item.save(), movement.save()... five round trips. Or you batch manually and bypass your own object model.

There's a third way. You change a few JS objects in memory, then say one word: flush. The ORM figures out what to insert, what to update, what to delete, and what order the foreign keys demand. It batches everything into a single transaction. You write less code, you make fewer mistakes, you don't think about the SQL.

That's MikroORM. And the reason it can do this is that it implements three patterns from Martin Fowler's Patterns of Enterprise Application Architecture — patterns most JS-flavored ORMs skip because they're harder to build.

Active Record vs Data Mapper — the philosophical split

Every ORM in history sits on one side of this fence.

📚
Active Record
The entity saves itself
Each model class knows how to talk to the database. user.save(), user.delete(). Cheap to learn. Couples your domain objects to persistence. Hard to unit-test. TypeORM, Sequelize, Eloquent.
🗂️
Data Mapper
Plain objects, separate manager
Entities are plain TypeScript classes. They know nothing about the database. A separate EntityManager handles persistence. Cleaner domain model. Pays back at scale. Hibernate, Doctrine, MikroORM.

Prisma is its own animal — not really either, more of a typed query-builder with a code-generated client. It's great at what it does, but it doesn't solve the “five-write transaction” problem we opened with. You still write the queries; Prisma just types them for you.

MikroORM is unapologetically Data Mapper. Your Book class doesn't have a save() method. It doesn't have any persistence method. It's a TypeScript class with fields. The framework wraps it in something called a Unit of Work, watches what you change, and on flush() writes the diff.

🤔
TypeORM dev: “I called user.save(), why didn't my related Orders update?”
Senior: “Did you save them too?”
TypeORM dev: “...there are eighteen.”
Senior: “user.save({cascade: true, deep: 3, ohGodPlease: true})?”
Active Record at scale becomes a series of save() incantations no one fully trusts.
🤔 Predict before reading on
If MikroORM's Book class has no save() method, no delete(), no database awareness at all — how does the ORM know that book.title = 'New Title' needs to become an UPDATE statement? Take ten seconds and write your guess.
There's no wrong answer. Most people guess “proxies” or “getters/setters”. The real answer is simpler — and you'll see it in Part 2.

Part 2: The Three Patterns That Make MikroORM Tick

Three patterns. If you understand these three, the rest of the course is naming and configuration.

1. Data Mapper

You already saw this one. Entities are plain classes. A separate object — the EntityManager — handles all persistence. Your domain stays pure.

2. Identity Map

This is the one that surprises people. The Identity Map is an in-memory dictionary inside the EntityManager keyed by primary key. It guarantees: within one request, every database row is represented by exactly one object instance.

If you load Book#42 in a controller, then ten function calls deep someone else loads Book#42, both calls return the same JavaScript object. Not a copy. The same reference. === is true.

const book1 = await em.findOne(Book, 42);
const book2 = await em.findOne(Book, 42);

console.log(book1 === book2); // true

Only the first call hits the database. The second sees 42 already in the Identity Map and returns the cached instance.

This is not just a performance trick — it's a correctness guarantee. If two parts of your code modify the “same book,” they're modifying the literal same object. There's no “wait, did the other handler stale-write over my change?” ambiguity within one request.

Crucial: per-request, not global. The Identity Map lives inside one EntityManager fork, and that fork lives for one HTTP request. After the response goes out, the fork is garbage-collected. Nothing leaks between users. We'll see how this is wired in Part 4.

3. Unit of Work

Now the answer to the recall-box question. How does MikroORM know that book.title = 'New Title' needs an UPDATE?

Trick: it doesn't, until you ask. When the ORM hydrates a row into an entity, it also stores a hidden copy of every property — a snapshot. When you call em.flush(), MikroORM walks every managed entity, compares its current state against the snapshot, and only emits SQL for the fields that actually changed.

That walk is called the Unit of Work. It does five things, in order, atomically:

🔍
1. Compute
Diff every managed entity against its snapshot. Build a list of inserts, updates, deletes.
🔗
2. Order
Topological sort by foreign keys. Insert parents before children. Delete children before parents.
📦
3. Batch
Group operations: one multi-row INSERT per table, batched UPDATEs, batched DELETEs.
🔐
4. Transact
Wrap the whole batch in a database transaction. All or nothing.
📸
5. Snapshot
After commit, take fresh snapshots of every entity so the next flush diffs against the new baseline.

The five-write request from Part 1, in MikroORM, is:

const order = await em.findOne(Order, orderId, { populate: ['items', 'customer'] });

order.items[0].quantity = 5;
order.items[1].quantity = 3;
order.items[2].quantity = 1;

em.create(StockMovement, { sku: 'A1', delta: -5 });
em.create(StockMovement, { sku: 'A2', delta: -3 });

order.customer.tier = 'gold';

await em.flush(); // one transaction, ordered, batched, atomic

Six lines of business logic. One flush. No transaction wrapper, no manual ordering, no Promise.all footgun. Compare that to the equivalent in raw Prisma or TypeORM Active Record. This is the payoff that makes Lesson 1 through Lesson 10 worth it.

The mental shift: with MikroORM, you stop writing queries and start writing changes to objects. The framework converts your changes into queries when you flush. The cognitive load shifts from “which SQL should I run” to “what should be true after this request.”

📝
Junior: “I changed the user's email but the database didn't update.”
Senior: “Did you flush?”
Junior: “The toilet?”
Senior: “em.flush(). Without it, your changes live only in JS memory.”
Junior: “Wait — so I can change ten things and ship them in one transaction by calling flush once?”
Senior: “Now you get it.”
The first time the penny drops on Unit of Work, you stop writing five-statement transactions forever.

Part 3: The Records Library Analogy

One running analogy for the entire course. Memorize this — every later lesson maps new concepts back to it.

Your MikroORM app is a research library

Imagine a serious research library. The kind with stacks you can't browse yourself — you fill out a request slip, hand it to the desk, and a few minutes later a clerk brings the volume to your reading carrel.

The library has one master catalog: every physical book has exactly one catalog card. Two readers asking for the same book don't get two cards — they get pointed to the same card, and the librarian schedules access. This is not optional; it's how the library guarantees that nobody walks out with a duplicate that nobody can reconcile later.

The librarians don't write changes to the master register every time you scribble in a margin or a clerk reshelves a volume. They keep a working ledger — a daily journal of every check-out, return, annotation, and reshelving. At the end of the shift, the head librarian reviews the ledger, applies all the changes to the master register in the right order, signs it, and locks the safe. If anything goes wrong mid-shift, they tear up the ledger and start over — the master register never saw the half-done work.

Each subject has a specialist — the science librarian, the history librarian. They don't have any power the head librarian doesn't have, but if you only need history books, you go to the history desk. It's a typed shortcut, not a separate authority.

The mapping in one line: Master Catalog = Identity Map. Working Ledger = Unit of Work. Head Librarian = EntityManager. Subject Specialist = Repository. End-of-Shift Sign-Off = em.flush(). That's the whole core.

The full mapping

Records Library MikroORM What it does
📖 Volume / Document Entity A plain TypeScript class instance representing one row. No persistence methods of its own.
👤 Head Librarian EntityManager The orchestrator. find, persist, remove, flush. Every operation goes through them.
🗃️ Master Catalog Identity Map One card per real volume. Within a request, every findOne(Book, 42) returns the exact same JS object.
📒 Working Ledger Unit of Work Tracks changes across the request. Computes the diff. Orders, batches, and commits everything in one transaction on flush.
🔍 Subject Specialist Repository Typed shortcut for one entity type. em.getRepository(Book) returns a typed handle. Same powers, narrower interface.
🔗 Cross-References Relations (1:1, 1:M, M:1, M:M) How one entity points to another. Owning side holds the foreign key; inverse side mirrors it.
🎟️ Request Slip QueryBuilder / FilterQuery How you describe what you want. { author: { name: 'Tolstoy' } } turns into a JOIN and WHERE.
📦 Cart on Wheels Loading Strategy Bring everything in one trip (joined) or by department (select-in)? Different strategies for different shapes of data.
🏗️ Reorganization Plan Migration A versioned, reviewable change to the building itself: new shelves, new wings, retired sections.
🕶️ Restricted Stacks Filter Volumes that exist but don't show up in normal searches. Soft-delete, multi-tenant scoping, archived records.
📝 Standing Procedure Lifecycle Hook / Subscriber “Before any new volume is registered, stamp today's date.” Code that runs at fixed entity-lifecycle moments.

You don't need all of this on day one. Lessons 2 through 4 cover entities, the EntityManager, and relations — that's enough to build a real CRUD service. Repositories arrive in Lesson 6, migrations in Lesson 7. By the capstone, you'll have used every row in this table.

Part 4: Your First MikroORM Project

Theory's done. From here on, every concept is grounded in code you can actually run. This is the project you'll grow across all 10 lessons.

Prerequisites

You'll need:

  • Node.js 20+ (LTS). Check with node --version.
  • PostgreSQL 14+ running locally. Easiest path: docker run --name pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 -d postgres:16.
  • A database called archive. Create it with createdb archive, or via the Postgres CLI: CREATE DATABASE archive;.

Scaffold the project

# create the project folder
mkdir archive-api && cd archive-api

# initialize npm + TypeScript
npm init -y
npm install --save-dev typescript @types/node ts-node
npx tsc --init

# install MikroORM core, the Postgres driver, and the CLI
npm install @mikro-orm/core @mikro-orm/postgresql
npm install --save-dev @mikro-orm/cli

Three packages. @mikro-orm/core is database-agnostic (EntityManager, Unit of Work, Identity Map). @mikro-orm/postgresql is the driver (it brings pg with it). @mikro-orm/cli is the dev tool you'll use for migrations and schema diffing in Lesson 7.

Driver versions must match. All three packages must be the exact same MikroORM version. Mixing @mikro-orm/core@7.0.1 with @mikro-orm/postgresql@6.4.0 produces obscure runtime errors. If you upgrade one, upgrade them all in lockstep.

Project structure

Create this layout. We'll build it up over the next ten lessons.

archive-api/ ├── src/ │ ├── entities/ │ │ └── Book.ts ← our first entity │ ├── mikro-orm.config.ts ← ORM configuration (read by the CLI too) │ └── main.ts ← entry point for this lesson's demo ├── package.json └── tsconfig.json

Define the Book entity

Open src/entities/Book.ts and write your first entity. We'll use the defineEntity helper — it's the modern, decorator-free, fully type-inferred way. (Decorators still work; we'll mention them in Lesson 2.)

// src/entities/Book.ts
import { defineEntity, p, InferEntity } from '@mikro-orm/core';

export const Book = defineEntity({
  name: 'Book',
  properties: {
    id: p.bigint().primary(),
    title: p.string(),
    author: p.string(),
    publishedYear: p.integer().nullable(),
    createdAt: p.datetime().onCreate(() => new Date()),
  },
});

export type IBook = InferEntity<typeof Book>;

Five properties. id is the primary key, a bigint that Postgres auto-generates. title and author are required strings. publishedYear is an optional integer (nullable in the DB). createdAt is a timestamp the ORM fills in for us on insert.

Notice: no save(), no delete(), no find(). The entity is just a shape. Persistence will live in the EntityManager.

Configure the ORM

Open src/mikro-orm.config.ts:

// src/mikro-orm.config.ts
import { defineConfig } from '@mikro-orm/postgresql';
import { Book } from './entities/Book';

export default defineConfig({
  entities: [Book],
  dbName: 'archive',
  user: 'postgres',
  password: 'postgres',
  host: 'localhost',
  port: 5432,
  debug: true, // log every SQL query — invaluable for learning
});

That's it. The defineConfig import comes from /postgresql, which means MikroORM infers the driver automatically — no separate driver: line needed. debug: true is what makes this lesson teach itself: every query the ORM fires will print to your console, and you'll see exactly when the Identity Map saves you a round trip.

Write the “Hello, librarian” demo

Open src/main.ts:

// src/main.ts
import { MikroORM } from '@mikro-orm/postgresql';
import config from './mikro-orm.config';
import { Book } from './entities/Book';

async function main() {
  const orm = await MikroORM.init(config);

  // 1. create the schema (we'll switch to migrations in Lesson 7)
  await orm.schema.refreshDatabase();

  // 2. fork the EM — one map, one ledger, scoped to this script
  const em = orm.em.fork();

  // 3. create two books — pure JS objects, no SQL fired yet
  em.create(Book, { title: 'War and Peace', author: 'Tolstoy', publishedYear: 1869 });
  em.create(Book, { title: 'Anna Karenina', author: 'Tolstoy', publishedYear: 1877 });

  // 4. flush — single transaction, two INSERTs, ordered correctly
  await em.flush();

  // 5. read both books back
  const book1 = await em.findOne(Book, 1);
  const book2 = await em.findOne(Book, 1);

  // 6. the Identity Map proof
  console.log('same instance?', book1 === book2); // true
  console.log('title:', book1?.title); // War and Peace

  await orm.close();
}

main().catch(console.error);

Run it

Add a start script to your package.json:

"scripts": {
  "start": "ts-node src/main.ts"
}

Then:

npm start

You'll see something like:

[query] begin
[query] insert into "book" ("title", "author", "published_year", "created_at")
        values ('War and Peace', 'Tolstoy', 1869, '...'),
               ('Anna Karenina', 'Tolstoy', 1877, '...') returning "id"
[query] commit
[query] select "b0".* from "book" as "b0" where "b0"."id" = 1 limit 1
same instance? true
title: War and Peace

Read those query logs carefully. Three things to notice:

✨
Single batched INSERT
Both books went in via one insert ... values (...), (...) — that's the Unit of Work batching.
🔐
Implicit transaction
begin ... commit wrapped the whole flush, even though we never wrote BEGIN ourselves.
🗂️
Identity Map at work
Two findOne(Book, 1) calls produced exactly one select. The second hit the map and returned the cached instance.

You just experienced everything Part 2 promised. Plain object changes turned into batched, ordered, transactional SQL on a single flush() call. And duplicate reads of the same primary key cost zero round trips. This is the core ergonomic win of MikroORM in one 30-line script.

Part 5: What Happens When You Call flush()

You've used flush(). Now let's trace exactly what it does, end-to-end. This diagram is the most important picture in the whole course.

Five phases. One transaction. The whole point of an ORM, in one round trip.

Why “forking” matters

You saw orm.em.fork() in the demo. That's the part of MikroORM most people miss on day one, and it's what makes the framework safe to use in a real web server.

orm.em is the global EntityManager — one per ORM instance for the life of the process. If you used it directly inside an HTTP handler, every request would share one Identity Map. Two users editing the same record would step on each other. The map would grow forever. Memory would leak. Welcome to production debugging at 2am.

Instead: at the start of every request, you call orm.em.fork() to get a fresh EntityManager with its own clean Identity Map and Unit of Work. That fork lives for one request, gets thrown away at the end, and never sees another user's data.

In an Express or NestJS app, this is wired up by middleware:

import { RequestContext } from '@mikro-orm/core';

app.use((req, res, next) => {
  RequestContext.create(orm.em, next);
});

Under the hood that uses Node's AsyncLocalStorage to scope the forked EM to the current request — so anywhere in your code, orm.em.find(...) automatically routes to the right fork. We'll see the NestJS version of this in Lesson 9. For now, just know: the global orm.em is a factory; the request-scoped fork is what you actually use.

Common mistake: sharing orm.em directly across requests, or holding entities loaded by one request in a module-level variable. Both poison the Identity Map. MikroORM 7 actively detects this and throws unless you set allowGlobalContext: true — which you should only ever set in unit tests.

Where the SQL actually lives

One conceptual lock-in: in MikroORM, you almost never write SQL strings yourself in normal flows. em.find, em.persist, em.remove, em.flush together cover ~85% of a typical CRUD service. For the other 15% — reports, complex joins, raw window functions — you'll meet the QueryBuilder in Lesson 6. Even there, you can lift the result into the Identity Map with .getResult().

The mental rule from Day 1: describe the change you want as JS objects, then flush. If that's not enough, escalate to the QueryBuilder. If that's not enough, drop to raw SQL with em.execute(...). In practice, most teams never need the third escape hatch.
